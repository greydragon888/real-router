# Снимок «ДО» для #1938

**Взят 2026-09-02 на `40fcdca9e`, до первого шага переноса шва.**

Существует потому, что два из шести исследований после реализации (`R5` и `R6` в
артефакте «Что схлопнется после шва») сравнивают «до» с «после» — а «до»
перестанет существовать в тот момент, когда сядет первый шаг. Та же логика, по
которой бенч-арм обязан лечь на `master` раньше изменения: дельта, посчитанная
против числа, жившего только на ветке, — не дельта.

```bash
node snapshot.mjs           # таблица
node snapshot.mjs --json    # для diff двух прогонов
```

`BEFORE.txt` и `before.json` — записанный выход этого прогона. «После» берётся той
же командой, и вся ценность в разности.

## Как брать «после»

Тем же прогоном, на коммите, где перенос шва закончен, и рядом положить второй
`AFTER.json`. Интересны ровно три разности:

1. **`scopeMass`** — сколько кода и прозы удалила одна доведённая до конца
   дедупликация. Это единственная точка калибровки для #2091: десятки строк —
   уборка попутно, сотни и мёртвая поверхность — программа.
2. **`vocab`** — словарь шва должен схлопнуться. `buildURLForCommit` и
   `pendingRemovals` до нуля, если гипотеза «посылка испаряется» верна;
   `resolveForward` — остаться, но потерять половину смысла (см. Фазу 0, раздел
   «что перерешать»).
3. **`proseCopies`** — изменилось ли распределение копий на подсистеме, которую
   только что упростили, и появились ли НОВЫЕ копии: структурная волна их и
   производит (`type-mirror-authority` фиксирует это в своём докблоке).

⚠ Один и тот же классификатор с обеих сторон. Любая правка `snapshot.mjs` между
прогонами обнуляет сравнение — тогда пересчитывать надо оба.
