# Invariants

> Property-based invariants verified via [fast-check](https://fast-check.dev/). See `tests/property/` for implementations.

## createRouter (factory)

`createRouter(routes?, options?, dependencies?)` is the factory function that creates a new router instance. These invariants verify that the factory produces a valid, unstarted router with the expected configuration.

| #   | Invariant               | Description                                                                                                           |
| --- | ----------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 1   | No-args returns router  | `createRouter()` with no arguments returns a valid router with `isActive() === false` and `getState() === undefined`. |
| 2   | Routes are registered   | For any array of uniquely-named routes, `getRoutesApi(router).has(name)` returns `true` for each provided route.      |
| 3   | Dependencies accessible | Dependencies passed as the third argument are retrievable via `getDependenciesApi(router).get(name)`.                 |

## nameToIDs (pure function)

`nameToIDs(name)` converts a dot-separated route name into an array of ancestor IDs. It has five fast-path branches for 0-4 segments and a general path for 5+. These invariants serve as a regression net for any future optimizations to those branches.

| #   | Invariant                          | Description                                                                                                                                |
| --- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | Last element equals original name  | `nameToIDs(name).at(-1) === name` for any non-empty name. The full name is always the last entry in the ID array.                          |
| 2   | First element equals first segment | `nameToIDs(name)[0] === name.split(".")[0]`. The root segment is always the first entry.                                                   |
| 3   | Length equals segment count        | For any name, `nameToIDs(name).length === name.split(".").length`. One ID per segment, no more, no less.                                   |
| 4   | Prefix property                    | `nameToIDs("a.b")` is a strict element-wise prefix of `nameToIDs("a.b.c")`. Shorter names produce arrays that are prefixes of longer ones. |
| 5   | Empty string acceptance            | `nameToIDs("") === [""]`. The empty string is a valid input and returns a single-element array.                                            |
| 6   | Monotonic string lengths           | Each element is strictly longer than the previous: `ids[i].length < ids[i+1].length`. Segments accumulate length as depth increases.       |
| 7   | Nesting via dot-prefix             | Each element is a dot-prefix of the next: `ids[i+1].startsWith(ids[i] + ".")`. The hierarchy is encoded in the string structure.           |

## areStatesEqual

`router.areStatesEqual(s1, s2, ignoreQueryParams?)` compares two router states. It operates on plain state objects and does not require registered routes.

| #   | Invariant                                               | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| --- | ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Reflexivity                                             | `areStatesEqual(s, s) === true` for any state. A state is always equal to itself.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| 2   | Symmetry                                                | `areStatesEqual(s1, s2) === areStatesEqual(s2, s1)`. Equality is commutative.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| 3   | Both undefined                                          | `areStatesEqual(undefined, undefined) === true`. Two absent states are considered equal.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| 4   | One undefined                                           | `areStatesEqual(s, undefined) === false` for any defined state. A defined state is never equal to an absent one.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| 5   | Monotonicity of ignoreQueryParams                       | If `areStatesEqual(s1, s2, false) === true`, then `areStatesEqual(s1, s2, true) === true`. Ignoring query params can only make states more equal, never less.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| 6   | Different names implies not equal                       | If `s1.name !== s2.name`, then `areStatesEqual(s1, s2) === false`. Route name is the primary equality discriminant.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| 7   | Transitivity                                            | If `areStatesEqual(a, b)` and `areStatesEqual(b, c)`, then `areStatesEqual(a, c)`. Equality is transitive.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| 8   | Provenance independence (#1554)                         | A state built from an intent equals the state its own `path` matches back to: `areStatesEqual(makeState(name, params, search), matchPath(thatState.path), false) === true`. The URL direction parses values (`?page=2` → `2`), the intent direction keeps the caller's — values printing into the same URL compare equal (`string` / `number` / `boolean` by printed form, arrays element-wise, a singleton array against its scalar). `null` / `undefined` / objects stay strict: they print differently (`?a` vs `?a=` vs nothing).                                                                                                                                                                                                                                                                                                                     |
| 9   | A forwarding alias is active on its destination (#1573) | `literal \|\| destination`: when `name` declares `forwardTo`, the predicate is repeated on the FULL output of stage ① — the resolved terminal name plus the chain's defaults, each hop's slot layered into its own channel — so `isActiveRoute("s2")` is `true` on the page `navigate("s2")` commits. A FALLBACK, never a pre-resolution: resolving first would darken a section link (`users` → `users.list`) while a sibling descendant is active. Repeated on ①'s OUTPUT rather than a substituted name, because the chain default lives on the forwarding SOURCE and a dynamic `forwardTo` is absent from the forward map entirely. Gated O(1) — a non-forwarding route pays one `Object.hasOwn`; a throwing dynamic callback yields `false` + `logger.warn`, never a throw from a render. Pinned in `tests/functional/routes/isActiveRoute.test.ts`. |

## buildPath / matchPath Roundtrip

`router.buildPath(name, params?, search?)` and `pluginApi.matchPath(path)` form an inverse pair (path params via `params`, query via the `search` channel — RFC-4 M2 / #1548). These invariants verify that the URL-building and URL-matching layers are consistent with each other.

| #   | Invariant                       | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| --- | ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Roundtrip name                  | `matchPath(buildPath(name, params)).name === name`. Building a URL and matching it back always recovers the original route name.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| 2   | Params preserved                | URL params from `matchPath(buildPath(name, params)).params` match the originals after string coercion. Numeric params become strings after decode, but values are preserved.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| 3   | Path starts with slash          | `buildPath(name, params)` always starts with `/`. All generated URLs are absolute paths.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| 4   | Determinism                     | `buildPath(name, params)` returns the same string for identical arguments. URL building is a pure function.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| 5   | Query params roundtrip          | For routes with query parameters (e.g., `?q&page`), query values survive the build-then-match cycle intact.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| 6   | Static route default            | `buildPath("home")` with no params returns `/`. Static routes with no required params work without arguments.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| 7   | href equals destination (#1578) | `buildPath(name, params, search) === (await navigate(name, params, search)).path` for the same intent, INCLUDING the arm where the caller names no query channel (`search` omitted). `buildPath` is the only URL producer reached without a state builder in front of it, so it is the only one that can drift: the default-withholding rule skipped a route's `defaultSearch` whenever the `search` ARGUMENT was absent, which is the arm every adapter's `<Link>` takes — the href dropped `defaultSearch` while the click kept it, and `matchPath` immediately rewrote the emitted URL into a different one. The skip now keys on the caller's BAG (a route-declared query name actually riding in `params` — the RETIRED v1 single-bag spelling), not on the absence of the argument. Property-verified in `tests/property/searchPathConsistency.properties.ts` block 8; mutation-checked (either buildPath-side mutation reddens that block and no other, 1 failed / 420 passed). |

## isActiveRoute

`router.isActiveRoute(name, params?, search?, strictEquality?, ignoreQueryParams?)` checks whether a route is currently active (query goes through the `search` slot at position 3 since RFC-4 M2 / #1548; `strictEquality` / `ignoreQueryParams` shifted to 4 / 5). It requires a started router with a current state.

| #   | Invariant                          | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| --- | ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Current route is active            | `isActiveRoute(currentState.name, currentState.params) === true`. The current route is always reported as active.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| 2   | Current route with strict equality | `isActiveRoute(currentState.name, currentState.params, currentState.search, true) === true`. Exact-match mode still recognizes the current route.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| 3   | Ancestor is active                 | `isActiveRoute(parentName) === true` when the current route is a descendant of `parentName`. Ancestor routes are active by default.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| 4   | Strict equality blocks ancestor    | `isActiveRoute(parentName, {}, undefined, true) === false` when `parentName !== currentState.name`. Strict mode requires an exact name match.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| 5   | Monotonicity of strict             | If `isActiveRoute(name, params, undefined, true) === true`, then `isActiveRoute(name, params, undefined, false) === true`. Strict active implies loose active.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| 6   | Monotonicity of ignoreQueryParams  | If `isActiveRoute(name, params, undefined, strict, false) === true`, then `isActiveRoute(name, params, undefined, strict, true) === true`. Ignoring query params can only make a route more active, never less.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| 7   | Empty string returns false         | `isActiveRoute("") === false`. An empty route name is never considered active, regardless of current state.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| 8   | Provenance independence (#1554)    | Both branches answer independently of how a value was written: on `/users/123` (URL decode yields the string `"123"`), `isActiveRoute("users.view", { id: 123 })` and the hierarchical `isActiveRoute("users", { id: 123 }, undefined, false, false)` are `true`. Shares the comparison predicate with areStatesEqual invariant 8.                                                                                                                                                                                                                                                                                                                                                                                                                   |
| 9   | Total — no input makes it throw    | The predicate ANSWERS for every input, from inside a render (#1577). Both branches READ the caller's bags — since nav-pipeline Phase 2 step 2-5 both do so through `canonicalize` in its literal form, the exact branch comparing the materialised target and the descendant branch comparing channel by channel (neither splits the caller's bag any more, and neither folds the two into one) — so an accessor-backed key, a `Proxy` or a reactive object throws there; #1573 had wrapped only the destination arm's `forwardState`. One boundary now covers the whole walk (the shape `isParams` took for the same class, #1052): a throw yields `false` + `logger.warn`, never an exception escaping into a render. Sibling of canNavigateTo #5. |

## shouldUpdateNode

`router.shouldUpdateNode(nodeName)` returns a predicate that tells view layers whether a given route segment needs to re-render after a navigation.

| #   | Invariant                         | Description                                                                                                                                                                        |
| --- | --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Consistency with navigate         | After `navigate(toName)`, `shouldUpdateNode(segment)(toState, fromState) === true` for every segment in `activated` or `deactivated`. All changed segments are flagged for update. |
| 2   | Root node on first navigation     | `shouldUpdateNode("")(state) === true` after the first navigation. The root node always updates when there is no previous state.                                                   |
| 3   | Unrelated segment returns false   | `shouldUpdateNode("admin")(toState, fromState) === false` when navigating between routes that do not touch the `admin` subtree. Unchanged segments are not flagged.                |
| 4   | Intersection segment returns true | `shouldUpdateNode(intersection)(toState, fromState) === true` when navigating between siblings. The shared ancestor is included in the update check.                               |

## buildNavigationState / makeState (state factories)

`pluginApi.buildNavigationState(name, params?)` and `pluginApi.makeState(name, params, search?, path?)` are factory functions for creating state objects (`makeState` gained the `search` channel at slot 3 in RFC-4 M2 / #1548; `path` shifted to slot 4; the partial `buildState` factory was removed in favor of `buildNavigationState` — #1548). They are used internally by the navigation pipeline and by plugins.

| #   | Invariant                                                                 | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| --- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | buildNavigationState path matches buildPath                               | `buildNavigationState(name, params, search).path === buildPath(name, params, search)` for a route without `forwardTo` (with one, the built path uses the RESOLVED target name). The path embedded in the built State matches the URL `buildPath` would generate — on BOTH channels, since #1571 gave the entry point its `search?` slot.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| 2   | buildNavigationState resolves the request                                 | `buildNavigationState(name, params).name` is the requested route name or its `forwardTo` target; an unknown route yields `undefined` instead of a State.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| 2a  | Every entry point can spell both channels (#1571)                         | `navigate` / `buildPath` / `canNavigateTo` / `isActiveRoute` / `makeState` / `buildNavigationState` all accept a query channel. `buildNavigationState` was the last without the slot, so a query intent through it was unspellable — the always-on channel guard would have made it unusable and broken its only consumer. ⚠ **Precedence reworded (#1572 follow-up).** This row used to add "and in every one an explicit `search` value beats a declared query key the caller rode in the `params` bag". Since P1 THROWS, a **producer** (`navigate` / `makeState` / `buildNavigationState`) cannot spell that collision at all — the shape is refused before any merge, so there is no precedence left to state for them. The rule survives unchanged on `buildPath` / `isActiveRoute`, which P1 deliberately does not instrument: they run on every `<Link>` render, an answer there is read immediately and corrupts nothing, and throwing inside a render across six adapters is not a trade this guard is worth. ⚠ **`canNavigateTo` no longer states it (#1576)** — not because it started throwing (it still does not; P1 leaves the predicates alone), but because it now ANSWERS `false` for that shape, so there is no precedence left to state there either. The clause it used to carry described precedence for an intent `navigate` refuses outright, and the predicate's job is to say whether `navigate` would work — see canNavigateTo #6. |
| 3   | makeState returns frozen state                                            | `Object.isFrozen(makeState(name, params, search, path)) === true`. All state objects are deeply frozen at creation.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| 4   | makeState determinism                                                     | `makeState(name, params, search, path)` with identical arguments produces structurally equal states (same name, path, params, and search). The `id` field differs between calls but all other fields are stable.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| 5   | `undefined` is absence on both sides of the default merge (#1550 / #1551) | No own key of `state.params` / `state.search` ever holds `undefined`, for any mix of route defaults and caller values. A caller's explicit `undefined` means "I said nothing" — the route default keeps the slot (`navigate("x", {}, { page: undefined })` with `defaultSearch { page: "1" }` commits `page: "1"`); a default that itself carries `undefined` behaves exactly like no entry (`defaultParams: { id: undefined }` neither leaks the key nor changes the "missing required param" error). Enforced in the merge (`mergeDefined`), not in an ordered normalize stage, so it holds for every producer.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| 6   | `state.search` carries only what `state.path` shows (#1575)               | `Object.keys(state.search) ⊆ Object.keys(matchPath(state.path).search)` in EVERY `queryParamsMode`, from BOTH directions. The URL build prints declared names only under `default` / `strict`, so a key the mode will not print is dropped from the query channel at the merge rather than published beside a path that contradicts it. A DROP, not a move — the key does not fall back into `state.params`. `loose` prints undeclared keys, so it admits everything and short-circuits. Compared by KEYS: values stay a mixed domain by decision (`{page: 2}` from a URL, `{page: "2"}` from an intent), so a value comparison must go through `areParamValuesEqual`. Side edge: a `defaultSearch` for a key the route does not declare with `?` is dead config under `default` / `strict`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |

## canonicalize (nav pipeline)

`canonicalize(port, name, params, search?, opts?)` is the single producer of `Canonical` — the opaque intent that `buildURL` (⑤a) and `materialize` (⑤b) are the only consumers of (`src/pipeline/`). It runs stage ① (forwardTo resolution through the interceptor seam, via the port) and stage ③ (route defaults merged UNDER the caller's value) in one pass; there is no separating stage — channels arrive correct by the producer contract. `opts.resolveForward: false` selects the LITERAL form (the route the caller NAMED, no chain, no seam), which is what `buildPath`, `isActiveRoute`'s literal arm and `makeState` take. Since Phase 4 this is the router's ONLY stage-③ implementation. Tested as a PURE function against a mocked port (`tests/property/canonicalize.properties.ts`), which is the only place the merge is observable without the seam, the URL build and forwardTo entangled with it.

| #   | Invariant                                                 | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| --- | --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Caller beats the route default, on both channels          | For every key the caller supplies with a DEFINED value, `Canonical.path[key]` / `Canonical.query[key]` is that value — whether the route declares the same key with a value or with `undefined`. This is the whack-a-mole class the pipeline exists to kill: a default silently outranking a user value (#1550).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| 2   | `undefined` is absence on both sides                      | No own key of either channel ever holds `undefined`; a key that is `undefined` on BOTH sides is absent entirely. Same rule as makeState #5 — one merge helper (`mergeDefined`), and since Phase 4 one stage-③ caller as well, so there is nothing left for it to drift between.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| 3   | Channels are independent — the pipeline never re-splits   | A value handed in the path bag stays in `path`, a value handed in the query bag stays in `query`, and a name occupying both (`/items/:id?id`) keeps two independent values. Stage ② is absent by design; channel correctness is the producer's contract, not a normalisation the pipeline applies.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| 4   | Channels are frozen by PUBLICATION, not by merge          | `Object.isFrozen(Canonical.query)` on every path — the fast path hands over the `EMPTY_SEARCH` singleton, the slow one its own frozen `admittedSearch` result. `Canonical.path` is frozen at the merge on the SLOW path and by `materialize` on the fast one (#1598): a `Canonical` has exactly two consumers — `buildURL`, which reads and returns a string, and `materialize`, which publishes — and the brand is unexported, so there can be no third. `materialize` freezes BEFORE the `skipFreeze` branch, which defers only the STATE OBJECT, so guards still observe immutable bags on the navigate path. The caller's own bag is never frozen — the merge copies first. ⚠ Stated over BOTH paths since #1599: the property used to pass a fresh query bag on every run, so it only ever exercised the slow one. See **State immutability** below. |
| 5   | Stage ③ is idempotent                                     | Re-canonicalizing a `Canonical`'s own channels under the same route defaults changes nothing. This is the premise behind `materialize` not calling `makeState` (a second merge would be a wasted pass, never a behaviour change) — and it is what made every mixed old/new path safe while the entry points migrated one per commit.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| 6   | The mode gate admits exactly what the mode prints (#1575) | Under a non-`loose` `queryParamsMode`, `Canonical.query` holds exactly the keys the route declares with `?` — every declared key the caller supplied is kept, every other one is dropped, and a dropped key never reappears in `Canonical.path` (a DROP, not a move). Under `loose` every key is admitted, declared or not, because `loose` is the one mode whose build prints undeclared keys. The pipeline reads the decision through one boolean port accessor (`admitsUndeclaredQuery()`) rather than learning the mode itself.                                                                                                                                                                                                                                                                                                                       |

## State immutability (who freezes what)

`CLAUDE.md` promises "states are **deeply frozen**", and they are — but the depth is not produced by one call. It is a **policy: every object is frozen once, where it is created**, and `freezeStateShell` (`src/helpers.ts`) freezes only the state object's own level. That distribution is deliberate and measured, not an oversight: re-freezing an already-frozen object costs ~8 ns (#1598), so a recursive walk at the publication boundary would pay per node for work the producers already did. What makes the policy safe is that it is stated here and pinned per producer — before #1599 it was neither, and two of the four freezes were unguarded (deleting the `canonicalize` one left the whole suite green).

Pinned in TWO layers, because a policy with five owners cannot be held by black-box assertions alone — those say the states that exist are frozen, never that a sixth producer has not appeared beside them.

**Black-box**, `tests/functional/error/helpers.test.ts` — "state immutability across every producer" — over every public exit that hands back a `State`: `navigate` (path params / query channel / route defaults / non-empty params through the `skipFreeze` pipeline), `makeState` with and without params, `matchPath`, `buildNavigationState`, `navigateToNotFound`, `replace()` revalidation, and a non-`loose` mode with a dropped key. Mutationally validated against all four sites below.

**Structural**, `tests/functional/state-freeze-authority.test.ts` — a CLOSED-SET census: exactly five `State` constructors in exactly five named files, and exactly two `freezeStateShell` call sites (the commit `update` on the table, and `materialize`'s publication boundary). A sixth of either fails, so an exception has to be argued for here rather than appearing quietly. ⚠ The scan keys on an object LITERAL carrying the `State` type — not on property names (which gave a false "two", then a false "three") and not on the type alone (which gave a false "six", counting `as State<P> | undefined` in `StateNamespace.get`, a narrowed READ). It carries its own positive/negative control for that reason, and all three mutations — a sixth constructor, a third freezer, a removed freezer — were checked to fail it.

| #   | Invariant                                                   | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| --- | ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Every published state is frozen on all four fields          | `name` / `params` / `search` / `transition` (+ nested) of any state a producer can hand to user code are frozen, whichever entry point produced it. "Published" is the boundary that matters — a `Canonical` the predicates discard is not one.                                                                                                                                                                                                                                                          |
| 2   | `state.context` is the one carve-out                        | Frozen SLOT, mutable object: `state.context = {}` throws, `state.context.ns = …` does not. The whole `claimContextNamespace` mechanism depends on it, so a test asserting `Object.isFrozen(state.context) === false` is the contract, not an omission.                                                                                                                                                                                                                                                   |
| 3   | Each object is frozen once, at its origin or at publication | `params` → `mergeWithDefault` on the SLOW path; on the fast one there is no merge to freeze it, so `materialize` does at the publication boundary (#1598), before its own `skipFreeze` branch; `search` → the `EMPTY_SEARCH` singleton or `admittedSearch`'s DROP branch — the only branch handing back a bag the caller did not already freeze; `transition` + nested → `buildTransitionMeta` (or inline in `navigateToNotFound`); the shell → `freezeStateShell`. No site re-freezes another's output. |
| 4   | The caller's own bag is never frozen out from under it      | Producers copy before freezing. A caller may reuse the object it passed to `navigate` / `makeState` / `buildPath`; only the `EMPTY_PARAMS` / `EMPTY_SEARCH` singletons it may receive back are frozen, and those are shared by design.                                                                                                                                                                                                                                                                   |

## Router Lifecycle (start / stop / dispose)

These invariants cover the FSM-driven lifecycle of the router. Each state transition has observable consequences on `isActive()` and `getState()`.

| #   | Invariant                    | Description                                                                                                                                                                                                                                                    |
| --- | ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | start sets isActive          | After `await start(path)`, `isActive() === true`. A started router reports itself as active.                                                                                                                                                                   |
| 2   | start sets state             | After `await start(path)`, `getState() !== undefined`. Starting the router establishes an initial state.                                                                                                                                                       |
| 3   | stop clears isActive         | After `stop()`, `isActive() === false`. A stopped router is no longer active.                                                                                                                                                                                  |
| 4   | stop clears state            | After `stop()`, `getState() === undefined`. Stopping the router clears the current state.                                                                                                                                                                      |
| 5   | Restart works                | After `stop()`, a subsequent `start(path)` succeeds and `isActive() === true`. The router can be restarted after stopping.                                                                                                                                     |
| 6   | Double start rejects         | Calling `start()` on an already-started router rejects with `ALREADY_STARTED`. Starting twice is an error.                                                                                                                                                     |
| 7   | dispose blocks all mutations | After `dispose()`, all 9 mutating methods (`navigate`, `navigateToDefault`, `navigateToNotFound`, `start`, `stop`, `usePlugin`, `subscribe`, `subscribeLeave`, `canNavigateTo`) throw `RouterError` with code `ROUTER_DISPOSED` (#946 added `subscribeLeave`). |
| 8   | dispose is idempotent        | Calling `dispose()` twice does not throw. The second call is a no-op.                                                                                                                                                                                          |

## navigate / transition.segments

## Route Management (getRoutesApi)

`getRoutesApi(router)` provides CRUD operations on the route tree. These invariants verify that add, remove, update, replace, and clear operations behave atomically and consistently.

**Crash-preventing guards** (always enforced by core, regardless of plugins): `guardRouteStructure` rejects non-object routes, non-function `canActivate`/`canDeactivate`, and async `encodeParams`/`decodeParams`/`forwardTo`. `guardDependencies` rejects non-plain-object dependency maps. Circular `forwardTo` chains are detected by `resolveForwardChain` at registration time. These guards prevent silent state corruption and always throw, even without the validation-plugin.

**Invariants requiring `@real-router/validation-plugin`** are marked _(validation-plugin only)_.

It used to drop the committed state silently: subscribers kept rendering a route the router had discarded, and the router was left `isActive() === true` with no state, a shape that otherwise exists only transiently _during_ `start()` (an always-on guard misreads it — path-less `navigateToNotFound()` answers `ROUTER_NOT_STARTED`). Announcing the reset instead was measured and rejected: it would make CRUD emit a transition event as a rule (`replace()` is deliberately the ONE structural mutation that emits one) and would not remove the shape. A THROW rather than the `logger.error` + no-op that the navigation-in-progress precondition uses, because the classes differ: that one clears by itself, this one never does. The two hand over — with a state committed this throws first; with a navigation in flight and NO state yet (the `start()` window) the older guard still logs and no-ops. Design note `fsm-as-state-owner-2026-07-31.md` §11.A1 option (в). |
| 18  | clear atomicity — STRUCTURAL, not declared (#1612) | After `clear()`, the tree, the lifecycle guards and BOTH state cells (`getState()` and `getPreviousState()`) are consistently empty **together**. ⚠ **Class matters:** unlike `replace` / `add` / `update`, whose prepare-then-commit contract is declared and pre-flighted (#698 / #1046 / #1193, invariant 5), this atomicity is _structural_ — three consecutive steps (`resetStore` → `lifecycleNamespace.clearAll()` → `clearState()`) with no try/catch, holding together only because **no user code runs in them**. A callback landing in any of the three is a **contract break, not a refactor**: partial application becomes reachable and nothing else would notice. Stated as a post-condition rather than an exception test because there is no exception to raise — that IS the structural class. Verified discriminating: dropping `clearAll()` or `clearState()` each fails the property (`getPreviousState()` survives `stop()`, which is what makes the state clause non-vacuous).                                                                                                                                                                                                                                |
| 19  | replace revalidation commits only a state the window did not invalidate (#1753 / #1754) | `replace()`'s revalidation is the THIRD commit door and asks, on BOTH arms, whether the URL's owner changed while its own application code ran. Both run application code between `matchPath` and the commit — the survivor arm through the route's own `decodeParams` (invoked by that `matchPath`), the route-identity arm additionally through the activation guards it consults (#1201) — and either can reach back into route-CRUD, because no navigation is in flight and the `TREE_CHANGED` dispatch has already returned. So a `replace()` never commits a state whose URL changed owner while its own application code ran. ⚠ NOT the stronger post-condition "`state.path` always routes back to `state.name`": two of this fix's own regression controls commit states that never round-tripped (`rewritePathOnMatch: false`, and the #1157 rebuild fallback), and the declared `forwardTo` boundary commits another. The guarantee is about CHANGE across the window, not about the state being well-formed to begin with. ⚑ #1754 widened this from existence to OWNERSHIP, asked as a DIFFERENCE against a snapshot taken before the window — an equality against `state.name` presumes the committed path belongs to the committed name, which `rewritePathOnMatch: false` and the #1157 rebuild fallback both deliberately break. `hasRoute(name)` left the route surviving under the same name at a URL it no longer owned (a nested `replace()` that moved it, a `setRootPath`, an `add` of a more specific route — all measured), and the widened form subsumes the old one. Boundary: a `forwardTo` installed inside the window changes resolution without changing matching and is deliberately not caught, since resolving the chain would run application code inside the predicate. It used to be neither: `systemCommit` asks whether the MACHINE may commit (#1186 / #1644), never whether the route exists, and a guard removing the route it was consulted about got that route committed with a clean `TRANSITION_SUCCESS`. ⚠ The check is at the DOOR, not beside the consult: pinning the consult leaves the survivor arm open, which is measured (a nested `replace()` from a decoder). The door SET is derived — `tests/functional/commit-door-authority-1753.test.ts` walks `src` for calls to the commit primitives and pins, per door, WHICH form of the question it asks, holding the DI plumbing to "forwards only what it was handed"; `navigateToNotFound` is the one exemption, since `UNKNOWN_ROUTE` is not a route to look up. |
| 20  | remove clears exactly what it removed (#1757) | `remove(name)` clears config and lifecycle handlers for the routes the SPLICE took out of the tree — the node and its real `children` — and for no others, and the `TREE_CHANGED` payload names that same set. Structural, not lexical: core accepts a dotted LEAF, so `{ name: "a.b" }` declared beside `{ name: "a" }` is a standalone node, and the name-prefix form it replaced purged a route that SURVIVED the removal — unregistering its blocking `canActivate` (a fail-open), dropping its config, clearing a third route's `forwardTo` pointing at it, and announcing it as removed while `has()` still answered `true`. The same rule decides the active-route refusal: the committed route blocks the removal exactly when the matcher's segment chain for it contains `name`. |

## Guards + navigate Interaction

Guards registered via `getLifecycleApi(router)` run during the transition pipeline and can block navigation. These invariants verify the interaction between guard results and navigation outcomes.

| #   | Invariant                     | Description                                                                                                                         |
| --- | ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Blocking activate guard       | An activate guard returning `false` causes `navigate()` to reject with `CANNOT_ACTIVATE`. Guards can block entry to a route.        |
| 2   | Passing activate guard        | An activate guard returning `true` allows navigation to proceed. Guards that pass do not interfere with navigation.                 |
| 3   | Deactivate before activate    | Deactivate guards run before activate guards. The order is: deactivate innermost-first, then activate outermost-first.              |
| 4   | Guard receives correct states | An activate guard receives `(toState, fromState)` with the correct route names. Guards can inspect both the origin and destination. |
| 5   | Async guard blocking          | An async activate guard returning `Promise.resolve(false)` blocks navigation with `CANNOT_ACTIVATE`. Async guards are awaited.      |
| 6   | Async guard allowing          | An async activate guard returning `Promise.resolve(true)` allows navigation to proceed. Async approval works the same as sync.      |
| 7   | Guard receives AbortSignal    | The guard function receives an `AbortSignal` instance as its third parameter for cooperative cancellation.                          |

## canNavigateTo

`router.canNavigateTo(name, params?)` is a synchronous predicate that checks whether navigation would be allowed by currently registered sync guards.

| #   | Invariant                          | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| --- | ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Unknown route returns false        | `canNavigateTo(unknownRoute) === false` for any route name not in the route tree. Unregistered routes are always blocked.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| 2   | No guards returns true             | Without any registered guards, `canNavigateTo(existingRoute) === true`. Routes are navigable by default.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| 3   | Passing sync guard returns true    | When a sync activate guard returns `true`, `canNavigateTo === true`. Guard approval is reflected synchronously.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| 4   | Blocking sync guard returns false  | When a sync activate guard returns `false`, `canNavigateTo === false`. Guard rejection is reflected synchronously.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| 5   | Total — no input makes it throw    | The predicate ANSWERS for every input. Missing required path params return `false` (the target path can't be built, so the route is unreachable with that input) rather than throwing `buildPath`'s error (#725). **Extended by #1577 to the whole resolution step:** a dynamic `forwardTo` callback, a plugin's `forwardState` interceptor, and the caller's own bag (the merge walks it key by key, so an accessor-backed key throws there — the channel guard itself does not, it catches its own read) all run USER code or user-owned data, and a throw from any of them is caught and reported as `false` + a `logger.warn` — never silent (user code crashing is an operational fault, the same split #959 draws for a throwing guard), never propagated.                             |
| 6   | Mis-channelled input returns false | A key the route declares as a **query** param, handed in the **path** bag, makes `navigate` throw a synchronous `TypeError` (channel guard P1, #1572) — so the route is unreachable with that input and the predicate returns `false` (#1576). The same rule as #5, for the other way `navigate` refuses the same arguments: the predicate answers, it never throws, and it never promises a navigation that would throw on the click. Read from the **raw** caller bag against the **raw** name, exactly as P1 does, so the predicate is neither stricter nor laxer than the verb: the `/items/:id?id` collision is absent from `queryNames` by construction (#843 / #1549) and stays navigable in both, and an `undefined` value is the removal marker, not a mis-channel (#1550 / #1551). |

## subscribe (event delivery)

`router.subscribe(listener)` registers a callback that fires after every successful navigation. These invariants verify that the delivered event data is consistent with the router's state.

| #   | Invariant                             | Description                                                                                                              |
| --- | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 1   | route equals getState                 | The `route` field in the subscriber callback is the same object as `getState()` at the time of delivery.                 |
| 2   | previousRoute equals getPreviousState | The `previousRoute` field in the subscriber callback is the same object as `getPreviousState()` at the time of delivery. |
| 3   | Called exactly once per navigation    | A subscriber is called exactly once per successful navigation, not zero times and not multiple times.                    |
| 4   | Unsubscribe stops delivery            | After calling the returned `unsubscribe()` function, the listener is not called on subsequent navigations.               |

## subscribeLeave

`router.subscribeLeave(listener)` registers a callback that fires when the FSM enters `LEAVE_APPROVED` — after deactivation guards pass and before activation guards run. This is the safe window for side-effects like scroll preservation, fetch abort, and analytics.

| #   | Invariant                          | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| --- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | Non-function throws                | `subscribeLeave(nonFunction)` throws `TypeError` immediately. Only functions are accepted as listeners.                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| 2   | Callback signature                 | Callback receives `{ route: State, nextRoute: State, signal: AbortSignal }` where `route` is the current (leaving) route, `nextRoute` is the destination, and `signal` enables cooperative cancellation.                                                                                                                                                                                                                                                                                                                                                                             |
| 3   | First navigation skipped           | NOT called on first navigation (no previous route — `fromState` is `undefined`). The leave phase requires an existing route to leave from.                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| 4   | navigateToNotFound skipped         | NOT called when navigating via `navigateToNotFound()` — that method bypasses the pipeline entirely and emits no `LEAVE_APPROVED` event.                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| 5   | Returns unsubscribe                | Returns a function that removes the listener. After calling it, the callback is not invoked on subsequent navigations.                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| 6   | Async listener blocks pipeline     | A listener returning `Promise<void>` blocks the navigation pipeline until resolved. Activation guards run only after all leave listeners complete. Property-verified — activation runs after **all N** async listeners settle, for any N (`subscribeLeave.properties.ts`, #1200 item 8).                                                                                                                                                                                                                                                                                             |
| 7   | Independent error isolation        | A sync throw or async rejection in one listener does not stop the others (sync listeners all run; async listeners settle via `Promise.allSettled`). Error precedence is **sync-first** — a sync throw wins over an async rejection — and `navigate()` rejects with the **original** error (a sync throw is **not** converted to `TRANSITION_CANCELLED`). Sync-first precedence is property-verified over **any** thrower position among N listeners (#1200 item 9a).                                                                                                                 |
| 8   | Signal aborts on cancel or failure | The `signal` passed to listeners aborts when the navigation is **cancelled** (superseded by a newer `navigate()`, `stop()`, `dispose()`, or an external `opts.signal` abort) **or fails** (a sync leave throw, a rejecting activation guard) — and **never** on successful completion. Holds identically on the guard and no-guards pipeline paths (#722). Verified functionally in `tests/functional/navigation/navigate/leave-signal-cancellation.test.ts`; property-verified generatively — every cancel source × N pending listeners aborts each captured signal (#1200 item 7). |
| 9   | Fires once, in order               | Every registered listener fires exactly once per leave, in registration order; unsubscribing K of N leaves exactly the remaining N−K firing. Property-verified in `tests/property/subscribeLeave.properties.ts`.                                                                                                                                                                                                                                                                                                                                                                     |
| 10  | Payload wrapper frozen             | The `{ route, nextRoute, signal }` wrapper is `Object.freeze`d — listeners cannot mutate or extend it. `route` is deeply frozen; `nextRoute` is the still-unfrozen pending target (deep-frozen on commit) and must be treated as read-only.                                                                                                                                                                                                                                                                                                                                          |
| 11  | Tentative departure (reject-half)  | When the leave listener has fired (departure approved) but an **activation** guard then rejects, the committed state stays `fromState`, `navigate()` rejects `CANNOT_ACTIVATE`, and the captured `signal` aborts with that reason — the departure was tentative, not committed (#932/#943). Property-verified over targets in `subscribeLeave.properties.ts` (#1200 item 6).                                                                                                                                                                                                         |
| 12  | No-fire without approved departure | The listener does NOT fire when no departure is approved: `navigateToNotFound` (row 4), a same-state navigation (the SAME_STATES fast-path returns before `LEAVE_APPROVED`), or a blocking deactivation guard (rejects before `LEAVE_APPROVED`). Property-verified over all three scenarios (#1200 item 9b).                                                                                                                                                                                                                                                                         |

## isLeaveApproved

`router.isLeaveApproved()` is a synchronous predicate that returns `true` only while the FSM is in the `LEAVE_APPROVED` state.

| #   | Invariant                 | Description                                                                                                                                   |
| --- | ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | LEAVE_APPROVED state only | Returns `true` only when the FSM is in `LEAVE_APPROVED` state — the window between deactivation guards passing and activation guards running. |
| 2   | All other states false    | Returns `false` in `IDLE`, `STARTING`, `READY`, `TRANSITION_STARTED`, and `DISPOSED` states.                                                  |

## subscribeChanges (TREE_CHANGED)

`getRoutesApi(router).subscribeChanges(handler)` is the single entry point for observing **structural** route-tree mutations. It reuses the router's `EventEmitter` through an internal-only `TREE_CHANGED` key (absent from the public `EventName` union / `Plugin` interface / `events.*` registry). The event is **post-commit** and **fire-and-forget**. See `.claude/rfc-tree-mutation-event.md`.

| #   | Invariant                        | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| --- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | One emit per CRUD call           | Each `add` / `remove` / `replace` / `clear`, and each structural `update`, emits exactly one event. `add([r1, r2, r3])` is one event, not three (atomicity is per call, not per route).                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| 2   | Discriminated by `op`            | Payload is a discriminated union keyed by `op` (`"add" \| "remove" \| "update" \| "replace" \| "clear"`). Consumers must `switch (event.op)` exhaustively, not inspect `Object.keys`/array order.                                                                                                                                                                                                                                                                                                                                                                                                                        |
| 3   | Post-commit timing               | The handler runs after the atomic commit — `has()` / `get()` reflect the post-mutation tree. For `replace`, the event fires after the tree swap but before state revalidation (handler sees old state). Carve-out: a handler that calls `router.dispose()` mid-dispatch tears the tree down (dispose is not a CRUD op, so the #1032 reentrancy ban does not apply) — the remaining handlers of that same emit observe the torn-down tree.                                                                                                                                                                                |
| 4   | update is structural-only        | `update` emits only when the patch contains a structural field (`forwardTo` / `defaultParams` / `encodeParams` / `decodeParams`). Guard-only and empty patches are silent (О-7).                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| 5   | Payload immutability             | `update.patch` is a frozen envelope built from a fresh object (caller's patch untouched); payload route arrays are frozen, with each route frozen on construction. Nested config values are by reference.                                                                                                                                                                                                                                                                                                                                                                                                                |
| 6   | Re-entrancy coalescing           | A runaway listener-driven **nested same-event emit** — e.g. a `router.subscribe` listener that calls `replace()`, whose #950 revalidation re-emits `TRANSITION_SUCCESS` and would re-enter the listener — is harmlessly **coalesced** at the `EventEmitter` (`#dispatching` guard, **depth ≤ 1**, #1033): the re-entrant emit is a no-op, so the listener runs once and the mutation still commits. There is **no depth limit** and no `RecursionDepthError`. (Direct reentrant tree mutation from inside a `subscribeChanges` handler is separately banned — it throws `REENTRANT_TREE_MUTATION` before mutating, #1032. The ban covers **six** doors: the five `getRoutesApi` mutators and `getPluginApi.setRootPath`, #1751.) |
| 7   | Clone isolation                  | A cloned router has an independent emitter — mutations on the parent never reach the clone's subscribers, and vice versa.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| 8   | Conditional `replace`/`add` diff | The flat removed/added diff is computed only when there is at least one listener (`listenerCount > 0`); otherwise the mutation is O(1) on the event path.                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| 9   | Listener error isolation         | A throwing handler is reported via `onListenerError`; other handlers still run and the CRUD caller never sees a re-throw.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| 10  | FIFO + snapshot delivery         | Handlers fire in registration order. A handler registered re-entrantly during emit `E1` is not invoked for `E1` (snapshot iteration); it participates from the next event onward.                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| 11  | dispose silences the channel     | `router.dispose()` releases all `TREE_CHANGED` listeners (step 4 of cleanup) before the internal route teardown — no event is emitted during disposal (the public `clear()` wrapper is bypassed).                                                                                                                                                                                                                                                                                                                                                                                                                        |
| 12  | subscribe-after-dispose throws   | A `subscribeChanges` reference used after `dispose()` — including one bound before disposal (`const s = routes.subscribeChanges.bind(routes)`) — throws `RouterError(ROUTER_DISPOSED)` instead of silently re-registering a listener that can never fire (the route tree is torn down during dispose). The internal-route-tree counterpart of the `subscribe`/`subscribeLeave` guard (#946). Verified functionally in `tests/functional/api/getRoutesApi/getRoutesApi.test.ts`.                                                                                                                                          |

## getDependenciesApi (CRUD)

`getDependenciesApi(router)` provides a key-value store for dependency injection. These invariants verify basic store semantics.

| #   | Invariant           | Description                                                                                                                         |
| --- | ------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 1   | set then has        | After `set(name, value)`, `has(name) === true`. A set dependency is immediately visible.                                            |
| 2   | set then get        | After `set(name, value)`, `get(name) === value`. The stored value is exactly what was set.                                          |
| 3   | remove then has     | After `set(name, value)` and `remove(name)`, `has(name) === false`. Removal is effective immediately.                               |
| 4   | setAll then getAll  | After `setAll(deps)`, `getAll()` contains all key-value pairs from `deps`. Bulk set is consistent with bulk get.                    |
| 5   | Idempotent set      | Calling `set(name, value)` twice with the same arguments does not change the stored value. Overwriting with the same value is safe. |
| 6   | reset clears all    | After `reset()`, `has(name) === false` for every previously set dependency. `reset()` removes all dependencies.                     |
| 7   | getAll returns copy | `getAll()` returns a new object on each call (not the internal store). Mutating the result does not affect the store.               |
| 8   | set undefined no-op | `set(name, undefined)` does not register the dependency. `has(name)` remains `false`.                                               |

## usePlugin

`router.usePlugin(...plugins)` registers one or more plugins and returns an unsubscribe function. Plugins are observer factories that receive lifecycle events during navigation.

| #   | Invariant                               | Description                                                                                                                                                             |
| --- | --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Unsubscribe calls teardown              | Calling the returned `unsubscribe()` function invokes `teardown()` on each plugin. Plugin resources are cleaned up on unsubscription.                                   |
| 2   | Idempotent unsubscribe                  | Calling `unsubscribe()` twice does not throw. The second call is a no-op.                                                                                               |
| 3   | Same toState/fromState across plugins   | All plugins registered in the same `usePlugin()` call receive the same `toState` and `fromState` references in `onTransitionSuccess`. Event data is shared, not cloned. |
| 4   | onStart missed after start              | Plugins registered after `router.start()` do not receive `onStart`. Lifecycle events are not replayed retroactively.                                                    |
| 5   | Disposed router throws ROUTER_DISPOSED  | Calling `usePlugin()` on a disposed router throws `RouterError` with code `ROUTER_DISPOSED`.                                                                            |
| 6   | Registration order preserved            | Plugins receive `onTransitionSuccess` in the order they were registered. First-registered plugin fires first.                                                           |

## Navigation cancellation

Cancellation is owned by the FSM: every source routes through FSM `CANCEL`, and the `CANCEL` action aborts the in-flight controller (RFC `navigation-cancellation-unification` §5). The controller is a field of the navigation the machine carries, so the action reads it straight off `ctx.inflight` (#1684), and when it does not exist yet the action RECORDS the cancellation on the navigation instead, for the pipeline's single `openController` door to replay (#1706). See `EventBusNamespace.handleCancel`.

**An external `opts.signal` reaches it through a bridge, and "was it already aborted?" has exactly ONE owner (#1704).** `addEventListener` never fires retroactively, so a bridge is only as good as the instant it is registered — and `beginTransition` reads `opts.signal` and `opts.forceDeactivate` in front of the earliest registration (the `NAVIGATE` action since #1724), which is application code whenever `opts` is accessor- or Proxy-backed. The pipeline asks once, inline immediately after the announce; neither registration site carries a copy. It cannot be asked earlier: `CANCEL` is declared on `TRANSITION_STARTED` / `LEAVE_APPROVED` only, so before the announce the send is a table no-op. It is safe to ask again later for the same reason — `sendCancelIfPossible` is `canCancel()`-guarded, so a navigation announces exactly one `TRANSITION_CANCEL` whatever the arc.

⚑ **The scope is OPENED and CLOSED by the machine, not by the pipeline (#1716 + #1724).** Detaching it used to be four settle sites in `executeNavigation` (#1688); the cancellability scope travels with the plan, the `NAVIGATE` edge adopts it in its `update`, OPENS it in its action, and the ACTION of whichever terminal edge the navigation left the band through — `CANCEL`, `FAIL` or `COMPLETE` — closes it. `DISPOSE` is deliberately not in the closing set: its `update` (`resetState`) zeroes `inflight` before the action would run and it carries no payload, but more to the point it has nothing to close — instrumented over the whole tier, all 230 `DISPOSE` traversals came from `IDLE` or `STARTING`, never from inside the band, because `dispose()` and `stop()` both send `sendCancelIfPossible` FIRST. ⚑ **The pipeline's last closing call went by moving the OPENING (#1724).** It existed for the navigation the machine never ADOPTED — a `NAVIGATE` that is a table no-op has no edge to close it, and the bridge used to be registered before the send — so opening from the action means a refused edge opens nothing, while the `onTransitionStart` window stays covered (the action runs before the emit; measured: the bridge fires from inside the announce 4 times across the tier). ⚠ "The edge fired" is NARROWER than "`sendNavigate` returned true": a navigation whose announce moves the machine gets `false` having opened a scope, and the `CANCEL` that moved the machine closes it (16 arrivals at that branch across the tier, 7 of which ran no action). Registration stays CONDITIONAL (#1690) — asked in the action, of the namespace holding both listener counts, because registering unconditionally measures +23…30 % on the guard-free, listener-free arc — and the late registration is REFUSED when the machine has already cancelled the navigation (`plan.cancelReason !== undefined`), because a listener installed after the terminal edge is one nothing would ever remove; measured, it leaked 4 listeners across 4056 passing tests. Exactly ONE of the two sites owns "is a bridge already standing?": duplicating the test makes the owner's branch structurally unreachable, and a second registration on the arc that reaches both moments would orphan the first. Pinned by `cancellability-scope-1716.test.ts`, which COUNTS `addEventListener`/`removeEventListener` on the caller's signal per arc — the both-moments arc included — because a leaked listener changes no outcome, no event and no state.

| #   | Invariant                                                                | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| --- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | Cancellation wakes the nav & settles FSM                                 | For any random sequence of suspended navigations cancelled by `stop` / `dispose` / external `opts.signal`, each cancelled navigation rejects (the CANCEL action's controller-abort wakes the parked async pipeline, #1018) and the FSM is left settled — never stuck in `TRANSITION_STARTED`/`LEAVE_APPROVED` (`isLeaveApproved() === false`; `stop` → IDLE, external → READY); route-CRUD blocked-while-transitioning (#1030) works after. Verified **discriminating**: the guards never settle, so removing the abort hangs every cancellation.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| 2   | One terminal event per navigation (#1609)                                | A navigation gets **exactly one** terminal event. Under supersede — whatever the superseded navigation's own guard decided in the meantime (`false`, a rejection, or a thrown `RouterError(TRANSITION_CANCELLED)`), on either the activate or the deactivate phase, at any microtask delay between that verdict and the supersede — its terminal is a single `TRANSITION_CANCEL` or a single `TRANSITION_ERROR`, never both; and the navigation that superseded it still commits and emits `TRANSITION_SUCCESS`. The second half is what catches the corrupting form: a stale `FAIL` takes the real edge `TRANSITION_STARTED --FAIL--> READY`, so the live navigation's later `COMPLETE` becomes a table no-op — state committed, no `TRANSITION_SUCCESS`, no subscriber notified. Supersede is the axis invariant 1 deliberately excludes (it starts a new in-flight navigation rather than settling the router). Covers the ASYNC arc only; the synchronous one (`handleNavigateError`) is pinned functionally in `tests/functional/navigation/superseded-guard-rejection-1609.test.ts`. |
| 3   | A cancelled navigation stops asking GUARDS (#1687)                       | After `TRANSITION_CANCEL` no guard of that navigation runs — on any source, on the deactivate phase, on the activate phase (later segments included) and on an arc parked in an async guard. The fence at the head of each guard step asks the pair the asynchronous half asks: still the navigation in flight, **and the controller not aborted**. The abort term is the one that DECIDES — instrumented over the functional and property tiers, 317 refusals with `aborted` true in every one — and it is the only answer for an external `opts.signal`, which fails the identity term not at all (`CANCEL` carries no `update`, so `ctx.inflight` still names the navigation, #1671, and it lands the machine in `READY`). Without that, a `CANCEL` landing before the guard fork opened its controller left the fresh one unaborted, all three terms true, and the whole walk ran. Pinned in `tests/functional/navigation/cancellation-stops-the-guard-walk-1687.test.ts` — the class, with the two already-stopped sources as controls, plus a COUNTING case for the pre-controller window (the outcome does not discriminate there; only the invocation count does).                                                                                                                                                 |
| 4   | …but it still DELIVERS the leave, with an aborted signal (#1687 / #1697) | A `subscribeLeave` listener whose leave was approved before the cancellation is **still called**, and its `signal.aborted` is already `true` when it is. That is the contract, not a leak — it is what `subscribeLeave` 8 promises from the other side, and two shipped primitives key their skip on exactly that flag: `guardLeaveListener` (behind `useRouteExit` / `injectRouteExit` in all six adapters) and the reentrant-abort return in `dom-utils/view-transitions`. Holds on BOTH leave arcs: the guard-free one used to allocate its controller after the announce, so a cancel fired from inside `onTransitionLeaveApprove` had nothing to abort and handed the listener a live signal (#1697). Holds for a listener REGISTERED from inside that announce too (#1706): it cannot be counted before it exists, but the controller its own registration opens is born aborted from the `cancelReason` the `CANCEL` action recorded, so nothing is allocated for a listener that never appears and no cell is left open.                                                                                                                                                                                             |

## Committed-state ownership

Assembled from several independent decisions and, until #1610, written down
nowhere — while `transition.from`, the former `hasInflight` predicate (retired
in #1669 precisely because this invariant made it a tautology) and the whole
commit-gate semantics lean on it (`.claude/fsm-as-state-owner-2026-07-31.md`
§3.1, plan item 0.1).

⚑ **The ownership is now structural (#1641).** What the section below describes
as a set of independent decisions that happened to agree became one mechanism:
the committed state moved INTO the FSM context, so the invariants are properties
of the transition table rather than facts about scattered call sites. Invariants
4 and 5 are what that buys; 1–3 are stated as before and now hold for a shorter
reason.

⚠ **Wording matters, and the mechanism-level phrasing does not catch the bug.**
"While the FSM is in `TRANSITION_STARTED` / `LEAVE_APPROVED` the committed state
is unchanged" is TRUE, but it stayed true even on #1610 — measured over the full
generator, not argued: a nested navigation SUPERSEDES, so it cancels whatever was
in flight before committing, and its commit always lands inside its own
transition. It is kept below as a second, separately-asserted clause precisely so
that difference cannot be lost again; the caller-facing clause is the one with
discriminating power.
