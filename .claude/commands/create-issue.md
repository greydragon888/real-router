Создай GitHub issue — или комментарий к существующей задаче, если у находки есть дом: проверь дубликаты, оформи заголовок и тело по конвенции, повесь корректные labels.

Входные данные:
$ARGUMENTS

Формат аргументов (всё опционально — недостающее выведи из контекста разговора или спроси):

- Свободное описание проблемы/задачи/фичи
- Можно указать тип (`bug`/`feat`/`perf`/`task`/`docs`/`gfi`), area, priority — иначе определи сам

Репозиторий: `greydragon888/real-router`. **Заголовок, тело и комментарий — по-английски, для любого типа.** По-русски остаются только метки вариантов русских RFC (`(а)/(б)/(в)`), дословные цитаты документов `.claude/**` и вставленный вывод проб: перевод исказил бы источник.

Задача записывает то, что видно при создании. Работа над ней (`/bugfix`, `/enhance`) исследует глубже и перепишет тело, а её исход — закрыта, отложена, не воспроизвелась — решает тоже работа. Скил отвечает за то, чтобы записанное было верно, а находка легла в нужное место и в нужной форме.

## Шаг 0 — Тип

| Тип | Токен в заголовке | Метка типа | Секции тела (Шаг 4) |
| --- | --- | --- | --- |
| Баг | `[bug]` | `bug` | bug |
| Фича / улучшение | — | `enhancement` | feature |
| Производительность | `[perf]` | `performance` | perf |
| Рефакторинг / cleanup / infra | — | `enhancement` | task |
| Пин поведения, test-gap | `[test]` | `enhancement` | task |
| Развилка, которую решает владелец | `[research]` | `enhancement` | варианты и цена каждого; приёмка — «решение записано» |
| Документация | `[docs]` | `documentation` | docs |
| Good first issue | — | `good first issue` | gfi |

`bug` — если нарушен заявленный инвариант (round-trip `state ↔ URL`, равенство состояний, freeze, «нет `undefined` в state»), даже когда фикс требует выбора: выбор оформляется секцией `## Decision required`. `enhancement` — если «правильное» поведение лишь предпочтение. Решает инвариант, а не аналогия с соседней задачей. Тип ставится по постановке и пересматривается после Шага 2.5: проба и радиус его меняют.

Шаблоны `.github/ISSUE_TEMPLATE/*.yml` дают только структуру секций: их заголовки (`[Bug]: `) и эмодзи-метки в репозитории не используются.

## Шаг 1 — Данные одним вызовом

```bash
gh api rate_limit --jq .rate.remaining
gh label list --repo greydragon888/real-router --limit 200 --json name --jq '.[].name'
gh issue list --repo greydragon888/real-router --state all --limit 3000 \
  --json number,title,state,labels,createdAt > "$LIST"
```

`$LIST` — файл в скретч-каталоге сессии. Листинг — источник для дома, дублей, токенов заголовка и меток: дальше фильтруй его `jq`, а не новыми запросами.

- ⚠ Лимит — на весь трекер: задач больше тысячи, и `--limit 200` молча теряет старых соседей.
- ⚠ `error connecting to api.github.com` — отказ сети, а не пустая выдача. Пока GitHub недоступен, дедуп не выполнен и создавать нельзя.

## Шаг 2 — Дом, дубль, родня

**Предпочтительный исход — комментарий к существующей открытой задаче.** Он даёт её решению больше данных, а меньше задач — меньше потраченных токенов. Новая задача — когда дома нет или находка — отдельная работа, которая в его скоуп не помещается.

1. **Дом** ищи по заголовкам ВСЕХ открытых задач из листинга — их десятки, это один проход. Задача-класс названа по семейству («docblocks still describe …»), а не по символу из твоей находки, поэтому поиск по словам симптома её не находит.
2. **Закрытых соседей** — фильтром листинга по 2–4 именам символов (`select(.title | test("<kw1>|<kw2>";"i"))`) и по телам: `gh search issues --repo greydragon888/real-router <kw1> OR <kw2> --limit 20` (без `--state`: значения `all` у него нет). ⚠ Слова — отдельными аргументами, без общих кавычек: аргумент с пробелом `gh` берёт в кавычки и ищет точную фразу, и `"<kw1> <kw2>"` даёт ноль, похожий на «дублей нет». Поиск по телам идёт через индекс GitHub и отстаёт — «ноль» сверяй с листингом. Ключевые слова бери из имён символов: они переживают правки тела.
3. **Батч по аудиту или follow-up свежей крупной работы** — ещё и задачи, созданные сегодня (`createdAt` из листинга): параллельная волна могла завести родственников.

Что делать с найденным:

- **Открытый дом** — покажи номер, заголовок и черновик комментария; по согласию — Шаг 7, путь «комментарий».
- **Дубль** — покажи и спроси. Закрытый как `wontfix`/`duplicate` не воскрешай молча.
- **Родственник, но отдельная работа** — новая задача со ссылкой `parallel to #N` или `follow-up of #N`.
- **Закрытый сосед, явно отложивший ровно эту развилку** («a separate design change», «out of scope», «a follow-up step» — в теле или в комментарии кода, который оставил его PR; связывает `git log -S '<фраза>'`) — новая задача как эта отложенная работа: дословная цитата и явное «его решение не задето».
- **Соседа читай целиком:** пересечение часто живёт в разделе про механизм, ниже постановки.
- **Постановка взята из `.claude/**`-документа** — передатируй её: «остаток» в документе мог быть отгружен после его ревизии (`gh issue list --state all --search "<§N.N>"`).

## Шаг 2.5 — Что проверить до тела (bug / perf / task; для docs и gfi — пропусти)

Корень здесь не ищется — его ищет работа над задачей. Здесь проверяется, что каждое утверждение тела либо видно, либо названо гипотезой.

1. **Одна проба на `origin/master` через того, кто реально вызывает код.** Для пакета — публичный API против `src`. Для инфраструктуры — путь вызывающего: строка хука, шаг workflow, `pnpm <script>`, для pre-push — `git push --dry-run <remote> HEAD:refs/heads/<scratch>`. Проба утверждает правильное поведение (red = дефект) и идёт с контролем, показывающим границу. Команду и вывод — в тело. Не воспроизвелось — утверждение идёт гипотезой, отдельной строкой. Из пробы следуют тип (дефект, недостижимый ни одним вызывающим, — латентный: `enhancement` с секцией «Reachability today») и приоритет (Шаг 5).
2. **Быстрый радиус.** Grep того же шейпа по репозиторию. Найденные места — кандидаты, а не проверенный радиус; так и пиши. Сайт, найденный по имени или метке (одноимённая функция, заголовок теста), — тоже кандидат: у разных утверждений они совпадают. Радиус вырос — повтори Шаг 2 словами семейства: прецедент класса назван по семейству, а не по симптому.
3. **Родословная — из найденного в Шаге 2.** Закрытый сосед заявил покрытие («falls under the catch») или назвал свой будущий фикс X — проверь, отгружен ли X и закрыл ли он ЭТО, и процитируй. `follow-up of #N` — только если строки ввёл или оставил тот фикс, иначе `related to #N`. Происхождение строки — `git log -S '<фрагмент>' --reverse -- <весь src пакета>`, а не `git blame`: тот называет последнюю правку строки.

Масштаб — точечный фикс, класс или RFC — решает работа над задачей. Если по видимому он уже велик, скажи это в теле одной фразой.

## Шаг 3 — Заголовок

Формат: `[<area>][<type>] <concise declarative description>` — по-английски, без точки; симптом → следствие через `→`; `(parallel to #N)` при родстве. Выводи заголовок после дедупа: прецедент класса может перевернуть рисунок токенов.

**Токены копируй с прецедента, а не с формата:** возьми из листинга 3–5 свежих задач того же пакета и типа. Рисунки у пакетов разные: в `core` баг — `[core][bug]`; у прикладных плагинов, `sources` и `route-utils` баг идёт голым `[<pkg>]`; у `logger` тип первым — `[bug][logger]`. Семья, уже заведённая тем же аудитом или по тому же классу, важнее рисунка пакета — копируй её токены.

Что из соседей не выводится:

| Случай | Токены |
| --- | --- |
| Код движка (`packages/core/src/engine/`) | `[engine]`; `[core][engine]`, если задет публичный API ядра |
| Shared-слой (`browser-env`, `dom-utils`, `ssr`) | токен слоя первым, затем затронутые пакеты или собирательный: `[browser-env][plugins]`, `[dom-utils][adapters]`, `[ssr][plugins]`; без `[bug]` |
| 3+ адаптера / 3+ плагина | `[adapters]` или точный поднабор / `[plugins]`; два-три — перечислением |
| Вынос кода в новый пакет | токен пакета-источника (`[core]`) или без токена; слияние пакетов — их токены |
| Бенч, измеряющий ядро / поведение отчёта CodSpeed / регрессия ядра, найденная бенчем | `[benchmarks][core]` / `[ci][benchmarks]` / `[core][perf]` |

## Шаг 4 — Тело

`gh` не применяет YAML-шаблоны — секции пиши вручную как `### Heading`:

- **bug** → `### What happened?`, `### Reproduction steps`, `### Environment`, `### Additional context`
- **feature** → `### What's the feature?`, `### Why is it useful?`, `### Additional context`
- **perf** → как feature, плюс замеры: текущее против целевого и как мерили
- **task** → `### What needs to be done?`, `### Related context`
- **docs** → `### What needs documentation?`, `### Suggestions / Draft`
- **gfi** → `### What's the task?`, `### Where to find it in the code?`, `### Additional notes`

Правила записанного:

- Ссылка на код — `packages/<pkg>/src/...:line`, измеренная на `origin/master` после `git fetch`, с SHA в теле («line numbers on `master` @ `<sha>`»): локальный `master` и рабочая ветка дают номера, которые на GitHub не сойдутся.
- Сравнение двух копий («отличаются только X») — по коду обеих, а не по их сообщениям: одинаковый текст ошибки прячет разную логику.
- Производные числа (суммы, «в N раз», «до и после») — тем же скриптом, что и таблицу, а не в уме.
- Кандидаты радиуса и гипотезы — отдельными строками, не вперемешку с проверенным.

## Шаг 5 — Метки и приоритет

Обычно три метки: тип, `priority: <x>` и area. Каждую сверь со списком из Шага 1: `gh issue create` падает на несуществующей метке. Нужной нет — ближайшая существующая или, с согласия владельца, `gh label create`. Area-метку бери с прецедента пакета в листинге: описание метки врёт в обе стороны.

| Случай | Метки |
| --- | --- |
| Ядро и движок | `area: core` (`area: engine` нет) |
| Плагины, `sources`, `route-utils` | `area: plugins` |
| `react` / `solid` / `vue`, `svelte`, `angular`, `preact` | `area: react` / `area:solid` (без пробела) / имя без префикса |
| `logger`, `ssr-utils`, `rx` | без area-метки — две метки |
| 3+ адаптера | без area-меток: area живёт в токенах |
| Test-gap пакета | `area: <pkg>`, не `area: tests`; тест-авторитет (`*-authority-*`, ратчет, перепись) — плюс `area: tests` |
| Дефект сборки или тулинга внутри пакета | плюс `area: build` |
| Создание или вынос публикуемого пакета | `area: <источник>` + `area: build` + `area: npm` |
| Код переезжает из ядра в существующий пакет | по источнику: `area: core` |
| Бенч ядра / отчёт CodSpeed | `area: benchmarks` / `area: ci/cd` + `area: benchmarks` |
| Зависимости | `dependencies` |

**Приоритет:** `critical` — блокирует пользователей; `high` — чинить скоро; `medium` — обычный; `low` — nice to have. Ставь по пробе Шага 2.5: дефект, достижимый через публичный API, и видимый только на unit-уровне расходятся на ступень. Пограничный случай калибруй по прецеденту того же класса из листинга и сошлись на него в теле; прецедента нет — спроси одним вопросом. Старые задачи без `priority:` — эпоха до конвенции, а не образец.

## Шаг 6 — Превью

Покажи владельцу title, labels и полное тело (для комментария — номер задачи и текст) и дождись ответа. Не ответил (таймаут, afk) — создавай по рекомендованному варианту превью и скажи об этом.

Без превью — когда владелец прямо поручил завести задачу со скоупом, уже разобранным в только что показанном отчёте, или под твою же работу: создавай сразу и покажи результат. Превью обязательно, когда заводишь по своей инициативе и скоуп вывел сам.

⛔ «Отгружено» в задаче или комментарии пиши только после проверки удалённого состояния: `git merge-base --is-ancestor <sha> origin/master` или смёрженный PR. Одноимённая удалённая ветка не доказательство: ветки под задачу GitHub заводит пустыми, на `master`.

## Шаг 7 — Создание

Тело пиши в файл и передавай `--body-file`: zsh разбирает `$( )` до heredoc, и backticks тела ломают `--body "$(cat <<'EOF' … EOF)"`. Апостроф в `--title` экранируй как `'\''`.

```bash
BODY=<скретч-каталог сессии>/issue-body.md
cat > "$BODY" <<'BODYEOF'
### What happened?
...
BODYEOF
gh issue create --repo greydragon888/real-router \
  --title '[core][bug] add() does not dedupe names — the caller'\''s second route wins' \
  --label bug --label "priority: medium" --label "area: core" \
  --body-file "$BODY"
```

Выведи номер и URL.

**Комментарий к дому** — тем же файлом: `gh issue comment <N> --repo greydragon888/real-router --body-file "$BODY"`. В нём — что увидено и чем (команда и вывод), ссылки на код @ SHA, кандидаты и гипотезы отдельными строками, и чем находка связана с постановкой дома. Выведи URL комментария.

**Батч связанных задач:** якорную создай первой, компаньонов — с её реальным номером в теле, затем одним проходом `gh issue edit <N> --body-file …` допиши номера, которых не было при создании. Плейсхолдеров `#<tbd>` в создаваемых телах нет.

**Опционально** предложи ветку `<number>-<slug>` в своём worktree вне репозитория: `/changeset` и `/create-pr` берут номер задачи из имени ветки. Работа идёт в существующей батч-ветке — не предлагай.

## Самокоррекция скила (журнал кандидатов)

Скил правится по накопленному, а не после каждого прогона: правка по одному инциденту описывает случай, а не класс, а платит за неё каждый следующий прогон.

1. **Запись в журнал, а не правка** — после создания issue. Где текст скила промолчал, был двусмыслен или неверен и это стоило вызовов, реплики владельца или риска ошибки, допиши строку в `.claude/skill-candidates/create-issue.md` основного чекаута (gitignored; из worktree — `dirname "$(git rev-parse --path-format=absolute --git-common-dir)"`): дата, задача, раздел, класс (молчит / двусмыслен / неверен), инцидент, цена. Строка того же класса уже есть — допиши инцидент к ней. В отчёте — одна строка: что записано.
2. **Правка созревает, когда класс повторился** — в другой задаче или сессии. Неверный факт текста (команда, флаг, путь, число) — исправление, а не правило: его предлагай сразу. Планка: правка предотвратила бы ошибку или сняла бы лишние шаги.
3. **Разовое ≠ паттерн.** Специфику конкретного issue (разовую) → в память, НЕ в скил. В скил идёт только повторяющийся класс, полезный СЛЕДУЮЩЕМУ ДРУГОМУ issue.
4. **Правка не растит файл:** сначала заточи существующий абзац; новое правило называет, что в том же разделе сжато или удалено. Рост — только с согласия владельца.
5. **Предлагай, не применяй молча.** Созревшие правки — таблицей (раздел | инциденты из журнала | текст | что сжато), спроси разрешения; итог помечай в журнале. В скил — правило в настоящем времени, без номеров прогонов и дат; инциденты — в сообщение коммита. Применил по согласию → `.claude/commands/` это infra, в master напрямую, без changeset. ⚠ В сообщении такого коммита не ставь закрывающее слово (close/fix/resolve) вплотную к `#N`, даже в бэктиках: push в `master` закроет задачу.
6. **Ничего не записано и не созрело** — так и скажи одной строкой.
