Сгенерируй commit message на основе текущих изменений в git.

Шаги:

1. Выполни `git diff --stat` для обзора изменённых файлов
2. Выполни `git diff` для анализа содержимого изменений
3. Определи тип изменений — только из `TYPES` в `commitlint.config.mjs` (`type-enum` отвергает любой другой)
4. Сформулируй краткое описание — не длиннее 100 символов (`subject-max-length`)
5. При необходимости добавь детали в body

Формат Conventional Commits:

```
<type>(<scope>): <description>

[optional body]
```

Типы (`TYPES` в `commitlint.config.mjs`):

- feat: новая функциональность
- fix: исправление бага
- refactor: рефакторинг без изменения поведения
- docs: только документация
- chore: обслуживание (deps, configs)
- ci: CI/CD изменения
- test: только тесты
- perf: оптимизация производительности
- build: система сборки и внешние зависимости
- style: форматирование, не меняющее смысла кода
- revert: откат коммита
- release: релизный коммит

Scopes — только из `SCOPES` в `commitlint.config.mjs`: `scope-enum` отвергает любой другой, а `pnpm commit` (`cz.config.js`) предлагает тот же список.

Правила:

- Описание в imperative mood ("add", не "added")
- Scope — только из `SCOPES` (кастомный commitlint отвергнет)
- Не начинай с заглавной буквы после двоеточия
- Без точки в конце description
- Body через пустую строку, каждый пункт с "- "
- Строки body не длиннее 100 символов (`body-max-line-length`): длинный пункт переноси с отступом в два пробела. Проверка — `pnpm exec commitlint < msg.txt`.

Примеры:

```
feat(core): add route guards support
```

```
fix(lint): add dependency check rule, fix unlinted property tests

- Add eslint rule to catch missing dependencies
- Add missing logger dependency to browser-plugin and logger-plugin
- Fix duplicate imports in property tests
```

Выведи только готовый commit message без пояснений.

## Самокоррекция скила (в конце каждого прогона)

Этот файл — живой. После вывода commit message (правило «выведи только сообщение» относится к самому message; самокоррекцию — лишь при инциденте — выведи ОТДЕЛЬНОЙ секцией ПОСЛЕ него) вынеси короткую секцию **«Самокоррекция»** — критику не своей работы, а САМОГО ЭТОГО СКИЛА: где его текст промолчал, соврал, был двусмыслен или избыточен — и это стоило времени, лишнего шага или риска ошибки.

1. **Привязка к ИНЦИДЕНТУ, не общие советы.** Каждая правка — из конкретного момента ЭТОГО прогона: «скил сказал X / промолчал про X → реальность Y → я потерял/чуть не ошибся на Z». Нет инцидента — нет правки (не выдумывай улучшения впрок). Инцидент — довод в таблице кандидатов и в сообщении коммита; в текст скила идёт правило в настоящем времени с причиной в общем виде — без номера прогона, раунда и даты.
2. **Высокая планка: изменило бы исход?** Предлагай, только если правка реально предотвратила бы ошибку, сократила перебор или сняла двусмысленность, на которой ты споткнулся. Косметику и «было бы неплохо» — отбрасывай.
3. **Разовое ≠ паттерн.** Специфику конкретного диффа (разовую) → в память, НЕ в скил. В скил идёт только повторяющийся класс, полезный СЛЕДУЮЩЕМУ ДРУГОМУ коммиту.
4. **Сначала заточи, потом дописывай (анти-раздувание).** Предпочитай усиление существующего абзаца новой секции; если правка делает прежний текст избыточным — консолидируй, не дублируй. Удаление устаревшего текста предлагай наравне с добавлением.
5. **Предлагай, не применяй молча.** Выведи кандидатов таблицей (раздел | инцидент | предлагаемый текст), спроси разрешения. Применил по согласию → `.claude/commands/` это infra, в master напрямую, без changeset.
6. **Честность про «нечего править».** Прогон прошёл чисто и скил нигде не подвёл → так и скажи: «правок нет». Пустая самокоррекция честнее придуманной — пункты 1–2 это допускают.
