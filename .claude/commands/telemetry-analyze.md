Входные данные:
$ARGUMENTS

Формат аргументов (всё необязательно): фокус (джоба, пакет, задача, событие), окно (`7d` по умолчанию; в Free-тарифе метрики живут 14 дней), `--quick` — только инвентаризация и топ-находки без локальных проб.

> **Это НЕ `/perf-optimize`.** Тот меряет код рантайма. Здесь предмет — CI и инструменты: время задач turbo, кеш, конкуренция за CPU, дрейф тулчейна, качество самой телеметрии.

## Фаза 0 — Доступ, не печатая секретов

Данные: turbo шлёт OTLP → nginx → OTel Collector на `77.222.38.47` (`/opt/real-router-telemetry`, конфиг как код — `ops/telemetry/`) → Grafana Cloud Prometheus. Подробности — IMPLEMENTATION_NOTES, записи #1745.

- Чтение: `GRAFANA_PROM_URL` и `GRAFANA_PROM_LOGIN` (логин уже `user:token`) в `~/.zshrc`. Bash-тул видит снимок `~/.zshrc` со старта сессии, поэтому строки грузятся в подоболочке. ⛔ Значения не печатать, не класть в аргументы, которые попадут в вывод.
- Создай в scratchpad два помощника и работай только через них:

```bash
# prom.sh <api-path> [--data-urlencode 'k=v' ...] — печатает только тело JSON
eval "$(grep -E '^export GRAFANA_PROM_(URL|LOGIN)=' ~/.zshrc)"
path="$1"; shift
curl -sS --max-time 60 -u "$GRAFANA_PROM_LOGIN" -G "$GRAFANA_PROM_URL$path" "$@"
```

```bash
# pq.sh '<promql>' [limit] — instant-запрос, строки «значение  метки», по убыванию
"$(dirname "$0")/prom.sh" /api/v1/query --data-urlencode "query=$1" | node -e '
const lim = Number(process.argv[1] || 60);
const j = JSON.parse(require("fs").readFileSync(0, "utf8"));
if (j.status !== "success") { console.log("ERROR", j.errorType, j.error); process.exit(1); }
const rows = j.data.result.map((r) => [Number(r.value[1]), Object.entries(r.metric).map(([k, v]) => `${k.replace(/^(ci_|turbo_task_|turbo_)/, "")}=${v}`).join(" ")]);
rows.sort((a, b) => b[0] - a[0]);
for (const [v, l] of rows.slice(0, lim)) console.log(`${(Math.round(v * 10) / 10).toString().padStart(12)}  ${l}`);
console.log(`(${rows.length} rows)`);' "${2:-60}"
```

## Фаза 1 — Модель данных: как читать, чтобы не соврать

**Метрики** (имена после коллектора): `turbo_run_duration_ms_milliseconds_{bucket,sum,count}`, `turbo_run_tasks_{attempted,cached,failed}_total`, `turbo_task_duration_ms_sum_milliseconds_total` + `turbo_task_duration_ms_count_total` (у задач только сумма и счёт; перцентили и отдельные прогоны — из сырых сэмплов, ниже), `turbo_task_cache_events_total`. Метки: `ci_job`, `ci_event` (`pull_request`/`push`/`local`), `ci_runner`, `process_runtime_version`, `turbo_version`, `turbo_scm_branch`, `turbo_task_{name,package,cache_status,cache_source,exit_code,command}`, `turbo_run_exit_code`. `cache_status` строчными (`hit`/`miss`), `cache_source` заглавными (`LOCAL`/`REMOTE`). Зонды (`*-probe`, `conc-*`) отсекает только `ci_runner="github-hosted"`: все они `macbook`, а `telemetry-branch-probe` записан как `pull_request`.

⚠ **Счётчики накапливает коллектор** (`delta_to_cumulative`): пересоздание контейнера и простой потока дольше `max_stale` (72h) сбрасывают их в ноль. `increase()` сбросы переживает, но экстраполирует — счёт выходит дробным.

⚑ **Сырые сэмплы точнее PromQL.** `prom.sh /api/v1/query --data-urlencode 'query=<counter>[10d]'` отдаёт все точки серий. Коллектор пишет по точке на экспорт turbo, поэтому приращение между соседними точками — ровно один прогон: длительность задачи в нём (отсюда перцентили задач), связь задач с прогоном по общей метке времени, точный счёт без экстраполяции. Предпосылку проверь: все приращения `…_count` равны 1 (28.09 — 8246 из 8246 у задач, 666 из 666 у прогонов). Первая точка серии — приращение от нуля; сброс — падение значения или рестарт коллектора между точками (время последнего — `docker inspect -f '{{.State.StartedAt}}'` на хосте).

⚠ **Серии PR до 2026-09-28 10:53 UTC одноточечные.** Тогда `turbo_scm_branch` нёс ref PR (`N/merge`), у каждого PR были свои серии в 1–2 точки, и `increase()`/`rate()` по ним возвращают ПУСТО — без ошибки. Для этого периода бери сырые сэмплы или сумму по сериям `max_over_time(<counter>[<окно>])` (коллектор копил с нуля). С отметки коллектор сводит ref к `pr`, прочие ветки кроме `master` — к `branch`, и `increase()` работает.

⚠ **Пустой ответ — ещё не «данных нет».** Сначала проверь, что запрос вообще может что-то вернуть на этом наборе серий (контроль: тот же запрос по `ci_event="push"`).

## Фаза 3 — Оси анализа

Числа в скобках — замер 28.09, ориентир масштаба, а не норма.

### Время и CPU

1. **Куда уходит время:** сумма длительностей по задаче / пакету / джобе, отдельно промахи и попадания.
2. **Самые долгие задачи:** средняя длительность промаха по `(package, task)`. Разброс одной задачи между пакетами — повод составить таблицу разделения по структурному признаку (инструмент сборки, симлинк, конфиг). Проверь КАЖДУЮ гипотезу по всем пакетам: верна та, что делит без исключений.
3. **Эффект контекста:** одна задача в разных джобах (одна против полного графа на 4 vCPU) — конкуренция или регрессия.
4. **Критический путь:** длительность прогона против самых долгих задач джобы. Задача короче пола джобы не окупит ускорения.
5. **Хвосты джоб:** p50/p95 прогона по `ci_job` — по сырым сэмплам `turbo_run_duration_ms_milliseconds_sum` (p95 post-merge `build` 17,1 мин). ⚠ Не `histogram_quantile`: бакеты прогона идут 300/600/900/1800/3600 с, и интерполяция внутри 900–1800 с дала p95 26,4 мин — выше максимума прогона в 17,9 мин.
6. **Реальный параллелизм:** сумма длительностей задач джобы, делённая на сумму длительностей её прогонов. Около 4 — упор в CPU при `concurrency: 4`, около 1 — упор в критический путь (post-merge `build` 3,7).
7. **Баланс шардов:** p95 по `pipeline-sharded-*` и `base-test-*`; время PR задаёт самый долгий шард. Среднее тут врёт: шарды в основном попадают в кеш.

### Кеш

8. **Доля попаданий:** по событию / джобе / задаче; `REMOTE` против `LOCAL`. Задача, которая на push промахивается без изменения входов, — кандидат в нестабильный ключ (сверь хеши `turbo run … --dry=json`). Сначала исключи три штатные причины — 28.09 ими объяснились все промахи push: аргументы после `--` хешируются (`--shard=N/4`, `--concurrency=auto` в PR), и такая задача PR никогда не совпадёт с post-merge; сменились внешние зависимости самого пакета (`hashOfExternalDependencies` задачи); отменённый предыдущий прогон успел залить часть задач в удалённый кеш, и промахнулись недоделанные.
9. **Ценность кеша:** попадания × средний промах той же задачи ≈ сэкономленное время (`timeSaved` в OTLP нет) — 26 ч задач за 24–28.09. И обратная сторона — цена попадания: средняя длительность `hit`; тяжёлые выходы (`coverage/**`, blob) делают попадание дорогим (максимум 2,8 с у `core#lint`).
10. **Объём затронутого:** `turbo_run_tasks_attempted_total` и `…_cached_total` на прогон. Весь граф или почти весь идёт по трём причинам, и `turbo.json` среди них нет — правка чужой задачи в нём ничего не перекеширует (28.09: 0 промахов):
    - файл из `global.inputs` — при `globalConfiguration` он дописан во входы КАЖДОЙ задачи (правка `eslint.config.mjs` → 125 из 125);
    - корневые зависимости — глобальный `hashOfExternalDependencies`: любой devDependency корня, даже тул, которого не запускает ни одна задача (бамп knip → 125 из 125);
    - не-src файл upstream-пакета — `type-check` core читает `**/*.ts` вместе с тестами, а зависимые ждут `^type-check` (тест core → 100 из 125, всё, кроме `bundle`).

    Посчитай частоту каждой по `git log`, причину конкретного прогона подтверди парой `--dry=json` (фаза 4).

### Надёжность и изменения

11. **Падения:** `turbo_task_exit_code!="0"` по задачам, `turbo_run_exit_code` по джобам. Падение и зелёный повтор того же коммита — флейк, сверяй с `gh run list --commit <полный sha>`.
12. **Цена смены версии:** та же задача по `turbo_version` и `process_runtime_version` до и после бампа; плюс дрейф локального против CI. ⚠ Сравнивай не средние по прогонам, а индекс скорости прогона — медиану отношений «длительность задачи / её обычная медиана». Индекс бимодален: ~20 % джоб попадает на раннеры быстрее остальных на 25–30 % (28.09: 0,70–0,80 против 0,95–1,10), и одна смесь железа сделала turbo 2.11 «медленнее на 12–17 %» на всех типах задач.
13. **Во времени:** `query_range` с шагом 1d — ступенька в задаче или пакете → `git log` за этот интервал; рост среднего `test` пакета — тесты замедляются. Смена `turbo_task_command` даёт новую серию: сравни до и после.

### Здоровье самой телеметрии

14. **Сбросы и пропуски:** `resets(<counter>[окно])` — пересоздание коллектора или поток, простоявший дольше `max_stale`; день без точек `push` — либо не было пушей, либо отвалился экспорт.
15. **Полнота охвата:** список `ci_job` против джоб workflow, которые запускают turbo. Пропажа из телеметрии — ещё не поломка штампа или экспорта: джоба перестала звать turbo (`examples-*` после переезда в свой workspace), прогон запустил `dependabot[bot]` до 2026-09-29 (тогда у Dependabot не было копий секретов `TELEMETRY_OTLP_*`, и его PR видны, только если в ветку пушил человек; с 29.09 они экспортируют, но делят серию `pr` с человеческими — метки актора нет), прогон отменён. Потерю доказывает трёхсторонняя сверка: строки `Tasks:` в `gh run view --log` = прогоны в сырых сэмплах = POST `/v1/metrics` в `/var/log/nginx/access.log*` на хосте (время там MSK). 28.09: 579 = 579 у PR, 666 = 666 nginx → Grafana, одна потеря turbo → nginx.
16. **Кардинальность:** активные серии против квоты Free в 10k, серии по джобе и ветке; метка, которая плодит серии, и зонды, оставшиеся в данных (как отсечь — в фазе 1).

## Фаза 4 — Причину подтверждай пробой

- ⚑ **Находка из телеметрии — корреляция.** Причиной её делает локальный замер: тот же шаг, чередующиеся прогоны, контрольная рука. Пример 28.09: `bundle` пакетов с симлинком `shared/` в CI 24–58 с против 3,6–7,2 с; локально 12,5 с против 1,2 с; `DEBUG=rolldown-plugin-dts:*` показал отдельную TS-программу на каждый модуль `shared/`.
- ⚠ **Правдоподобную гипотезу опровергай данными.** Там же гипотеза «`types` в tsconfig» выглядела не хуже и разваливалась на двух пакетах в каждую сторону.
- ⚠ **Упавший эксперимент — не замер.** Сборка, умершая на `publint`, ничего не говорит о dts. Читай код выхода и последние строки лога.
- **Ключ кеша проверяй парой `--dry=json`, без сборки.** Коммит и его родитель — в `git worktree add --detach <scratch>/…`; обе руки одним нативным бинарём (`node_modules/.pnpm/@turbo+<платформа>@<версия>/node_modules/@turbo/<платформа>/bin/turbo`), с `--cache-dir` в scratch и без `TURBO_TOKEN`/`TURBO_API`; сравни `hash` задач и `globalCacheInputs.hashOfExternalDependencies`. Контроль — коммит, трогающий один лист (28.09: 4 из 125). Той же парой проверяется и дизайн правки: примени её в обеих руках. Worktree потом удали.
- **Правка коллектора:** сперва локально — тот же образ по digest, экспортёр `debug`, синтетический OTLP и контроль без правки. Потом хост: загрузить `.new`, `validate` образом с `--env-file .env`, бэкап, подмена, `docker compose up -d --force-recreate`, сверка sha256 с репо. В конце сквозной зонд через публичный адрес с отдельным `ci_job` (`telemetry-*-probe`).

## Самокоррекция скила (ОБЯЗАТЕЛЬНО, в конце КАЖДОГО прогона)

Этот файл — живой; каждый прогон обязан его затачивать. После отчёта вынеси короткую секцию **«Самокоррекция»** — критику не своей работы, а САМОГО ЭТОГО СКИЛА: где его текст промолчал, соврал, был двусмыслен или избыточен — и это стоило времени, лишнего шага или риска ошибки.

1. **Привязка к ИНЦИДЕНТУ, не общие советы.** Каждая правка — из конкретного момента ЭТОГО прогона: «скил сказал X / промолчал про X → реальность Y → я потерял/чуть не ошибся на Z». Нет инцидента — нет правки (не выдумывай улучшения впрок).
2. **Высокая планка: изменило бы исход?** Предлагай, только если правка реально предотвратила бы ошибку, сократила перебор или сняла двусмысленность, на которой ты споткнулся. Косметику и «было бы неплохо» — отбрасывай.
3. **Разовое ≠ паттерн.** Специфику конкретного прогона (разовую) → в память, НЕ в скил. В скил идёт только повторяющийся класс, полезный СЛЕДУЮЩЕМУ ДРУГОМУ прогону.
4. **Сначала заточи, потом дописывай (анти-раздувание).** Предпочитай усиление существующего абзаца новой секции; если правка делает прежний текст избыточным — консолидируй, не дублируй.
5. **Предлагай, не применяй молча.** Выведи кандидатов таблицей (раздел | инцидент | предлагаемый текст), спроси разрешения. Применил по согласию → `.claude/commands/` это infra, в master напрямую, без changeset.
6. **Честность про «нечего править».** Прогон прошёл чисто и скил нигде не подвёл → так и скажи: «правок нет». Пустая самокоррекция честнее придуманной — пункты 1–2 это допускают.
