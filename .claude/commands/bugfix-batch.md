Оркеструй батч багфиксов одной группы — задач одного класса, одного пакета или одной цепочки зависимостей: один worktree/ветка → per-bug фиксы по методологии `/bugfix` → один общий PR. Один CI-прогон вместо N.

Входные данные:
$ARGUMENTS

Формат аргументов:

- Список номеров issue одной группы (`#2796 #2788`): задачи одного класса — их называет папка класса (`ls -d .claude/*/ | rg /class-`), — одного пакета или одной цепочки зависимостей. Группы между собой не пересекаются по файлам; перекрытие багов по одному файлу ВНУТРИ группы — норма (один PR их и покрывает).

Этот скилл — **ОРКЕСТРАТОР**. Он НЕ дублирует TDD-методологию: per-bug ядро берётся из скилла `/bugfix` (Фазы 0→3 + коммит+changeset). Здесь — только то, что специфично для группы: общая ветка, порядок, один PR. Меняется методология фикса → правится `/bugfix`, этот скилл наследует.

## Бюджет токенов

Расход прогона — размер контекста, умноженный на число вызовов, а в батче контекст ещё и копится от бага к багу. Из раздела «Бюджет токенов» в `/bugfix` здесь действуют пакетные чтения, вывод в файл и перечни субагентом; своё у батча — три правила:

1. **Один батч — одна сессия.** Если до вызова скила в этой сессии шла другая работа, до Шага 1 одной строкой предложи пользователю новую сессию (или `/clear`) с повторным `/bugfix-batch <аргументы>` и закончи ход: весь прежний контекст перечитывается на каждом шаге прогона. Продолжай в этой сессии, только если пользователь так ответил.
2. **`/bugfix` читай по разделам — не целиком и не вызовом скила.** Прочитанное остаётся в контексте до конца сессии, а нужна каждый раз одна фаза. Заголовки — `rg -n '^## ' .claude/commands/bugfix.md`; читай раздел той фазы, на которую ссылается текущий шаг, когда до неё дошёл. Сжатие контекста прочитанное не сохраняет: после него перечитай раздел текущей фазы.
3. **Повторяемые проверки — одним скриптом**: точечную валидацию перед коммитами Шага 2 и в Шаге 3.1, батарею мутантов атаки. Внутри скрипта — по пакету на команду, с кодом возврата и строкой `Tests N passed` каждого шага в выводе.

## Шаг 1 — Один worktree/ветка на всю группу

1. **Ведущая задача = первый номер группы** (по dependency-chain — корневой баг). Заведи ветку и worktree ОДИН раз, под ведущую задачу; основной чекаут остаётся на `master` (правило CLAUDE.md):
   - Ветка — `<lead>-<slug>`. `<slug>` — **общий идентификатор группы** (`path-matcher-fixes`, а НЕ имя одного бага), всё имя ≤ 64 символов. ⚠ **НЕ `gh issue develop`:** он создаёт ветку В ORIGIN, то есть является push-действием, и `/bugfix` 0.3 запрещает его прямым правилом. Единственное, что теряется, — строка в секции Development у задачи, и её заменяет `Closes #<N>` в PR. База — **`origin/master`, а не локальный `master`**: локальный может держать ещё не запушенные коммиты по другим задачам.
   - Каталог `<wt>` — `.claude/worktrees/<lead>-<slug>` основного чекаута (он — первая строка `git worktree list`), путь абсолютный. ⚠ Node, не найдя пакет в `node_modules` worktree, поднимается в `node_modules` основного чекаута и молча берёт его оттуда: отсюда установка сразу после входа (ниже), а пакет, которого у ветки нет, а у основного чекаута есть, локально всё равно найдётся — его отсутствие покажет только CI.
   - `git fetch origin` → `git worktree add -b <lead>-<slug> <wt> origin/master` → **`EnterWorktree` с `path: <wt>`** (`path:`, а не `name:`: `name:` заводит ветку `worktree-…`, а нужна `<lead>-<slug>`).
   - **После входа — `pnpm install --frozen-lockfile` в этом worktree ПЕРЕД любой валидацией/пробой и первым коммитом**: хуки `.husky/*` git запускает в нём сразу, а зависимости им даёт установка. Свежий git-worktree своих `node_modules` не имеет (они gitignored), а `PATH` сессии может держать `node_modules/.bin` основного чекаута: голые `vitest`/`tsx` в таком worktree запускают его версии, а не версии ветки, — зови их через `pnpm exec` после установки; pnpm store общий → установка — в основном линковка (секунды). **И `pnpm install` НЕ собирает `dist` и не ставит отдельные воркспейсы.** cross-router-bench — свой воркспейс: он меряет npm-релиз, а не этот чекаут, так что A/B неопубликованной правки на нём сейчас не поставить ни в worktree, ни в основном чекауте (#2720). Собранный `dist` читают angular-сьют adapter-bench и `benchmarks/plugin-seam`; core-сьют и остальные сьюты adapter-bench читают `src`. Собирать весь граф в worktree ради бенча — та же полная сборка, которую прогоняет pre-push; не делай.
2. Весь батч — внутри этого ОДНОГО worktree, в ветке `<lead>-<slug>`. Несовпадение «номер ветки (ведущая) ≠ номера остальных issues» здесь ожидаемо.

**Весь батч — infra / benchmarks (не меняет код ни в `packages/*/src/`, ни в `shared/<dir>/*.ts`; правка только тестов, комментариев или доков — тоже infra)? Форма батча другая — реши ДО создания worktree:** (1) **ни ветки, ни worktree: коммиты прямо в `master` основного чекаута** (CLAUDE.md: infra-задачи идут в `master` без ветки и PR) — там и стоит то, что читает бенч-верификация: cross-router-bench — свой воркспейс (`pnpm install` корня его не ставит), angular-сьют adapter-bench и `plugin-seam` — собранный `dist`; в свежем worktree этого нет, так что сам прогон «до/после», ради которого взят баг, упал бы; (2) **доставка = `git push origin master`, без PR, без changeset и без `--no-verify`**: push в `master` мимо PR до приземления проверяет только pre-push; при сомнении спроси PR-vs-master через `AskUserQuestion` (PR — это ветка, то есть Шаг 1); (3) **баг харнесс-ИЗМЕРЕНИЯ** (бенч/профайлер) не имеет unit-теста: RED/GREEN — эмпирический прогон «до/после», мутационная валидация = дискриминирующая дельта чисел, гейт «частичный фикс» (ниже) читай как «дельта не дискриминирует»; (4) **тяжёлый data-regen хвост** — если фикс делает committed `results/*.json` устаревшими, отделяй код от данных: код+верификация сейчас, полный re-run матрицы делегируй на штатный `n` пользователя (частичный low-`n` перезапишет валидные СОСЕДНИЕ метрики того же сценария).

**Возобновление (worktree уже существует).** Не пересоздавай. Сначала `pwd` + `git branch --show-current`: прерванная сессия могла восстановиться **уже внутри** worktree (тогда `EnterWorktree` не нужен — повторный вызов падает «is the current working directory»). Затем `git log master..HEAD` + `git status`: что уже закоммичено / лежит в рабочем дереве — чтобы не делать заново. **Worktree уже создан через `EnterWorktree name:`** (лежит в `.claude/worktrees/`, ветка вида `worktree-…` вместо `<lead>-<slug>` — напр. пользователь сказал «работай в worktree» ДО загрузки скила): работы в нём ещё нет — `ExitWorktree` (`remove`) и Шаг 1; есть — не пересоздавай: `git branch -m worktree-<…> <lead>-<slug>` в конвенцию и продолжай в нём. **Сессия внутри ЧУЖОГО worktree** (запущена/восстановилась в worktree другой задачи): сперва `ExitWorktree` (`keep`) — в основной чекаут он возвращает, только если сессия вошла в этот worktree через `EnterWorktree`, а иначе ничего не делает, — затем Шаг 1. **Ветка группы УЖЕ ЕСТЬ, а worktree нет** (заведена раньше — локально или в origin): `git fetch origin` → `git worktree add <wt> <lead>-<slug>`, без `-b` — ветку, которая есть только в origin, git заведёт сам, с отслеживанием. Отказ `'<lead>-<slug>' is already used by worktree at '<путь>'` называет дерево, где она стоит: другой worktree — это и есть worktree батча (возобновление выше); основной чекаут — он стоит не на `master` вопреки правилу: назад его сам не переключай (под ним может идти чужая сборка или push), покажи `git worktree list` и спроси пользователя.

## Шаг 2 — Per-bug цикл

Порядок: батч класса — как места названы в README папки класса; цепочка зависимостей — корневой → зависящие; батч по ПАКЕТУ (несвязанные баги рядом) — (1) ведущий = первый номер группы; (2) баги, делящие ОДИН файл, — подряд (коммить каждый ДО правки следующего в этом файле); прочие — произвольно, они изолированы. Для КАЖДОГО бага по очереди:

1. Выполни per-bug ядро **по скиллу `/bugfix`, Фазы 0→3** (контекст из issue → RED → GREEN → REFACTOR), **без** финальных фаз (валидация/PR/comment — они в Шаге 3). Worktree/ветку на группу уже создал Шаг 1; `/bugfix` инфраструктуру не заводит — лишь проверяет, что ветка не `master` (в батче это уже выполнено), поэтому отдельных оговорок про worktree-setup не нужно. Все гейты `/bugfix` применяются: эмпирическое воспроизведение (0.6), критика предложенного решения (0.7), флапающий-RED guard (1.3).
   - Если фикс корневого уже закрыл зависимый баг — перепроверь эмпирически (0.6), НЕ пиши лишний фикс, отметь это в отчёте.
   - Design-call — развилка владельцу до RED — и ужесточающий фикс, роняющий чужие тесты, ведутся по `/bugfix` («Как формулировать вопрос пользователю», 0.7).
2. **Отдельный коммит + changeset на КАЖДЫЙ баг** с его `#<N>` (`/commit-msg` → Skill `changeset`); фикс, который меняет в `src` только комментарии или доки, changeset не требует. Гранулярность критична: review читается по одному дефекту, история привязана к issue, спорный баг выдёргивается без развала всего PR. **Форматтер — только по своим файлам, и только если их HEAD-версия проходит формат или формат гейтится** (`git show HEAD:<путь>` в форматтер): чужой дрейф без гейта не трогай, иначе коммит утащит посторонние строки. Когда баги группы трогают РАЗНЫЕ участки одного файла, доводи каждый баг до коммита ПЕРЕД правкой следующего в том же файле — рабочее дерево на момент коммита содержит изменения только одного бага, и хватает обычного `git add <файл>` (предпочтительный путь, без риска зацепить чужой hunk). `git add -p` по hunk'ам нужен, только если перекрывающиеся правки уже сделаны до коммита. **Коммить с `--no-verify` + точечная per-package валидация (type-check/lint/test) перед каждым коммитом — в т.ч. `lint --fix` на файлах ИМЕННО ЭТОГО бага, не только `type-check`**: иначе финальный `lint --fix` Шага 3.1 переформатирует уже-закоммиченные файлы ПРЕДЫДУЩИХ багов, и hygiene-дельта повиснет в чужом non-HEAD коммите → дорогая `reset --soft`-amend хирургия (`-i` rebase недоступен); не-автофиксимые warning'и (напр. `no-empty-function` на пустом `teardown(){}` в RED-тесте) лови на этапе ИХ бага. pre-commit hook гонит `turbo run test` по всему графу (минуты, легко >2-мин лимита Bash), а за батч это N прогонов одного и того же. Полный граф прогоняет pre-push при push (Шаг 3.5) — не гоняй его на каждый коммит. `--no-verify` снимает и хук `commit-msg`: сообщение проверь тем же вызовом, что валидацию (`/commit-msg`, «Проверка»). ⚠ **Changeset-файл НОВЫЙ, а `-o`/`--only` принимает только известные git пути** — `git commit -o … .changeset/<файл>.md` падает `pathspec … did not match any file(s) known to git`. Порядок: `git add <changeset>` → затем `git commit --no-verify -o <src> <tests> <changeset>`; состав коммита всё равно ограничен явным списком, поэтому чужое staged-содержимое параллельной сессии не уедет (в отличие от `git add -A` / голого `git commit`). Changeset'ы — по пакету на файл (`check-changeset.mjs` — гейт), для правки в `shared/` — каждому потребителю, чьё поведение изменилось: пишет и сверяет их Skill `changeset`. **Два бага — одна неразделимая реализация?** Если фиксы двух issues сходятся в ОДНУ atomic-правку (общий helper/функция, которую `git add -p` не режет начисто на два коммита — **или общий тест-артефакт: один генератор/property/RED-фикстура, зеленеющий сразу для двух багов, плюс переслоённый describe**), допусти **один коммит + отдельный changeset на каждый issue** (`Closes #A` + `Closes #B` в теле PR) — гранулярность сохраняется в CHANGELOG, а искусственное разделение дало бы неполный intermediate-коммит (RED упал бы без ещё-не-влитого src-фикса второго бага). Перекрытие по РАЗНЫМ участкам файла (выше) дели на коммиты; перекрытие в ОДНОЙ функции / ОДНОЙ тест-фикстуре — нет.

**Батч одного класса** — задачи группы называет папка класса (`ls -d .claude/*/ | rg /class-`): §5 её README — DoD батча. Страж и его доказательство из §5 идут тем же PR, своим коммитом; без них класс не закрыт, сколько бы задач ни закрылось. Новый экземпляр того же класса по ходу — строкой в §1 папки и в этот батч, а не задачей.

## Шаг 3 — Финал на всю группу (один раз)

1. **Точечная валидация** по ОБЪЕДИНЁННОМУ набору затронутых пакетов: на каждый — `pnpm -F <pkg> type-check`, `lint`, `test -- --run` (+ `test:properties` / `test:stress`, если фиксы касались инвариантов / конкурентности / памяти). 100% coverage обязательно. Полный `pnpm build` **не запускай**: полный граф прогоняет pre-push при push (Шаг 3.5). **«Затронутый набор» = пакеты, чей `src/` правил батч, НЕ их транзитивные потребители:** если фикс в широко-консумируемом пакете (`sources` / `core`) меняет ПОВЕДЕНИЕ, потребительские сьюты (адаптеры и пр.) валидирует полный граф pre-push — не гоняй их per-package, это не входит в «затронутый набор». В отчёте отметь, какие потребители затронуты поведенчески, чтобы было видно, за чем следить на pre-push и в CI. **⚠️ Правка в `shared/<dir>` своего пакета НЕ имеет, и правило выше на неё не отвечает.** Затронутый набор там — это ВЛАДЕЛЕЦ ПОКРЫТИЯ каталога (его называет `tests/**/authority-1838.test.ts` в пакете-владельце) плюс все потребители: симлинки видно `find packages/*/src -maxdepth 1 -type l`. Ловушки молчащего `-F`, кода возврата и `--cache` — в Фазе 4.1 `/bugfix`; сверх них **несколько `-F` в одной команде (`pnpm -F a -F b test -- --run`) пишут ПУСТОЙ лог при `exit 0`** — гони по одному пакету на команду. **⚠️ И помни, что `pnpm -F <pkg> exec <tool> <пути>` стартует из каталога ПАКЕТА: аргументы-пути относительны пакету, не корню репозитория.** Репо-относительный путь даёт `No files matching the pattern` с ненулевым exit — по виду неотличимо от настоящего провала линтера/тула, и правка «починить найденное» уходит не туда. Либо давай пути от пакета (`src/foo.ts`), либо гони тул из корня без `-F`. Пакеты фильтруй npm-именем (`-F @real-router/<имя>`): каждый `packages/*` публичен, а код движка, FSM, эмиттера и логгера живёт в `@real-router/core`. **⚠️ `test:stress`-падение в свежем worktree может быть worktree-environment артефактом (timing/count-sensitive), НЕ твоей регрессией.** Прежде чем атрибутировать падение своему фиксу: (а) прогони на **pristine original в ТОМ ЖЕ worktree** — версиях файлов до батча (база — `git merge-base origin/master HEAD`: фиксы уже закоммичены, и HEAD их содержит); подменяй и возвращай файлы способом из `/bugfix` Фаза 4.5, не `git checkout` — он разрушителен; (б) прогони на **ОСНОВНОМ чекауте**. Падает на pristine / проходит на main → пре-существующий env-флейк (stress гоняется pre-push-only, поэтому дрейфит незамеченным): не блокируй батч, отметь в отчёте, при необходимости заведи отдельный issue.
2. **Атака на решение** (`/bugfix` Фаза 4.5) — обязательна и здесь, но проводится **по каждому багу группы отдельно**: векторы Фазы 4.5 адресуют термы, class-guard и клеймы КОНКРЕТНОГО фикса, а не объединённый дифф, и мутация одного терма должна краснить тесты своего бага. ⚑ **Счёт ведётся по САЙТАМ, а не по багам: N сайтов ⇒ N мутантов.** Когда один слот читают несколько сайтов, откат ОДНОГО сайта оставляет весь сьют пакета зелёным: «тесты своего бага краснеют» выполняется и ничего не значит. Общей у группы остаётся только организация: один заход роя на весь дифф ветки дешевле N заходов (линза на агента, одно досье на всю группу — `/bugfix` Фаза 4.5, «Досье роя»), а починку раскладывай по коммитам-владельцам. Найденное чини ДО пункта 3 — changeset'ы уже написаны в Шаге 2 по `/bugfix` Фазе 4.2, и опровергнутый атакой клейм надо снять из них, а не из отчёта.
3. **Docs/wiki sync** одним проходом (`/bugfix` Фаза 5) по всем затронутым пакетам/API — баг-фиксы часто означают расхождение доков с реальным поведением. **Вики — отдельный git-repo (`real-router.wiki`; путь — абсолютный, из environment, как в `/bugfix` Фаза 5), нередко с посторонними незакоммиченными правками от прошлой/чужой работы: коммить ТОЛЬКО свои файлы явным `git add <файл>`, НИКОГДА `-a`/`commit -am`** — иначе утащишь чужое в свой wiki-коммит. Один отдельный wiki-коммит на всю группу; push wiki вместе с push ветки (Шаг 3.5), тот же гейт явной просьбы.
4. **Один PR** через `/create-pr` из N коммитов:
   - В теле — **`Closes #736`, `Closes #738`, `Closes #749`: по отдельной строке на КАЖДЫЙ issue группы.** Без этого при merge GitHub закроет только ведущую задачу, остальные останутся открытыми.
   - Заголовок отражает группу/пакет, не один баг.
5. **Push** (только по явной просьбе пользователя). **Перед push синхронизируй ветку с `master`: `git fetch origin && git rebase origin/master`** — worktree базировался от `origin/master` на момент Шага 1, за время батча master уходит вперёд; rebase (НЕ merge — master защищён, «Merge commits are not allowed», история линейна) гонит CI и мёрж PR на актуальной базе и снимает конфликты заранее. Конфликты разрешай до push. Затем `git push -u origin <lead>-<slug>` — без `--no-verify`: pre-push — единственный локальный прогон полного графа, он же досматривает коммиты Шага 2, сделанные с `--no-verify`, и он единственный гейт `test:stress`; точечная валидация Шага 3.1 его не заменяет. Push идёт минуты — запускай его в фоне, а не под лимитом Bash. Падение pre-push — настоящее, не обходи.
6. **Комментарии в issue** (черновики; публикуй только по явной просьбе): по комментарию на каждый баг ИЛИ один сводный со ссылками на коммиты — по ситуации. Содержание — как `/bugfix` Фаза 7 (корень, фикс, тесты, скоуп-решения).

## Гейты (наследуются от `/bugfix`)

- **НЕ пуш / НЕ создавай PR / НЕ публикуй комментарии в issue без явной просьбы пользователя** — эти исходящие действия готовь и показывай, жди явного «go». Локальные per-bug коммиты (Шаг 2) — это сам воркфлоу, НЕ гейт: коммить по ходу, не переспрашивай.
- Не помечай группу выполненной при падающих тестах или частичном фиксе хотя бы одного бага. **Исключение — триаж-короткое замыкание (`/bugfix` 0.6):** issue группы оказался не дефектом (observation / wontfix) → корректный исход «задокументировано, без правок кода» (коммит-доки, БЕЗ changeset, issue закрывается через `Closes`). Это НЕ частичный фикс — зафиксируй такой статус в отчёте, группу им не блокируй.

## Итоговый отчёт

- Workspace/ветка: `<wt>` на ветке `<lead>-<slug>`; infra-форма — `master` основного чекаута.
- Таблица по багам: `#<N>` → корень → тест(ы) → коммит → статус (исправлен / не нужен, если корневой фикс уже покрыл / **документирован, без правок кода** — триаж-non-defect 0.6, коммит-доки без changeset).
- Точечная валидация объединённого набора пакетов (полный граф — на pre-push при push: его итог, если push уже был).
- Docs/wiki: что проверено/обновлено.
- Рой: таблица отдачи линз — как в итоговом отчёте `/bugfix`.
- PR: ссылка (или черновик), `Closes #<N>` для всех issues группы.
- Черновики issue-комментариев.

## Жизненный цикл worktree

Держи worktree и ветку до мёржа PR. После мёржа почисти вручную: `git worktree remove <wt>` (worktree, в который вошли через `EnterWorktree path:`, харнесс автоматически не удаляет). `git worktree list` — обзор всех активных батчей.

## Параллельные батчи

Несколько групп можно вести **параллельно** — каждый `/bugfix-batch` живёт в своём worktree (изолированы). Условие чистоты: группы **не пересекаются по файлам**, и PR'ы мержатся независимо. Запускай параллельные группы в **отдельных сессиях** — один Claude в одной сессии работает в одном worktree за раз; параллельность даёт число сессий, не один Claude.

## Самокоррекция скила (журнал кандидатов)

Скил правится по накопленному, а не после каждого прогона: правка по одному инциденту описывает случай, а не класс, а платит за неё каждый следующий прогон.

1. **Запись в журнал, а не правка** — после итогового отчёта. Где текст скила промолчал, был двусмыслен или неверен и это стоило вызовов, реплики владельца или риска ошибки, допиши строку в `.claude/skill-candidates/bugfix-batch.md` основного чекаута (gitignored; из worktree — `dirname "$(git rev-parse --path-format=absolute --git-common-dir)"`): дата, задача, раздел, класс (молчит / двусмыслен / неверен), инцидент, цена. Под `EnterWorktree` запись в основной чекаут отклоняется, а «копия в worktree», которую предлагает отказ, пропадёт вместе с worktree (`.claude/*` в `.gitignore`) — держи строку в scratchpad и перенеси её сам: `ExitWorktree` (`keep`), запись, `EnterWorktree` с `path` обратно. Строка того же класса уже есть — допиши инцидент к ней. В отчёте — одна строка: что записано.
2. **Правка созревает, когда класс повторился** — в другой задаче или сессии. Неверный факт текста (команда, флаг, путь, число) — исправление, а не правило: его предлагай сразу. Планка: правка предотвратила бы ошибку или сняла бы лишние шаги.
3. **Граница bugfix ↔ bugfix-batch.** Методология одного фикса (RED/GREEN/критерии) → правь `/bugfix`, НЕ здесь. Сюда идёт только то, что про оркестрацию группы (ветка/порядок/PR/параллельность). Не дублируй per-bug инструкции.
4. **Правка не растит файл:** сначала заточи существующий абзац; новое правило называет, что в том же разделе сжато или удалено. Рост — только с согласия владельца.
5. **Предлагай, не применяй молча.** Созревшие правки — таблицей (раздел | инциденты из журнала | текст | что сжато), спроси разрешения; итог помечай в журнале. В скил — правило в настоящем времени, без номеров прогонов и дат; инциденты — в сообщение коммита. Применил по согласию → `.claude/commands/` это infra, в master напрямую, без changeset.
6. **Ничего не записано и не созрело** — так и скажи одной строкой.
