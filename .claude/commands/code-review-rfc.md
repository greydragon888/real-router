Проведи глубокое code-review РЕАЛИЗАЦИИ RFC/плана: сверь diff с каноном документа пункт-за-пунктом (недовыполнение / перевыполнение / отклонение), прогони КЛАСС каждого фикса по всем параллельным путям кода, эмпирически воспроизведи каждый заявленный багфикс «до/после», проверь оптимальность решения и возможности упростить код, вынеси ранжированный вердикт.

Входные данные:
$ARGUMENTS

Формат аргументов:

- Путь к RFC/плану (напр. `packages/core/.claude/rfc-navigation-commit-gate-2026-07-08.md`) + опционально диапазон реализации (`<base>..HEAD`, номер PR или список коммитов). Диапазон не задан → выведи его сам: коммиты, ссылающиеся на issue/RFC-маркеры документа (`git log --oneline --grep`), либо текущая ветка от merge-base с master.
- Опционально `--fix` — применить находки после отчёта (correctness — с regression-тестами; simplification/doc-drift — механически). Дизайн-развилки НИКОГДА не правятся молча — выносятся автору с вариантами.
- Опционально `max` — использовать workflow-backed ревью (`Workflow({name:"code-review", args:"max — …"})`), передав в args RFC-канон, диапазон и оси §3 как инструкции; findings воркфлоу затем прогнать через §2–§7 этого скила (воркфлоу не знает RFC-контекста сам). **Нет сохранённого `code-review` workflow (`.claude/workflows/` пуст) — сразу пиши inline RFC-scoped скрипт** (finder-оси §3 как отдельные finder'ы, канон embed'ом в их промпты, адверсариальная verify-стадия на каждую находку); это штатный путь для `max`, а не фолбэк — инлайн даже точнее, т.к. finder'ы получают канон в промпте вместо «воркфлоу не знает RFC» вслепую. Не трать проверку на «а есть ли named workflow» — по умолчанию пиши inline. Калибровка: `max` — для реализаций, идущих в master, трогающих security/cancellation-швы или большие diff'ы (десятки агентов, миллионы токенов — потому и явный опт-ин; его независимые finder-углы + адверсариальная верификация ловят слепые зоны автора — прецеденты: #1331 (3 CONFIRMED-бага на clone/error-путях, пропущенные инлайн-взглядом), commit-gate-1169 (finder нашёл `onTransitionLeaveApprove`-окно, не покрытое `suspendable` — автор проверил только onTransitionStart/subscribeLeave)); без `max` — компактные правки, где хватает собственных проб. **Гигиена рабочего дерева при `max`:** finder/verify-агенты пишут пробы прямо в рабочее дерево (иногда `*.test.ts` в `tests/`, где vitest их подхватит и уронит финальный гейт); ПОСЛЕ workflow — детерминированный скан+чистка leftover'ов (`_tmp*`, `probe-*`, `zz-*`, `qa-*`) ПЕРЕД гейтами §7, и не считать их за diff. ⚠ **Лишний `M`-файл в `src` — это ДВА разных события, и уборка у них противоположная:** невосстановленная МУТАЦИЯ (сносить) или применённый агентом ФИКС (сохранять). Агенту сказано не менять git-состояние, но не запрещено писать в файл, и «поломка ради замера» от «правки ради находки» отличается только СОДЕРЖАНИЕМ — `git status` их не различает. Поэтому по каждому лишнему файлу читай `git diff` ПРЕЖДЕ чем восстанавливать, и если это фикс — сперва `git diff <file> > scratchpad/agent-applied-<name>.patch`, потом откат: применять его ты будешь сам, осознанно и с regression-тестом, но потерять его содержание нельзя. (Прецедент ревью #1673: в дереве осталась правка `emitNavigationFail`, оказавшаяся единственной CONFIRMED-находкой прогона.) **Сверяй не только файлы, но и git-СОСТОЯНИЕ:** `git worktree list` (агенты добавляют свои worktree — даже созданные в scratchpad, они регистрируются в метаданных основного репо → `git worktree prune`), `git stash list`, `git log -1` (HEAD не сдвинут), и **staged-состояние** — агент, которому понадобился `git stash`/диф, делает `git add`, после чего ранее untracked-файлы становятся `A`/`AM` и вывод `git status` / `git diff --diff-filter` меняется под уже сделанными сверками. Снимай эталон ДО запуска workflow и сравнивай с ним — **по КАЖДОМУ рабочему каталогу сессии, включая соседние репозитории** (в этом репо — `real-router.wiki`, отдельный git-репозиторий в additional working directories: скан doc-drift штатно ходит туда, значит агент может там и написать). Авторство «лишних» модификаций различай по `mtime` (`stat -f '%Sm %N'`), а не по факту модификации: в соседнем репо могут месяцами лежать незакоммиченные правки пользователя, и принять их за мусор агентов — значит предложить снести чужую работу. И НЕ гоняй собственные src-мутации (§2 мутационная валидация) КОНКУРЕНТНО с бегущим workflow — finder прочитает транзиентную мутацию (`if (false && …)`) как working-tree-находку; либо серии по очереди, либо своя мутация в отдельном worktree.

Пример:

```
/code-review-rfc packages/core/.claude/rfc-navigation-commit-gate-2026-07-08.md 72517c6c..HEAD
/code-review-rfc .claude/rfc-file-routes.md --fix
```

## Принцип

**RFC — канон, реализация — претендент.** Это НЕ /audit-rfc (тот валидирует сам документ до реализации) и НЕ голый /code-review (тот не знает, что код ОБЯЗАН делать). Здесь двусторонняя сверка: (а) каждый пункт/DoD/шаг RFC → реализован ли, как заявлено; (б) каждый фрагмент diff → покрыт ли каноном. Три класса расхождений, все — находки до вердикта:

- **Недовыполнение** — пункт RFC отсутствует/частичен в diff (включая doc-sync-пункты и regression-план).
- **Перевыполнение** — реализация добавила поведение/обещание, которого в RFC НЕТ. Особо опасно, когда добавка _рекламирует_ побочную возможность: пин-тест и комментарий «X works» на паттерн, который RFC предписывал запретить, — это новый публичный контракт, протащенный мимо дизайн-решения. (Прецедент #1331: RFC-оговорка требовала контракт «guard-фабрики side-effect-free», реализация вместо этого зарекламировала `usePlugin`-из-фабрики комментарием + пином `usePlugin:'ok'` — ревью вскрыло дубль плагина на каждом clone и самопротиворечие CLAUDE.md.)
- **Отклонение** — реализовано иначе, чем в RFC. Не автоматически ошибка: сверь мотив, вынеси вердикт «лучше/хуже/эквивалентно» с доказательством; молчаливое отклонение без записи в RFC-журнале — находка само по себе.

**Метод — эмпирика, не чтение.** Заявленный багфикс воспроизводится на базовом коммите (`git show <base>:<file>` / прогон пробы на base) и перепроверяется на HEAD; новый тест валидируется мутационно (red без фикса — иначе он пин, а не защита). Вердикты субагентов/воркфлоу на несущих находках перепроверяй собственным прогоном.

## Шаг 0 — Скоуп и карта канона

1. Прочитай RFC целиком; выпиши таблицу обязательств: каждый шаг плана (A1…), каждый пункт DoD, regression-план, doc-sync-пункты, perf-план, заявленные метрики выгоды («−N строк», «закрывает issues X,Y»), явные НЕ-цели («что НЕ делаем»).
2. Определи diff (`git diff <base>..HEAD --stat`) и сверь границы: файлы вне карты канона → кандидаты в «перевыполнение»; пункты канона без файлов → «недовыполнение».
   - **zsh глотает мету в revision-range/grep.** `<base>^..HEAD`, `~1`, а также `|` в grep-паттерне под zsh раскрываются как glob/negation → path-limited `git diff <range> -- <path>` молча возвращает ПУСТО (не «файл не менялся», а команда не отработала как задумано). Квотируй диапазон (`git diff '<base>~1..HEAD' -- <path>`) или бери явные SHA / `git show <sha>:<path>`; пустой path-diff при непустом `--stat` того же диапазона — красный флаг тула, перепроверь другим способом, НЕ выводи «doc-sync чист» из пустоты.
   - **⚠ Тот же класс на ДРУГОЙ половине команды — PATHSPEC, и кавычки от него не спасают.** `git diff <range> --stat -- 'packages/*/src'` возвращает ПУСТО: в git-pathspec `*` не переходит через `/`, поэтому `packages/*/src` не матчит `packages/core/src`. Квотирование тут ни при чём — оно защищает от zsh, а глотает pathspec уже сам git. Пиши `-- packages` (шире) и фильтруй вывод, либо `-- ':(glob)packages/*/src'`. **Диагностика одна и та же в обоих случаях: пустой path-limited результат при непустом `--stat` БЕЗ path-limit — это отказ инструмента, а не факт о коде.** Правило: любой вывод, из которого собираешься сделать вывод «этого не менялось / этого нет», сначала предъяви на ПОЛОЖИТЕЛЬНОМ контроле (тот же скан без фильтра обязан что-то найти).
   - **⚠ Третья половина того же класса — cwd Bash-тула ПЕРЕЖИВАЕТ вызовы.** Один `cd packages/core` в предыдущей команде, и следующий `git archive <sha> packages/core/src` падает с `pathspec did not match any files`, а `git diff -- packages/…` молча пустеет — pathspec-то repo-relative. Диагностика та же (пустой результат = отказ инструмента), но искать причину будешь в git, а она в шелле. Для любой git-команды, чей аргумент repo-relative, ставь явный `cd <repo-root>` в ту же строку.
   - **История могла переписаться в ходе ревью.** На активном `master` диапазон/HEAD дрейфует под тобой (squash/rebase/amend между твоими git-вызовами). Если ревью длится — перед вердиктом пере-сними HEAD и диапазон, и **якорь находки к КОНТЕНТУ рабочего дерева, не к границам коммитов**: `git diff <old-HEAD> <new-HEAD> --stat` пуст ⇒ tree идентичен (прежнее чтение файлов валидно, менялись лишь коммит-границы); непуст ⇒ перечитай изменённое.
3. RFC под `.claude/` gitignored — реализация могла разойтись с ним молча; если у RFC есть журнал ревизий, сверь, против какой ревизии писалась реализация.

## Шаг 1 — Пункт-за-пунктом

Каждая строка карты канона получает статус: **DONE** (с `file:line`-доказательством) / **PARTIAL** / **DEVIATED** (+вердикт лучше/хуже) / **OVER-DELIVERED** (+что именно добавлено сверх) / **MISSING**. Явные НЕ-цели RFC — проверь, что реализация их НЕ сделала (ползучий скоуп — находка).

## Шаг 2 — Багфиксы: «до/после» исполнением

- Для каждого заявленного фикса: воспроизведи дефект на base (проба/`git stash`-free способ: `git show`, отдельный worktree или прогон committed-проб на base) и его отсутствие на HEAD. Если RFC ссылается на committed-пробы (`benchmarks/audit-probes/…`) — прогони их: ожидания должны были «флипнуться» ровно так, как RFC предсказывал.
- Новые тесты — мутационно: временно откати фикс (или внеси эквивалентную мутацию) → тест обязан покраснеть. Зелёный-до-фикса тест — недискриминирующий пин, не регресс-защита (находка).
  - ⚠ **Мутируй только через резервную КОПИЮ файла** (`cp` в scratchpad → мутация → восстановление из копии). `git checkout -- <file>` откатывает к HEAD, а при `--fix` в файле уже лежат ТВОИ применённые фиксы — он сотрёт их вместе с мутацией, молча и целиком (проверяй `git status` после каждого отката: исчезнувший из списка `M`-файл = стёртая работа).
  - ⚠ **Мутант, не уронивший тест, — это ДВЕ гипотезы, а не одна:** тест недискриминирующий ИЛИ мутация не достигла ветки (short-circuit, ранний `return`, кэш, второе условие того же `if`). Разведи их вторым мутантом на ДРУГОЙ половине условия, прежде чем чинить тест или объявлять его пином. Прецедент: сужение правила на два условия — первый мутант снял только per-key-проверку, а тест защищал ранний `length === 0`, и «зелено» читалось как «тест слабый».
  - ⚠ **То же правило зеркально — для ПРОБЫ, не воспроизведшей заявленный дефект.** «Не воспроизвелось» — это тоже две гипотезы: находка неверна ИЛИ проба не дошла до кода (не та точка входа, не тот фасад, аргумент отсеян валидатором выше по стеку, гард бросил раньше). Прежде чем отвергать чужую находку (агента или свою прежнюю) — смени ФОРМУ вызова: фасад ↔ `getPluginApi`/standalone API, с обязательным аргументом ↔ без него, голое ядро ↔ с плагином. И держи в пробе ПОЛОЖИТЕЛЬНЫЙ контроль: тот же вызов на входе, где эффект обязан быть, — если контроль тоже молчит, молчит проба, а не код. Прецедент (#1584, второй терминал mode-gate): `router.makeState(…)` не существует на фасаде, проба дала 0 предупреждений и читалась как опровержение; `getPluginApi(r).makeState(name, {}, search, path)` — та же интенция через реальную точку входа плагинов — дала предупреждение, и находка оказалась верной.
  - ⚠ **Форма вызова — не единственная ось: меняй и ФИКСТУРУ.** Общий тестовый роутер может делать предикат исследуемой ветки КОНСТАНТНЫМ, и тогда проба не доходит до кода не из-за точки входа, а из-за данных. В real-router `createTestRouter()` несёт definition-гварды в дереве маршрутов (`admin-protected` / `auth-protected` с `canActivate`), поэтому `hasGuards` у него истинно ВСЕГДА — любая проба на безгвардовую ветку `#executeNavigation` на этой фикстуре молча меряет соседнюю ветку. ⚠ И «залипший» предикат у неё **не один**: она же включает `allowNotFound`, из-за чего непопадание в маршрут уезжает в 404-КОММИТ (`SYSTEM_COMMIT`) вместо отказа `ROUTE_NOT_FOUND` — то есть в другой путь ядра, с другими рёбрами и другим набором событий. Симптом узнаваем: проба ждёт reject, а получает резолв со `state.name === UNKNOWN_ROUTE`. Фикстура принимает опции (`createTestRouter({ allowNotFound: false })`), так что чинится это параметром, а не отказом от неё; правило же общее — **перечисли предикаты, которые твой сценарий обязан менять, и убедись, что фикстура не держит КАЖДЫЙ из них константным**. Собирай роутер вручную (`createRouter([...])`) ровно под предикат и держи ПОЛОЖИТЕЛЬНЫЙ КОНТРОЛЬ на второй половине предиката (тот же сценарий с гвардом обязан дать другое число). Прецедент (ревью #1588): мутант `if (hasGuards) → if (true)` на `createTestRouter` дал 1 вызов leave-листенера (= «эквивалентен, находка ложна»), на голом `createRouter` — 2 (= находка верна, а весь сьют слеп). Та же слепота, кстати, и объясняла, почему мутант выживал в CI: фикстура — общая, и ветку не проходил НИ ОДИН тест. ⚠ **И предусловие ветки бывает не в аргументах вызова, а в КОНФИГЕ** — тогда «правильная» точка входа с «правильной» фикстурой всё равно не доходит. Прецедент (этот прогон): проба на арку `#1627` (`replace()` коммитит, пока гвард-фабрика оставила навигацию в полёте) дала `compiles=1` и читалась как «не воспроизводится» — а `clearDefinitionGuards()` рекомпилирует фабрику только для имени, держащего ОДНОВРЕМЕННО definition- и external-гвард; с `canDeactivate` в конфиге маршрута плюс `addDeactivateGuard` та же проба дала `compiles=2` и находка подтвердилась A/B. Приём: **всегда инструментируй сам факт достижения** (счётчик вызовов пользовательского кода, которое ветка обязана выполнить) — `compiles=1` сразу говорит «проба не дошла», а голый результат сценария этого не говорит никогда.
- Проба, читающая поток событий/логов, фиксирует снимок ДО своих же диагностических пост-вызовов — иначе артефакты хелперов читаются как события сценария.

## Шаг 3 — Класс по всем путям (главный урок)

Каждый исправленный дефект — представитель КЛАССА. «Починен на пути X» ≠ «класс закрыт»: перечисли все параллельные пути, где живёт та же механика, и прогони класс на каждом. Оси real-router (расширяй по месту):

- **constructor ↔ cloneRouter ↔ #recompileSlot** — код, исполняющий пользовательские фабрики (guard/plugin), исполняет их повторно на клоне и при рекомпиляции слота; фикс «фабрика видит готовый инстанс» обязан держаться на всех трёх. (Прецедент: план A починил конструктор — clone-путь re-исполнял фабрики на пустом config и дублировал плагины; оба бага CONFIRMED ревью.)
- **happy-path ↔ error-path нового кода** — брось исключение в середине новой процедуры: что остаётся? fail-open или fail-closed? Утёкшие наружу ссылки на полусобранный/полуразобранный объект должны быть инертны. (Прецедент: throw в середине flushPendingGuards оставлял живой router без поздних гардов — access-control bypass; фикс dispose-before-rethrow.)
- **sync ↔ async ветви**, **navigate ↔ start() ↔ navigateToState ↔ replace()-ревалидация**, **bare core ↔ с validation-plugin** (дефолтный конфиг проверяется ПЕРВЫМ), **base ↔ per-request clone (SSR)**, **dispose/teardown-симметрия** (всё, что фикс регистрирует, — снимается ли).

## Шаг 4 — Оптимальность решения (обязательный)

- **Аллокации и hot-path:** новые замыкания/объекты на per-call пути (не per-instance) — находка, если рядом уже есть shared-паттерн; сверь с Performance Notes пакета (какие пути «горячие» — задокументировано). (Прецедент: `getDependency`-замыкание аллоцировалось на каждый compile при уже существующей shared-фабрике рядом.)
- **Заявленные метрики выгоды пересчитай:** «−N строк», «−M аллокаций», «закрывает K issues» — `git diff --stat`/скан, не вера. Расхождение метрики при сохранённой структурной ценности — MINOR-находка с честной цифрой; расхождение, рушащее мотивацию решения, — SHOULD-FIX с эскалацией автору. (Прецедент: план B обещал −150 строк, реально −11 — ценность пересформулирована как структурная.)
- **Sub-ms перф-утверждения** («не медленнее», «+2 сравнения — шум») на hot-path — ТОЛЬКО same-session A/B (swap+rebuild+back-to-back, бенчи пакета); кросс-сессионные цифры не принимаются. RFC обещал perf-замер → он должен быть выполнен или явно передан пользователю как хвост.
- **«Можно лучше → надо», симметрия:** найденная оптимизация портируется во ВСЕ применимые места diff, не только в предъявленное; «здесь уже быстро → пропустим» — не аргумент.
- **Анти-цель:** не предлагать микрооптимизации cold-path ценой читаемости и не «оптимизировать» без замера то, что RFC осознанно оставил простым.

## Шаг 5 — Упрощаемость (обязательный)

- **Дубли, внесённые реализацией:** скопипащенные замыкания/комментарии/хелперы — особенно когда в том же файле уже есть shared-паттерн для соседа (несогласованность = будущий drift). (Прецедент: `getValidator` продублирован в двух wire-функциях при shared `compileFactory` строкой выше.)
- **Мёртвое:** экспорты/реэкспорты/параметры/поля без консьюмеров (`grep`-ом наличие, node-сканом отсутствие); леса времянки (пробные хелперы, debug-логи, `(temp)`-маркеры).
- **Лишняя церемония:** класс на один call-site, builder без вариативности, интерфейс-прослойка с единственным имплементором, тройное повторение списка полей — кандидаты на схлопывание. Проверь и ОБРАТНОЕ: не пере-схлопнула ли реализация то, что RFC осознанно оставил разделённым.
- **Удаление оправдывается usage-сканом** (вызовы, `git log -S`), не памятью и не комментарием.
- Разграничение с /simplify: здесь упрощение сверяется с каноном RFC — «проще» не должно ломать пункт документа; каждое предложение-упрощение указывает пункт RFC, которому оно не противоречит.

## Шаг 6 — Doc-sync и хвосты

- Doc-коммит реализации сам аудитится: скан по СТАРЫМ именам/формулировкам во всём репо — включая ДРУГИЕ пакеты (тайпинги/комментарии в core-types!), тесты-комментарии, wiki, `IMPLEMENTATION_NOTES`/`ARCHITECTURE`/`CLAUDE.md` всех уровней. «Нулевой остаток» доказывается детерминированным сканом, не выборочным grep.
  - ⚠ **Позитивный контроль обязателен и для СОБСТВЕННОГО скана, не только для grep.** Правило «пустой grep ≠ отсутствие» все помнят, а самописный обходчик дерева обманывает тише: НЕПОЛНЫЙ скан выглядит ровно как чистый. Прежде чем поверить своему скрипту, предъяви ему файл, про который ТОЧНО известно, что совпадение там есть, — и убедись, что он его печатает. Прецедент (ревью #1588): node-обход по `lastSync*` не нашёл `NavigationNamespace/constants.ts`, где стухшее упоминание было в двух местах, — виноват `catch{return}` внутри цикла (он обрывал обход всей директории вместо пропуска одного файла), а прямой `grep` по тому же файлу нашёл сразу. Отсюда же и приём: **если скан и grep расходятся, прав тот, кто НАШЁЛ**; и не сводить оба к одному механизму — расхождение двух независимых инструментов и есть проверка.
- **Не форматируй файл, который и до тебя не был отформатирован.** Перед `prettier --write` на затронутом файле предъяви `--check` на версии из HEAD (`git show HEAD:<file> > /tmp/x && npx prettier --check /tmp/x`). Если он и так «грязный» — правь ТОЧЕЧНО и `--write` по нему НЕ гоняй, иначе к правке в две строки приедут сотни строк чужого переформатирования, неотличимые в диффе от твоей работы. Прецедент (ревью #1588): `--write` по `IMPLEMENTATION_NOTES.md` ради одного абзаца переписал **426 строк**; файл не был prettier-чистым на HEAD, то есть гейт репозитория его и не проверяет. Обратный случай (файл ЧИСТ на HEAD) — форматировать обязательно, но тогда сначала ужми собственную вставку: в markdown-таблице длинная ячейка перевыравнивает ВСЮ таблицу, и «диф на 34 строки ради одной строки» — это сигнал сократить текст, а не принять шум.
- Line-цитаты в комментариях/доках сдвигаются соседними мержами — проверяй адреса на HEAD; полу-обновлённый комментарий (одна строка поправлена, соседняя ссылается на старое имя) — типовая находка.
- Самопротиворечие доков: новый контракт в одном месте против старой формулировки в другом (тот же файл считается!).
- Changeset-дисциплина: bump по типу (fix=patch), один пакет на файл, private→changeset на core; cross-package правка src публичного пакета (даже комментарий в тайпингах) требует своего changeset.

## Шаг 7 — Гейты и вердикт

- Точечные прогоны затронутого пакета: type-check (`tsc`, IDE-диагностике не верить — бывает stale), functional c coverage-порогом, property, lint/prettier изменённых файлов, changeset-линт.
  - ⚠ **«Stale» тут — не «на пару правок отстала», а «описывает ДРУГОЕ дерево».** После мержа/смены ветки IDE может держать снимок кода ДО ревьюируемого диапазона и ругаться на символы, которые сам этот диапазон и удалил (прецедент ревью #1673: диагностика весь прогон требовала `myId` / `myEpoch` / `CommitPayload` — три типа, снятых ревьюируемым PR, — при `tsc --noEmit` exit 0). Читается это как «ты только что всё сломал», причём в файлах, которых ты не трогал. Единственный арбитр — собственный прогон `tsc`; и обратное тоже верно: ЧИСТАЯ диагностика не доказывает, что тип-чек пройдёт. Полный `pnpm build` НЕ гонять — финальная валидация у пользователя.
  - ⚠ **Гейты — только ПОСЛЕ завершения workflow, не конкурентно с ним.** Два vitest-прогона одного пакета делят `coverage.reportsDirectory` и второй падает ложно (`Error: Something removed the coverage directory "…/coverage/.tmp"` → `ENOENT coverage-NN.json`) — это читается как красный сьют, хотя тесты прошли (в логе `Test Files … passed` выше по стеку). Тот же класс, что запрет конкурентных src-мутаций выше, но про ЧТЕНИЕ: прогон агента и твой прогон мешают друг другу без всяких мутаций. Признак — падение БЕЗ единого `×` в списке тестов.
  - ⚠ **И запрет шире гейтов: конкурентно с workflow нельзя гонять НИЧЕГО, чему собираешься ВЕРИТЬ — даже read-only пробу.** Мутации агентов транзиентны: verify-агент копирует файл, ломает его, гоняет, восстанавливает — и твой прогон, попавший в это окно, читает чужого мутанта как рабочее дерево. Собственный `git status` при этом чист ДО и ПОСЛЕ, так что постфактум инцидент не виден. Если прогон всё же нужен раньше — обрамляй его хешем состояния (`git status --porcelain | md5` до и после) и **перезапускай при расхождении**, а не интерпретируй. Признак-подсказка: IDE-диагностика вдруг показывает ошибки в файлах, которых ты не трогал (`has no exported member 'X'` на только что удалённом символе).
  - Прогон, признанный несостоявшимся по такой причине, **перезапускается, а не интерпретируется**: `rm -rf packages/<pkg>/coverage` и заново. Не выносить его в находки и не описывать как «сьют красный».
  - ⚠ **«Нашёл ноль файлов» — это УСПЕХ для линтера, и выглядит он ровно как чистый гейт.** `npx eslint $FILES` под **zsh** не расщепляет переменную по словам (в отличие от bash): девять путей склеиваются в один несуществующий паттерн, ESLint печатает `No files matching the pattern` и **выходит с кодом 0**. Тот же зелёный `exit 0`, что и у настоящего прогона. Это тот же класс, что пустой path-limited `git diff` в Шаге 0, но на гейтовой половине, где цена ошибки — «линт чист» в вердикте. Правило: списки файлов передавать через `... | xargs npx eslint`, а не `$VAR`, и **требовать в выводе имя хотя бы одного проверенного файла** (либо `--format=json` и считать элементы) — «ни одной ошибки» принимается только вместе с «проверено N файлов, N>0». То же касается любого сканера, которому путь приходит переменной: `tsc`, `prettier --check`, самописный обходчик.
- **Отчёт:** (1) таблица канона со статусами и доказательствами; (2) findings **BLOCKER / SHOULD-FIX / MINOR**, каждая с категорией `correctness | rfc-deviation | optimality | simplification | doc-drift`, `file:line` и однострочным фиксом; (3) вердикт: реализация принимается / принимается с правками / возвращается — отдельно для кода и для соответствия канону; (4) если находки меняют сам RFC (новая грань, опровергнутая посылка) — предложи ревизию документа, не молчаливый дрейф.
- При `--fix`: correctness-фиксы — только с regression-тестом на каждый; после правок — повторные гейты; сводка «что применено / что оставлено автору».

## Жёсткие правила

- Несущие вердикты (баг подтверждён / класс закрыт / метрика сходится) — только собственным исполнением; агентское резюме — гипотеза.
- Дефолтный конфиг проверяется раньше максимального (opt-in-слои маскируют дыры).
- **При accept/reject-дивергенции двух слоёв — определи, КТО неправ, round-trip'ом принятой стороны, ПРЕЖДЕ чем фиксировать находку и её направление.** `gate=REJECT / backstop=ACCEPT` имеет ДВА взаимоисключающих прочтения: (a) gate ложно реджектит ВАЛИДНЫЙ роут — принятая сторона round-trip'ит (`buildPath`→`match` возвращает параметры) → баг в gate; (b) backstop молча принимает МЁРТВЫЙ роут (`buildPath` эмитит URL, который его же `match` отвергает) → баг в backstop, иной класс и severity. «Дивергенция подтверждена» без round-trip принятой стороны — недоказанное направление (частый источник ложной severity). (Прецедент tokenizer-review 07-10: `~:id` gate=REJECT/backstop=ACCEPT сперва прочитан как «gate ложно реджектит валидное», но принятая сторона оказалась DEAD → это backstop-баг класса «путь без ведущего /», другое направление и другой владелец фикса.)
- Не навязывай вкусовщину: отклонение от RFC без противоречия и без ухудшения — вердикт «эквивалентно», не находка.
- Правки реализации = обычный код-флоу репо (changeset, тесты, конвенции); правки RFC-документа — с ревизией в журнале. Push/commit — только по явной просьбе или заведённому в сессии порядку.
