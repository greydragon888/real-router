Проведи целенаправленное глубокое исследование вопроса, который не закрывается одним фиксом: заведи папку исследования с README, сформулируй проверяемые гипотезы, раздай линзы параллельным агентам, каждый из которых сохраняет полный отчёт в файл, подтверди ведущую гипотезу экспериментом, вынеси владельцу вывод и варианты — и, если решение крупное, разложи его в RFC для `/audit-rfc` → `/implement-rfc`.

Входные данные:
$ARGUMENTS

Формат аргументов:

- Вопрос или повод в свободной форме, номер issue (`#2627`) или цепочка issue (`#2626 #2627 #2628`).
- `--resume <папка>` — продолжить существующее исследование: дочитать README, статусы RFC, досчитать недостающее.
- `--no-rfc` — остановиться на выводах (§5), RFC не составлять.

Пример:

```
/research почему инфраправки идут волнами «фиксов фиксов»
/research #2626 #2627 #2628
/research --resume .claude/ci-cd-architecture-2026-09-29
```

> **Соседние скилы.** Класс ошибок — цепочка issue, где фикс каждого находит следующий, — это `/class-hunt`: тот же протокол с готовыми линзами переписи, механизма, истории и структуры. Кластеризация всей баг-истории рантайма по корням — `/debt-map`, одна цепочка долга — `/chain-resolve`. Сырая идея без вопроса «почему» — `/brainstorm`. Вопрос на один ответ — не исследование: отвечай сразу.

## Принцип

- **Исследование готовит РЕШЕНИЕ, а не список находок.** Назови решение до первого агента («переносить ли X», «какой механизм», «нужно ли вообще»). Нет решения — нет исследования.
- **У каждого утверждения — происхождение:** `[изм]` — измерено (команда, вывод), `[прочит]` — прочитано в файле (`путь:строка`), `[вывод]` — умозаключение. В выводы (§5) число попадает только с `[изм]`.
- **Отчёт агента — файл, а не контекст.** Агент пишет полный отчёт с доказательствами в `reports/`, а в ответе возвращает резюме. Доказательства переживают сессию и сжатие контекста, а контекст остаётся синтезу.
- **Гипотеза без наблюдения, которое её опровергнет, — не гипотеза.** У каждой — строка «опровергнет: …».
- **Отрицательный результат — результат.** Линза, которая ничего не нашла, записывает, что искала и чем.

## Фаза 0 — Вопрос и рамка

1. Запиши запрос владельца дословно — он войдёт в README.
2. Назови решение, которое исследование готовит.
3. **Не исследовано ли уже:** `ls -d .claude/*-20*/`, `rg` по памяти и `IMPLEMENTATION_NOTES.md` по предмету. Есть папка — продолжай её (`--resume`), параллельную не заводи. Есть запись NOTES — это данные для гипотез, а не ответ: перепроверяй на HEAD.
4. **Срез:** `git fetch origin && git rev-parse --short origin/master`. Каждый `[изм]` привязан к нему; если срез сдвинулся посреди исследования — `git log <срез>..origin/master` до того, как верить расхождению замеров.
5. **Папка:** `.claude/<slug>-<YYYY-MM-DD>/` с `README.md` и `reports/`. `.claude/*` в `.gitignore`, поэтому папка локальна и не коммитится — её адрес живёт в памяти (Фаза 7).

## Фаза 1 — README-скелет (до агентов)

```markdown
# <Предмет>: исследование

> **Статус:** <в работе | завершено YYYY-MM-DD; решение по §5 — за владельцем | реализовано: <коммиты/PR>>. Запрос владельца: «<дословно>».

## 1. Повод — таблица событий/экземпляров: что | как найдено

## 2. Гипотезы — H1..Hn (проверяемые), у каждой «опровергнет: …»

## 3. Метод — таблица линз: агент | предмет | файл отчёта; эксперимент и где он идёт

## 4. Результаты — по подразделу на гипотезу: вердикт + числа с метками + ссылки на reports/

## 5. Выводы — рекомендация, цена, риски, что не проверено; решения за владельцем — списком
```

Скелет пишется ДО роя: гипотезы и линзы, записанные после отчётов, подгоняются под отчёты.

## Фаза 2 — Линзы и рой

- **Линза — одна ось вопроса со своим предметом и своим способом измерения.** Режь по независимости предметов, а не по каталогам: две линзы над одним предметом дублируют работу и спорят о числах.
- **Агентов — в одном сообщении**, параллельно, 3–8 штук; больше — только по явной просьбе владельца. Пока они работают, их работу сам не делай.
- **Промпт агента** (каждый пункт обязателен):
  - контекст: вопрос, решение, срез SHA, чем эта линза отличается от соседних;
  - гипотеза(ы) линзы и что их опровергнет;
  - предмет и метод: что перечислить, что измерить, чем (`git ls-files` для множества файлов — не угаданный список; `git log -S/-G` для истории; исходники инструмента для предсказаний);
  - **абсолютный путь отчёта** `…/reports/<буква-или-номер>-<тема>.md` и формат: таблицы с `путь:строка`, команды с выводом, метки `[изм]/[прочит]/[вывод]`;
  - запреты: репозиторий только читать; пробы и мутации — в копиях дерева в scratchpad; ничего не писать вне scratchpad и своего отчёта; не коммитить, не пушить, не заводить issue;
  - ответ: резюме до ~20 строк + путь к отчёту.
- **После роя:** каждый отчёт на месте и не обрезан; `git status` основного чекаута чист от следов агентов; вне scratchpad ничего не появилось. (Прогон #2627: агент перепроверки создал `/tmp/claude-501-noop-ignore` — удалён вручную.)

## Фаза 3 — Синтез

- Сведи отчёты в §4: по каждой гипотезе — подтверждена / опровергнута / сужена.
- **Несущие утверждения агентов перепроверь сам** — это контрольная рука, а не недоверие: агент — второй инструмент со своими слепыми зонами. Расхождение двух отчётов в одном числе → третий замер, а не выбор более удобного.
- **Обобщение о поведении инструмента — отдельное утверждение:** «X не ходит по симлинкам» верно для конкретного X, замеренного на конкретном входе. Перечисли, для каких инструментов замерено, а не «инструменты не ходят». (Прогон #2627: верно для Node `globSync` и экстрактора CodeQL, а jscpd и `tsconfig.sonar.json` по ним «ходят и потому исключают алиасы»; замер 2026-10-05: jscpd 5.3.2 по ссылкам на каталоги под корнем скана не ходит — без трёх записей-алиасов отчёт тот же, — а корень-ссылку обходит.)

## Фаза 4 — Эксперимент

- Для ведущей гипотезы **выпиши предсказания ДО эксперимента** — из исходников инструмента, документации, отчётов. В README — таблица «№ | предсказание | замер».
- **Где:** detached worktree вне репозитория — `git worktree add --detach <scratchpad>/<name> <срез>`, затем `pnpm install --frozen-lockfile --offline`. Реальный `turbo run` — только с `--cache-dir` в scratchpad: без него worktree пишет в кеш основного чекаута. Базовую сборку для сравнения сохрани в scratchpad до правок.
- **Сравнение артефактов — побайтно** с базой; каждое отличие объяснено, необъяснённое — находка.
- **Упавший эксперимент — не замер:** код выхода и последние строки лога до любых выводов.
- В конце — `git worktree remove` и проверка `git worktree list`.

## Фаза 5 — Выводы и доставка

- **§5:** рекомендация, её цена и риск, что осталось непроверенным, какие решения за владельцем.
- **В чат — суть коротко:** в чём проблема, чем подтверждено, что предлагается, что решить владельцу. Детали — ссылкой на папку.
- **Доставка — по составу диффа:** трогает `packages/*/src/` → ветка в worktree, PR, changeset; иначе — инфраструктура, коммит прямо в `master` без PR и changeset. Push — только по явной просьбе.

## Фаза 6 — RFC (если решение крупное)

- **Критерий:** больше одного независимо внедряемого шага, или шаги с разным риском и мораторием, или документ просит владелец. Иначе — сразу `/bugfix` или инфракоммит.
- `rfc/README.md` — таблица RFC (что, волна, мораторий) и порядок внедрения с обоснованием.
- `rfc/rfc-<N>-<slug>.md` — проблема со ссылками на `reports/`, дизайн, шаги (изменение → верификация → откат), DoD, риски.
- ⚠ **Каждый RFC идёт в `/audit-rfc` непосредственно перед своим внедрением, а не все сразу:** внедрение одного сдвигает строки, на которые ссылается следующий. Замер 2026-09-30: после трёх коммитов 12 из 97 явных ссылок `файл:строка` указывали не на тот текст. Затем `/implement-rfc`.

## Фаза 7 — Жизнь после исследования

- **Статусы** README и `rfc/README.md` обновляются по мере внедрения: ✅ с коммитом или PR.
- **Память:** `project_<slug>.md` — адрес папки, решения владельца, мораторий, что внедрено; строка в `MEMORY.md`.
- **Вывод, опровергнувший записанное,** ставит указатель `> ⚠ Refuted on <дата>: … See "…".` рядом с опровергнутым в `IMPLEMENTATION_NOTES.md` — отдельной правкой в доставке, а не только в README исследования.

## Жёсткие правила

- В Фазах 0–4 код репозитория не правится — только scratchpad-копии.
- Не заводи issue на каждую находку до выводов: находка может оказаться экземпляром класса, и тогда три issue — это три фикса одного места вместо одного фикса класса.
- Папку исследования не коммить и не публикуй; наружу уходит только то, что вошло в доставку (NOTES, CLAUDE.md, PR).
- Числа в README — измеренные в этой сессии или с явной пометкой, откуда взяты.

## Самокоррекция скила (ОБЯЗАТЕЛЬНО, в конце КАЖДОГО прогона)

Этот файл — живой; каждый прогон обязан его затачивать. После выводов вынеси короткую секцию **«Самокоррекция»** — критику не своей работы, а САМОГО ЭТОГО СКИЛА: где его текст промолчал, соврал, был двусмыслен или избыточен — и это стоило времени, лишнего шага или риска ошибки.

1. **Привязка к ИНЦИДЕНТУ, не общие советы.** Каждая правка — из конкретного момента ЭТОГО прогона: «скил сказал X / промолчал про X → реальность Y → я потерял/чуть не ошибся на Z». Нет инцидента — нет правки.
2. **Высокая планка: изменило бы исход?** Предлагай, только если правка реально предотвратила бы ошибку, сократила перебор или сняла двусмысленность. Косметику отбрасывай.
3. **Разовое ≠ паттерн.** Специфику конкретного исследования — в его README или память, НЕ в скил.
4. **Сначала заточи, потом дописывай.** Предпочитай усиление существующего абзаца новой секции.
5. **Предлагай, не применяй молча.** Выведи кандидатов таблицей (раздел | инцидент | предлагаемый текст), спроси разрешения. Применил по согласию → `.claude/commands/` это infra, в master напрямую, без changeset. ⚠ В сообщении такого коммита не ставь закрывающее слово (close/fix/resolve) вплотную к `#N`: push в `master` закроет задачу.
6. **Честность про «нечего править».** Прогон прошёл чисто — так и скажи: «правок нет».
