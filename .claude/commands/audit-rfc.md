Проведи аудит RFC/дизайн-документа: провалидируй КАЖДОЕ утверждение против первоисточника (код, компилятор, прогон, смежные доки, доки/CLI/исходники сторонних продуктов) — НЕ против самого документа — найди ошибки, противоречия и непропагированные решения, вынеси вердикт о готовности к реализации.

Входные данные:
$ARGUMENTS

Формат аргументов:

- Путь к RFC/дизайн-документу (напр. `.claude/rfc-file-routes.md`, `.claude/rfc-type-safe-routing-generator.md`, `.claude/ci-acceleration-poc-ru.md`).
- Опционально `--fix` — применить ТОЛЬКО механические правки (фактические исправления, починка цитат, пропагация уже-ПРИНЯТОГО решения по всем таблицам/псевдокоду/DoD, снятие противоречий с однозначной резолюцией). Дизайн-вопросы НИКОГДА не правятся автоматически — выносятся автору. По умолчанию: report-only (доказанный порядок — сперва отчёт, правки по явной просьбе).
- Опционально `--delta <база>` — сверка правок: аудировать только разницу с последней проверенной версией (сохранённая копия или git-ревизия) независимым агентом (§«Режим `--delta`»). Запускать после серии правок — раунда `--fix` или решений владельца — перед `/implement-rfc`; цикл кончается сверкой без BLOCKER, если после неё не внесено ничего сверх её находок (§«Режим `--delta`», п. 4).

Пример:

```
/audit-rfc .claude/rfc-file-routes.md
/audit-rfc .claude/rfc-type-safe-routing-generator.md --fix
/audit-rfc .claude/ci-cd-architecture-2026-09-29/rfc/rfc-1-single-check-runner.md --delta <копия до правок>
```

## Принцип

Статус «готов к работе» в шапке НЕ значит, что документ корректен. RFC-«театр» проходит, когда: утверждение ссылается на код, который говорит не то, что заявлено; решение принято в прозе, но не пропагировано в таблицы/псевдокод/DoD; в алгоритме ordering-баг, который никто не протрассировал; цитата на смежный док не резолвится.

Цель аудита: для КАЖДОГО утверждения и вывода доказать его **первоисточником** — кодом, компилятором, реальным прогоном, содержимым смежного документа — а НЕ доверием к само-утверждению RFC или к резюме субагента. Это RFC-аналог мутационной валидации (см. `audit-pbt`/`audit-stress`): истинность claim'а доказывается походом в ground-truth, а не зелёным цветом документа.

Ключевая интуиция: самый опасный режим — **plausible-but-wrong**. Claim звучит убедительно, субагент его «подтверждает», но компилятор/код говорит обратное. Несущие и неожиданные claim'ы проверяй САМ, эмпирически (см. Жёсткие правила).

**Ground-truth включает данные, которые нужно ПОЛУЧИТЬ, а не только код, который нужно прочитать.** Для количественных claim'ов (тайминги, пороги, «уложится в ≤Xs», «доминирует пакет Y») первоисточник — это **замер**, а не число из документа. Не принимай оценку на веру и не понижай находку до «вероятно ок», когда вопрос закрывается 5-минутным замером / симуляцией / калибровкой по реальной истории. Эталон дисциплины — `.claude/ci-acceleration-poc-ru.md`: он сам ведёт ревизии «факты перепроверены эмпирически» (Ред. 16: `turbo --dry=json` на репо нашёл **3 бага** центрального скрипта) и явно метит **измеренное** (`32m 29s` на real CI run) против **оценочного** («arm64-дельта неизвестна → замер, не гипотеза»; «`K=5` — стартовый, подобрать по замерам»). Аудит обязан: (1) для каждой load-bearing-цифры определить — измерена она или предположена; (2) если предположена и гейтит решение — добыть данные или явно пометить ASSUMPTION+RISK.

**Claim'ы о СТОРОННИХ продуктах — отдельный первоисточник: сам продукт, не репо и не память.** Если документ ссылается на чужой API / поведение / лимит / опыт («turbo делает X», «GitHub Actions arm64 free для public-repo», «Nx Cloud умеет Y», «Vite-плагин поддерживает Z», «browser API ведёт себя так») — проверь в первоисточнике ПРОДУКТА (его CLI/`--help`/прогон, context7-доки, исходники, офиц. доки, web), а НЕ по training-памяти: стек bleeding-edge (версии — таблица «Toolchain Versions» в `CLAUDE.md`), и память систематически отстаёт от актуальных версий. «Я знаю, как работает X» без захода в источник — это plausible-but-wrong в чистом виде (см. memory `feedback_no_hallucinated_spec_facts`).

## Классификация утверждений (определи тип КАЖДОГО claim'а)

1. **CODE-FACT** — ссылка на файл/функцию/строку/regex/сигнатуру API/поведение. Проверяется чтением реального кода.
2. **TYPE/COMPILER** 🔬 — утверждение о поведении TypeScript (`keyof`, `Omit`, inference, module augmentation, index-signature). Проверяется ТОЛЬКО компиляцией — никогда рассуждением и никогда доверием агенту.
3. **CROSS-REF (внутренний)** — цитата на ВНУТРЕННИЙ док/RFC/секцию/issue/номер-решения. Должна резолвиться в существующий таргет с заявленным содержимым.
4. **EXTERNAL/THIRD-PARTY** 🌐 — утверждение о СТОРОННЕМ продукте: его API / поведение / лимит / прайсинг / «как делает инструмент X» (turbo, Nx, GitHub Actions, Vite, Vitest, browser API…). Первоисточник — САМ продукт: установленный CLI (`--help`/прогон), context7-доки, его исходники/репозиторий, офиц. доки (WebFetch), web (WebSearch). НЕ из памяти (training лагает на bleeding-edge) и НЕ из утверждения RFC.
5. **COUNT/INVENTORY** — счётчики пакетов, «N адаптеров», «9 инвариантов», **а также usage/frequency-счётчики, которыми RFC оправдывает УДАЛЕНИЕ фичи («used once», «barely used», «dead code», «нигде не вызывается»)**. Пересчитай сам: инвентарь — `ls`/скан; usage-частоту — эмпирически (`gh pr list --search`, `git log -S<маркер>`, code-скан по вызовам), НЕ со слов автора / по памяти. «Remove-because-unused» — проверяемый claim, а не мотивация. **Family-claim — свойство, заявленное разом для ВСЕХ N копий/вариантов/файлов** («все 5 копий byte-identical», «эти 4 варианта читают `?n=`») — проверяй на КАЖДОМ члене семьи детерминированным сканом (`md5` всех копий, скрипт-инвентарь по каждому файлу), никогда образец+аналогией: «проверил один, обобщил на пять» — plausible-but-wrong, переживающий даже само-аудит дока. Инвентарь «где живут копии X» собирай и по **смежным слоям-потребителям** (драйверы/раннеры/тест-фикстуры/CI-скрипты), не только по слою, который док называет: потребитель часто держит собственную hardcoded-копию контракта. **Инвентарь ссылок при переименовании/удалении пакета обязан отдельным пунктом покрывать КОРЕНЬ репо** — root-конфиги (sonar/size-limit/knip/CI-guard-скрипты) держат пакетные списки, а walk по подкаталогам корень не захватывает; плюс читай guard-скрипты (`check-*-scope` и т.п.): их заголовки называют файлы-потребители списков, отсутствующие в любом import-графе. **Инвентарь потребителей СНИМАЕМОЙ двери классифицируй по РОЛИ — чтение / запись / ЗАГЛУШКА, — а не считай импорты.** Заглушка передаёт имя члена СТРОКОЙ (`vi.spyOn(obj, "m")`, `defineProperty`), поэтому скан ЧТЕНИЙ возвращает по такому файлу пустое множество, и пустота читается как «дверью не пользуются»; а замены у заглушки нет ровно там, куда её отправляют, — на замороженной поверхности: `vi.spyOn` на ней падает `Cannot redefine property`. Роль меняет и цену снятия двери, и то, кто обязан ответить на вопрос. **Счётчик РЕГИСТРАЦИЙ** (арки бенча, кейсы, фикстуры, роуты) считается как число сайтов **× кардинальность цикла** — читай литеральный список, по которому сайт итерируется. Число вызовов и число зарегистрированных сущностей — разные величины, и обе могут не совпасть с клеймом, так что site-count «подтверждает» третье неверное число. **Документ, объявляющий НОРМАЛИЗАЦИЮ** («все счётчики пере-выведены против одной базы», «анкеры пересняты», «числа приведены к версии X»), **— это claim, и проверяется ПО-ВЕЛИЧИННО, а не оптом.** Приём, решающий это одним ходом: измерь ОДНУ И ТУ ЖЕ величину на ОБЕИХ базах и посмотри, к какой подходит число документа. Нормализация систематически ложится на то, что автор правил руками (номера строк), и НЕ ложится на производные метрики — всего строк, число функций, доля комментария, знаменатель прогона, — а гейтят решение обычно вторые.
6. **ALGORITHM/PSEUDOCODE** — читается как исполнение: ordering-баги, недостижимые ветки, необработанные edge-кейсы, расхождение сигнатуры вызова и определения. **Если док заменяет правило парсинга/классификации — прогони НОВОЕ правило по полному словарю форм СТАРОЙ грамматики** (и валидных, и отвергаемых, включая реверс- и двойные-глифы): каждая старая форма обязана получить названный исход (валидна / та же ошибка / новый рецепт); форма, тихо меняющая интерпретацию или тихо легализующая бывший reject, — находка. **То же — для КОПИИ значения из инструмента A в инструмент B** («дословно», «генерируется из»): текст не меняется, а разборщик меняется. Прогони словарь форм, которые принимает A, через разборщик B; форма, которую B читает иначе, — находка, а критерий для генератора — закрытый словарь общих форм с отказом на остальном. (Пример: `ignore` из `.jscpd.json`, перенесённый «дословно» в `sonar.cpd.exclusions`, — jscpd разворачивает `{a,b}`, а Sonar читает фигурные скобки буквально и делит значение по запятой. Этот класс переживает полный аудит.) **То же — для смены ПОРЯДКА **или КАНАЛА** мёржей/нормализаций** (defaults/normalize/canonicalize): прогони СТАРЫЙ фактический и НОВЫЙ заявленный вариант по решётке граничных входов — {значение, `undefined`, отсутствие} × {дефолт есть/нет} × {каждый канал}; клетка с молча изменившимся исходом = находка. **Клейм «этот шаг — no-op» доказывается ТОЛЬКО решёткой** {вызывающий молчит} × {значение в канале A} × {значение в канале B}: совпадение выхода на одном входе — не доказательство, а ровно та форма, которой пишут приёмку такого шага, поэтому дефект переживает и её. Проверять надо и то плечо, где новый код и старый пишут в РАЗНЫЕ каналы. **Унификация N точек входа на одну проверку** («паритет», «третья точка популяции», «дать конструктору то, что уже есть у add/replace») — тот же класс, но словарь строится ЗЕРКАЛЬНО: из входов, которые **отстающая** точка принимает СЕГОДНЯ, а не из тех, что отвергают ведущие. Дельта живёт ровно там, и док систематически описывает её как «гейт срабатывает раньше бэкстопа», когда на деле это «срабатывает там, где не срабатывало ничто» — особенно если новая проверка и старый бэкстоп судят по РАЗНЫМ признакам (строка против семантики), потому что тогда их множества не вложены ни в одну сторону. **Прескриптивный абзац, назначающий МОМЕНТ, — тот же класс, даже когда это чистая проза без псевдокода** («на входе в X», «до Y», «один раз при Z», «а не по факту первого потребителя»). Рецепт: выпиши величины, от которых зависит предписанное действие, и проверь для КАЖДОЙ, известна ли она в названный момент. Ответ обычно уже лежит в том же документе — чаще всего в разделе, где док ХВАЛИТ чужую правку за обход ровно этой незнаемости: такой абзац и есть контрпример его же предписанию. Проверь заодно, не закрыл ли документ своим же разделом «отвергнуто» единственный оставшийся выход — тогда предписание не просто недоспецифицировано, а невыполнимо, и находка BLOCKER.
7. **DESIGN-DECISION** 🔁 — выбор, принятый в прозе («Принято», О-N). Должен быть пропагирован в КАЖДЫЙ downstream-артефакт: convention-таблицы, псевдокод, DoD этапов, Risks, сводную таблицу. **Если решение меняет форму/сигнатуру осевого поля или API, а док даёт список затронутых/незатронутых потребителей — построй инвентарь читателей этого поля (и вызовов меняемых сигнатур) НЕЗАВИСИМО**, сканом по всем слоям — включая symlink-shared источники и каналы мимо названного механизма (док говорит «sweep интерцепторов» — а читатели бывают не-интерцепторными), — и сравни со списком дока: потребитель вне списка — находка; «не затронут» доказывается инвентарём читателей, не доверием списку. **Если решение УДАЛЯЕТ защитную/нормализующую стадию** (развод каналов, санитайзер, дефолтизатор, коэрсер), инвентарь строится ДУАЛЬНО — не читатели поля, а **producer'ы, писавшие в эту стадию**: кто полагался на то, что она приберёт за ним. Опора на стадию часто не выражена вызовом — потребитель просто передаёт мешок дальше, а своё допущение держит в КОММЕНТАРИИ, поэтому call-graph и «кто вызывает X» его не покажут; ищи текстом по имени удаляемой стадии И по её эффекту. Отдельно перепроверь клейм «этот слой чист по построению»: чистым может быть один под-слой (парсер), а соседний (пользовательский хук того же шва) — держаться ровно на удаляемой стадии. **Если решение ПЕРЕНОСИТ проверку доверия** (кто попадёт на self-hosted, чей код исполнится рядом с секретами) из места, которое вычисляет платформа — `if:` по `github.*`, ruleset, условие триггера, — в значение, которое кто-то ЗАПИСЫВАЕТ — output шага, артефакт, файл, переменную окружения, — это отдельный клейм, даже когда док называет перенос «побайтным» и пишет, что «меняется только место». Место и есть предмет проверки: перечисли всех, кто может записать новое значение, и исполняется ли в том же джобе недоверенный код до записи или параллельно с ней. Тест, закрепляющий только ПОТРЕБИТЕЛЯ («джобы читают `needs.X.outputs.trusted`»), закрепляет и подделываемую форму производителя.
8. **INVARIANT/TEST-PLAN** — предлагаемые инварианты/тесты. Проверяется на корректность (свойство реально держится с учётом ОСТАЛЬНЫХ решений?) и неизбыточность (не дубль другого инварианта). **Особый под-класс — критерий «эквивалентность текущему поведению» (fuzz-паритет, golden-сравнение): если тот же док обещает чинить известные баги, критерий обязан явно исключать баг-грани (на них эталон — корректный вывод, расхождение ожидаемо), иначе он самопротиворечив — первая же генерация на баг-грани уронит прогон.** ⚠ **Клейм «тест остаётся зелёным» — не то же, что «тест продолжает работать», и проверяется МУТАЦИЕЙ, а не прогоном.** Когда документ меняет код, который тест пинит, и подаёт зелёный цвет как подтверждение («остальные N тестов того же файла ЗЕЛЁНЫЕ»), прогони дискриминирующую мутацию этого теста на ОБЕИХ базах. Искать её обычно не нужно — она уже описана в его же docblock'е («moving X below Y flips these and reds them»). Зелёный-и-НЕдискриминирующий — ровно тот ложно-зелёный, ради которого аудит существует, и прячется он систематически в разделе «что не сломалось», то есть там, где скил иначе велит награждать, а не искать.
9. **PERF/EMPIRICAL-ESTIMATE** 📊 — количественный claim: тайминг, порог (`K=5`), «уложится в ≤Xs», «пакет Y доминирует wall-time», счётчик, варьирующийся по входу. Первоисточник — **замер / симуляция / калибровка по реальной истории**, не число из документа. Проверь дополнительно: помечено ли явно как измеренное vs оценочное.
10. **PROSE/MOTIVATION** — мотивация/рамка, не привязанная к коду. Низкий приоритет; проверяется лишь на внутреннее противоречие.
11. **PLAN-STEP/GATE** 🧱 — шаг плана внедрения и его гейт («после шага X зелёный Y»). Гейт — утверждение о состоянии ПОСЛЕ шага, и проверяется оно исполнением, а не чтением: пройди шаги ПО ПОРЯДКУ против правил самого документа (переходные тесты, исключения, моратории, на каком шаге что входит в реестр); дешёвый шаг примени буквально в копии дерева и гоняй ВЕСЬ сьют, который исполняет гейт, а не тест, названный в плане, — и в том окружении, где гейт исполняется: сьют, который в CI идёт внутри другой проверки, наследует её переменные, а джоб, сделанный «по образцу» соседнего, — форму его рабочей копии: глубину checkout и то, есть ли в ней база PR. Читателей поверхности, которую шаг меняет (текст хука, workflow, API модуля), ищи по всему дереву, а не в каталоге, который назвал план: тест пакета, читающий хук, исполняется своим сканом, и гейт «сьют `scripts/tests` зелёный» его не видит. Проверка, которую документ регистрирует в CI, охраняет файлы: перечисли формы PR, на которых её джоб не запускается вовсе (`if:` джоба, фильтры путей, short-circuit гейта «нет кода»), и сверь их с охраняемыми файлами — файл, чья правка в одиночку не будит джоб, в CI не охраняется, а гейт отчитается зелёным «Skipped». Гейт, красный по построению, — BLOCKER, кроме случая, когда правку предписывает общее правило плана самого документа (см. «Классификация находок»).

## Протокол на каждый claim

1. **Классифицируй** (тип выше) и выдели первоисточник, который его докажет/опровергнет.
2. **Собери ground-truth.** Для широты — fan-out `Explore`-агентов, сгруппированных по кластерам (типы; конкретный пакет; смежные доки; инфра/тесты); каждому — точные вопросы + требование цитировать `file:line` и выносить вердикт CONFIRMED/REFUTED/PARTIAL/NOT-FOUND. **Вопрос формулируй В ФАЗЕ клейма RFC** — цитируй клейм дословно и проси вердикт ИМЕННО к нему, а не независимый вопрос в противофазе: «импортируют ли конфиги X?» при клейме «НЕ импортируют» возвращает «REFUTED», означающий CONFIRMED для RFC, — инверсию знака придётся держать в голове на каждой строке сводной таблицы, и один пропущенный флип портит вердикт. Прежде чем спрашивать смежный док про «Решение N»/«О-N» — установи по тексту САМОГО RFC, чей это ярлык: документы нумеруют решения каждый у себя, и кросс-реф в скобках рядом с номером issue легко приписать не тому владельцу. Агенты должны читать **рабочее дерево текущей ветки** (read-only, без worktree-изоляции — иначе ветвление от origin/master даст аудит устаревшего кода).
3. **Несущие и неожиданные claim'ы перепроверь САМ, эмпирически** — НЕ доверяй вердикту агента на load-bearing-утверждении:
   - **TYPE/COMPILER:** напиши scratch-`.ts`, прогони `npx tsc --noEmit --strict --ignoreConfig <file>` (флаг обязателен — иначе TS5112 на найденном tsconfig; существует только в tsc ≥ 6.0. На TS5023 «Unknown compiler option» сперва проверь, ЧЕЙ tsc запущен: `npx tsc` из каталога вне репо — scratchpad! — резолвит чужой/глобальный tsc, а не то, что репо-TS стар; прогоняй из корня репо, передавая scratch-файлы абсолютными путями. Если репо-TS действительно < 6.0 — убери флаг и гони из каталога, в чьих предках нет tsconfig — это снимает и TS5112); читай, какие именно строки дали ошибку. ⚠ **`--ignoreConfig` выключает и `customConditions`**, поэтому в монорепо, где workspace-имена резолвятся условием (`@real-router/internal-source`), проба на них разваливается `TS2307: Cannot find module` — и это артефакт флага, а не факт о типах. Импортируй в scratch-файле **относительными путями к `src`** (`./src/api/index`, `./src/pipeline/materialize`) — тогда `--ignoreConfig` безвреден; передавать `--customConditions` вместе с ним бесполезно, конфликт снимается только сменой стиля импорта. (Агент может доложить результат компиляции, которой не запускал: вердикт по такому клейму даёт только твой прогон `tsc`.)
   - **regex/parsing:** прогони паттерн на реальных строках-нарушителях (`node -e`), не «на глаз». **Инвентарь regex-литералов в коде НЕ собирай грепом:** метасимволы искомой строки (`[^>]`, скобки, кванторы) + вариативность grep-бинаря (BSD/ugrep) дают молчаливую пустоту на реально существующих строках, а пустота читается как «отсутствует» (класс feedback_tool_error_not_absence). Первичный инструмент инвентаризации — детерминированный скан (node-скрипт: `fs` + `String.includes`) или `Read` файла; grep — лишь вторичное подтверждение НАЛИЧИЯ, никогда доказательство отсутствия. **Инвентарь ВЫЗОВОВ API ищи по ОКНУ строк (2–4), а не по одной** — Prettier переносит первый аргумент на свою строку, поэтому однострочный паттерн (что grep, что node-скан) систематически слеп к БОЕВЫМ сайтам и оставляет видимыми только тесты и доки, где вызов уместился в строку; «нашлось только в тестах» — почти всегда симптом этой слепоты, а не факт о коде. Это касается и **glob-расширений**: grep-verify цитаты/комментария обязан покрывать ВСЕ реальные расширения цели — `--include='*.ts'` молча пропускает `.tsx`/`.svelte.ts`/`.mts` — и вердикт «отсутствует» выносится только после `Read` конкретного файла. Node-скан сам тоже валидируй `Read`'ом — минимум один позитив и один негатив на каждое извлекаемое поле. ⚠ **Ложный ноль — не единственный исход кривого паттерна: слишком узкий класс символов даёт ложную НАХОДКУ.** `[a-zA-Z-]` без `0-9` (или `\w` без дефиса) не «не находит» сущность, а **обрезает** её имя, и она читается как несуществующая — то есть паттерн порождает находку, а не прячет её, и обычный негативный контроль этого не ловит. Прежде чем метить именованную сущность как отсутствующую, грепни её **отличительный корень**, а не полный шаблон имени. Тот же класс на уровне СЕМАНТИКИ ключа: инвентарь сущностей, собираемых **спредом** (`{ ...prev, field }`), не ловится фильтром по имени свойства ВООБЩЕ — у такого литерала свойств нет, — так что ключом обязан быть тип/конструкция, а не поле. Универсальная страховка, дешевле любого перебора ключей: прогони паттерн **негативным контролем на заведомо подходящем сайте из СОСЕДНЕГО раздела того же документа** — если известный сайт в скан не попал, паттерн неверен независимо от того, сколько он вернул. Классические артефакты: numeric separators (`30_000` → regex-обрезок «30»), совпадение токена в **комментарии** (`includes` не отличает код от комментария, объясняющего, почему фичи НЕТ: конфиг с текстом «No --expose-gc» засчитывается как имеющий флаг) и **regex-якоря**: `^`/`$` без флага `m` матчат только границы ВСЕЙ строки-файла, поэтому проверка «строка начинается с X» по `lines.join("\n")` даёт ложный НЕГАТИВ — гоняй такие regex по массиву строк либо ставь `m`; то же с `\b` — он определён на ASCII-word-символах, поэтому residue-греп по кириллице (или любому не-латинскому тексту) молча возвращает НОЛЬ при живых вхождениях. На нелатинском тексте якоря не ставь вовсе. В verify-харнессе (residue-чек после `--fix`) ложный негатив опаснее ложного позитива: он читается как «правка не применилась» и провоцирует второй, дублирующий edit.
   - **code-path:** открой функцию и протрассируй конкретный вход до точки, где решается поведение (порядок веток!). **Если пакет собран — прогони заявленное поведение напрямую вместо/поверх трассировки:** сверь свежесть dist (mtime dist новее последнего src-коммита: `stat` + `git log -1 -- <pkg>/src`), затем `node -e` + `require('<pkg>/dist/…')` на заявленном входе. **Dist протух → проба идёт на `src`, и тогда КРОСС-ПАКЕТНАЯ проба в монорепо с custom-условием (`customConditions` в tsconfig, напр. `@real-router/internal-source`) обязана гнаться `node --conditions=<условие> --import tsx` И импортировать ОБА пакета ПО ИМЕНИ, из каталога пакета, который реально от них зависит — файл пробы клади ТУДА ЖЕ.** Из scratchpad workspace-имена не резолвятся вовсе (`ERR_MODULE_NOT_FOUND` на первом же `@scope/pkg`): симлинк корневого `node_modules` выручает смок-прогон СТОРОННЕГО тула, но не workspace-пакеты. Смешение стилей — один пакет абсолютным путём к `src`, другой по имени — даёт ДВЕ копии одного модуля (второй резолвится в `dist`); симптом маскируется под баг пробы: `Invalid instance`, провал `instanceof`, пустой WeakMap-реестр, «not found in registry». Исполнение бьёт трассировку и попутно ловит соседние контракт-claims. ⚠ **Когда клейм назначает момент ВНУТРИ диспетчера** (FSM `send`, редьюсер, middleware-цепочка, edge-`update`/`action`), сперва выпиши ФАЗЫ одного вызова — условие → своп состояния → `update` → action → listeners — и определи, в какой из них стоит предписанная точка. Проза систематически сворачивает три фазы в одно слово («до анонса», «на входе в полосу», «в момент открытия»), а предикат, ложный в одной фазе, истинен в соседней: тогда обоснование дока верно ПО ВЫВОДУ и ложно ПО МЕХАНИЗМУ, и реализатор, идущий за его же рассуждением, приземляется в дефект. Пробу пиши на самом движке с мини-таблицей на два состояния — десять строк, и она бьёт любое рассуждение о порядке. **Когда клейм доказывается МУТАЦИЕЙ** (скил требует её для «эта проверка избыточна» / «этот шаг несущий»), рецепт такой: бэкап файла копией → правка → прогон → восстановление копией → сверка `md5` с `git show HEAD:<path>`. ⚠ **Мутация, симулирующая УДАЛЕНИЕ (ключа, поля, стадии), обязана быть тождественной во всём остальном.** Пересобрать объект «как было минус одно» — самая естественная реализация и самый частый брак: лишний `undefined`-ключ, изменённый порядок, потерянный прототип ломают `toStrictEqual` / `toHaveBeenCalledWith` и красят тесты, к искомому дефекту отношения не имеющие, — а ты прочтёшь их число как «контракт держат все». Признак — падают тесты, чьи ИМЕНА про другое; поэтому читай имена прежде, чем верить счётчику. И группируй падения по ТЕКСТУ ошибки: брак собственной вставки — `ReferenceError`, `SyntaxError`, `is not defined` — роняет всё подряд одной и той же ошибкой, и счётчик красных тогда меряет пробу, а не правило. Строй мутацию фильтром по существующим ключам, а не литералом. **Восстановление ставь в `trap 'cp "$BAK" "$TARGET"' EXIT` ДО первой правки, а не последней строкой скрипта:** харнесс из нескольких мутаций обрывается на любом шаге (`set -e`, таймаут, zsh, съевший неквотированный `?`/`*` в безобидном `echo`) — и обрывается ровно МЕЖДУ правкой и восстановлением, оставляя репозиторий мутированным; `git status`, снятый позже, ты прочтёшь как свои же правки. Удаление файла, который создала сама проба (прототип теста, фикстура в дереве), пиши в том же `trap` литеральным абсолютным путём: строку `trap` шелл разбирает заново, проверка безопасности харнесса переменную в ней не разрешает и отклоняет `rm` вместе со всей командой — то есть и с пробой. Никогда `git checkout -- .` / `git stash` / `git restore`: в репозитории может работать параллельная сессия, владеющая ДРУГИМИ грязными путями, и снимок `git status`, снятый в начале аудита, к моменту восстановления уже неверен. **Если предписание допускает больше одного прочтения** (записать vs выполнить, пометить vs отправить, лениво vs сразу), мутируй КАЖДОЕ и сравни исходы: типовой результат — одно прочтение падает шумно, другое проходит тир целиком, и выберет реализатор именно второе. Тихое прочтение и есть находка; шумное лишь показывает, что тесты видят половину. Severity у тихого прочтения — как у ложно-зелёного гейта, то есть BLOCKER: реализатор выберет именно его. То же — у стража (мета-теста, проверки охвата), который зелёный на форме внутри своей заявленной области, если эта форма уже встречается в репозитории или названа в самом документе: латентна защищаемая форма, а не дефект стража, — будущие формы и есть его область. Формы нет ни в репозитории, ни в документе — это УКРЕПЛЕНИЕ, а не BLOCKER (раздел «Классификация находок»). И мутируй ОБЕ стороны: «X избыточен» доказывается не только зелёным прогоном без X, но и красным прогоном без того, что его подстраховывает — иначе «избыточен» и «не покрыт тестами» неразличимы. ⚠ **Клейм «это НЕ выражено тестом / не пинится / невыразимо» — такой же claim, как «здесь баг», и проверяется тем же прогоном сьюта под мутацией, а не чтением.** Он ощущается фоновым (автор про свой код знает лучше) и потому проскакивает без проверки — а опровержение обычно меняет сам диагноз: «не пинилось никогда» и «пинилось, но распинила соседняя правка» — разные находки, и вторая сильнее. Мерь на ОБЕИХ базах, если база двигалась. **Если RFC включает собственный проверочный сниппет/гейт** (`node -e`-страж версии, валидатор, regex-чек, выданный за доказательство свойства) — он сам claim, а не инструмент: прогони его поперёк ВСЕЙ граничной полосы, которую он берётся гейтить (чуть-ниже / на / чуть-выше порога), не только на target/happy-значении. Гейт, пропускающий значение, которое заявляет отбраковывать, — ложно-зелёный BLOCKER. **Гейт, который док НЕ пишет, а НАЗЫВАЕТ митигацией** (существующий тест/линт-правило/CI-чек в колонке «как проверяется»), — тоже claim, и проверяется в два шага: (1) что он ФАКТИЧЕСКИ ассертит — читай маркеры/паттерны в теле, а не название файла, не прозу дока и не собственную шапку теста; (2) не переводит ли планируемое изменение систему в форму его **дискриминирующей мутации** — она часто прямо описана в шапке («injecting X here fails the assertion»), и планируемая правка может ЕЮ И БЫТЬ. Митигация, не касающаяся того, на чём гейт срабатывает, — no-op, и рядом с такой почти всегда лежит неназванный настоящий риск: прогони его. **Гейт, чей ПРОХОД — пустой вывод** (`diff --name-only`, `grep -c` → 0, `find`, «должен вывести ПУСТО»), самонеразличим: пустота одинаково означает «чисто» и «гейт не матчит вообще ничего», и граничная полоса тут не помогает — полосы нет. Обязателен **позитивный контроль**: прогон на входе, который гейт заведомо обязан завалить; не покраснел — сломан гейт, а не чист код. (Пример: в pathspec `'packages/*/tests/'` wildcard переключает git на сопоставление с ПОЛНЫМ путём файла, а путь на `/` не кончается, — критерий печатает «пусто» при любом числе правленых тестов.) ⚠ **То же обязательно, когда проба ОПРОВЕРГАЕТ клейм о дефекте** — «дефект не наблюдается» самонеразличимо с «проба не достигает его формы», и богатый правдоподобный вывод этого не снимает, а маскирует: прогони её на состоянии, где дефект ЗАЯВЛЕН (коммит до фикса, ветка, конфиг) — не покраснела, сломана проба, а не клейм опровергнут. **Claim о `production`-поведении, зависящий от ОПЦИОНАЛЬНОГО слоя (плагин / флаг / dev-guard), проверяй на ДЕФОЛТНОМ/минимальном конфиге, не максимальном** — он может держаться лишь с opt-in-компонентом, которого в дефолте нет. **Проба, читающая ПОТОК СОБЫТИЙ/логов, обязана зафиксировать снимок ДО своих же пост-вызовов** (диагностических navigate/cleanup-хелперов) — иначе события артефактов читаются как события испытуемого сценария; неожиданную event-находку ре-исполняй изолированной пробой без хелперов. ⚠ **Зеркальная половина: SETUP-вызовы ДО измеряемой операции тоже гоняют хуки, которые проба зарегистрировала** (`start()`, прогрев, первая навигация), поэтому хук-триггер срабатывает на ФИКСТУРЕ, а не на испытуемом, и к моменту измерения уже израсходован. Взводи триггер флагом ПОСЛЕ setup'а — **и обнуляй счётчики там же, потому что флаг закрывает только половину**: триггер, израсходованный на фикстуре, даёт ложный НЕГАТИВ, а счётчик, не сброшенный после неё, — ложный ПОЗИТИВ, и `armed` от второго не спасает. События setup'а (`start()`, прогрев, первая навигация) попадают в те же наблюдатели и читаются как события испытуемого. Симптом обратной половины — пустая трасса / не сработавший колбэк, читаемый как «эта точка входа арку не достаёт», то есть ложный негатив ровно там, где ищешь радиус. **Пробу собирай по РЕАЛЬНОЙ поверхности API, не по сниппетам аудируемого RFC** — сними exports пакета (`Object.keys(require('<pkg>'))`, `package.json#exports`) и сигнатуру фабрики с её типов/тестов ДО прогона: проба, собранная по цитатам документа, наследует его неточности и падает TypeError'ом, маскируя проверяемый клейм. ⚠ **Если проба ПОДАЁТ колбэк, который зовёт библиотека** (кодек, guard, интерцептор, фабрика плагина, декодер), его форма — параметры И возвращаемое значение — тоже часть поверхности, и снимать её надо с шипнутого теста/типа, а не с текста RFC. Отличие от неверного импорта критично: колбэк неверной формы **не бросает** — он тихо становится no-op, а «ничего не произошло» неотличимо от опровержения клейма. **`cd` в Bash-туле липкий между вызовами**, а рецепт «гони из каталога пакета» этим и создаёт ловушку: каждую пробу запускай самодостаточно (`cd <repo> && … && cd <pkg> && node …`), иначе следующая команда стартует из каталога пакета и падает `no such file or directory` на путях от корня — а команды УБОРКИ (`rm -f` пробников) под липким `cd` не падают вовсе, а тихо промахиваются мимо цели, оставляя артефакты в чужом репозитории: факт удаления подтверждай `git status`, не кодом выхода — **и сам `git status` пиши с абсолютным путём (`git -C <repo> status`)**: под липким `cd` внутри worktree он отчитается о WORKTREE, то есть верификатор унаследует ровно тот баг, который ищет, и напечатает «чисто» про другое дерево. ⚠ **Липкий `cd` в ДРУГОЙ РЕПОЗИТОРИЙ — вики, worktree, второй рабочий каталог из окружения — опаснее, чем в подкаталог: скан по относительным корням там не падает, а возвращает НОЛЬ.** Штатная защита от липкого `cd` (падение на путях от корня) здесь не срабатывает вовсе, потому что путь существует — просто пустой, — и ноль читается как «остатков нет». Признак: ноль на паттерне, который обязан что-то находить; лечение: префиксовать `cd <repo> &&` КАЖДУЮ команду и держать позитивный контроль на заведомом сайте. **Команда может провалиться так, что провал читается как РЕЗУЛЬТАТ — три повторяющихся случая.** (1) В репо с глобальным coverage-порогом одиночный файл выходит **красным по покрытию**, а не по тестам, и хвост вывода состоит из `ERROR: Coverage … does not meet global threshold`, тогда как `Tests N passed` осталось выше и в `tail` не попало — суди по строке `Tests`, либо гони с `--coverage.enabled=false`. ⚠ И зеркальный случай: **отчёт покрытия не печатается с КРАСНОГО прогона вовсе**, а прототип рефактора красен ПО ПОСТРОЕНИЮ (намеренные N падений) — значит вопрос «покроется ли новая ветка?» через coverage не отвечается в принципе, сколько раз ни перезапускай. Инструментируй ветку счётчиками, по одному на КАЖДОЕ плечо, и суди по попаданиям: это и сильнее отчёта — различает «ветка исполнена» и «исполнены ОБА плеча», чего процент не показывает. (2) В zsh **не квотированный glob-аргумент съедает шелл**: `grep -rn X --include=*.ts` падает `no matches found` и печатает ноль, что неотличимо от «в коде этого нет» — пиши `--include='*.ts'`. (3) **apply-шаг применил НОЛЬ, и следующий прогон измерил БАЗУ.** В zsh неквотированное `$VAR` в `for f in $VAR` НЕ расщепляется по словам (в отличие от bash), поэтому `cp`/`sed` получает весь список одной строкой и падает `No such file or directory` — а прогон ПОСЛЕ него печатает ровно то число, которое клейм и предсказывает, то есть провал применения маскируется под подтверждение. После ЛЮБОГО apply-шага (прототип, мутация, патч) докажи, что правка ЛЕГЛА — `grep -c` по внесённой строке — прежде чем верить прогону: зелёный тир без применённой правки неотличим от зелёного тира с ней. **Сьют пакета гоняй через workspace-фильтр (`pnpm -F <pkg> exec vitest run <файл>`), а НЕ раннером из корня с `--config <pkg>/vitest.config`:** в pnpm-монорепо корневой include видит копии тестов внутри symlinked `node_modules` (workspace-линки, worktree-копии), и прогон одного файла превращается в тысячи чужих. Симптом — вал `FAIL` с путями вида `node_modules/.pnpm/**/tests/<твой-файл>` и ошибка про ненайденный `setup.ts`; это не красный тир, а неверный запуск. **Каждый цитируемый прогон — на СВОЕЙ минимальной фикстуре.** Общая фикстура, дополненная конфигом ради соседнего клейма, — неконтролируемая переменная: лишний `defaultParams`/`defaultSearch`/опция меняет вывод и читается как REFUTED цитаты. Совпал вывод — всё равно перепроверь на минимуме, прежде чем метить расхождение. ⚠ **И для МАТРИЦЫ замеров проверь, что соседние клетки различаются РОВНО одной переменной** — читай, как проба строит каждый СТОЛБЕЦ, а не только что она напечатала. Столбец, отличающийся от соседа двумя условиями сразу (окно И форма колбэка, режим И входные данные), приписывает эффект не той оси — и дальше это читается как факт о заявленной оси: неверны и число, и причинный рассказ, а внутренняя согласованность таблицы при этом полная, поэтому дефект переживает и само-аудит. **Клейм, чьё условие — «операция ещё НЕ завершилась» (in-flight, parked, suspended), синхронной пробой не проверяется:** синхронный дубль добегает до конца внутри того же тика и попадает в СОСЕДНЮЮ клетку, где поведение часто обратное, — то есть даёт ложный REFUTED живой находки. «В полёте» воспроизводится только удержанием (async-guard на промисе-воротах, parked-интерцептор, незавершённый `await`), и ЧЕМ именно удерживаешь — назови до прогона. **Проба через optional chaining (`?.`) неразличима на ДВУХ исходах** — «метода нет» и «результат пуст» оба дают `undefined`. Прежде чем трактовать `undefined` как ЗНАЧЕНИЕ клейма, докажи, что вызов вообще состоялся: позитивный контроль на заведомо валидном входе либо чтение тела функции. **Тот же класс на уровне СЛОЁВ: публичный примитив с именем внутренней стадии часто её КОМПОЗИЦИЯ.** Замеряя выход стадии, которую RFC называет по имени, сперва прочитай, что стоит между примитивом и стадией: обёртка может дописывать ровно ту нормализацию, чьё отсутствие ты проверяешь, и «гипотеза не подтвердилась» окажется замером не того слоя. **Клейм «тест X покрывает Y» проверяется ДО EOF, а не по верхнему docblock'у файла.** Хедер описывает ПЕРВЫЙ блок, а не файл: тир, дописанный вторым, регулярно противоречит собственному хедеру — и противоречие читается как REFUTED. Перечисли `describe`/`test.prop`-блоки скриптом либо дочитай файл; «в хедере сказано, что покрыт один кейс» — не доказательство, что покрыт один кейс.
   - **Расхождение оракулов (IDE/tsserver/линтер vs сборка/прогон):** прав тот инструмент, который ИСПОЛНЯЕТ заявленный контракт — «builds green» доказывается сборкой (+ артефакт, дошедший до bundle/dist), не отсутствием IDE-подчёркиваний, и наоборот; второй оракул фиксируй в отчёте как residual-шум, не как вердикт — особенно если репо УЖЕ документирует свой IDE-шум как ложный.
   - **Claim о сложности/инкрементальности — проверяй на ДВУХ уровнях: примитив И системный вызывающий путь.** Инкрементальный/O(1) примитив пакета не доказывает инкрементальность фичи — интеграция может сводить его к полному ребилду; трассируй от публичного API вниз до примитива.
   - **CROSS-REF (внутренний):** `grep`-ни цитируемый файл на цитируемый заголовок/секцию — резолвится ли. Не резолвится, а репо недавно пережил реорганизацию (merge/rename/split пакетов)? Прежде чем выносить NOT-FOUND, проверь предка реорганизации (`git show <merge-commit>^:<старый-путь>`): ссылка может быть валидной на файл, потерянный при реорганизации — это ДВОЙНАЯ находка (STALE-CITATION у дока + потерянный артефакт у самой реорганизации, отдельный репорт владельцу), а не битая цитата. Зеркальный случай — артефакт из БУДУЩЕГО: несущий CODE-FACT о «только что сделанном» изменении не находится в рабочем дереве → прежде чем REFUTED, проверь несмёрженные ветки/worktree (`git log --all --grep`, `git branch -a --contains`): RFC мог писаться в сессии с параллельной веткой — тогда валидируй claim по той ветке и фиксируй в отчёте порядковую зависимость мержей, а не ошибку.
   - **EXTERNAL/THIRD-PARTY:** проверь в первоисточнике ПРОДУКТА, по убыванию силы: (1) **установленный инструмент** → запусти его (`<tool> --help`, реальный прогон/вывод — сильнейшее); в pnpm-монорепо пакет может быть НЕ виден из корня (строгая изоляция: dep только у workspace-консьюмера) — `require` по имени падает MODULE_NOT_FOUND, что НЕ значит «не установлен»: резолвь через `node_modules/.pnpm/<pkg>@*/node_modules/<pkg>`, каталог консьюмера (`benchmarks/node_modules/…`), а смок-прогон стороннего тула в scratchpad получает резолюцию симлинком корневого `node_modules` репо в каталог смока; для **существования/версии npm-пакета — `npm view <pkg> version`** (registry-факт; `npmjs.com` часто 403'ит WebFetch, а `E404` = пакета нет — валидное доказательство ОТСУТСТВИЯ, сильнее «я не нашёл»); **для статуса github-issue `/issues/N` (через API) НЕДОСТАТОЧЕН** — `state_reason: "completed"` бывает административным закрытием БЕЗ code-fix; cross-check `/issues/N/timeline` (есть ли merged-PR / release-tag у close-события) + `npm view <pkg> version` (вышел ли релиз с фиксом). `closed` ≠ resolved-in-code; один эндпоинт ведёт в обе стороны (closed-as-fixed ↔ still-broken). (2) **context7** (`resolve-library-id` → `query-docs`) для актуальных доков библиотеки/CLI/сервиса; (3) **офиц. доки** через `WebFetch`; (4) `WebSearch`. Для load-bearing — cross-check ≥2 источника. ⚠ **WebFetch отдаёт пересказ страницы малой моделью, а не её текст:** «на странице этого нет» от него — не доказательство отсутствия; дословную цитату проверяй сырым HTML (`curl -sL <url> | rg -o '.{0,80}<фраза>.{0,80}'`), а страницу, которую рисует скрипт и в сыром HTML текста нет, помечай ASSUMPTION. Память НЕ источник. Не проверяемо (платное/закрытое/нерелизнутое API) → пометь **ASSUMPTION**, не утверждай. **Когда RFC даёт shell-команду, чтобы ДОБЫТЬ значение для конфиг-поля/токена** (хэш/id для вставки в `packageManager`, lockfile, `.npmrc`) — прогони её и сверь **формат вывода** (кодировку/алгоритм/длину) с форматом ЦЕЛЕВОГО поля, не только корректность значения: правильное значение в неправильной кодировке тихо ломает шаг и проваливает его же цель. (Пример: `npm view … dist.integrity` отдаёт `sha512-<base64>`, а поле `packageManager` требует `+sha512.<hex>`; `dist.shasum` — вовсе sha1.) **Клейм НЕВОЗМОЖНОСТИ о тулинге** («одной аннотацией нельзя», «единственная рабочая форма — Y», «тег не прикрепляется») проверяется перебором синтаксических ПОЗИЦИЙ, а не проверкой одной названной формы: у аннотации их минимум три — над объявлением, над инструкцией и на СПЕЦИФИКАТОРЕ внутри скобок, — и опровергает клейм обычно та, которую док не рассматривал. Проверять надо оба оракула, компилятор и линтер: правило может расходиться с диагностикой TS. **Прогон CI/бенча в статусе `in_progress` — это ОТЛОЖЕННЫЙ первоисточник, а не недоступный.** Сними его ещё раз ПЕРЕД записью вердикта: структурный вывод «почему джоба упадёт» и её лог — разные уровни доказательства, а ждать обычно нечего, кроме собственного отчёта.
   - **COUNT:** `ls`/`grep` и пересчитай. ⚠ **Прежде чем вынести REFUTED по СЧЁТУ или ПОРЯДКОВОМУ номеру — и тем более поправить его по первоисточнику, — проверь, не согласован ли он ВНУТРИ дока под его собственным разбиением.** Если да — это расхождение разбиения, а не ошибка счёта: в отчёте — сноска, а при `--fix` сохраняй нумерацию дока и выноси расхождение сноской: переписывание «как в источнике» ломает соседние предложения, которые на этот счёт опираются, и создаёт новое противоречие вместо снятого.
   - **PERF/EMPIRICAL:** прогони реальную команду и засеки (`time`, turbo `--dry=json`/`--summarize`, `.turbo/runs/*.json`); порог — откалибруй по реальной истории (`gh pr list` + `git diff`/turbo affected на последних N PR — распределение, не одна точка); скрипт-эскиз — прогони на реальных сценариях (его вывод = функциональный unit-тест без обвязки). Если репо ведёт трекаемый perf-ledger — бенч-клеймы сверяй с ним, ища сценарий по синонимам: имя в RFC может не совпадать с именем в ledger, и пустой grep по RFC-имени ≠ отсутствие данных. **Число из harness'а и число из документа могут быть в РАЗНЫХ ЕДИНИЦАХ**, и нормализатор живёт в коде бенча, а не в его выводе: раннеры печатают агрегат (латентность на батч, на итерацию, ops/s), а док цитирует стоимость одной операции. Прочитай сайт (`batched(N, …)`, `iterations`, `time`, `batch:`) ПРЕЖДЕ чем сравнивать — расхождение на порядки почти всегда единица измерения, а не находка. **Агрегат НЕ проверяет экстремум.** Когда док даёт и сводные числа по набору (среднее, число сверх порога, размер набора), и НАЗВАННОГО чемпиона по тому же набору, сверка агрегата не доказывает имя: среднее инвариантно к тому, какой член максимален, поэтому сошедшийся агрегат активно МАСКИРУЕТ мис-атрибуцию экстремума. Пересчитывай экстремум отдельно, поэлементно. Типовая подмена — «худший» прочитан как «самый дорогой по абсолюту», а не «с наибольшей дельтой». **Сперва ищи СЫРЫЕ по-прогонные записи**, названные приложением дока (`*-results.jsonl`, логи прогонов, `summary.json`), и переагрегируй их сам: совпадение медиан доказывает числа дешевле и надёжнее ре-замера, а **число строк** доказывает заявленный размер выборки — величину, которую агрегат прячет полностью. Если замер ПРИНЦИПИАЛЬНО недоступен (нужен CI-hardware / прод-трафик) — пометь claim как **ASSUMPTION** и вынеси, что решение висит на неизмеренном числе; НЕ выдавай оценку за факт. ⚠ **Дыра охвата, найденная замером** (файл вне входов кеша, тест вне шарда, проверка вне стадии), — гипотеза, пока не перечислены ВСЕ исполнители этого файла: репозиторий часто гоняет его вторым путём — отдельным сканом, стадией хука, своим джобом.
   - **Exit-код пробы снимай с самой команды, не через пайп** (`cmd; echo $?` или массив статусов пайпа: в zsh `$pipestatus`, в bash `PIPESTATUS` — в zsh `PIPESTATUS` пуст) — пайп возвращает статус ПОСЛЕДНЕЙ стадии, и зелёный хвост (парсер/`jq`/`head`) маскирует красную пробу. Вердикт — по наблюдаемому выводу пробы; exit-код лишь сверка. Для **async-пробника** (node async-IIFE) `exit=0` вдобавок ≠ «дошёл до конца»: невыполненный `await` при опустевшем event loop даёт молчаливый exit 0 и срезает хвостовые кейсы — печатай маркер-строку на КАЖДЫЙ кейс и суди по напечатанным маркерам, не по коду выхода. Альтернатива IIFE — **top-level `await`, но у `tsx` он требует расширения `.mts`**: на `.ts` внутри CJS-пакета esbuild падает «Top-level await is not supported with the cjs output format». И **не режь вывод пробы `tail`/`head`** — маркеры теряются молча ровно так же, как при раннем exit; печатай компактно и читай целиком. Не режь и листинг, по которому судишь об отсутствии файла: отсутствие доказывает `ls`/`find` по точному имени, а не обрезанный список каталога. **Тот же класс — у ВОЗВРАТА API, чей документированный отказ есть логируемый no-op:** успех и отказ возвращают одно и то же (часто `void`/`undefined`), поэтому колонка вердикта, снятая с возврата, самонеразличима. Снимай вердикт с СОСТОЯНИЯ, которое операция обязана была изменить (членство в дереве/реестре, `getState()`, счётчик), плюс позитивный контроль на заведомо проходящем входе. ⚠ **Отдельный слепой наблюдаемый — ПОРЯДОК событий.** Счётные пины (`toHaveBeenCalledTimes`), матрицы клеток и проверки исхода инвариантны к перестановке эмитов, поэтому инверсия вида «терминальное событие раньше стартового» проходит весь тир, не покраснев ни разу. Если правка двигает ТОЧКУ эмита (а не его наличие), снимай СПИСОК событий — наблюдатель, взведённый флагом после setup, — и сравнивай с базой; количество тут не различает ничего. ⚠ **А КАНАЛ инструментирования выбирай раньше, чем наблюдаемое: `console.*` внутри тестового прогона самонеразличим — `setup`-файл пакета может глушить консоль (`console.log/warn/error = () => {}`), и проба печатает ноль попаданий при заведомо исполняемом коде.** Перед первым выводом грепни setup на переопределение `console`; надёжнее вообще не консоль, а побочный эффект, который setup перехватить не может — `fs.appendFileSync` в файл (он же переживает воркеры vitest, тогда как счётчик на `globalThis` живёт по воркеру), — либо наблюдаемое уровнем выше по правилу абзацем раньше: список событий, счётчик вызовов, состояние. ⚠ **Проба, чей наблюдаемый пишется ВРЕМЕННОЙ инструментацией (счётчик в `globalThis`, зонд в чужом файле), не самодостаточна — и её повторный прогон печатает «ничего не произошло».** Инструментацию снимает `trap`, а проба остаётся и молча возвращает нулевое значение, неотличимое от опровержения. Поэтому такая проба обязана падать ГРОМКО, когда её счётчика нет (`if (hits() === undefined) throw`), а документ — записывать рядом с числом, какая правка какого файла его произвела. Иначе следующий прогон отзовёт верный замер как «незначимый», и отзыв попадёт в документ рядом с таблицей, на которой держится вывод раздела.
   - **Чистота рабочего дерева для git-diff/affected-проб (скил read-only → одноразовый worktree).** Инструменты, считающие affected по git (`turbo affected`/`turbo query affected`/`nx affected`/`--filter='...[ref]'`/`lint-staged`), **сворачивают незакоммиченные правки рабочей копии в результат** — грязное дерево даёт ложный affected (твои правки читаются как «затронуто»). Гоняй такую пробу в **detached-worktree на нужном ref** (`git worktree add --detach <scratch> <ref>` → прогон → `git worktree remove`; turbo-бинарь из основного репо через `--cwd`/`--skip-infer`), удаляемом в конце — скил ничего не пишет в репо, worktree безопасно сносится. Сначала `git status`; дерево грязное и проба про affected → worktree обязателен. **Дерево на ref — тот же worktree или копия `git archive` (какую брать — п. 1 «Режима `--delta`») — единственный способ атрибутировать РЕГРЕССИЮ конкретному коммиту (BASE↔HEAD), и там есть своя ловушка: в таком дереве нет `node_modules`**, поэтому `--import tsx` падает `ERR_MODULE_NOT_FOUND` ещё до пробы. Симлинкуй корневой `node_modules` основного репо внутрь дерева (он даёт лишь раннер), а испытуемый пакет импортируй **относительным путём ИЗ дерева** — по workspace-имени резолюция уведёт в HEAD-копию, обе стороны сравнения станут одинаковыми, и регрессия «не воспроизведётся». Приписав дельту к ref'у, сузь её до ОДНОГО коммита вторым деревом на подозреваемом. ⚠ **Симлинк `node_modules` годится под `node` и `npx vitest`, но не под pnpm**: `pnpm <скрипт>` и `pnpm exec` в pnpm 12 перед запуском сверяют установку и при расхождении ставят её — через симлинк, то есть в `node_modules` ОСНОВНОГО чекаута, чьё состояние после этого указывает на worktree. Ловушка в том, что pnpm зовёт не только твоя команда: CLI под тестом и скрипт, который тест запускает, тоже, а тест, урезающий окружение до `PATH` и `HOME`, теряет переменные, которыми ты установку отключил. Если сьют может позвать pnpm — в worktree настоящий `HUSKY=0 pnpm install --frozen-lockfile --offline` (на ref, чей `prepare` ещё зовёт husky, установка без `HUSKY=0` переключает хуки всех worktree), а не симлинк, и `ps` до и после: нет ли чужих pnpm и turbo в основном чекауте. **Отдельно — АТРИБУЦИЯ БАЗЫ: прежде чем выносить вердикт, сними `git log master..HEAD` и `HEAD..master`.** Если несущий REFUTED опирается на код с **незамерженной** ветки — это не «клейм устарел», а «клейм устареет при мерже», и проверять обязан ОБЕ стороны (`git show <base>:<path>`), а отчёт — называть ref, на котором клейм опровергнут. Для RFC, запланированного ПОСЛЕ чужого PR, базой аудита является ветка того PR, а не `master`; иначе прототип-гейт/приёмка документа замеряют состояние, которого к моменту работы уже не будет. ⚠ **Рой read-only агентов и твои собственные мутации дерева НЕСОВМЕСТИМЫ, и это отдельный класс от грязного дерева на старте.** Пока агенты сканируют рабочую копию, любая твоя проба-мутация (прототип, мутационная валидация, apply-шаг) делает их вердикты недостоверными — а распознать это по отчёту нельзя: ложный REFUTED выглядит как находка, потому что агент честно цитирует `file:line` того, что видел. Лечится одним из трёх: свои пробы в одноразовой копии дерева; либо все мутации ПОСЛЕ возврата всех агентов; либо в промпте КАЖДОГО агента предписать сверку через `git show <база>:<путь>`, а не чтение рабочей копии. ⚠ **База двигается и ВПЕРЁД — прямо во время прогона, и это отдельный класс от незамерженной ветки.** Документ, содержащий выполнимую рекомендацию, провоцирует автора выполнить её, пока ты меришь: снимок `git log <база документа>..HEAD` на СТАРТЕ пуст, а к моменту вердикта — нет. Поэтому пере-снимай его перед каждым эмпирическим вердиктом, а не однажды. Симптом ни с чем не спутать: измеренное число БОЛЬШЕ документного, и **знаменатель прогона выдаёт виновника точнее любых дат** — расхождение в единицы тестов равно размеру свежего тест-коммита. Лечится не переизмерением и не «клейм устарел», а возвратом К БАЗЕ: одноразовая копия дерева на базе либо, если дельта — один-два файла, `git show <база>:<путь>` поверх них на время прогона (с `trap`-восстановлением). Вердикт после этого атрибутируется обеим точкам.
   - **Hardware-bound vs hardware-invariant — ключевое различие, не путать.** _Логика/структура_ (классификация, routing-решение, граф affected, счётчики) — hardware-**инвариантна**: локальный прогон = истина и для CI, переносится 1:1. _Тайминги_ — hardware-**bound**: локальная абсолютная цифра на CI-цель НЕ переносится, и сравнивать её с CI-оценкой дока **нельзя** (apples/oranges → не пиши «REFUTED» из локального замера CI-числа). Переносится лишь **отношение**, и только когда обе величины упираются в ОДИН ресурс (CPU/CPU — `angular` vs `preact` bundle: да; CPU/IO — dry-run-операция vs checkout+install: нет, разные узкие места). Абсолютный CI-таргет (`≤Xs`) меряется ТОЛЬКО на CI-железе — иначе ASSUMPTION. Прежде чем мерить тайминг локально, спроси: «это про скорость (hardware-bound → нужен CI или same-bottleneck ratio) или про корректность (hardware-invariant → локально достаточно)?».
4. **Раздели «claim технически верен как сформулирован» и «вывод держится».** Посылка может быть верна при неверном выводе — и наоборот (верный вывод на слегка кривой цитате).
5. **Для DESIGN-DECISION — охота за непропагированными копиями.** `grep`-ни сигнатурные строки старого решения по всему документу; каждое вхождение, противоречащее принятому решению — находка. Решение в прозе ≠ решение в алгоритме: если псевдокод не enforce-ит решение, реализация воспроизведёт баг, против которого решение и принято. **Отдельный подкласс — САМО-РАЗОРУЖАЮЩЕЕСЯ условие: правило, которое док написал о собственном будущем** («если к моменту X случится Y — это слагаемое отпадает», «проверить перед написанием, а не унаследовать»). Это клейм с триггером, и проверка триггера — работа аудита, а не автора: сработавший и не отражённый триггер = находка того же класса, что непропагированное решение. ⚠ Но заслуга принадлежит ДОКУ — фиксируй, что он предсказал развилку, вместо того чтобы подавать сработавшее условие как небрежность; иначе аудит наказывает ровно ту дисциплину, которой сам требует.

## Классификация находок (severity)

- **BLOCKER** — реализация по документу даст неверный код / ложно-зелёный тест / воспроизведёт описанный баг (непропагированное решение в алгоритме; ordering-баг в псевдокоде; инвариант, противоречащий другому решению; внутреннее противоречие в контракте/представлении данных).
- **SHOULD-FIX** — не ломает реализацию, но недоспецифицировано/вводит в заблуждение (over-promise механизма; недоопределённая область инварианта; неозвученный trade-off; решение, не перенесённое в DoD или обзорный раздел, когда шаг плана описывает его полностью).
- **MINOR** — цитата/факт/счётчик мимо при верном по сути выводе; редундантный инвариант; формулировка.
- **УКРЕПЛЕНИЕ** — правило, критерий или страж документа можно усилить против формы входа, которой нет ни в репозитории, ни в тексте документа: сегодня страж ничего не пропускает, а форма — гипотеза. Это не SHOULD-FIX и не повод переписывать тело: в отчёте — отдельным списком, у каждого пункта шаг плана и клетка его теста (вход → ожидаемый исход), а если клетку не на чем исполнить — строка принятого разрыва. Нового раунда сверки не требует. «Форма» — синтаксическая форма входа, которую страж пропускает, а не проявившееся расхождение: если запись этой формы уже лежит в источнике или названа в документе, это латентный дефект стража (правило о страже в п. 3 протокола), даже когда на сегодняшнем дереве расхождение не проявляется. Отсутствие формы доказывай сканом с позитивным контролем, а не памятью. Правка каждой такой формы в теле добавляет текст, и в нём следующий раунд находит большую часть своих SHOULD-FIX и MINOR. Тот же класс — дыра, поданная как over-promise. Over-promise — это когда документ заявляет, что проверка ПОКРЫВАЕТ форму; «заявленная область» стража — то, что о нём говорит документ. Если он говорит лишь, что проверка исполняет X, а дефектная форма лежит вне X (во входе, который X получает готовым), это непокрытое — УКРЕПЛЕНИЕ клеткой или строкой принятого разрыва. (Например: тест исполняет фрагмент, но не `env:`, дающий ему значения.)
- ⚠ **Severity класса, уже оценённого прошлым отчётом этого документа, сверяй с той оценкой**, а расхождение объясняй в строке находки: без этой сверки один и тот же класс получает в соседних раундах разные оценки.

Каждая находка: тип claim'а + `file:line` доказательства из ground-truth + **исправление ИЛИ критерий — по одному признаку: следует ли исправление из первоисточника однозначно.** Следует — пиши верное значение (якорь, счёт, формулировку, уже принятое решение для пропагации): это факт, а не предложение, и на нём работает `--fix`. Не следует — это вопрос владельцу, и решения аудит НЕ предлагает: вместо него **критерий приёмки** — что должно стать истинным после любого исправления — и проба, которая это проверит. Решение, предложенное аудитом, пишется в конце прогона, на остатке бюджета, и проверено обычно по одному свойству, без разбора альтернатив, а несёт печать «проверено» и задаёт направление отдельному разбору, на который владелец отдаёт находку: разбор начинает с проверки чужого варианта, а не с вопроса. ⚠ **Severity и форма исправления — разные оси.** Severity говорит, что даст реализация по документу, а «исправление или критерий» — кто и как правит; гейт, красный по построению, остаётся BLOCKER и тогда, когда правка — одна строка, однозначно следующая из соседнего раздела. ⚠ **Исключение — правка, которую предписывает общее правило плана.** Если документ содержит правило, обязывающее каждый шаг сделать правку этого рода — перевести читателей поверхности, фикстуры и CONTROL итоговой строки, обновить ledger, — а гейт краснеет громко, экземпляр идёт в SHOULD-FIX: реализатор встретит красный гейт на своём шаге, и правило скажет ему, что делать. Проверяй тогда не экземпляр, а правило: покрывает ли оно класс целиком. BLOCKER остаётся за тихим дефектом — гейт зеленеет вхолостую, тест ложно-зелёный, неверный код без сигнала — и за громким, правку которого не предписывает ни одно правило документа или которая требует решения. ⚠ **Находка, у которой есть класс, несёт перепись всех его членов** — сканом с позитивным контролем на каждую форму, приложенным к отчёту, — и критерий требует свойства от каждого члена переписи, а не от найденного экземпляра. ⚠ **Критерий — свойство на ЗАКРЫТОЙ области, и его атакуют до передачи.** Автор реализует критерий дословно и проверяет правку ровно по его клеткам, поэтому дыра критерия становится находкой следующей сверки. Список мутаций — не критерий, а его проба: формулируй, что должно держаться для ВСЕХ входов области, и прогони свойство на контрпримерах до записи (правило «всё, что сочинил сам», раздел «Починка»). Если область открыта — события GitHub, семантика выражений, произвольные формы кода, — критерий требует её закрыть: «вне явного перечня — красное» (fail-closed), а не добавляет очередной случай; находки одного стража сводятся в одну с таким критерием. ⚠ **Критерий над синтаксисом чужого языка — выражения GitHub, YAML, глобы, TOML — задавай по разборщику ПРОДУКТА, его исходнику или CLI, а не по видимой форме текста,** и атакуй формами, на которых форма и разбор расходятся. Лучше всего — критерий, которому разбор не нужен вовсе: равенство с закреплённым текстом, перечень вместо классификации, исполнение вместо чтения. (Пример: критерий «одна обёртка `${{ }}` на всё значение» пропускает `if: ${{ A }} && B }}` — раннер GitHub заканчивает выражение на первом `}}`, и такое `if:` всегда истинно, а actionlint молчит.)

## Починка (только при `--fix`)

Правится МЕХАНИЧЕСКОЕ и однозначное:

- фактические исправления (неверная сигнатура/счётчик/цитата → верная, подтверждённая ground-truth);
- пропагация уже-ПРИНЯТОГО решения во все таблицы/псевдокод/DoD/сводку (+ `grep`-доказательство нулевого остатка старой формулировки);
- снятие противоречия, когда корректная резолюция однозначна (одна сторона уже канонизирована решением) — **либо когда однозначной её делает РЕ-ЗАМЕР**: числовое расхождение между двумя ячейками ОДНОГО документа мерить дешевле, чем выносить владельцу, и по букве «одна сторона канонизирована» такой случай ушёл бы к автору зря. ⚠ Не предполагай, что таблица каноничнее прозы;
- ordering-фиксы в псевдокоде, восстанавливающие заявленную семантику.

При правке псевдокода **читай его как исполнение** — наивная вставка может оказаться мёртвым кодом: проверка, поставленная после другой, которая уже ловит тот же вход, недостижима — переупорядочь проверки или сузь раннюю.

⚠ **Всё, что ты САМ сочинил, — тоже claim, и планка для него ВЫШЕ, а не ниже, чем для клеймов дока.** Аудит валидирует чужие утверждения — но `--fix` и критерии приёмки вносят в документ и отчёт ТВОИ: «правильную» формулировку взамен опровергнутой, пропагированное решение, критерий — инвариант, property или поведение, которому обязано удовлетворять любое исправление. Для доковых клеймов ты ищешь подтверждение первоисточником; для своих — **ищи КОНТР-ПРИМЕР, и найди его ДО записи в документ**, а не после. Минимум: (1) для property — прогони её кодом (мысленно — только если исполнить не на чем) на входах, которые док объявляет РАЗНЫМИ по дизайну; property, включающая намеренно-различающиеся точки, ложно-красная (тот же дефект, что у критерия «эквивалентность текущему поведению» на баг-грани, п. 8 классификации утверждений); (2) для критерия, задающего поведение, — построй самый ЧАСТЫЙ сценарий фичи, а не тот, из которого родилась находка, и проверь, что критерий его не запрещает; (3) вердикт формулируй как «выжило под атакой», а не «выглядит верно»; (4) мутант, клетку или проверку, которые правка или критерий вписывает в документ, прогони до записи в двух прочтениях и при снятом правиле: мутация, красная и без правила, ничего не доказывает и в документ не идёт. Записанные без этого правка или критерий — новый ложный клейм внутри аудируемого документа, ровно того класса, который аудит ищет, и он опаснее исходного дефекта: он несёт печать «проверено аудитом».

НЕ правится автоматически: выбор IN/OUT фичи, смена архитектуры, переименование API — любой вопрос, требующий решения автора → выносится в отчёт как открытый, с критерием приёмки и без предложенного решения. Укрепление `--fix` тоже не вносит: клетка теста или строка разрыва — выбор владельца, а описание правила в теле ради укрепления не расширяется. Исправление и укрепление не добавляют в тело и перечней форм: документ называет тест-авторитет, а форма входит в тест клеткой и поштучно не описывается ни в теле, ни в приложении. Перечень форм в документе — храповик: по правилу о страже каждая названная форма делает пробел соседнего стража BLOCKER.

⚠ **Пакетное переанкерирование гони ТОЛЬКО ПО ТЕЛУ, исключив журнал ревизий.** В журнале старые номера строк — **провенанс** прошлых прогонов (записи вида «`:708,750,794,836`→`:743,…`»), а не остаток: замена по всему файлу переписывает историю в фикцию, причём молча и необратимо. Режь файл по заголовку журнала ДО замены. Тем же разрезом классифицируй residue-чек (body / journal) — иначе легитимные journal-вхождения читаются как непропагированный остаток и провоцируют вторую, разрушительную правку.

Подними ревизию в шапке + добавь запись в журнал ревизий (что и почему). **Запись в журнал — последним шагом, после residue-чека, и каждый заявленный в ней фикс подтверди грепом.** Журнал, перечисляющий не применённую правку, — новый ложный клейм внутри аудируемого документа, т.е. ровно тот дефект, который аудит ищет. ⚠ И после вставки проверь ПОРЯДОК строк (`grep -n` по номеру ревизии): якорем служит предыдущая запись, а в журнале, отсортированном по возрастанию, она ПОСЛЕДНЯЯ — значит наивная вставка «перед якорем» ставит новую ревизию не в конец, а между предпоследней и последней. ⚠ **И пере-сними журнал НЕПОСРЕДСТВЕННО перед вставкой, а не по снимку начала прогона: аудируемый документ мог измениться под тобой.** Правило «сверь fingerprint» ниже (Оговорки) написано про ЧУЖИЕ ground-truth файлы; тот же риск есть у самого правимого дока, и цена другая — не устаревшая цитата, а **коллизия номера ревизии**: владелец заводит свою запись параллельно, ты вставляешь свою с тем же номером, и `grep -n` по номеру покажет ДВЕ строки «6». Проверять надо не только порядок, но и уникальность. Номер ревизии и хвост журнала снимай и ДО начала правок: ревизия, которую назвал владелец, может уже быть сделана параллельной сессией, и тогда правка дублирует чужую работу или ложится поверх неё.

## Режим `--delta` (сверка правок)

Правка, закрывающая находку, систематически повторяет её класс, а её автор проверяет ту форму, которую закрывал. Поэтому дельту аудирует не автор.

1. **Независимый агент без контекста автора** — документ, дифф `<база>` → текущий и репозиторий. Своих подозрений автор ему не передаёт, чтобы не задать направление, — и готовых команд проб тоже: команда из записки об окружении становится формой пробы. Нейтральный перечень правок — ревизии, затронутые разделы, решения владельца — передавать можно: он очерчивает дельту и направления не задаёт. Отчёт агент возвращает текстом (субагент не пишет файлы отчёта) — по шкале раздела «Классификация находок» и в форме раздела «Валидация и отчёт», с ревизией, которая внесла каждую находку. Эксперименты ставит только в копиях дерева, а вывод каждой пробы пишет в новый файл: файл прошлого прогона с тем же именем выдаёт старый результат за новый. Копия для пробы, которой не нужны ни история git, ни pnpm, — не worktree, а `git archive <ref> | tar -x -C <scratch>` (при нужде — свой `git init`): она ничего не пишет в `.git` основного чекаута. Worktree — когда проба читает историю или зовёт pnpm, и под pnpm — с настоящей установкой (п. 3 протокола, «Чистота рабочего дерева»). Кеши уровня пользователя (`~/.cache/uv`, store pnpm) — такое же общее состояние, как рабочее дерево: пробы идут с изолированным кешем (`UV_CACHE_DIR` в scratch), а состояние кеша машины снимается листингом — проба в кеш по умолчанию меняет то самое предусловие гейта, которое проверяется. **База — это копия, а не номер ревизии.** Каждый прогон `/audit-rfc`, полный или сверка, первым шагом сохраняет копию аудируемой версии и называет в отчёте её путь, md5 и размер: она — база следующей сверки, а gitignored-документ git не восстановит. Копию клади рядом с документом — в его `archive/` или каталог, — а не в каталог job: тот удаляется вместе с job, и база пропадает к следующей сверке. Копии нет — база собирается из вывода чтений прошлого прогона (Read-чанки по номерам строк в его транскрипте) и принимается только при совпадении md5 и размера с замером того прогона: Read показывает завершающий перевод строки отдельной пустой строкой, и склейка «как прочитано» даёт лишний байт. Названная база совпадает с текущей версией — дельта пуста, а не «проверять нечего»: базой берётся последняя ПРОВЕРЕННАЯ копия (её md5 назван в прошлом отчёте), отчёт говорит, от какой базы шёл, а без проверенной копии это полный аудит, а не сверка. Перед запуском агентов из их рабочего каталога убираются артефакты прошлых прогонов — вердикт, пробы, бэкапы: запрет «не читай» слабее отсутствия файла.
2. **Линзы дельты:** каждое новое утверждение — против первоисточника; правка, закрывающая находку новым стражем — читателем, держателем, сверкой, закрытым перечнем, — это новый claim со своей областью входов: перечисли, какие входы он видит и какие формы этих входов есть в репозитории и документе, и атакуй его в этой же сверке; шаги плана — как PLAN-STEP/GATE; правило-преемник шире или уже того, что старое правило реально проверяет в коде; проверка, которая не может не пройти (обязательное поле как «причина», пустой набор правил); инструмент, который правка вызывает по-новому (готовый режим, флаг, список файлов), — прогоном на пустом входе и на пути из его же исключений: там прячутся значения по умолчанию; а если вызов стоит в строгом пути — и с отрезанной сетью (`HTTPS_PROXY` на закрытый порт): там прячется загрузка, которой в этом пути быть не должно. Но режь только эту сеть и зови инструмент в той форме, в какой его зовёт скрипт, — и назови состояние кешей со сроком жизни: без сети исход решает возраст HTTP-кеша установщика. У `uvx` ответы индекса PyPI живут 600 с: в этом окне после прогона с сетью он проходит и без сети, позже падает с кодом 2. Детерминированных по времени состояний два — пустой кеш (у uv — `UV_NO_CACHE=1`) и офлайн-режим (`UV_OFFLINE=1`); ими, а не прокси, задавай ячейку гейта, а ячейку, зависящую от такого кеша, гоняй по обе стороны окна. Содержимое кеша офлайн-режим не фиксирует: исход задаёт форма прогона, который кеш заполнил (пины, `--exclude-newer`, `--with`), поэтому ячейку с офлайн-режимом гоняй на двух кешах — заполненном формой гейта и заполненном повседневным путём (например, хуком без пинов); утверждение «выводится» или «проверяется тестом» — против того, лежат ли все его входы в репозитории: ruleset, настройки и секреты GitHub тест не видит; отвергнутый владельцем вариант, возвращающийся через значение по умолчанию; новые решения против ПОСЫЛОК прежних решений того же документа — принятые по очереди, они сверяются и друг с другом, а правила одной ревизии — кодированием их как ограничений и прогоном по настоящим файлам: так видно противоречие двух правок, которое чтение пропускает; числа в тексте — под новыми правилами самого документа; нетронутые разделы (TL;DR, примеры модели, DoD, риски, самокритика) против дельты; соседние документы; декларация, на которую опирается другой шаг, — против исполнения.
3. **Отчёт агента — гипотеза.** Несущие и неожиданные утверждения автор перепроверяет сам, прежде чем править; механическое — по правилам `--fix`, выбор — владельцу, по одному.
4. **Повторять после каждой серии правок**, пока сверка находит BLOCKER. Сверка без BLOCKER — конец цикла, как и в п. 0 `/implement-rfc`: правки по её находкам, SHOULD-FIX в том числе, нового раунда не требуют, и отчёт так и пишет — «сверки сошлись»; новая сверка — только если после неё внесено что-то сверх находок. Находки делятся на внесённые дельтой и старые — текст старше базы и сдвиг внешнего мира: старые идут отдельным списком и нового раунда сверки не требуют, но старый BLOCKER блокирует свой шаг так же, как новый. MINOR и УКРЕПЛЕНИЕ нового раунда не требуют: MINOR правят в шаге внедрения, который он затрагивает, а укрепление входит в этот шаг клеткой теста или строкой разрыва. Готовность — по шагам плана: шаг, которого не касается ни один открытый BLOCKER — ни через его гейты, ни через шаги, на которые он опирается, — идёт в `/implement-rfc`, не дожидаясь остальных. Когда все шаги плана внедрены, BLOCKER шага закрывается кодом, клеткой, исполняющей его критерий, и прогоном критерия — без нового раунда; находки о журнале, приложении внедрения, статусе и датированных снимках идут в отчёт списком и новой ревизии тела не требуют, а следующая сверка нужна только после правки решения, гейта, DoD или рисков. Если больше половины находок раунда — адреса, счёты и датированные замеры, рекомендуй вынести их из тела: называть файл или тест-авторитет вместо числа, а замеры — в датированное приложение (см. Оговорки).

## Жёсткие правила

- Доказывай **первоисточником**, не документом. RFC — не свидетель собственной корректности. Это включает код, который RFC **цитирует** (комментарий, заголовок скрипта, docstring): проверяй против _первичного_ источника (config / поведение / прогон), а не против цитаты — комментарий устаревает, RFC наследует устаревание, а claim, звучащий и в RFC, и в цитируемом им коде, ощущается дважды-подтверждённым, оставаясь **одним эхом**. **Тот же статус — у audit-log / ревизионной записи в шапке САМОГО документа, особенно оставленной прошлым прогоном `/audit-rfc`:** её вердикты (CONFIRMED / No BLOCKER / «ready to implement» / выбранный bump) — subagent-grade claims, не установленный факт; несущую посылку под выводом «ready/patch/GREEN» перепроверь исполнением с нуля — прошлый прогон мог рубер-стемпнуть plausible-but-wrong. Это касается и документа, написанного ЭТОЙ ЖЕ сессией: свежесть прогона защищает от устаревания, но не от артефактов интерпретации — неожиданные грани, не подтверждённые независимым источником, ре-исполняй изолированной пробой прежде чем принять их как ground-truth.
- На load-bearing/неожиданном claim'е НЕ доверяй вердикту субагента без собственной перепроверки (компиляция/прогон/трассировка). Subagent-резюме — гипотеза, не факт. ⚠ **А РАСХОЖДЕНИЕ двух агентов по одному факту — бесплатный дискриминатор: резолвь его САМ, прежде чем любой из ответов попадёт в отчёт, и никогда не отдавай победу более подробному.** Развёрнутый разбор с трассировкой звучит авторитетнее короткого «подтверждено», а ошибается ровно так же. Цена ошибки здесь ВЫШЕ, чем у пропущенной находки: `--fix`, «исправляющий» верный анкер, своей рукой вносит в документ дефект, которого там не было.
- TYPE/COMPILER/regex/algorithm — только эмпирика (`tsc`/`node`/трассировка), никогда «логически очевидно».
- Claim о стороннем продукте (API/поведение/лимит/опыт) проверяется в **первоисточнике продукта** (CLI/context7/доки/исходники/web), НЕ из памяти и НЕ из утверждения RFC. Стек bleeding-edge — training систематически отстаёт; «я знаю, как работает X» без захода в источник = находка-в-зеркале. Для установленного инструмента прогон его CLI бьёт любые доки.
- Решение «исправлено» ТОЛЬКО когда пропагировано везде; докажи `grep`-ом нулевой остаток старой формулировки. ⚠ **И верификацию СВОИХ правок гони по ОКНУ строк, не по одной:** прозу переносит по ширине, поэтому однострочный греп по фразе, которую ты только что вписал, даёт ложный ноль ровно так же, как на вызовах API, — а читается он хуже, как «правка не легла», и провоцирует вторую, дублирующую. Резидью-паттерн включай с уникальным якорем строки (ключ строки / первая ячейка), не только заменённым хвостом — одинаковые хвосты соседних строк таблицы дают ложный остаток на строке, которую менять и не требовалось. **Правка, объясняющая снятый дефект, цитирует его дословно**, поэтому residue-чек обязан различать _остаток_ и _цитату-объяснение_ — классифицировать `Read`'ом каждое вхождение, а не судить по счётчику: и ложный ноль, и ложный не-ноль здесь одинаково дороги. **Для документа из СЕМЬИ (зонтик + дочерние RFC, док + его резюме/сводные таблицы в родителе) пропагация и grep нулевого остатка обязаны покрывать ВСЕ документы семьи** — родитель дублирует формулировки дочерних, и правка в одном файле при живой копии в сиблинге = непропагированное решение, доживающее до следующего аудита. ⚠ **Семья бывает и в ДВУХ репозиториях: доки пакета и одноимённая страница вики.** Бареное имя компонента в клейме («`search-schema-plugin`: сказано X») тогда двусмысленно, и агент, просканировавший только пакет, вернёт REFUTED на формулировке, живущей в вики. Прежде чем принять REFUTED по такому клейму — прогони тот же скан по ВТОРОМУ рабочему каталогу. ⚠ И читай производный артефакт ЦЕЛИКОМ, а не только на резолвимость цитаты: он мог ОБОГНАТЬ источник — issue/PR-описание, написанное ИЗ дока, дописывается позже и несёт разбор, которого в доке нет, так что расхождение — находка в ДОКЕ, а не в производном. **Решение, меняющее СЧЁТЧИК, грепай и цифрой, и числительным словом** («7» И «семи»/«seven»): прозаические эха («размазанную по 7 точкам» в шапке-визии, «в семи местах») переживают паттерны, построенные от заменённых строк таблиц. **Пакетную замену гони скриптом, печатающим счётчик применений НА КАЖДУЮ пару** (`применено N/M` + список несработавших): `0 вхождений` — это находка о ТВОЁМ паттерне, а не о документе, и без счётчика правка молча не применяется, а residue-чек потом покажет её как «непропагированный остаток». Типовая причина нуля — markdown-разметка, съехавшая внутрь искомой строки (`**хвост)** текст` против `**хвост) текст**`), поэтому паттерн строй по содержимому, а звёздочки оставляй снаружи; вторая — предыдущая пара уже переписала подстроку следующей, поэтому строй пары от самых длинных к коротким и не вкладывай одну в другую.
- Верный вывод на кривой цитате → чини цитату, вывод сохрани. Не выбрасывай хороший вывод из-за плохого адреса.
- Дизайн-выбор автора — не «ошибка», пока не порождает противоречие. Не навязывай вкусовщину под видом находки.
- Раздели **измеренное и оценочное**. Оценка, поданная как факт — находка. Load-bearing-оценка, гейтящая решение, должна быть либо измерена, либо явно помечена ASSUMPTION+RISK с планом замера. 5-минутный замер бьёт хедж-вердикт «вероятно ок» — стремись получить данные, а не обойти их.
- Раздели **измеренное и измеренное КОГДА**. Если шапка/журнал документа сами заявляют «issue X исправлен коммитом Y» (тем более — коммитом СЕГОДНЯШНИМ), КАЖДАЯ эмпирическая строка, описывающая симптом X, обязана быть перепрогнана на HEAD: провенанс-замер, оставленный в настоящем времени, — тот же plausible-but-wrong, только состаренный собственным прогрессом дока, и он переживает статус «все клеймы проверены прогоном». Триггер дешёвый: сверь mtime `dist` / дату последнего замера с датами фикс-коммитов из шапки. ⚠ **И шире симптома: отгруженный коммит роняет замеры, к его собственной задаче отношения не имеющие.** Правило выше ловит строки про симптом X, а ревизия, отгруженная САМИМ документом, переписывает код, на котором стоят замеры ДРУГИХ, уже закрытых вопросов — и у таких строк нет ни одного признака устаревания, потому что их вопрос помечен «ЗАКРЫТ». Ищи их пересечением diff коммита (файлы и функции) с файлами, которые цитируют закрытые замеры, и перепрогоняй каждый такой замер. ⚠ **Тот же триггер применяй к АНКЕРАМ, а не только к замерам, и с особым подозрением — к файлу, который правил САМ прогон** (docs-фикс, комментарий, переименование): его строки сдвигаются последними, а re-anchor-список прогона систематически его пропускает, потому что файл ощущается «уже обработанным». Дешёвая проверка перед вердиктом: `git log --since='<mtime документа минус час>' -- <файлы, которые док цитирует>`. Провенанс не удаляй — пометь «замер ДО `<sha>`» и допиши текущий исход. Отдельно проверь, не стал ли ОСТАВШИЙСЯ симптом КОРРЕКТНЫМ поведением после фикса (иначе фаза миграции будет чинить не-баг).
- Раздели **измеренное и измеренное В КАКОЙ КОНФИГУРАЦИИ**. Когда док отвергает альтернативу контр-примером, сверь конфигурацию замера у ОБЕИХ сторон: цена статус-кво и цена альтернативы обязаны меряться в одной. Разные конфигурации (bare core vs с opt-in плагином; дефолтные опции vs максимальные) дают внешне решающий контр-пример при неопределённом сравнении. И отдельно — **прогони отвергающий контр-пример на самом статус-кво**: часто тот же отказ там уже живёт, только на меньшей популяции, и тогда «альтернатива хуже» верно количественно, а не качественно.
- **Контрольная рука.** Если индекс памяти или записка владельца упоминает руку или контроль для `/audit-rfc` по аудируемому документу, не открывай её до вердикта: сверка с рукой идёт после отчёта и показывает, насколько аудит был слеп. Прочёл раньше (в том числе ради ориентации) — скажи в отчёте, что рука скомпрометирована, и дальше считай её лишь ещё одним источником утверждений.
- Push/commit не делай без явной просьбы.

## Оговорки (НЕ метить как находку)

- **PROSE/MOTIVATION** не обязана цитировать код — мети только противоречия в ней.
- **CROSS-REF в правильную сущность, но слегка не тот файл/секция** — MINOR (суть важнее адреса), не BLOCKER.
- **Субъективное дизайн-предпочтение** без противоречия — не ошибка.
- **Не каждое число нужно мерить** — только load-bearing, гейтящее решение. Цифра, честно помеченная «оценочно, замер в фазе X» с планом — это правильная дисциплина (награждай, не мети как находку). Estimate ≠ ошибка; estimate, выданный за факт — ошибка. ⚠ Но «награждай» ≠ «оставь висеть»: **раздел «что НЕ проверялось» / «риски» аудируемого дока — это список работ АУДИТА**, а не оговорка, снимающая вопрос. Пункт, закрываемый ОДНИМ прогоном (покрыта ли новая ветка прототипа, воспроизводится ли названный побочный эффект), меряй и переводи в измеренное — честная пометка автора заслуживает того, чтобы её сняли, а не процитировали.
- **Число в датированном приложении-снимке** («Снимок <дата>», объявленном основанием решений, а не утверждением о HEAD) сверяй, только если от него зависит шаг плана или решение; расхождение с HEAD без такой зависимости — MINOR. Число, которое гейтит шаг, — утверждение о HEAD, где бы оно ни стояло.
- **Сторонний продукт, чьё поведение нельзя проверить** (закрытое/платное/нерелизнутое API) → пометь **ASSUMPTION** с указанием, что нужен доступ/релиз; не выдавай память за факт. Если RFC сам честно назвал это гипотезой / «надо измерить» (как arm64-дельта) — это дисциплина, не находка.
- **Re-audit гигиена:** после слов автора «исправил» сперва сверь, что читаешь ТЕКУЩИЙ файл — fingerprint (`stat` mtime/size + `md5`); если твой read выглядит неизменным, а автор настаивает — пере-`stat`, кэш инструментов/ФС может отставать от свежего сохранения. Не выноси «изменений нет», не сверив fingerprint. (RFC под `.claude/` — gitignored: `git diff`/`git status` для него всегда пусты — верь содержимому/хэшу, не git.) **Первым шагом прогона снимай `git log --since="<mtime документа>"`** — для gitignored-дока его mtime и есть граница «что случилось после написания», и это дешевле любой сверки шапки. Ловит класс «база сменилась, пока документ лежал», который сверкой дат из шапки не ловится вовсе. ⚠ Но снятый на СТАРТЕ он отвечает только про прошлое: база уезжает и вперёд, пока ты меришь — см. «АТРИБУЦИЯ БАЗЫ» в Протоколе п. 3, там же признак и лечение. ⚠ **И `git log` слеп к правке владельца, лежащей НЕЗАКОММИЧЕННОЙ** — а рабочая копия и есть то место, куда владелец кладёт реакцию, пока ты пишешь отчёт. Пере-снимай перед вердиктом ОБА: `git log` и `git status --short`; расхождение со стартовым снимком СТАТУСА означает, что база уехала в рабочем дереве, и `--since` этого не покажет никогда. ⚠ **Внешнее состояние, на которое опирается отчёт, — алерты, статусы PR, настройки репозитория, прогоны CI, — тоже база, и она уезжает без единого коммита**: ни `git log`, ни `git status` её не видят. Замер агента о нём — гипотеза с отметкой времени; каждое такое утверждение, попадающее в отчёт, пере-сними сам перед вердиктом. То же — для **ground-truth файлов, изменившихся ПО ХОДУ прогона** (нотификация системы / линтер / правка пользователя): line-цитаты по такому файлу пере-сними `grep -n` ПОСЛЕ изменения — вердикт «line-цитата верна/сдвинута», вынесенный по до-изменения read'у, невалиден.

## Валидация и отчёт

1. **Отчёт-таблица:** claim | тип | ground-truth (`file:line` / замер / context7·CLI·доки продукта) | вердикт (CONFIRMED / REFUTED / PARTIAL / STALE-CITATION / NOT-FOUND / MEASURED / ASSUMPTION) | severity | исправление (однозначное) / критерий приёмки.
2. Раздели находки на **BLOCKER / SHOULD-FIX / MINOR** и отдельный список **УКРЕПЛЕНИЕ** (шаг плана и клетка теста или строка разрыва; в счёт находок раунда не входит); для каждой — однозначное исправление с `file:line` либо, если исправление требует выбора, вопрос владельцу с критерием приёмки и пробой (см. «Классификация находок»). В отчёт владельцу идут ВСЕ находки — сокращай формулировку, но не список: автор правит по отчёту, и не попавшее в него остаётся в документе до следующего прогона. Находка, повторяющая неисправленную находку прошлого отчёта, — одна строка «не исправлено с <раунд/id>» вне счёта раунда, с прежней severity, если нет нового довода.
3. **Вердикт о готовности:** оцени архитектуру (зелёная/нет) ОТДЕЛЬНО от исполнения; перечисли, что закрыть до «готов к реализации», по шагам плана — какие идут в реализацию сейчас и какие ждут какого решения; явно раздели «ревизия документа» и «пересмотр архитектуры».
4. При `--fix`: после правок — `grep`-доказательство нулевого остатка старых формулировок + новый fingerprint файла; перечитай наиболее переструктурированные зоны, убедись, что псевдокод/таблицы не порвались. Таблицы проверяй **механически, а не глазами**: посчитай разделители на строку (минус экранированные `\|`) — строка с иным числом колонок сломана. Типовой источник — неэкранированный `\|\|`/`\|` внутри инлайн-кода в ячейке (`` `literal || resolved` ``); грепом по тексту он невидим и потому переживает несколько аудитов подряд. ⚠ **Экранируй пайпы В МОМЕНТ ЗАПИСИ, а не полагайся на чекер:** когда `--fix` вносит в ячейку кодовое выражение (`a \|\| b`, `A \| B`), самый частый автор этого дефекта — сам аудит, а не автор дока. Правка, пропагирующая изменившуюся формулу по нескольким таблицам, попадается на нём системно: одну ячейку экранируешь, соседнюю забываешь. Чекер тут бэкстоп, а не план. ⚠ Считай пайпы в **СЫРОЙ** строке: стрип инлайн-кода перед подсчётом — естественная первая реализация — удаляет ровно те пайпы, которые ты ищешь, и чекер становится структурно слеп, печатая «таблицы целы». Это гейт, чей проход — пустой вывод, значит обязателен позитивный контроль (вставь `\|\|` в заведомо целую строку копии — не покраснел, сломан чекер). ⚠ Правя документ на нелатинском языке, прогони заодно проверку на **смешанный скрипт** — и паттерн обязан быть ДВУНАПРАВЛЕННЫМ: `[А-Яа-яЁё]+[a-zA-Z]+|[a-zA-Z]+[А-Яа-яЁё]+`, а не `[А-Яа-яЁё]+[a-zA-Z][А-Яа-яЁё]+`, который требует кириллицу ПОСЛЕ латиницы и потому слеп к самому частому случаю — латинской букве на КОНЦЕ слова (`термa`, `схемa`). Латинская буква внутри кириллического слова невидима при вычитке и делает слово ненаходимым грепом — в том числе твоим же residue-чеком, который тогда печатает ложный ноль.

## Замечание

RFC/дизайн-доки под `.claude/` обычно gitignored (не трекаются) — изменения не видны в `git`, верифицируй содержимым и fingerprint'ом. Правки документа changeset не требуют. Push не делай без явной просьбы.

## Самокоррекция скила (в конце каждого прогона)

Этот файл — живой. После отчёта (Валидация п.1–3) вынеси короткую секцию **«Самокоррекция»** — критику не своей работы, а САМОГО ЭТОГО СКИЛА: где его текст промолчал, соврал, был двусмыслен или избыточен — и это стоило времени, лишнего шага или риска ошибки.

1. **Привязка к ИНЦИДЕНТУ, не общие советы.** Каждая правка — из конкретного момента ЭТОГО прогона: «скил сказал X / промолчал про X → реальность Y → я потерял/чуть не ошибся на Z». Нет инцидента — нет правки (не выдумывай улучшения впрок). Инцидент — довод в таблице кандидатов и в сообщении коммита; в текст скила идёт правило в настоящем времени с причиной в общем виде — без номера прогона, раунда и даты.
2. **Высокая планка: изменило бы исход?** Предлагай, только если правка реально предотвратила бы ошибку, сократила перебор или сняла двусмысленность, на которой ты споткнулся. Косметику и «было бы неплохо» — отбрасывай.
3. **Разовое ≠ паттерн.** Специфику конкретного RFC/стороннего продукта (разовую) → в отчёт/память по этому RFC, НЕ в скил. В скил идёт только повторяющийся класс, полезный СЛЕДУЮЩЕМУ аудиту ДРУГОГО документа.
4. **Сначала заточи, потом дописывай (анти-раздувание).** Предпочитай усиление существующего абзаца новой секции; если правка делает прежний текст избыточным — консолидируй, не дублируй. Удаление устаревшего текста предлагай наравне с добавлением.
5. **Предлагай, не применяй молча.** Выведи кандидатов таблицей (раздел | инцидент | предлагаемый текст), спроси разрешения. Применил по согласию → `.claude/commands/` это infra, в master напрямую, без changeset; коммить строго `git commit -o .claude/commands/<skill>.md -m …` (only-путь): staged-зона общая, в репо может работать параллельная сессия — голый `git commit` после неудачной первой попытки (напр. commitlint-реджект scope) утащит твой файл в её коммит. ⚠ **И ПЕРЕД правкой скила проверь, на какой ветке рабочее дерево и содержит ли она `master`:** `git branch --show-current` + `git log --oneline HEAD..master`. Непустой вывод второй команды означает, что файл на диске — СТАРАЯ копия, и твой Edit ляжет поверх неё: коммит тогда не только уедет на чужую ветку, но и ОТКАТИТ правки предыдущего прогона при мерже, а `git status` останется чистым и ничего не скажет. Это тот же класс, что «сверь fingerprint» в Оговорках, но с другой ценой — не устаревшая цитата, а молчаливый регресс живого файла. Сессионный снимок `gitStatus` в шапке не годится: он мог быть снят до переключения ветки.
6. **Честность про «нечего править».** Прогон прошёл чисто и скил нигде не подвёл → так и скажи: «правок нет». Пустая самокоррекция честнее придуманной — пункты 1–2 это допускают.
