Проведи аудит RFC/дизайн-документа: провалидируй КАЖДОЕ утверждение против первоисточника (код, компилятор, прогон, смежные доки, доки/CLI/исходники сторонних продуктов) — НЕ против самого документа — найди ошибки, противоречия и непропагированные решения, вынеси вердикт о готовности к реализации.

Входные данные:
$ARGUMENTS

Формат аргументов:
- Путь к RFC/дизайн-документу (напр. `.claude/rfc-file-routes.md`, `.claude/rfc-type-safe-routing-generator.md`, `.claude/ci-acceleration-poc-ru.md`).
- Опционально `--fix` — применить ТОЛЬКО механические правки (фактические исправления, починка цитат, пропагация уже-ПРИНЯТОГО решения по всем таблицам/псевдокоду/DoD, снятие противоречий с однозначной резолюцией). Дизайн-вопросы НИКОГДА не правятся автоматически — выносятся автору. По умолчанию: report-only (доказанный порядок — сперва отчёт, правки по явной просьбе).

Пример:
```
/audit-rfc .claude/rfc-file-routes.md
/audit-rfc .claude/rfc-type-safe-routing-generator.md --fix
```

## Принцип

Статус «готов к работе» в шапке НЕ значит, что документ корректен. RFC-«театр» проходит, когда: утверждение ссылается на код, который говорит не то, что заявлено; решение принято в прозе, но не пропагировано в таблицы/псевдокод/DoD; в алгоритме ordering-баг, который никто не протрассировал; цитата на смежный док не резолвится.

Цель аудита: для КАЖДОГО утверждения и вывода доказать его **первоисточником** — кодом, компилятором, реальным прогоном, содержимым смежного документа — а НЕ доверием к само-утверждению RFC или к резюме субагента. Это RFC-аналог мутационной валидации (см. `audit-pbt`/`audit-stress`): истинность claim'а доказывается походом в ground-truth, а не зелёным цветом документа.

Ключевая интуиция: самый опасный режим — **plausible-but-wrong**. Claim звучит убедительно, субагент его «подтверждает», но компилятор/код говорит обратное. Несущие и неожиданные claim'ы проверяй САМ, эмпирически (см. Жёсткие правила).

**Ground-truth включает данные, которые нужно ПОЛУЧИТЬ, а не только код, который нужно прочитать.** Для количественных claim'ов (тайминги, пороги, «уложится в ≤Xs», «доминирует пакет Y») первоисточник — это **замер**, а не число из документа. Не принимай оценку на веру и не понижай находку до «вероятно ок», когда вопрос закрывается 5-минутным замером / симуляцией / калибровкой по реальной истории. Эталон дисциплины — `.claude/ci-acceleration-poc-ru.md`: он сам ведёт ревизии «факты перепроверены эмпирически» (Ред. 16: `turbo --dry=json` на репо нашёл **3 бага** центрального скрипта) и явно метит **измеренное** (`32m 29s` на real CI run) против **оценочного** («arm64-дельта неизвестна → замер, не гипотеза»; «`K=5` — стартовый, подобрать по замерам»). Аудит обязан: (1) для каждой load-bearing-цифры определить — измерена она или предположена; (2) если предположена и гейтит решение — добыть данные или явно пометить ASSUMPTION+RISK.

**Claim'ы о СТОРОННИХ продуктах — отдельный первоисточник: сам продукт, не репо и не память.** Если документ ссылается на чужой API / поведение / лимит / опыт («turbo делает X», «GitHub Actions arm64 free для public-repo», «Nx Cloud умеет Y», «Vite-плагин поддерживает Z», «browser API ведёт себя так») — проверь в первоисточнике ПРОДУКТА (его CLI/`--help`/прогон, context7-доки, исходники, офиц. доки, web), а НЕ по training-памяти: стек bleeding-edge (TS 6 / turbo 2.9 / ESLint 10 / Vitest 4…), и память систематически отстаёт от актуальных версий. «Я знаю, как работает X» без захода в источник — это plausible-but-wrong в чистом виде (см. memory `feedback_no_hallucinated_spec_facts`).

## Классификация утверждений (определи тип КАЖДОГО claim'а)

1. **CODE-FACT** — ссылка на файл/функцию/строку/regex/сигнатуру API/поведение. Проверяется чтением реального кода.
2. **TYPE/COMPILER** 🔬 — утверждение о поведении TypeScript (`keyof`, `Omit`, inference, module augmentation, index-signature). Проверяется ТОЛЬКО компиляцией — никогда рассуждением и никогда доверием агенту.
3. **CROSS-REF (внутренний)** — цитата на ВНУТРЕННИЙ док/RFC/секцию/issue/номер-решения. Должна резолвиться в существующий таргет с заявленным содержимым.
4. **EXTERNAL/THIRD-PARTY** 🌐 — утверждение о СТОРОННЕМ продукте: его API / поведение / лимит / прайсинг / «как делает инструмент X» (turbo, Nx, GitHub Actions, Vite, Vitest, browser API…). Первоисточник — САМ продукт: установленный CLI (`--help`/прогон), context7-доки, его исходники/репозиторий, офиц. доки (WebFetch), web (WebSearch). НЕ из памяти (training лагает на bleeding-edge) и НЕ из утверждения RFC.
5. **COUNT/INVENTORY** — счётчики пакетов, «N адаптеров», «9 инвариантов», **а также usage/frequency-счётчики, которыми RFC оправдывает УДАЛЕНИЕ фичи («used once», «barely used», «dead code», «нигде не вызывается»)**. Пересчитай сам: инвентарь — `ls`/скан; usage-частоту — эмпирически (`gh pr list --search`, `git log -S<маркер>`, code-скан по вызовам), НЕ со слов автора / по памяти. «Remove-because-unused» — проверяемый claim, а не мотивация (в сессии-родителе «`#trivial` использован однажды» → `gh pr list` показал 2 PR-title). **Family-claim — свойство, заявленное разом для ВСЕХ N копий/вариантов/файлов** («все 5 копий byte-identical», «эти 4 варианта читают `?n=`») — проверяй на КАЖДОМ члене семьи детерминированным сканом (`md5` всех копий, скрипт-инвентарь по каждому файлу), никогда образец+аналогией: «проверил один, обобщил на пять» — plausible-but-wrong, переживающий даже само-аудит дока. (Сессия bench-app-linter: Rev-2 сам заявлял «byte-identical, verified empirically» — md5 ВСЕХ копий дал расхождение в 4/5 файлов; из «4 вариантов на `?n=`» реально читали его 2/4.) Инвентарь «где живут копии X» собирай и по **смежным слоям-потребителям** (драйверы/раннеры/тест-фикстуры/CI-скрипты), не только по слою, который док называет: потребитель часто держит собственную hardcoded-копию контракта. (Та же сессия: RFC инвентаризовал spec-копии в `_shared/` + angular-инлайны, а сценарные драйверы несли ТРЕТЬЮ копию свип-констант — целая дрейф-поверхность мимо инвентаря и мимо проектируемого паритет-чека.) **Инвентарь ссылок при переименовании/удалении пакета обязан отдельным пунктом покрывать КОРЕНЬ репо** — root-конфиги (codecov/sonar/size-limit/knip/CI-guard-скрипты) держат пакетные списки, а walk по подкаталогам корень не захватывает; плюс читай guard-скрипты (`check-*-scope` и т.п.): их заголовки называют файлы-потребители списков, отсутствующие в любом import-графе. (Сессия engine-merge: `codecov.yml` с 3 компонентами и двусторонним pre-commit-гейтом нашёлся только через header `check-coverage-scope.mjs` — главная S1-находка аудита лежала вне скана подкаталогов.) **Счётчик РЕГИСТРАЦИЙ** (арки бенча, кейсы, фикстуры, роуты) считается как число сайтов **× кардинальность цикла** — читай литеральный список, по которому сайт итерируется. Число вызовов и число зарегистрированных сущностей — разные величины, и обе могут не совпасть с клеймом, так что site-count «подтверждает» третье неверное число. (Прогон rfc-two-pipelines: клейм «15 навигационных арок» — 13 `bench.add`-сайтов, четыре из них в `for` по `[1,3,5]`/`[5,10]`, итого 19 зарегистрированных.) **Документ, объявляющий НОРМАЛИЗАЦИЮ** («все счётчики пере-выведены против одной базы», «анкеры пересняты», «числа приведены к версии X»), **— это claim, и проверяется ПО-ВЕЛИЧИННО, а не оптом.** Приём, решающий это одним ходом: измерь ОДНУ И ТУ ЖЕ величину на ОБЕИХ базах и посмотри, к какой подходит число документа. Нормализация систематически ложится на то, что автор правил руками (номера строк), и НЕ ложится на производные метрики — всего строк, число функций, доля комментария, знаменатель прогона, — а гейтят решение обычно вторые. (Прогон rfc-nav-cancellation-scope: шапка ред. 2 заявляла «одну базу» своей заглавной правкой; номера строк и счёт тестов §8 действительно шли против неё, а «977 строк / 14 функций», «517 строк комментария» и знаменатель свипа — против несмёрженной ветки, на базе это 890 / 13, 456 и 4009. Дока при этом считала ветковую функцию в «14 функций», пока соседняя таблица помечала её «только ветка».)
6. **ALGORITHM/PSEUDOCODE** — читается как исполнение: ordering-баги, недостижимые ветки, необработанные edge-кейсы, расхождение сигнатуры вызова и определения. **Если док заменяет правило парсинга/классификации — прогони НОВОЕ правило по полному словарю форм СТАРОЙ грамматики** (и валидных, и отвергаемых, включая реверс- и двойные-глифы): каждая старая форма обязана получить названный исход (валидна / та же ошибка / новый рецепт); форма, тихо меняющая интерпретацию или тихо легализующая бывший reject, — находка. (Сессия m1-drop: правило среза `?` тихо превращало сегодня-валидную `/:id??tab` в мёртвую query-декларацию, а сегодня-отвергаемые `?<x>`/`a<b`/`a>b` — в тихо-принятые; вскрыто только перебором словаря форм прогоном на dist.) **То же — для смены ПОРЯДКА **или КАНАЛА** мёржей/нормализаций** (defaults/normalize/canonicalize): прогони СТАРЫЙ фактический и НОВЫЙ заявленный вариант по решётке граничных входов — {значение, `undefined`, отсутствие} × {дефолт есть/нет} × {каждый канал}; клетка с молча изменившимся исходом = находка. (Прогон rfc-nav-pipeline: заявленный порядок «дефолты→normalize» инвертировал судьбу explicit-`undefined` на path-канале — дефолт переставал выживать, required-параметр терялся; вскрыто только решёткой, притом каналы вели себя противоположно друг другу.) **Клейм «этот шаг — no-op» доказывается ТОЛЬКО решёткой** {вызывающий молчит} × {значение в канале A} × {значение в канале B}: совпадение выхода на одном входе — не доказательство, а ровно та форма, которой пишут приёмку такого шага, поэтому дефект переживает и её. (Тот же прогон, ред. 30: шаг, переложивший дефолты цепочки в query-канал, назван «no-op» и запинен тестом — оба покрывали только плечо «вызывающий молчит / кладёт в тот же канал»; на плече «вызывающий кладёт в СОСЕДНИЙ канал» шаг молча инвертировал приоритет, и значение пользователя исчезало. Проверять надо и то плечо, где новый код и старый пишут в РАЗНЫЕ каналы.) **Унификация N точек входа на одну проверку** («паритет», «третья точка популяции», «дать конструктору то, что уже есть у add/replace») — тот же класс, но словарь строится ЗЕРКАЛЬНО: из входов, которые **отстающая** точка принимает СЕГОДНЯ, а не из тех, что отвергают ведущие. Дельта живёт ровно там, и док систематически описывает её как «гейт срабатывает раньше бэкстопа», когда на деле это «срабатывает там, где не срабатывало ничто» — особенно если новая проверка и старый бэкстоп судят по РАЗНЫМ признакам (строка против семантики), потому что тогда их множества не вложены ни в одну сторону. (Прогон rfc-routes-crud: `createRouter` принимал двух сиблингов с `path: ""`, а `add`/`replace` ту же форму отвергали; унифицирующий гейт делал это accept → throw, тогда как §5 дока утверждала «факт и момент отказа не меняются», а коммит был помечен «поведение неизменно». В обратную сторону тот же разрыв дал вторую находку: гейт сравнивает пути строкой и НЕ видит `/:id` против `/:name`, которые бэкстоп отвергает.) **Прескриптивный абзац, назначающий МОМЕНТ, — тот же класс, даже когда это чистая проза без псевдокода** («на входе в X», «до Y», «один раз при Z», «а не по факту первого потребителя»). Рецепт: выпиши величины, от которых зависит предписанное действие, и проверь для КАЖДОЙ, известна ли она в названный момент. Ответ обычно уже лежит в §2 того же документа — и чаще всего в том разделе, где док ХВАЛИТ чужую правку за обход ровно этой незнаемости: такой абзац и есть контрпример собственному §4. Проверь заодно, не закрыл ли документ своим же разделом «отвергнуто» единственный оставшийся выход — тогда предписание не просто недоспецифицировано, а невыполнимо, и находка BLOCKER. (Прогон rfc-nav-cancellation-scope: §4.2 предписывала материализовать ресурс «на входе в полосу по предикату, вычисленному один раз, а не по факту первого потребителя»; половина предиката (`hasGuards`) не знаема на входе в полосу ПО ПОСТРОЕНИЮ — что §2.1 сама ставит в заслугу чужому PR, — единственный знаемый там предикат ломает магистральную арку, а «аллоцировать всегда» отвергнуто §6. Единственный BLOCKER прогона, и найден он чтением прозы как исполнения, а не сверкой фактов.)
7. **DESIGN-DECISION** 🔁 — выбор, принятый в прозе («Принято», О-N). Должен быть пропагирован в КАЖДЫЙ downstream-артефакт: convention-таблицы, псевдокод, DoD этапов, Risks, сводную таблицу. **Если решение меняет форму/сигнатуру осевого поля или API, а док даёт список затронутых/незатронутых потребителей — построй инвентарь читателей этого поля (и вызовов меняемых сигнатур) НЕЗАВИСИМО**, сканом по всем слоям — включая symlink-shared источники и каналы мимо названного механизма (док говорит «sweep интерцепторов» — а читатели бывают не-интерцепторными), — и сравни со списком дока: потребитель вне списка — находка; «не затронут» доказывается инвентарём читателей, не доверием списку. (Сессия url-model-v2: независимый sweep читателей `state.params` вскрыл sources / shared/browser-env / preload / logger вне списка «не затронуты» §7.5 и вне плана Этапа 3 — три дыры скоупа, одна с silent-обеднением пользовательских колбэков.) **Если решение УДАЛЯЕТ защитную/нормализующую стадию** (развод каналов, санитайзер, дефолтизатор, коэрсер), инвентарь строится ДУАЛЬНО — не читатели поля, а **producer'ы, писавшие в эту стадию**: кто полагался на то, что она приберёт за ним. Опора на стадию часто не выражена вызовом — потребитель просто передаёт мешок дальше, а своё допущение держит в КОММЕНТАРИИ, поэтому call-graph и «кто вызывает X» его не покажут; ищи текстом по имени удаляемой стадии И по её эффекту. Отдельно перепроверь клейм «этот слой чист по построению»: чистым может быть один под-слой (парсер), а соседний (пользовательский хук того же шва) — держаться ровно на удаляемой стадии. (Прогон rfc-nav-pipeline: инвентарь потребителей стадии ② объявлял «в first-party коде их нет» — независимый скан писателей нашёл `shared/browser-env/plugin-utils.ts`, шипнутый в трёх плагинах, чей КОММЕНТАРИЙ прямо называет ② механизмом; там же клейм «matchPath-декод чист по построению» оказался верен для парса матчера и ложен для выхода пользовательского `decodeParams`.)
8. **INVARIANT/TEST-PLAN** — предлагаемые инварианты/тесты. Проверяется на корректность (свойство реально держится с учётом ОСТАЛЬНЫХ решений?) и неизбыточность (не дубль другого инварианта). **Особый под-класс — критерий «эквивалентность текущему поведению» (fuzz-паритет, golden-сравнение): если тот же док обещает чинить известные баги, критерий обязан явно исключать баг-грани (на них эталон — корректный вывод, расхождение ожидаемо), иначе он самопротиворечив — первая же генерация на баг-грани уронит прогон.** (Сессия invertible-grammar: спайк-критерий «выходы ≡ текущим codec'ам» на срезе, намеренно включающем optional-leading-баг #1147, — BLOCKER: половина omit-генераций попадает в грань.) ⛔ **Клейм «тест остаётся зелёным» — не то же, что «тест продолжает работать», и проверяется МУТАЦИЕЙ, а не прогоном.** Когда документ меняет код, который тест пинит, и подаёт зелёный цвет как подтверждение («остальные N тестов того же файла ЗЕЛЁНЫЕ»), прогони дискриминирующую мутацию этого теста на ОБЕИХ базах. Искать её обычно не нужно — она уже описана в его же docblock'е («moving X below Y flips these and reds them»). Зелёный-и-НЕдискриминирующий — ровно тот ложно-зелёный, ради которого аудит существует, и прячется он систематически в разделе «что не сломалось», то есть там, где скил иначе велит награждать, а не искать. (Прогон rfc-opts-normalisation: §9 подавал «остальные три теста ЗЕЛЁНЫЕ» как довод; их собственная мутация роняет 3 из 4 на базе и НОЛЬ новых на прототипе — два теста переживали ровно то, ради поимки чего написаны, став дублем соседней арки под прежним именем. Это поменяло цену развилки, которую документ выносил владельцу: предмет терял не один тест, а весь файл.)
9. **PERF/EMPIRICAL-ESTIMATE** 📊 — количественный claim: тайминг, порог (`K=5`), «уложится в ≤Xs», «пакет Y доминирует wall-time», счётчик, варьирующийся по входу. Первоисточник — **замер / симуляция / калибровка по реальной истории**, не число из документа. Проверь дополнительно: помечено ли явно как измеренное vs оценочное.
10. **PROSE/MOTIVATION** — мотивация/рамка, не привязанная к коду. Низкий приоритет; проверяется лишь на внутреннее противоречие.

## Протокол на каждый claim

1. **Классифицируй** (тип выше) и выдели первоисточник, который его докажет/опровергнет.
2. **Собери ground-truth.** Для широты — fan-out `Explore`-агентов, сгруппированных по кластерам (типы; конкретный пакет; смежные доки; инфра/тесты); каждому — точные вопросы + требование цитировать `file:line` и выносить вердикт CONFIRMED/REFUTED/PARTIAL/NOT-FOUND. **Вопрос формулируй В ФАЗЕ клейма RFC** — цитируй клейм дословно и проси вердикт ИМЕННО к нему, а не независимый вопрос в противофазе: «импортируют ли конфиги X?» при клейме «НЕ импортируют» возвращает «REFUTED», означающий CONFIRMED для RFC, — инверсию знака придётся держать в голове на каждой строке сводной таблицы, и один пропущенный флип портит вердикт (инцидент rfc-1512: Q8-«REFUTED» агента был подтверждением клейма R13). Прежде чем спрашивать смежный док про «Решение N»/«О-N» — установи по тексту САМОГО RFC, чей это ярлык: документы нумеруют решения каждый у себя, и кросс-реф в скобках рядом с номером issue легко приписать не тому владельцу (прогон rfc-generator: «Решение 3» рядом с «#338» оказалось собственным решением аудируемого RFC — агент был отправлен искать его в чужом доке, цикл ушёл на разбор ложного REFUTED-по-атрибуции). Агенты должны читать **рабочее дерево текущей ветки** (read-only, без worktree-изоляции — иначе ветвление от origin/master даст аудит устаревшего кода).
3. **Несущие и неожиданные claim'ы перепроверь САМ, эмпирически** — НЕ доверяй вердикту агента на load-bearing-утверждении:
   - **TYPE/COMPILER:** напиши scratch-`.ts`, прогони `npx tsc --noEmit --strict --ignoreConfig <file>` (флаг обязателен — иначе TS5112 на найденном tsconfig; существует только в tsc ≥ 6.0. На TS5023 «Unknown compiler option» сперва проверь, ЧЕЙ tsc запущен: `npx tsc` из каталога вне репо — scratchpad! — резолвит чужой/глобальный tsc, а не то, что репо-TS стар (инцидент rfc-generator: `cd` в scratchpad → TS5023 при репо-TS 6.0); прогоняй из корня репо, передавая scratch-файлы абсолютными путями. Если репо-TS действительно < 6.0 — убери флаг и гони из каталога, в чьих предках нет tsconfig — это снимает и TS5112); читай, какие именно строки дали ошибку. ⚠ **`--ignoreConfig` выключает и `customConditions`**, поэтому в монорепо, где workspace-имена резолвятся условием (`@real-router/internal-source`), проба на них разваливается `TS2307: Cannot find module` — и это артефакт флага, а не факт о типах. Импортируй в scratch-файле **относительными путями к `src`** (`./src/api/index`, `./src/pipeline/materialize`) — тогда `--ignoreConfig` безвреден; передавать `--customConditions` вместе с ним бесполезно, конфликт снимается только сменой стиля импорта. (Прогон rfc-nav-pipeline phase-2: раунд потерян на TS2307 по трём workspace-импортам подряд, притом сам проверяемый клейм — про генерик-цепочку — к резолюции отношения не имел.) (Пример из сессии-родителя: агент «опроверг» claim про `Omit` выдуманным результатом компиляции; реальный `tsc` доказал, что claim ВЕРЕН — `keyof` с индекс-сигнатурой коллапсирует в `string|number`, и `Omit` ничего не убирает.)
   - **regex/parsing:** прогони паттерн на реальных строках-нарушителях (`node -e`), не «на глаз». **Инвентарь regex-литералов в коде НЕ собирай грепом:** метасимволы искомой строки (`[^>]`, скобки, кванторы) + вариативность grep-бинаря (BSD/ugrep) дают молчаливую пустоту на реально существующих строках, а пустота читается как «отсутствует» (класс feedback_tool_error_not_absence). Первичный инструмент инвентаризации — детерминированный скан (node-скрипт: `fs` + `String.includes`) или `Read` файла; grep — лишь вторичное подтверждение НАЛИЧИЯ, никогда доказательство отсутствия. **Инвентарь ВЫЗОВОВ API ищи по ОКНУ строк (2–4), а не по одной** — Prettier переносит первый аргумент на свою строку, поэтому однострочный паттерн (что grep, что node-скан) систематически слеп к БОЕВЫМ сайтам и оставляет видимыми только тесты и доки, где вызов уместился в строку; «нашлось только в тестах» — почти всегда симптом этой слепоты, а не факт о коде. (Прогон rfc-nav-pipeline ред. 30: предписанный самим RFC class-guard `git grep 'addInterceptor("forwardState"'` не видел НИ ОДИН из двух production-регистрантов и 3 из 6 живых нарушителей в тестах — ложно-зелёный гейт; мой первый node-скан повторил тот же дефект, пока не получил окно.) (Сессия-родитель: два грепа подряд «не нашли» `<[^>]+>` в buildParamMeta.ts — ложное «desync устранён» успело попасть в RFC ещё до аудита; вскрыто только Read + node-сканом.) Это касается и **glob-расширений**: grep-verify цитаты/комментария обязан покрывать ВСЕ реальные расширения цели — `--include='*.ts'` молча пропускает `.tsx`/`.svelte.ts`/`.mts` — и вердикт «отсутствует» выносится только после `Read` конкретного файла. (Сессия rfc-1435: grep с `*.ts` «не нашёл» parity-литерал в solid `useRouteEnter.tsx:105` — ложный REFUTED предотвращён только Read'ом.) Node-скан сам тоже валидируй `Read`'ом — минимум один позитив и один негатив на каждое извлекаемое поле. ⚠ **Ложный ноль — не единственный исход кривого паттерна: слишком узкий класс символов даёт ложную НАХОДКУ.** `[a-zA-Z-]` без `0-9` (или `\w` без дефиса) не «не находит» сущность, а **обрезает** её имя, и она читается как несуществующая — то есть паттерн порождает находку, а не прячет её, и обычный негативный контроль этого не ловит. Прежде чем метить именованную сущность как отсутствующую, грепни её **отличительный корень**, а не полный шаблон имени. (Прогон fsm-as-state-owner: `'"state/[a-zA-Z-]*"'` не увидел бенч-арку `state/isActiveRoute-navbar-5`, и «одной из девяти арок не существует» едва не ушло в отчёт BLOCKER'ом; греп по `navbar` снял это за один вызов.) Тот же класс на уровне СЕМАНТИКИ ключа: инвентарь сущностей, собираемых **спредом** (`{ ...prev, field }`), не ловится фильтром по имени свойства ВООБЩЕ — у такого литерала свойств нет, — так что ключом обязан быть тип/конструкция, а не поле. Универсальная страховка, дешевле любого перебора ключей: прогони паттерн **негативным контролем на заведомо подходящем сайте из СОСЕДНЕГО раздела того же документа** — если известный сайт в скан не попал, паттерн неверен независимо от того, сколько он вернул. (Тот же прогон: `getRoutesApi.ts:481` стоит сайтом 3 в инвентаре §2 аудируемого дока и обязан был попасть в скан §11.A6 — не попал, и «конструкторов ровно три» пережило собственный само-аудит дока дважды.) Классические артефакты: классические артефакты: numeric separators (`30_000` → regex-обрезок «30»), совпадение токена в **комментарии** (`includes` не отличает код от комментария, объясняющего, почему фичи НЕТ — так конфиг type-guards с текстом «No --expose-gc» посчитался как имеющий флаг) и **regex-якоря**: `^`/`$` без флага `m` матчат только границы ВСЕЙ строки-файла, поэтому проверка «строка начинается с X» по `lines.join("\n")` даёт ложный НЕГАТИВ — гоняй такие regex по массиву строк либо ставь `m`; то же с `\b` — он определён на ASCII-word-символах, поэтому residue-греп по кириллице (или любому не-латинскому тексту) молча возвращает НОЛЬ при живых вхождениях. На нелатинском тексте якоря не ставь вовсе. (Прогон rfc-nav-pipeline phase-2: `\bчетыр[её]х?\b` дал 0 при пяти вхождениях «ЧЕТЫРЕ»/«четырёх»; ложный ноль прочитался как «пропагация чистая» и на раунд спрятал настоящий остаток в соседней таблице.) В verify-харнессе (residue-чек после `--fix`) ложный негатив опаснее ложного позитива: он читается как «правка не применилась» и провоцирует второй, дублирующий edit. (Прогон rfc-nav-pipeline ред. 21: чекер отрапортовал «ПРОПУЩЕНО» о правке, которая была на месте.)
   - **code-path:** открой функцию и протрассируй конкретный вход до точки, где решается поведение (порядок веток!). (Так найден silent-баг optional-splat: `segment.endsWith("?")` перехватывает `*slug?` в optional-param-fork раньше splat-ветки.) **Если пакет собран — прогони заявленное поведение напрямую вместо/поверх трассировки:** сверь свежесть dist (mtime dist новее последнего src-коммита: `stat` + `git log -1 -- <pkg>/src`), затем `node -e` + `require('<pkg>/dist/…')` на заявленном входе. **Dist протух → проба идёт на `src`, и тогда КРОСС-ПАКЕТНАЯ проба в монорепо с custom-условием (`customConditions` в tsconfig, напр. `@real-router/internal-source`) обязана гнаться `node --conditions=<условие> --import tsx` И импортировать ОБА пакета ПО ИМЕНИ, из каталога пакета, который реально от них зависит — файл пробы клади ТУДА ЖЕ.** Из scratchpad workspace-имена не резолвятся вовсе (`ERR_MODULE_NOT_FOUND` на первом же `@scope/pkg`): симлинк корневого `node_modules` выручает смок-прогон СТОРОННЕГО тула, но не workspace-пакеты. Смешение стилей — один пакет абсолютным путём к `src`, другой по имени — даёт ДВЕ копии одного модуля (второй резолвится в `dist`); симптом маскируется под баг пробы: `Invalid instance`, провал `instanceof`, пустой WeakMap-реестр, «not found in registry». (Прогон rfc-nav-pipeline ред. 11: два холостых раунда — core из `src` по абсолютному пути + плагин, чей внутренний импорт core ушёл в dist от 26-го числа.) Исполнение бьёт трассировку и попутно ловит соседние контракт-claims. ⚠ **Когда клейм назначает момент ВНУТРИ диспетчера** (FSM `send`, редьюсер, middleware-цепочка, edge-`update`/`action`), сперва выпиши ФАЗЫ одного вызова — условие → своп состояния → `update` → action → listeners — и определи, в какой из них стоит предписанная точка. Проза систематически сворачивает три фазы в одно слово («до анонса», «на входе в полосу», «в момент открытия»), а предикат, ложный в одной фазе, истинен в соседней: тогда обоснование дока верно ПО ВЫВОДУ и ложно ПО МЕХАНИЗМУ, и реализатор, идущий за его же рассуждением, приземляется в дефект. Пробу пиши на самом движке с мини-таблицей на два состояния — десять строк, и она бьёт любое рассуждение о порядке. (Прогон rfc-nav-cancellation-scope: §4.1 предписывала открывать ресурс в `update` ребра `NAVIGATE`, обосновывая ограничение тем, что «до анонса `CANCEL` — табличный no-op»; движок свопает состояние ДО `update`, так что `canSend(CANCEL)` там ИСТИНА, а мутация, которой док это «доказал», тестировала третью точку — до `send`.) (Сессия invertible-grammar: три бага §1.3 доказаны прогоном за минуты — `buildPath('home',{})` → `"//home"` → `match` → undefined — и тот же прогон попутно REFUTED соседний claim «parse тотальна»: URIError на `%E0%41`.) **Когда клейм доказывается МУТАЦИЕЙ** (скил требует её для «эта проверка избыточна» / «этот шаг несущий»), рецепт такой: бэкап файла копией → правка → прогон → восстановление копией → сверка `md5` с `git show HEAD:<path>`. ⚠ **Мутация, симулирующая УДАЛЕНИЕ (ключа, поля, стадии), обязана быть тождественной во всём остальном.** Пересобрать объект «как было минус одно» — самая естественная реализация и самый частый брак: лишний `undefined`-ключ, изменённый порядок, потерянный прототип ломают `toStrictEqual` / `toHaveBeenCalledWith` и красят тесты, к искомому дефекту отношения не имеющие, — а ты прочтёшь их число как «контракт держат все». Признак — падают тесты, чьи ИМЕНА про другое; поэтому читай имена прежде, чем верить счётчику. Строй мутацию фильтром по существующим ключам, а не литералом. (Прогон rfc-opts-normalisation: «плоская запись» из всех семи полей дала 6 красных в ядре и 12 в плагинах; та же мутация, копирующая лишь ПРИСУТСТВУЮЩИЕ поля, — 1 и 12, и эта единица оказалась находкой, опровергшей пункт гейта.) **Восстановление ставь в `trap 'cp "$BAK" "$TARGET"' EXIT` ДО первой правки, а не последней строкой скрипта:** харнесс из нескольких мутаций обрывается на любом шаге (`set -e`, таймаут, zsh, съевший неквотированный `?`/`*` в безобидном `echo`) — и обрывается ровно МЕЖДУ правкой и восстановлением, оставляя репозиторий мутированным; `git status`, снятый позже, ты прочтёшь как свои же правки. (Прогон rfc-nav-cancellation-scope: `echo "--- applied? ---"` внутри функции убил скрипт `no matches found` сразу после мутации `Router.ts` — спасло только то, что следующий запуск начинался с `cp` бэкапа.) Никогда `git checkout -- .` / `git stash` / `git restore`: в репозитории может работать параллельная сессия, владеющая ДРУГИМИ грязными путями, и снимок `git status`, снятый в начале аудита, к моменту восстановления уже неверен. **Если предписание допускает больше одного прочтения** (записать vs выполнить, пометить vs отправить, лениво vs сразу), мутируй КАЖДОЕ и сравни исходы: типовой результат — одно прочтение падает шумно, другое проходит тир целиком, и выберет реализатор именно второе. Тихое прочтение и есть находка; шумное лишь показывает, что тесты видят половину. (Тот же прогон: «область рождается отменённой» как ЗАПИСЬ уронила 5 из 4056 и воспроизвела закрытый баг, как ОТМЕНА — 0 из 4056 при молча инвертированном порядке событий.) И мутируй ОБЕ стороны: «X избыточен» доказывается не только зелёным прогоном без X, но и красным прогоном без того, что его подстраховывает — иначе «избыточен» и «не покрыт тестами» неразличимы. (Прогон rfc-two-pipelines: снятие пяти cancel-check — 3793/3793 зелёные, снятие ОДНОГО внешнего liveness-check — 51 упавший тест; вторая половина и опровергла заявленную причину избыточности.) ⛔ **Клейм «это НЕ выражено тестом / не пинится / невыразимо» — такой же claim, как «здесь баг», и проверяется тем же прогоном сьюта под мутацией, а не чтением.** Он ощущается фоновым (автор про свой код знает лучше) и потому проскакивает без проверки — а опровержение обычно меняет сам диагноз: «не пинилось никогда» и «пинилось, но распинила соседняя правка» — разные находки, и вторая сильнее. Мерь на ОБЕИХ базах, если база двигалась. (Прогон rfc-nav-cancellation-scope: док заявлял три несущих факта «не выразимы ни типом, ни тестом»; мутация первого на базе дока уронила именованный тест, а на HEAD оказалась зелёной И безвредной — перф-правка одновременно сделала дефект недостижимым и ослабила ассерт до баланса `remove === add`, который на нулевом мосте выполняется тождественно. Соседний «дискриминирующий» тест терма не покрывал: он поднимал `subscribeLeave`, с которым предикат истинен и без терма.) **Если RFC включает собственный проверочный сниппет/гейт** (`node -e`-страж версии, валидатор, regex-чек, выданный за доказательство свойства) — он сам claim, а не инструмент: прогони его поперёк ВСЕЙ граничной полосы, которую он берётся гейтить (чуть-ниже / на / чуть-выше порога), не только на target/happy-значении. Гейт, пропускающий значение, которое заявляет отбраковывать, — ложно-зелёный BLOCKER. (Сессия-родитель: страж `(min===0 && pat<=1)` для «≥ 11.1.3» пропускал 11.0.2–11.1.2 — поймано только прогоном по диапазону, а на 11.8.0 он зелёный.) **Гейт, который док НЕ пишет, а НАЗЫВАЕТ митигацией** (существующий тест/линт-правило/CI-чек в колонке «как проверяется»), — тоже claim, и проверяется в два шага: (1) что он ФАКТИЧЕСКИ ассертит — читай маркеры/паттерны в теле, а не название файла, не прозу дока и не собственную шапку теста; (2) не переводит ли планируемое изменение систему в форму его **дискриминирующей мутации** — она часто прямо описана в шапке («injecting X here fails the assertion»), и планируемая правка может ЕЮ И БЫТЬ. Митигация, не касающаяся того, на чём гейт срабатывает, — no-op, и рядом с такой почти всегда лежит неназванный настоящий риск: прогони его. (Прогон rfc-routes-crud: док двумя разделами предписывал «guard-тест обязан начать сторожить новые имена» — тест не сторожил имён вовсе, он проверял отсутствие строк-маркеров в главном чанке бандла, а границу, о которой говорил док, держал вообще другой файл, сканирующий по имени давно удалённого пакета. Настоящий риск — что разрез заводит импорт в главный вход, то есть ровно шапочную мутацию теста, — в доке отсутствовал; прототип показал, что tree-shaking его снимает, и риск закрылся замером вместо гипотезы.) **Гейт, чей ПРОХОД — пустой вывод** (`diff --name-only`, `grep -c` → 0, `find`, «должен вывести ПУСТО»), самонеразличим: пустота одинаково означает «чисто» и «гейт не матчит вообще ничего», и граничная полоса тут не помогает — полосы нет. Обязателен **позитивный контроль**: прогон на входе, который гейт заведомо обязан завалить; не покраснел — сломан гейт, а не чист код. ⚠ **То же обязательно, когда проба ОПРОВЕРГАЕТ клейм о дефекте** — «дефект не наблюдается» самонеразличимо с «проба не достигает его формы», и богатый правдоподобный вывод этого не снимает, а маскирует: прогони её на состоянии, где дефект ЗАЯВЛЕН (коммит до фикса, ветка, конфиг) — не покраснела, сломана проба, а не клейм опровергнут. (Прогон rfc-10a: свип по микрозадачам «опроверг» класс стейл-FAIL полными трассами событий, а на пред-фиксном коммите дал тот же вывод — реджект освобождался ПОСЛЕ supersede, то есть форма дефекта не достигалась ни разу; верная форма взята из шипнутого теста и воспроизвела обе грани.) (Прогон rfc-nav-pipeline веха №1: pathspec `'packages/*/tests/'` — wildcard переключает git на wildmatch по ПОЛНОЙ строке пути, а путь файла на `/` не кончается, поэтому ЕДИНСТВЕННЫЙ бинарный критерий вехи печатал «пусто» и при 262 реально правленых тестах; вскрыто только сверкой с заведомо-красным `master...HEAD`, `ls-files` с той же формой дал 0 при 1167 файлах.) **Claim о `production`-поведении, зависящий от ОПЦИОНАЛЬНОГО слоя (плагин / флаг / dev-guard), проверяй на ДЕФОЛТНОМ/минимальном конфиге, не максимальном** — он может держаться лишь с opt-in-компонентом, которого в дефолте нет. (Сессия parse-segment: «production gate-first» держался лишь С `validation-plugin`; дефолтный bare core — валидация opt-in — ПРИНИМАЛ `/:y*`, что и вскрыло BLOCKER, замаскированный максимально-конфигурным чтением.) **Проба, читающая ПОТОК СОБЫТИЙ/логов, обязана зафиксировать снимок ДО своих же пост-вызовов** (диагностических navigate/cleanup-хелперов) — иначе события артефактов читаются как события испытуемого сценария; неожиданную event-находку ре-исполняй изолированной пробой без хелперов. (Сессия commit-gate: «spurious TRANSITION_ERROR на guard-пути» оказался SAME_STATES-эмитом post()-хелпера самого пробника — ложная грань дошла до RFC, вскрыта только чистым ре-прогоном.) ⚠ **Зеркальная половина: SETUP-вызовы ДО измеряемой операции тоже гоняют хуки, которые проба зарегистрировала** (`start()`, прогрев, первая навигация), поэтому хук-триггер срабатывает на ФИКСТУРЕ, а не на испытуемом, и к моменту измерения уже израсходован. Взводи триггер флагом ПОСЛЕ setup'а — **и обнуляй счётчики там же, потому что флаг закрывает только половину**: триггер, израсходованный на фикстуре, даёт ложный НЕГАТИВ, а счётчик, не сброшенный после неё, — ложный ПОЗИТИВ, и `armed` от второго не спасает. События setup'а (`start()`, прогрев, первая навигация) попадают в те же наблюдатели и читаются как события испытуемого. (Прогон rfc-nav-cancellation-scope: наблюдательный плагин зарегистрирован до `start()` → `SUCCESS=1` во ВСЕХ четырёх клетках матрицы, включая ту, где документ обещал «событий нет вовсе»; клетки читались как расхождение с доком, пока счётчики не обнулились после `start()` — после чего матрица сошлась дословно 4/4.) Симптом обратной половины — пустая трасса / не сработавший колбэк, читаемый как «эта точка входа арку не достаёт», то есть ложный негатив ровно там, где ищешь радиус. (Прогон rfc-1684: аборт из плагинных `onTransitionStart` / `onTransitionLeaveApprove` сработал на `router.start()`; две строки из трёх дали пустую трассу и едва не ушли в отчёт как недостижимые — под флагом `armed` обе воспроизвели дефект дословно.) **Пробу собирай по РЕАЛЬНОЙ поверхности API, не по сниппетам аудируемого RFC** — сними exports пакета (`Object.keys(require('<pkg>'))`, `package.json#exports`) и сигнатуру фабрики с её типов/тестов ДО прогона: проба, собранная по цитатам документа, наследует его неточности и падает TypeError'ом, маскируя проверяемый клейм. (Прогон rfc-file-routes: три холостых раунда подряд — `matchPath` из чужого интерфейса, `getRoutesApi` из корневого entry вместо subpath `/api`, `createMatcher(routes)` по памяти вместо `createMatcher(options)` + `registerTree(tree)`.) ⛔ **Если проба ПОДАЁТ колбэк, который зовёт библиотека** (кодек, guard, интерцептор, фабрика плагина, декодер), его форма — параметры И возвращаемое значение — тоже часть поверхности, и снимать её надо с шипнутого теста/типа, а не с текста RFC. Отличие от неверного импорта критично: колбэк неверной формы **не бросает** — он тихо становится no-op, а «ничего не произошло» неотличимо от опровержения клейма. (Прогон rfc-nav-pipeline phase-2: декодер написан в старой одномешковой форме `(p) => ({...p, q})`, тогда как кодеки двухканальны с `afa48879b` — ключ лёг на верхний уровень, ни в один канал не попал, и верный замер родителя чуть не ушёл в отчёт как REFUTED; на правильной форме `(a) => ({params:{...a.params,q}, search:{...a.search}})` он воспроизвёлся точь-в-точь.) **`cd` в Bash-туле липкий между вызовами**, а рецепт «гони из каталога пакета» этим и создаёт ловушку: каждую пробу запускай самодостаточно (`cd <repo> && … && cd <pkg> && node …`), иначе следующая команда стартует из каталога пакета и падает `no such file or directory` на путях от корня — а команды УБОРКИ (`rm -f` пробников) под липким `cd` не падают вовсе, а тихо промахиваются мимо цели, оставляя артефакты в чужом репозитории: факт удаления подтверждай `git status`, не кодом выхода — **и сам `git status` пиши с абсолютным путём (`git -C <repo> status`)**: под липким `cd` внутри worktree он отчитается о WORKTREE, то есть верификатор унаследует ровно тот баг, который ищет, и напечатает «чисто» про другое дерево. (Прогон rfc-two-pipelines: `rm -f packages/core/probe-*.mts` из каталога пакета напечатал warning про несуществующий `packages/core/packages/` и оставил оба пробника на месте.) **Команда может провалиться так, что провал читается как РЕЗУЛЬТАТ — три повторяющихся случая.** (1) В репо с глобальным coverage-порогом одиночный файл выходит **красным по покрытию**, а не по тестам, и хвост вывода состоит из `ERROR: Coverage … does not meet global threshold`, тогда как `Tests N passed` осталось выше и в `tail` не попало — суди по строке `Tests`, либо гони с `--coverage.enabled=false`. ⚠ И зеркальный случай: **отчёт покрытия не печатается с КРАСНОГО прогона вовсе**, а прототип рефактора красен ПО ПОСТРОЕНИЮ (намеренные N падений) — значит вопрос «покроется ли новая ветка?» через coverage не отвечается в принципе, сколько раз ни перезапускай. Инструментируй ветку счётчиками, по одному на КАЖДОЕ плечо, и суди по попаданиям: это и сильнее отчёта — различает «ветка исполнена» и «исполнены ОБА плеча», чего процент не показывает. (Прогон rfc-1649: клейм дока «новая ветка отката может оказаться непокрытой, потенциальный блокер отгрузки» снят одним прогоном — 37 попаданий в одно плечо, 1 в другое, — после двух холостых попыток вычитать coverage из прототипа с девятью намеренно красными тестами.) (2) В zsh **не квотированный glob-аргумент съедает шелл**: `grep -rn X --include=*.ts` падает `no matches found` и печатает ноль, что неотличимо от «в коде этого нет» — пиши `--include='*.ts'`. (3) **apply-шаг применил НОЛЬ, и следующий прогон измерил БАЗУ.** В zsh неквотированное `$VAR` в `for f in $VAR` НЕ расщепляется по словам (в отличие от bash), поэтому `cp`/`sed` получает весь список одной строкой и падает `No such file or directory` — а прогон ПОСЛЕ него печатает ровно то число, которое клейм и предсказывает, то есть провал применения маскируется под подтверждение. После ЛЮБОГО apply-шага (прототип, мутация, патч) докажи, что правка ЛЕГЛА — `grep -c` по внесённой строке — прежде чем верить прогону: зелёный тир без применённой правки неотличим от зелёного тира с ней. (Прогон rfc-1648: `for f in $FILES; do cp …` не применил ни одного из шести файлов прототипа, и «`tsc` чист + 198/3964 зелёные» было валидацией HEAD, а не варианта С.) **Сьют пакета гоняй через workspace-фильтр (`pnpm -F <pkg> exec vitest run <файл>`), а НЕ раннером из корня с `--config <pkg>/vitest.config`:** в pnpm-монорепо корневой include видит копии тестов внутри symlinked `node_modules` (workspace-линки, worktree-копии), и прогон одного файла превращается в тысячи чужих. Симптом — вал `FAIL` с путями вида `node_modules/.pnpm/**/tests/<твой-файл>` и ошибка про ненайденный `setup.ts`; это не красный тир, а неверный запуск. (Прогон rfc-nav-pipeline phase-2: `npx vitest --config packages/core/vitest.config.mts <file>` дал 4524 упавших файла за 73 с, `pnpm -F` тем же файлом — 65/65 зелёных за 0.4 с.) **Каждый цитируемый прогон — на СВОЕЙ минимальной фикстуре.** Общая фикстура, дополненная конфигом ради соседнего клейма, — неконтролируемая переменная: лишний `defaultParams`/`defaultSearch`/опция меняет вывод и читается как REFUTED цитаты. Совпал вывод — всё равно перепроверь на минимуме, прежде чем метить расхождение. (Прогон rfc-nav-pipeline ред. 6: маршрут-фикстура несла `defaultParams{z:"5"}` для клейма §10.5, и цитата §10.9 «`buildPath("a")` при `a→b` даёт `/a`» вернула `/a?z=5` — ложный REFUTED снят только повторной пробой на чистом forward-маршруте.) **Клейм, чьё условие — «операция ещё НЕ завершилась» (in-flight, parked, suspended), синхронной пробой не проверяется:** синхронный дубль добегает до конца внутри того же тика и попадает в СОСЕДНЮЮ клетку, где поведение часто обратное, — то есть даёт ложный REFUTED живой находки. «В полёте» воспроизводится только удержанием (async-guard на промисе-воротах, parked-интерцептор, незавершённый `await`), и ЧЕМ именно удерживаешь — назови до прогона. (Прогон fsm-as-state-owner: находка «вложенная навигация, ещё НЕ добежавшая, теряет свой результат» на синхронной пробе дала ОБРАТНОЕ — `SUCCESS:b`, результат цел; на том же сценарии с async-guard'ом воспроизвелась дословно — `START:a · CANCEL:a · START:b · SUCCESS:a`.) **Проба через optional chaining (`?.`) неразличима на ДВУХ исходах** — «метода нет» и «результат пуст» оба дают `undefined`. Прежде чем трактовать `undefined` как ЗНАЧЕНИЕ клейма, докажи, что вызов вообще состоялся: позитивный контроль на заведомо валидном входе либо чтение тела функции. (Прогон rfc-nav-pipeline ред. 24: `ctx.routes?.getQueryParams("nope")` вернул `undefined` и едва не стал REFUTED клейма «возвращает `[]`» — на деле не существовало `ctx.routes`, а исходник даёт ровно `[]`.) **Тот же класс на уровне СЛОЁВ: публичный примитив с именем внутренней стадии часто её КОМПОЗИЦИЯ.** Замеряя выход стадии, которую RFC называет по имени, сперва прочитай, что стоит между примитивом и стадией: обёртка может дописывать ровно ту нормализацию, чьё отсутствие ты проверяешь, и «гипотеза не подтвердилась» окажется замером не того слоя. (Прогон rfc-nav-pipeline ред. 25: `getPluginApi().forwardState` = ① *плюс* ② `separateChannels` (`Router.ts:275-292`); замер через него «опроверг» дефект ①, который на сыром ① воспроизводится и даёт BLOCKER-класс — findings спасло только чтение композиции.) **Клейм «тест X покрывает Y» проверяется ДО EOF, а не по верхнему docblock'у файла.** Хедер описывает ПЕРВЫЙ блок, а не файл: тир, дописанный вторым, регулярно противоречит собственному хедеру — и противоречие читается как REFUTED. Перечисли `describe`/`test.prop`-блоки скриптом либо дочитай файл; «в хедере сказано, что покрыт один кейс» — не доказательство, что покрыт один кейс. (Прогон rfc-two-pipelines: хедер `cancellation.properties.ts` описывает единственную точку приостановки и прямо выводит supersede из модели, а матрица на 25 клеток (`point × callSite × guarded × source`) лежит вторым блоком на 130 строк ниже под своим баннером — по одному хедеру верный гейт-клейм ушёл бы в отчёт сфабрикованной находкой.)

Зеркальный случай — артефакт из БУДУЩЕГО: несущий CODE-FACT о «только что сделанном» изменении не находится в рабочем дереве → прежде чем REFUTED, проверь несмёрженные ветки/worktree (`git log --all --grep`, `git branch -a --contains`): RFC мог писаться в сессии с параллельной веткой — тогда валидируй claim по той ветке и фиксируй в отчёте порядковую зависимость мержей, а не ошибку. (Сессия logger-into-core: «fsm+event-emitter уже в `core/src/foundation`» — в master папки нет, перенос жил в несмёрженной `worktree-fsm-ee-into-core`; без `--all`-поиска несущая предпосылка RFC ушла бы в ложный REFUTED.)
   - **EXTERNAL/THIRD-PARTY:** проверь в первоисточнике ПРОДУКТА, по убыванию силы: (1) **установленный инструмент** → запусти его (`<tool> --help`, реальный прогон/вывод — сильнейшее); в pnpm-монорепо пакет может быть НЕ виден из корня (строгая изоляция: dep только у workspace-консьюмера) — `require` по имени падает MODULE_NOT_FOUND, что НЕ значит «не установлен»: резолвь через `node_modules/.pnpm/<pkg>@*/node_modules/<pkg>`, каталог консьюмера (`benchmarks/node_modules/…`), а смок-прогон стороннего тула в scratchpad получает резолюцию симлинком корневого `node_modules` репо в каталог смока (инцидент rfc-1512: два холостых MODULE_NOT_FOUND подряд — analog-плагин и picomatch); для **существования/версии npm-пакета — `npm view <pkg> version`** (registry-факт; `npmjs.com` часто 403'ит WebFetch, а `E404` = пакета нет — валидное доказательство ОТСУТСТВИЯ, сильнее «я не нашёл»); **для статуса github-issue `/issues/N` (через API) НЕДОСТАТОЧЕН** — `state_reason: "completed"` бывает административным закрытием БЕЗ code-fix; cross-check `/issues/N/timeline` (есть ли merged-PR / release-tag у close-события) + `npm view <pkg> version` (вышел ли релиз с фиксом). `closed` ≠ resolved-in-code; один эндпоинт ведёт в обе стороны (closed-as-fixed ↔ still-broken). (Сессия-родитель: #822 `closed/completed` 6 дней назад, но `/timeline` без merged-PR + latest changesets без новой опции → workaround всё ещё за пользователем; вывод «фикс есть, peer-правка не нужна» был бы ложным.) (2) **context7** (`resolve-library-id` → `query-docs`) для актуальных доков библиотеки/CLI/сервиса; (3) **офиц. доки** через `WebFetch`; (4) `WebSearch`. Для load-bearing — cross-check ≥2 источника. Память НЕ источник. Не проверяемо (платное/закрытое/нерелизнутое API) → пометь **ASSUMPTION**, не утверждай. (Примеры сессии-родителя: «turbo не шардит matrix OOTB / нет DTE» — CLI `--help` + context7 Turborepo; shape `turbo query affected` — прогон CLI; «arm64-runners free для public-repo» — внешний GitHub-факт → офиц. доки/web.) **Когда RFC даёт shell-команду, чтобы ДОБЫТЬ значение для конфиг-поля/токена** (хэш/id для вставки в `packageManager`, lockfile, `.npmrc`) — прогони её и сверь **формат вывода** (кодировку/алгоритм/длину) с форматом ЦЕЛЕВОГО поля, не только корректность значения: правильное значение в неправильной кодировке тихо ломает шаг и проваливает его же цель. (Сессия-родитель: `npm view … dist.integrity` отдаёт `sha512-<base64>`, а поле `packageManager` требует `+sha512.<hex>`; `dist.shasum` вовсе sha1 — наивная вставка = малформед.)
   - **COUNT:** `ls`/`grep` и пересчитай (в сессии-родителе агент насчитал 33 пакета, реально — 32).
   - **PERF/EMPIRICAL:** прогони реальную команду и засеки (`time`, turbo `--dry=json`/`--summarize`, `.turbo/runs/*.json`); порог — откалибруй по реальной истории (`gh pr list` + `git diff`/turbo affected на последних N PR — распределение, не одна точка); скрипт-эскиз — прогони на реальных сценариях (его вывод = функциональный unit-тест без обвязки). Если репо ведёт трекаемый perf-ledger — бенч-клеймы сверяй с ним, ища сценарий по синонимам: имя в RFC может не совпадать с именем в ledger, и пустой grep по RFC-имени ≠ отсутствие данных (сессия url-model-v2: «query-scaling» в RFC = `search-param-scaling` в ledger, где посылка «лидерство 4×» оказалась «4/5 когорт + code-traced lag в пятой»). **Число из harness'а и число из документа могут быть в РАЗНЫХ ЕДИНИЦАХ**, и нормализатор живёт в коде бенча, а не в его выводе: раннеры печатают агрегат (латентность на батч, на итерацию, ops/s), а док цитирует стоимость одной операции. Прочитай сайт (`batched(N, …)`, `iterations`, `time`, `batch:`) ПРЕЖДЕ чем сравнивать — расхождение на порядки почти всегда единица измерения, а не находка. (Прогон rfc-10a: `buildPath/warm-static` отдал `663 458 нс` против документных `≈83 нс`; батч оказался 6144, реальная величина `≈108 нс` — без чтения `batched()` в отчёт ушёл бы «регресс в 8000×» вместо верного «якорь уехал на 30 % за счёт конвейера».) **Агрегат НЕ проверяет экстремум.** Когда док даёт и сводные числа по набору (среднее, число сверх порога, размер набора), и НАЗВАННОГО чемпиона по тому же набору, сверка агрегата не доказывает имя: среднее инвариантно к тому, какой член максимален, поэтому сошедшийся агрегат активно МАСКИРУЕТ мис-атрибуцию экстремума. Пересчитывай экстремум отдельно, поэлементно. Типовая подмена — «худший» прочитан как «самый дорогой по абсолюту», а не «с наибольшей дельтой». (Прогон slice-state-ownership: все агрегаты §5a сошлись ТОЧНО — +0.17 / +1.53 / +0.60 %, 12 · 24 · 66 арок, 5 и 6 сверх порога, — и на этом основании раздел чуть не был подписан; худшей render-аркой названа `isActiveRoute-search` 21.2→21.3 мс, самая медленная по абсолюту, дельта **+0.5 %**, тогда как +1.8 % дала `isActiveRoute-exact` 11.3→11.5.) **Сперва ищи СЫРЫЕ по-прогонные записи**, названные приложением дока (`*-results.jsonl`, логи прогонов, `summary.json`), и переагрегируй их сам: совпадение медиан доказывает числа дешевле и надёжнее ре-замера, а **число строк** доказывает заявленный размер выборки — величину, которую агрегат прячет полностью. (Прогон rfc-1648: все медианы §6/§6.1 сошлись до сотых, а «9 троек, 27 процессов» оказалось 7 троек / 21 — в сыром файле 21 строка, и никакая сверка медиан этого бы не показала.) Если замер ПРИНЦИПИАЛЬНО недоступен (нужен CI-hardware / прод-трафик) — пометь claim как **ASSUMPTION** и вынеси, что решение висит на неизмеренном числе; НЕ выдавай оценку за факт.
   - **Exit-код пробы снимай с самой команды, не через пайп** (`cmd; echo $?` или `PIPESTATUS`) — пайп возвращает статус ПОСЛЕДНЕЙ стадии, и зелёный хвост (парсер/`jq`/`head`) маскирует красную пробу. Вердикт — по наблюдаемому выводу пробы; exit-код лишь сверка. (Сессия R3: `validator --json | node-парсер; echo $?` дал `exit=0` от парсера — на несущем факте «валидатор отвергает пустые changeset'ы» это читалось бы как ПРОТИВОПОЛОЖНЫЙ вывод; спасло только то, что JSON-ошибки были в выводе перед глазами.) Для **async-пробника** (node async-IIFE) `exit=0` вдобавок ≠ «дошёл до конца»: невыполненный `await` при опустевшем event loop даёт молчаливый exit 0 и срезает хвостовые кейсы — печатай маркер-строку на КАЖДЫЙ кейс и суди по напечатанным маркерам, не по коду выхода. (Сессия rfc-1435: вечно-pending leave-промис завесил ВТОРУЮ навигацию того же пробника — CASE2/3 молча не выполнились при exit=0.) Альтернатива IIFE — **top-level `await`, но у `tsx` он требует расширения `.mts`**: на `.ts` внутри CJS-пакета esbuild падает «Top-level await is not supported with the cjs output format». И **не режь вывод пробы `tail`/`head`** — маркеры теряются молча ровно так же, как при раннем exit; печатай компактно и читай целиком. (Прогон rfc-nav-pipeline ред. 11: `.ts`-проба не стартовала вовсе, а `tail -30` позже срезал первый кейс — два лишних раунда на ровном месте.) **Тот же класс — у ВОЗВРАТА API, чей документированный отказ есть логируемый no-op:** успех и отказ возвращают одно и то же (часто `void`/`undefined`), поэтому колонка вердикта, снятая с возврата, самонеразличима. Снимай вердикт с СОСТОЯНИЯ, которое операция обязана была изменить (членство в дереве/реестре, `getState()`, счётчик), плюс позитивный контроль на заведомо проходящем входе. (Прогон rfc-1684: `getRoutesApi().replace()` отдаёт `void` и при применении, и при заблокированном во время навигации no-op'е — проба напечатала «применён» для двух клеток, где ничего не применилось, и только `logger.error` в выводе выдал подмену; пересъём по `api.has("z")` инвертировал обе клетки.) ⚠ **Отдельный слепой наблюдаемый — ПОРЯДОК событий.** Счётные пины (`toHaveBeenCalledTimes`), матрицы клеток и проверки исхода инвариантны к перестановке эмитов, поэтому инверсия вида «терминальное событие раньше стартового» проходит весь тир, не покраснев ни разу. Если правка двигает ТОЧКУ эмита (а не его наличие), снимай СПИСОК событий — наблюдатель, взведённый флагом после setup, — и сравнивай с базой; количество тут не различает ничего. (Прогон rfc-nav-cancellation-scope: прескрипция дока давала `$$cancel` → `$$start` вместо `$$start` → `$$cancel` при 4056/4056 зелёных, и ни один пункт гейта самого документа этого не ловил.) ⚠ **А КАНАЛ инструментирования выбирай раньше, чем наблюдаемое: `console.*` внутри тестового прогона самонеразличим — `setup`-файл пакета может глушить консоль (`console.log/warn/error = () => {}`), и проба печатает ноль попаданий при заведомо исполняемом коде.** Перед первым выводом грепни setup на переопределение `console`; надёжнее вообще не консоль, а побочный эффект, который setup перехватить не может — `fs.appendFileSync` в файл (он же переживает воркеры vitest, тогда как счётчик на `globalThis` живёт по воркеру), — либо наблюдаемое уровнем выше по правилу абзацем раньше: список событий, счётчик вызовов, состояние. (Прогон rfc-opts-normalisation: зонд в `completeTransition` дал 0 попаданий и на прототипе, и НА БАЗЕ, где функция исполняется заведомо; спас только базовый контроль, а механизм в итоге снят событийным потоком — `events=[]` против `[START,CANCEL]` — за один прогон.)
   - **Чистота рабочего дерева для git-diff/affected-проб (скил read-only → одноразовый worktree).** Инструменты, считающие affected по git (`turbo affected`/`turbo query affected`/`nx affected`/`--filter='...[ref]'`/`lint-staged`), **сворачивают незакоммиченные правки рабочей копии в результат** — грязное дерево даёт ложный affected (твои правки читаются как «затронуто»). Гоняй такую пробу в **detached-worktree на нужном ref** (`git worktree add --detach <scratch> <ref>` → прогон → `git worktree remove`; turbo-бинарь из основного репо через `--cwd`/`--skip-infer`), удаляемом в конце — скил ничего не пишет в репо, worktree безопасно сносится. Сначала `git status`; дерево грязное и проба про affected → worktree обязателен. **Тот же worktree — единственный способ атрибутировать РЕГРЕССИЮ конкретному коммиту (BASE↔HEAD), и там есть своя ловушка: в worktree нет `node_modules`**, поэтому `--import tsx` падает `ERR_MODULE_NOT_FOUND` ещё до пробы. Симлинкуй корневой `node_modules` основного репо внутрь worktree (он даёт лишь раннер), а испытуемый пакет импортируй **относительным путём ИЗ worktree** — по workspace-имени резолюция уведёт в HEAD-копию, обе стороны сравнения станут одинаковыми, и регрессия «не воспроизведётся». Приписав дельту к ref'у, сузь её до ОДНОГО коммита вторым worktree на подозреваемом. (Прогон rfc-nav-pipeline ред. 30: так «шаг — no-op» превратился в «инверсия приоритета, внесённая ровно этим шагом».) **Отдельно — АТРИБУЦИЯ БАЗЫ: прежде чем выносить вердикт, сними `git log master..HEAD` и `HEAD..master`.** Если несущий REFUTED опирается на код с **незамерженной** ветки — это не «клейм устарел», а «клейм устареет при мерже», и проверять обязан ОБЕ стороны (`git show <base>:<path>`), а отчёт — называть ref, на котором клейм опровергнут. Для RFC, запланированного ПОСЛЕ чужого PR, базой аудита является ветка того PR, а не `master`; иначе прототип-гейт/приёмка документа замеряют состояние, которого к моменту работы уже не будет. (Прогон rfc-10a: три BLOCKER'а опровергаются кодом #1588/#1607, которого на `master` нет — `git show master:…` показал, что там опровергнутая §8.1 всё ещё верна; из этой развилки родилась целая правка раздела «Координация», а без неё вердикт был бы неатрибутирован.) (Сессия-родитель: A5-проба `turbo query affected` на грязном `packages/core` вернула `core` в affected → выглядело как REFUTED линчпина; чистый worktree дал `[rx]` без core.) ⛔ **Рой read-only агентов и твои собственные мутации дерева НЕСОВМЕСТИМЫ, и это отдельный класс от грязного дерева на старте.** Пока агенты сканируют рабочую копию, любая твоя проба-мутация (прототип, мутационная валидация, apply-шаг) делает их вердикты недостоверными — а распознать это по отчёту нельзя: ложный REFUTED выглядит как находка, потому что агент честно цитирует `file:line` того, что видел. Лечится одним из трёх: свои пробы в одноразовом worktree; либо все мутации ПОСЛЕ возврата всех агентов; либо в промпте КАЖДОГО агента предписать сверку через `git show <база>:<путь>`, а не чтение рабочей копии. (Прогон rfc-1663: рой из семи агентов шёл параллельно со сборкой прототипа на 8 путей — два агента отчитались, что видят применённый план, один выдал REFUTED на верном числе `85` — «20/97», — а второй уцелел только потому, что сам догадался сверяться через `git show`.) ⚠ **База двигается и ВПЕРЁД — прямо во время прогона, и это отдельный класс от незамерженной ветки.** Документ, содержащий выполнимую рекомендацию, провоцирует автора выполнить её, пока ты меришь: снимок `git log <база документа>..HEAD` на СТАРТЕ пуст, а к моменту вердикта — нет. Поэтому пере-снимай его перед каждым эмпирическим вердиктом, а не однажды. Симптом ни с чем не спутать: измеренное число БОЛЬШЕ документного, и **знаменатель прогона выдаёт виновника точнее любых дат** — расхождение в единицы тестов равно размеру свежего тест-коммита. Лечится не переизмерением и не «клейм устарел», а возвратом К БАЗЕ: одноразовый worktree либо, если дельта — один-два файла, `git show <база>:<путь>` поверх них на время прогона (с `trap`-восстановлением). Вердикт после этого атрибутируется обеим точкам. (Прогон rfc-1650: мутация «второго окна» дала 6 падений против документных 2 — это уже писалось в отчёт как REFUTED несущего клейма, пока `git log -S` по имени `describe`-блока не показал коммит, отгруженный автором через 15 минут после сохранения дока и реализующий ЕГО ЖЕ рекомендацию; на возвращённой базе числа сошлись 4042/267/2 точь-в-точь, а находка превратилась в «рекомендация выполнена».)
   - **Hardware-bound vs hardware-invariant — ключевое различие, не путать.** *Логика/структура* (классификация, routing-решение, граф affected, счётчики) — hardware-**инвариантна**: локальный прогон = истина и для CI, переносится 1:1. *Тайминги* — hardware-**bound**: локальная абсолютная цифра на CI-цель НЕ переносится, и сравнивать её с CI-оценкой дока **нельзя** (apples/oranges → не пиши «REFUTED» из локального замера CI-числа). Переносится лишь **отношение**, и только когда обе величины упираются в ОДИН ресурс (CPU/CPU — `angular` vs `preact` bundle: да; CPU/IO — dry-run-операция vs checkout+install: нет, разные узкие места). Абсолютный CI-таргет (`≤Xs`) меряется ТОЛЬКО на CI-железе — иначе ASSUMPTION. Прежде чем мерить тайминг локально, спроси: «это про скорость (hardware-bound → нужен CI или same-bottleneck ratio) или про корректность (hardware-invariant → локально достаточно)?».
4. **Раздели «claim технически верен как сформулирован» и «вывод держится».** Посылка может быть верна при неверном выводе — и наоборот (верный вывод на слегка кривой цитате).
5. **Для DESIGN-DECISION — охота за непропагированными копиями.** `grep`-ни сигнатурные строки старого решения по всему документу; каждое вхождение, противоречащее принятому решению — находка. Решение в прозе ≠ решение в алгоритме: если псевдокод не enforce-ит решение, реализация воспроизведёт баг, против которого решение и принято. **Отдельный подкласс — САМО-РАЗОРУЖАЮЩЕЕСЯ условие: правило, которое док написал о собственном будущем** («если к моменту X случится Y — это слагаемое отпадает», «проверить перед написанием, а не унаследовать»). Это клейм с триггером, и проверка триггера — работа аудита, а не автора: сработавший и не отражённый триггер = находка того же класса, что непропагированное решение. ⚠ Но заслуга принадлежит ДОКУ — фиксируй, что он предсказал развилку, вместо того чтобы подавать сработавшее условие как небрежность; иначе аудит наказывает ровно ту дисциплину, которой сам требует. (Прогон rfc-10a ред. 11: §11 заранее записала «если клетка (а) окажется закрыта иначе — слагаемое отпадает»; клетку закрыл вышедший позже фикс, и это перевело находку из «док устарел» в «док предсказал, триггер сработал».)

## Классификация находок (severity)

- **BLOCKER** — реализация по документу даст неверный код / ложно-зелёный тест / воспроизведёт описанный баг (непропагированное решение в алгоритме; ordering-баг в псевдокоде; инвариант, противоречащий другому решению; внутреннее противоречие в контракте/представлении данных).
- **SHOULD-FIX** — не ломает реализацию, но недоспецифицировано/вводит в заблуждение (over-promise механизма; недоопределённая область инварианта; неозвученный trade-off).
- **MINOR** — цитата/факт/счётчик мимо при верном по сути выводе; редундантный инвариант; формулировка.

Каждая находка: тип claim'а + `file:line` доказательства из ground-truth + **конкретная однострочная правка**.

## Починка (только при `--fix`)

Правится МЕХАНИЧЕСКОЕ и однозначное:
- фактические исправления (неверная сигнатура/счётчик/цитата → верная, подтверждённая ground-truth);
- пропагация уже-ПРИНЯТОГО решения во все таблицы/псевдокод/DoD/сводку (+ `grep`-доказательство нулевого остатка старой формулировки);
- снятие противоречия, когда корректная резолюция однозначна (одна сторона уже канонизирована решением) — **либо когда однозначной её делает РЕ-ЗАМЕР**: числовое расхождение между двумя ячейками ОДНОГО документа мерить дешевле, чем выносить владельцу, и по букве «одна сторона канонизирована» такой случай ушёл бы к автору зря. ⚠ Не предполагай, что таблица каноничнее прозы. (Прогон slice-state-ownership: таблица §5b говорила −178 Б, проза −372, сумма её же слагаемых −343 — три числа на одну величину, ни одно не канонизировано; ре-замер по коммитам-точкам воспроизвёл ПРОЗУ — S5b −642 против документных −643, S7 −57 против −57, итог −374 против −372, — а не сошлось ровно одно слагаемое, из-за которого арифметика и не закрывалась.);
- ordering-фиксы в псевдокоде, восстанавливающие заявленную семантику.

⚠ **Правя СЧЁТ или ПОРЯДКОВЫЙ номер по первоисточнику, сперва проверь, не согласован ли он ВНУТРИ дока под его собственным разбиением.** Если да — сохраняй нумерацию дока и выноси расхождение сноской: переписывание «как в источнике» ломает соседние предложения, которые на этот счёт опираются, и создаёт новое противоречие вместо снятого. (Прогон slice-state-ownership: фикс «шестой → пятый» по леджеру первоисточника разошёлся с соседним предложением того же абзаца «все ПЯТЬ пунктов приземлились» — счёт дока был внутренне непротиворечив под его расщеплением пункта надвое и отличался от источника только нумерацией; поймано перечиткой переструктурированной зоны, откачено на «шестой» + сноска.)

При правке псевдокода **читай его как исполнение** — наивная вставка может оказаться мёртвым кодом (в сессии-родителе throw для `[[...slug]]`, вставленный после dot-check, был бы недостижим, т.к. `[[...slug]]` содержит `.`; пришлось переупорядочить проверки и сузить dot-check до имени токена).

⛔ **Всё, что ты САМ сочинил, — тоже claim, и планка для него ВЫШЕ, а не ниже, чем для клеймов дока.** Аудит валидирует чужие утверждения — но `--fix` и раздел «советы» вносят в документ ТВОИ: предлагаемый инвариант/property, рекомендованное изменение поведения, «правильную» формулировку взамен опровергнутой. Для доковых клеймов ты ищешь подтверждение первоисточником; для своих — **ищи КОНТР-ПРИМЕР, и найди его ДО записи в документ**, а не после. Минимум: (1) для property — прогони её мысленно (лучше кодом) на входах, которые док объявляет РАЗНЫМИ по дизайну; property, включающая намеренно-различающиеся точки, ложно-красная (тот же дефект, что §8-критерий «эквивалентность текущему поведению» на баг-грани); (2) для изменения поведения — построй самый ЧАСТЫЙ сценарий фичи, а не тот, из которого родилась идея, и проверь, что он не деградирует; (3) вердикт формулируй как «выжило под атакой», а не «выглядит верно». Записанный без этого совет — новый ложный клейм внутри аудируемого документа, ровно того класса, который аудит ищет, и он опаснее исходного дефекта: он несёт печать «проверено аудитом». (Прогон rfc-nav-pipeline ред. 21→22: из пяти собственных рекомендаций, УЖЕ внесённых в RFC, три пали на первом же контр-примере — property «все точки входа на одном интенте дают один `Canonical`» была ложна по построению; blanket-резолв `forwardTo` в `isActiveRoute` гасил секционную ссылку в самом частом паттерне forwardTo; «guard переезжает на сырой аргумент» оставляло без надзора две из трёх популяций контракта.)

НЕ правится автоматически: выбор IN/OUT фичи, смена архитектуры, переименование API — любой вопрос, требующий решения автора → выносится в отчёт как открытый.

⚠ **Пакетное переанкерирование гони ТОЛЬКО ПО ТЕЛУ, исключив журнал ревизий.** В журнале старые номера строк — **провенанс** прошлых прогонов (записи вида «`:708,750,794,836`→`:743,…`»), а не остаток: замена по всему файлу переписывает историю в фикцию, причём молча и необратимо. Режь файл по заголовку журнала ДО замены. Тем же разрезом классифицируй residue-чек (body / journal) — иначе легитимные journal-вхождения читаются как непропагированный остаток и провоцируют вторую, разрушительную правку. (Прогон rfc-10a ред. 11: девять пар анкеров, четыре из которых живут и в теле, и в журнальных записях ред. 5/6/9/10.)

Подними ревизию в шапке + добавь запись в журнал ревизий (что и почему). **Запись в журнал — последним шагом, после residue-чека, и каждый заявленный в ней фикс подтверди грепом.** Журнал, перечисляющий не применённую правку, — новый ложный клейм внутри аудируемого документа, т.е. ровно тот дефект, который аудит ищет. (Прогон rfc-nav-pipeline ред. 6: журнал заявлял фикс line-цитаты `§10.7 :38-46 → :37-45`, которого не было — вскрыл только финальный residue-греп.) ⚠ И после вставки проверь ПОРЯДОК строк (`grep -n` по номеру ревизии): якорем служит предыдущая запись, а в журнале, отсортированном по возрастанию, она ПОСЛЕДНЯЯ — значит наивная вставка «перед якорем» ставит новую ревизию не в конец, а между предпоследней и последней. (Прогон fsm-as-state-owner: ред. 7 встала между 5 и 6, вскрыто только финальным `grep -n "^| [0-9] |"`.) ⚠ **И пере-сними журнал НЕПОСРЕДСТВЕННО перед вставкой, а не по снимку начала прогона: аудируемый документ мог измениться под тобой.** Правило «сверь fingerprint» ниже (Оговорки) написано про ЧУЖИЕ ground-truth файлы; тот же риск есть у самого правимого дока, и цена другая — не устаревшая цитата, а **коллизия номера ревизии**: владелец заводит свою запись параллельно, ты вставляешь свою с тем же номером, и `grep -n` по номеру покажет ДВЕ строки «6». Проверять надо не только порядок, но и уникальность. (Прогон slice-state-ownership: пока шли правки, владелец добавил ред. 6 со своим содержанием; моя запись встала вторым номером 6 — пришлось перенумеровать в 7, переставить в начало нисходящего журнала и починить две внутренние ссылки «ред. 6», которые я же и написал.)

## Жёсткие правила

- Доказывай **первоисточником**, не документом. RFC — не свидетель собственной корректности. Это включает код, который RFC **цитирует** (комментарий, заголовок скрипта, docstring): проверяй против *первичного* источника (config / поведение / прогон), а не против цитаты — комментарий устаревает, RFC наследует устаревание, а claim, звучащий и в RFC, и в цитируемом им коде, ощущается дважды-подтверждённым, оставаясь **одним эхом**. (Сессия-родитель: и RFC, и `cap-major.mjs:15` хором «no config to prevent this» — а реальный `config.json` уже содержал `onlyUpdatePeerDependentsWhenOutOfRange`; claim REFUTED только походом в config, не в цитату.) **Тот же статус — у audit-log / ревизионной записи в шапке САМОГО документа, особенно оставленной прошлым прогоном `/audit-rfc`:** её вердикты (CONFIRMED / No BLOCKER / «ready to implement» / выбранный bump) — subagent-grade claims, не установленный факт; несущую посылку под выводом «ready/patch/GREEN» перепроверь исполнением с нуля — прошлый прогон мог рубер-стемпнуть plausible-but-wrong. (Сессия parse-segment: Rev-1 audit-log заявлял «production gate-first → patch → No BLOCKER → ready»; bare-core прогон `createRouter([{path:'/:y*'}])` опроверг посылку — BLOCKER, а не patch.) Это касается и документа, написанного ЭТОЙ ЖЕ сессией: свежесть прогона защищает от устаревания, но не от артефактов интерпретации — неожиданные грани, не подтверждённые независимым источником, ре-исполняй изолированной пробой прежде чем принять их как ground-truth.
- На load-bearing/неожиданном claim'е НЕ доверяй вердикту субагента без собственной перепроверки (компиляция/прогон/трассировка). Subagent-резюме — гипотеза, не факт.
- TYPE/COMPILER/regex/algorithm — только эмпирика (`tsc`/`node`/трассировка), никогда «логически очевидно».
- Claim о стороннем продукте (API/поведение/лимит/опыт) проверяется в **первоисточнике продукта** (CLI/context7/доки/исходники/web), НЕ из памяти и НЕ из утверждения RFC. Стек bleeding-edge — training систематически отстаёт; «я знаю, как работает X» без захода в источник = находка-в-зеркале. Для установленного инструмента прогон его CLI бьёт любые доки.
- Решение «исправлено» ТОЛЬКО когда пропагировано везде; докажи `grep`-ом нулевой остаток старой формулировки. ⚠ **И верификацию СВОИХ правок гони по ОКНУ строк, не по одной:** прозу переносит по ширине, поэтому однострочный греп по фразе, которую ты только что вписал, даёт ложный ноль ровно так же, как на вызовах API, — а читается он хуже, как «правка не легла», и провоцирует вторую, дублирующую. (Прогон rfc-opts-normalisation: чек-лист из 20 фиксов отрапортовал ⛔ на единственной правке, лёгшей с переносом между «это уже» и «спред-копия».) Резидью-паттерн включай с уникальным якорем строки (ключ строки / первая ячейка), не только заменённым хвостом — одинаковые хвосты соседних строк таблицы дают ложный остаток на строке, которую менять и не требовалось. (Прогон rfc-1439: хвост «есть ×4 + AOT-only» изменённой M4 легитимно жил и в неизменяемой M3 — потерян верификационный раунд на разборе ложного остатка.) **Правка, объясняющая снятый дефект, цитирует его дословно**, поэтому residue-чек обязан различать *остаток* и *цитату-объяснение* — классифицировать `Read`'ом каждое вхождение, а не судить по счётчику: и ложный ноль, и ложный не-ноль здесь одинаково дороги. (Прогон rfc-nav-pipeline веха №1: три подсвеченных вхождения сломанного pathspec оказались собственными предупреждениями `--fix`, а четвёртое — настоящим непропагированным остатком в журнале ревизий канона.) **Для документа из СЕМЬИ (зонтик + дочерние RFC, док + его резюме/сводные таблицы в родителе) пропагация и grep нулевого остатка обязаны покрывать ВСЕ документы семьи** — родитель дублирует формулировки дочерних, и правка в одном файле при живой копии в сиблинге = непропагированное решение, доживающее до следующего аудита. (Прогон зонтика url-model: обе SHOULD-FIX — хвосты собственных правок M1/M2, не долитые в §8/§14 зонтика.) ⚠ И читай производный артефакт ЦЕЛИКОМ, а не только на резолвимость цитаты: он мог ОБОГНАТЬ источник — issue/PR-описание, написанное ИЗ дока, дописывается позже и несёт разбор, которого в доке нет, так что расхождение — находка в ДОКЕ, а не в производном. (Прогон rfc-1648: тело issue несло блок про порядок работ и ВЕРНУЮ трактовку born-dead арки, тогда как §5.2/§9 дока обещали механизм, которого нет; обе SHOULD-FIX пришли из чтения потомка.) **Решение, меняющее СЧЁТЧИК, грепай и цифрой, и числительным словом** («7» И «семи»/«seven»): прозаические эха («размазанную по 7 точкам» в шапке-визии, «в семи местах») переживают паттерны, построенные от заменённых строк таблиц. (Прогон rfc-nav-pipeline: смена «7 точек» → 9 — residue-чек по заменённым строкам зелёный, три прозаических эха вскрыты только обязательной перечиткой + грепом числительного словом.) **Пакетную замену гони скриптом, печатающим счётчик применений НА КАЖДУЮ пару** (`применено N/M` + список несработавших): `0 вхождений` — это находка о ТВОЁМ паттерне, а не о документе, и без счётчика правка молча не применяется, а residue-чек потом покажет её как «непропагированный остаток». Типовая причина нуля — markdown-разметка, съехавшая внутрь искомой строки (`**хвост)** текст` против `**хвост) текст**`), поэтому паттерн строй по содержимому, а звёздочки оставляй снаружи; вторая — предыдущая пара уже переписала подстроку следующей, поэтому строй пары от самых длинных к коротким и не вкладывай одну в другую. (Прогон rfc-nav-pipeline phase-2: 18 из 19 пар применились, девятнадцатая молчала бы до финального грепа.)
- Верный вывод на кривой цитате → чини цитату, вывод сохрани. Не выбрасывай хороший вывод из-за плохого адреса.
- Дизайн-выбор автора — не «ошибка», пока не порождает противоречие. Не навязывай вкусовщину под видом находки.
- Раздели **измеренное и оценочное**. Оценка, поданная как факт — находка. Load-bearing-оценка, гейтящая решение, должна быть либо измерена, либо явно помечена ASSUMPTION+RISK с планом замера. 5-минутный замер бьёт хедж-вердикт «вероятно ок» — стремись получить данные, а не обойти их.
- Раздели **измеренное и измеренное КОГДА**. Если шапка/журнал документа сами заявляют «issue X исправлен коммитом Y» (тем более — коммитом СЕГОДНЯШНИМ), КАЖДАЯ эмпирическая строка, описывающая симптом X, обязана быть перепрогнана на HEAD: провенанс-замер, оставленный в настоящем времени, — тот же plausible-but-wrong, только состаренный собственным прогрессом дока, и он переживает статус «все клеймы проверены прогоном». Триггер дешёвый: сверь mtime `dist` / дату последнего замера с датами фикс-коммитов из шапки. ⚠ **Тот же триггер применяй к АНКЕРАМ, а не только к замерам, и с особым подозрением — к файлу, который правил САМ прогон** (docs-фикс, комментарий, переименование): его строки сдвигаются последними, а re-anchor-список прогона систематически его пропускает, потому что файл ощущается «уже обработанным». Дешёвая проверка перед вердиктом: `git log --since='<mtime документа минус час>' -- <файлы, которые док цитирует>`. (Прогон fsm-as-state-owner ред. 10→11: комментарная правка `d038657ae`, отгруженная самим прогоном за **43 секунды** до сохранения документа, сдвинула на +10 строк ВСЕ анкеры в этом файле — журнал при этом заявлял «анкеры пересняты» и перечислял 13 позиций, среди которых ни одной из него.) Провенанс не удаляй — пометь «замер ДО `<sha>`» и допиши текущий исход. Отдельно проверь, не стал ли ОСТАВШИЙСЯ симптом КОРРЕКТНЫМ поведением после фикса (иначе фаза миграции будет чинить не-баг). (Прогон rfc-nav-pipeline ред. 11: два фикса отгружены за 1.5 часа до аудита — 2 строки таблицы «проверенных фактов» REFUTED на HEAD, §A.2 противоречила собственному ✅-буллету четырьмя строками ниже, а уцелевший `Missing required param` оказался ровно тем исходом, который фикс и предписывает.)
- Раздели **измеренное и измеренное В КАКОЙ КОНФИГУРАЦИИ**. Когда док отвергает альтернативу контр-примером, сверь конфигурацию замера у ОБЕИХ сторон: цена статус-кво и цена альтернативы обязаны меряться в одной. Разные конфигурации (bare core vs с opt-in плагином; дефолтные опции vs максимальные) дают внешне решающий контр-пример при неопределённом сравнении. И отдельно — **прогони отвергающий контр-пример на самом статус-кво**: часто тот же отказ там уже живёт, только на меньшей популяции, и тогда «альтернатива хуже» верно количественно, а не качественно. (Прогон rfc-nav-pipeline ред. 24: цена (б′) названа для bare core, контр-пример против (в′) прогнан с плагином и схемой; на статус-кво тот же отказ воспроизвёлся на intent-со-строкой — вывод устоял, но обоснование пришлось переписать.)
- Push/commit не делай без явной просьбы.

## Оговорки (НЕ метить как находку)

- **PROSE/MOTIVATION** не обязана цитировать код — мети только противоречия в ней.
- **CROSS-REF в правильную сущность, но слегка не тот файл/секция** — MINOR (суть важнее адреса), не BLOCKER.
- **Субъективное дизайн-предпочтение** без противоречия — не ошибка.
- **Не каждое число нужно мерить** — только load-bearing, гейтящее решение. Цифра, честно помеченная «оценочно, замер в фазе X» с планом — это правильная дисциплина (награждай, не мети как находку). Estimate ≠ ошибка; estimate, выданный за факт — ошибка. ⚠ Но «награждай» ≠ «оставь висеть»: **раздел «что НЕ проверялось» / «риски» аудируемого дока — это список работ АУДИТА**, а не оговорка, снимающая вопрос. Пункт, закрываемый ОДНИМ прогоном (покрыта ли новая ветка прототипа, воспроизводится ли названный побочный эффект), меряй и переводи в измеренное — честная пометка автора заслуживает того, чтобы её сняли, а не процитировали. (Прогон rfc-1649: два таких пункта закрыты по одному прогону каждый; один док называл «потенциальным блокером отгрузки» — замер его снял, второй числился «обнаружено чтением, пробой не подтверждено» — проба подтвердила дословно.)
- **Сторонний продукт, чьё поведение нельзя проверить** (закрытое/платное/нерелизнутое API) → пометь **ASSUMPTION** с указанием, что нужен доступ/релиз; не выдавай память за факт. Если RFC сам честно назвал это гипотезой / «надо измерить» (как arm64-дельта) — это дисциплина, не находка.
- **Re-audit гигиена:** после слов автора «исправил» сперва сверь, что читаешь ТЕКУЩИЙ файл — fingerprint (`stat` mtime/size + `md5`); если твой read выглядит неизменным, а автор настаивает — пере-`stat`, кэш инструментов/ФС может отставать от свежего сохранения. Не выноси «изменений нет», не сверив fingerprint. (RFC под `.claude/` — gitignored: `git diff`/`git status` для него всегда пусты — верь содержимому/хэшу, не git.) **Первым шагом прогона снимай `git log --since="<mtime документа>"`** — для gitignored-дока его mtime и есть граница «что случилось после написания», и это дешевле любой сверки шапки. Ловит класс «база сменилась, пока документ лежал», который сверкой дат из шапки не ловится вовсе. (Прогон rfc-10a: одна такая команда вскрыла четыре фикса той же ночи — #1609–#1612 — закрывшие ровно те дефекты, которые документ числил открытыми, включая единственное заявленное им отступление от паритета.) ⚠ Но снятый на СТАРТЕ он отвечает только про прошлое: база уезжает и вперёд, пока ты меришь — см. «АТРИБУЦИЯ БАЗЫ» в Протоколе п. 3, там же признак и лечение. То же — для **ground-truth файлов, изменившихся ПО ХОДУ прогона** (нотификация системы / линтер / правка пользователя): line-цитаты по такому файлу пере-сними `grep -n` ПОСЛЕ изменения — вердикт «line-цитата верна/сдвинута», вынесенный по до-изменения read'у, невалиден. (Прогон rfc-1439: react/CLAUDE.md изменился внешней правкой посреди аудита — цитируемый диапазон :169-174 подтверждён только повторной съёмкой.)

## Валидация и отчёт

1. **Отчёт-таблица:** claim | тип | ground-truth (`file:line` / замер / context7·CLI·доки продукта) | вердикт (CONFIRMED / REFUTED / PARTIAL / STALE-CITATION / NOT-FOUND / MEASURED / ASSUMPTION) | severity | правка.
2. Раздели находки на **BLOCKER / SHOULD-FIX / MINOR**; для каждой — однострочный конкретный фикс с `file:line`.
3. **Вердикт о готовности:** оцени архитектуру (зелёная/нет) ОТДЕЛЬНО от исполнения; перечисли, что закрыть до «готов к реализации»; явно раздели «ревизия документа» и «пересмотр архитектуры».
4. При `--fix`: после правок — `grep`-доказательство нулевого остатка старых формулировок + новый fingerprint файла; перечитай наиболее переструктурированные зоны, убедись, что псевдокод/таблицы не порвались. Таблицы проверяй **механически, а не глазами**: посчитай разделители на строку (минус экранированные `\|`) — строка с иным числом колонок сломана. Типовой источник — неэкранированный `\|\|`/`\|` внутри инлайн-кода в ячейке (`` `literal || resolved` ``); грепом по тексту он невидим и потому переживает несколько аудитов подряд. ⚠ **Экранируй пайпы В МОМЕНТ ЗАПИСИ, а не полагайся на чекер:** когда `--fix` вносит в ячейку кодовое выражение (`a \|\| b`, `A \| B`), самый частый автор этого дефекта — сам аудит, а не автор дока. Правка, пропагирующая изменившуюся формулу по нескольким таблицам, попадается на нём системно: одну ячейку экранируешь, соседнюю забываешь. Чекер тут бэкстоп, а не план. (Прогон rfc-10a ред. 11: та же двухчастная формула ушла в три ячейки, экранирована в одной — две строки §7.4 отрендерились с двумя лишними колонками, поймано только пайп-чекером.) ⚠ Считай пайпы в **СЫРОЙ** строке: стрип инлайн-кода перед подсчётом — естественная первая реализация — удаляет ровно те пайпы, которые ты ищешь, и чекер становится структурно слеп, печатая «таблицы целы». Это гейт, чей проход — пустой вывод, значит обязателен позитивный контроль (вставь `\|\|` в заведомо целую строку копии — не покраснел, сломан чекер). (Прогон rfc-nav-pipeline ред. 24: строка §4.4 рендерилась с двумя лишними колонками начиная с ред. 22 — вскрыта только подсчётом пайпов, притом в соседней таблице §7 те же пайпы были экранированы верно, т.е. конвенция в доке уже была.) ⚠ Правя документ на нелатинском языке, прогони заодно проверку на **смешанный скрипт** — и паттерн обязан быть ДВУНАПРАВЛЕННЫМ: `[А-Яа-яЁё]+[a-zA-Z]+|[a-zA-Z]+[А-Яа-яЁё]+`, а не `[А-Яа-яЁё]+[a-zA-Z][А-Яа-яЁё]+`, который требует кириллицу ПОСЛЕ латиницы и потому слеп к самому частому случаю — латинской букве на КОНЦЕ слова (`термa`, `схемa`). Латинская буква внутри кириллического слова невидима при вычитке и делает слово ненаходимым грепом — в том числе твоим же residue-чеком, который тогда печатает ложный ноль. (Прогон rfc-nav-cancellation-scope: односторонний паттерн отрапортовал «чисто», двунаправленный нашёл `термa` в правке, внесённой этим же прогоном.) (Прогон fsm-as-state-owner: три таких слова в собственных правках `--fix`.)

## Замечание

RFC/дизайн-доки под `.claude/` обычно gitignored (не трекаются) — изменения не видны в `git`, верифицируй содержимым и fingerprint'ом. Правки документа changeset не требуют. Push не делай без явной просьбы.

## Самокоррекция скила (ОБЯЗАТЕЛЬНО, в конце КАЖДОГО прогона)

Этот файл — живой; каждый прогон обязан его затачивать. После отчёта (Валидация п.1–3) вынеси короткую секцию **«Самокоррекция»** — критику не своей работы, а САМОГО ЭТОГО СКИЛА: где его текст промолчал, соврал, был двусмыслен или избыточен — и это стоило времени, лишнего шага или риска ошибки.

1. **Привязка к ИНЦИДЕНТУ, не общие советы.** Каждая правка — из конкретного момента ЭТОГО прогона: «скил сказал X / промолчал про X → реальность Y → я потерял/чуть не ошибся на Z». Нет инцидента — нет правки (не выдумывай улучшения впрок).
2. **Высокая планка: изменило бы исход?** Предлагай, только если правка реально предотвратила бы ошибку, сократила перебор или сняла двусмысленность, на которой ты споткнулся. Косметику и «было бы неплохо» — отбрасывай.
3. **Разовое ≠ паттерн.** Специфику конкретного RFC/стороннего продукта (разовую) → в отчёт/память по этому RFC, НЕ в скил. В скил идёт только повторяющийся класс, полезный СЛЕДУЮЩЕМУ аудиту ДРУГОГО документа.
4. **Сначала заточи, потом дописывай (анти-раздувание).** Предпочитай усиление существующего абзаца новой секции; если правка делает прежний текст избыточным — консолидируй, не дублируй.
5. **Предлагай, не применяй молча.** Выведи кандидатов таблицей (раздел | инцидент | предлагаемый текст), спроси разрешения. Применил по согласию → `.claude/commands/` это infra, в master напрямую, без changeset; коммить строго `git commit -o .claude/commands/<skill>.md -m …` (only-путь): staged-зона общая, в репо может работать параллельная сессия — голый `git commit` после неудачной первой попытки (напр. commitlint-реджект scope) утащит твой файл в её коммит (инцидент url-model-v2: правка скилла уехала в чужой feat(ci)-коммит). ⛔ **И ПЕРЕД правкой скила проверь, на какой ветке рабочее дерево и содержит ли она `master`:** `git branch --show-current` + `git log --oneline HEAD..master`. Непустой вывод второй команды означает, что файл на диске — СТАРАЯ копия, и твой Edit ляжет поверх неё: коммит тогда не только уедет на чужую ветку, но и ОТКАТИТ правки предыдущего прогона при мерже, а `git status` останется чистым и ничего не скажет. Это тот же класс, что «сверь fingerprint» в Оговорках, но с другой ценой — не устаревшая цитата, а молчаливый регресс живого файла. Сессионный снимок `gitStatus` в шапке не годится: он мог быть снят до переключения ветки. (Прогон rfc-nav-cancellation-scope: дерево стояло на ветке issue #1702, отстающей от `master` ровно на коммит предыдущего прогона этого же скила; я снял `git log master..HEAD` — пусто — и не снял ЗЕРКАЛЬНЫЙ `HEAD..master`, хотя правило атрибуции базы требует обоих. Итог: три правки легли на копию без правок предыдущего прогона, и коммит пришлось откатывать и переделывать на `master`.)
6. **Честность про «нечего править».** Прогон прошёл чисто и скил нигде не подвёл → так и скажи: «правок нет». Пустая самокоррекция честнее придуманной — пункты 1–2 это допускают.
