Проанализируй и обнови зависимость-инструмент: прочитай все релизы от версии в проекте до целевой и ответь на два вопроса — **безопасно ли обновлять** и **что даст обновление**. Если всё хорошо, подними версию и поправь инфраструктуру, которую задел бамп. Код пакетов (`packages/*/src`, `shared/`) команда не правит.

Входные данные:
$ARGUMENTS

Формат аргументов: имя зависимости (`tsdown`) или семейство связанных пакетов одной строкой (`size-limit @size-limit/preset-small-lib`); опционально целевая версия (`tsdown@0.23.0`).

> **Пакет eslint-экосистемы — не этот скил.** `eslint`, `@eslint/js`, `eslint-plugin-*`, `@*/eslint-plugin`, `eslint-config-*`, `typescript-eslint`, `@typescript-eslint/*`, `*-eslint-parser`, `@stylistic/*`, `eslint-import-resolver-*` → останови и используй `/bump-eslint`: линтер влияет набором активных правил, и процесс там свой. Исключение — `eslint-config-turbo`: он выходит одной версией с turbo и идёт с ним одним семейством (группа `turbo` в `.github/dependabot.yml`); его единственное правило `turbo/no-undeclared-env-vars` мерь как сканер-гейт.

## Бюджет токенов

**Один бамп — одна сессия.** Если до вызова скила в этой сессии шла другая работа, до Фазы 0 одной строкой предложи пользователю новую сессию (или `/clear`) с повторным `/bump-dep <аргументы>` и закончи ход: весь прежний контекст перечитывается на каждом шаге прогона. Продолжай в этой сессии, только если пользователь так ответил. Семейство пакетов в одних аргументах — один бамп.

## Фаза 0 — Локализация и доставка

1. **Где объявлена.** Карта объявлений: `grep -rn "\"<pkg>\"" package.json packages/*/package.json benchmarks/package.json examples/**/package.json cross-router-bench/package.json`. `pnpm up -r` правит весь корневой воркспейс (корень, `packages/*`, `shared`, `benchmarks`), а syncpack (`lint:deps`) держит в корне, `packages/*` и `benchmarks/` одну версию — точную, кроме `~`-группы `syncpack.config.mjs`. `examples/` и `cross-router-bench/` — отдельные pnpm-воркспейсы со своим lockfile: корневой `pnpm up -r` их не достаёт, нужен второй шаг (Фаза 4). Посчитай ожидаемый охват до применения.
2. **Доставка.** Бамп — инфраструктура: коммит прямо в `master`, без задачи, ветки, changeset и PR. Условие одно — пакета нет в `peerDependencies` публичного пакета: корень несёт только `devDependencies`, а внешних `dependencies` у публичных пакетов нет (это держит `published-dependency-authority.test.ts`):
   ```bash
   for d in packages/*/; do node -e "const q=require('./$d/package.json');
     if(!q.private && (q.peerDependencies||{})['<pkg>']) console.log('$d')"; done
   ```
   Пусто — применяй. Есть — диапазон peer опубликован: Фазы 1–3 проведи, а бамп — через задачу на миграцию (Фаза 3). Некорневые пакеты по умолчанию доставляют групповые PR Dependabot; чего они не показывают — `CLAUDE.md` § «Grouped Dependabot PRs».
3. **Цель** — из аргумента или `npm view <pkg> version`. Сначала прочитай `ignore` пакета в `.github/dependabot.yml` и его комментарий: заблокированный мажор — записанное решение с причиной, условием снятия и пакетами, которые двигаются вместе. Такой мажор бери только по явной просьбе пользователя, иначе цель — последняя версия, которую `ignore` пропускает. `current == target` — сообщи и закончи. Цель моложе `cooldown` её записи в `dependabot.yml` (`npm view <pkg> time`) — назови в отчёте возраст цели и пина: ждать выдержки или бампать сейчас, решает владелец. Пререлиз (в `dist-tags` не под `latest`): на пиннутом пререлизе Dependabot предлагает пререлизы той же версии-релиза и стабильные.
4. **Патчи pnpm** — `patchedDependencies` в `pnpm-workspace.yaml` и `grep patch_hash pnpm-lock.yaml`, на сам пакет и на его транзитивы. Ключ патча — точная версия: бамп делает патч неприменимым, и запись с файлом удаляются в той же правке до `pnpm up`.
5. **Парная зависимость вне `package.json`.** Тул часто ходит парой с GitHub Action (`@changesets/cli` ↔ `changesets/action`): грепни `uses:` того же вендора в `.github/workflows/`. Мажор одного обычно тянет мажор другого. PR Dependabot на мажор action правит только строку `uses:`, а неизвестные входы `with:` Actions молча игнорирует. Сверь каждый передаваемый вход со списком `inputs` целевого тега: `gh api "repos/<vendor>/<action>/contents/action.yml?ref=<tag>" --jq '.content' | base64 -d`.

## Фаза 1 — Релизы `(current, target]`

1. Репозиторий — `npm view <pkg> repository.url`. Сверь `npm view <pkg> version` с тегами (`gh release list`, `gh api repos/<o>/<r>/tags`): версия в npm бывает новее последнего тега, а тела релизов при едином `CHANGELOG.md` бывают пусты. Изменения версии без тега ищи в `## Unreleased` changelog или диффом тарболов.
2. **Точная дельта** — `gh api repos/<o>/<r>/compare/v<cur>...v<tgt> --jq '.commits[].commit.message'`. Автоматические notes `X.Y.0` перечисляют всё от `X.(Y-1).0`, включая уже установленное. В окне бывает back-merge-коммит `release …` со встроенным changelog прошлой версии: его тело отбрасывай.
3. **Changelog пуст или неточен — сравнивай по факту.** Пакетное тегирование монорепо, тонкая CLI-обёртка (`Updated dependencies → <core>@x`), сиблинги с общей версией: иди к пакету, который держит предмет проверки (движок, реализации правил), а не к тому, чьё имя звучит как ядро, — к его changelog, а если тот пуст, к диффу тарболов. Раскладку тарбола выясняй `find`, а не предполагай.
4. **Движки.** Сравни `npm view <pkg>@<cur> dependencies optionalDependencies --json` с целевой версией. Значимый сдвиг движка (minor или major транзитива) разбирай как отдельный релиз по его changelog: minor хоста бывает новым кодогенератором всего вывода. Обёртка над нативным бинарём держит движок в `optionalDependencies`, и её пины протухают: сравни их по всем версиям диапазона, а после установки сверь `<tool> --version` с целью. У пакета без зависимостей глубину бампа меряют коммиты `compare`, а не дифф `dist`: ре-бандл двигает почти каждую строку.
5. Для мажора — migration guide (`WebFetch`, `context7`).
6. Сгруппируй по версиям и пометь тип: **bugfix / feature / deprecation / breaking / chore**. Semver-метка глубину не задаёт: фичи и breaking приходят и в patch, поэтому каждый релиз диапазона читай целиком.

## Фаза 2 — Влияние на проект

Каждое значимое изменение сопоставь с реальным кодом и конфигами.

**Релевантность — по фактическому запуску, и первый фильтр — конфиг тула.** Сначала конфиг: форматы, входные корни и имена ключей снимают целые фиксы. Затем запуск: флаги, ОС (dev — macOS, CI — Linux), активные плагины; источники — скрипты `package.json`, стадии `scripts/checks.mjs`, workflows. Фикс пути, который мы не вызываем, нерелевантен. Тот же вопрос задай про гейт: какая задача реально проверяет файл тула; нет такой — проверяй точечно (`tsc --noEmit --ignoreConfig <file>`) и прогоном тула. И как тул читает конфиг: имя файла, формат против `type` корня и что целевая версия делает с этим расширением (`loaders`/`searchPlaces` в её dist).

- **Bugfix** — касается ли нашего пути и снимает ли обход: `eslint-disable`, `@ts-expect-error`, патч, `overrides`, пин окружения в CI ради бага транзитива (`pnpm why -r <транзитив>` до и после). Обход мог стать лишним уже на установленной версии: `grep -rni 'workaround\|DEPRECATED\|PENDING REMOVAL\|<pkg>/issues' scripts/ .<tooldir>/ .github/workflows/`, статус названного issue — `gh api repos/<o>/<r>/issues/<N> --jq '{state,state_reason}'`, посылки его докблока перемерь. Удаление обхода доказывай контролем: сначала обход ловит подложенный дефект, потом ловить нечего.
- **`overrides` может заблокировать бамп.** Сверь `dependencies` целевой версии с `overrides`: глобальное ограничение `<N`, заведённое ради другого потребителя, молча отдаёт цели старый движок — install проходит, тул падает в рантайме. Сужение до `parent>child` развязывает обе стороны.
- **Feature** — полезна ли здесь конкретно: файл, конфиг, что улучшает. Пользы нет — так и скажи. Фича, включённая по умолчанию, — изменение поведения: разбирай её как breaking, особенно запись в дерево репозитория и реакцию на агента (`CLAUDECODE`). Если её включает установленная версия пакета, а не запущенный бинарь, проба scratch-бинарём слепа: мерь в worktree с установленной целью.
- **Deprecation/removal** — используем ли, где, чем заменить. У опции конфига важно, **читается** ли она, а не принимает ли её схема: грепни имя по dist каждого пакета, которому передаётся конфиг. И не сменился ли её **дефолт**: сравни присваивание в dist старой и новой версии, типы и доки бывают неверны. Дефолт, сдвинувшийся к меньшей строгости, фиксируй значением явно. «Депрекацию поймает гейт» пиши, только сделав её красной позитивным контролем в той форме, которой пользуется проект: правило может ловить ссылку и молчать на ключ объектного литерала, а `tsc` депрекацию не гейтит.
- **Breaking** — что ломается у нас → Фаза 3.

## Правила замера

Действуют во всех фазах.

1. **Отсутствие — только с позитивным контролем.** «Не найдено», «ноль», «идентично» засчитывается, когда то же выражение находит заведомо присутствующее; счётчик печатай со знаменателем. Сравнение должно различать: правка входа обязана сдвинуть результат, а контроль — дать вердикт, противоположный пробе.
2. **Читай целевой артефакт.** `.pnpm` хранит каталоги прошлых версий, и `find … | head -1` отдаёт любой из них: иди через `node_modules/<pkg>` или запусти тул и прочитай его `--version`. Пробу-скрипт запускай из каталога воркспейса: вне дерева воркспейсные пакеты не резолвятся.
3. **Мерь то, что читает потребитель:** тот же поток (машинный вывод — stdout, баннеры — stderr), каждый канал, который проект читает (второй репортер, SARIF, выгрузка), и последствие загрузки, а не её факт. Вход — в форме из прода, включая миноритарную: упрощённая репетиция бывает вакуумной. Проверь и аварийную форму машинного вывода: объект ошибки вместо массива проходит сквозь `${out:-[]}`.
4. **Код возврата ≠ гейт.** Сверь, как тул вызывают хук и CI (`|| true`, `continue-on-error`). Тул сам может напечатать ошибку и выйти с 0: мерь обе версии на одном подложенном сбое, на пути, который тул исполняет. Baseline бывает красным до бампа — снимай состав находок, а не только код.
5. **Бинарь отдельно от входа.** Тул, хеширующий lockfile или манифесты, видит твой бамп как изменённый вход: прогони старый бинарь по обновлённому дереву.
6. **Одно окно.** Дерево общее с другими сессиями: обе руки снимай в одном коротком окне и закрывай повтором первой — расхождение значит, что окно грязное.
7. **Подложенный вход — вне общего чекаута:** копия конфига в scratch через флаг пути самого тула (`--config`), иначе одноразовый worktree. В общем чекауте — одним вызовом, с откатом и полным `git status`: правка `pnpm-workspace.yaml` или манифеста при первом запуске pnpm доходит до `pnpm-lock.yaml`.

## Фаза 3 — План миграции

Триггер — фактический breaking change, а не номер версии. Упорядоченные шаги: какие файлы и конфиги, before/after, что проверять после каждого; механическое отдельно от ручного; риск. Объёмную или рискованную миграцию предложи и дождись согласия.

Правка тестов (`packages/*/tests/`) и инфраструктуры — часть бампа. Бамп требует правки в `packages/*/src`, `shared/` или в диапазоне peer публичного пакета — это не работа команды: заведи задачу на миграцию через `/create-issue` (прецеденты — #2150, #2659, #2226), бамп ждёт её. Changeset решается в ней.

## Фаза 4 — Применение (после согласования)

**Пре-флайт — `git status`.** Дерево бывает грязным: незакоммиченный прошлый бамп или чужая работа. Стейджи только файлы этого бампа, явно, никогда `git add -A`. Прошлый незакоммиченный бамп делит с текущим `pnpm-lock.yaml` — не разделяй руками, вынеси пользователю: объединить или отложить. Чужая правка в том же файле — собери индекс из `git show HEAD:<file>` плюс своя правка (`git hash-object -w`, затем `git update-index --cacheinfo 100644,<blob>,<file>`) и проверь двумя диффами: `--cached` — только твоё, рабочее дерево — только чужое.

1. `pnpm up -r <pkg>@<target>` → `pnpm dedupe`; для `examples/` и `cross-router-bench/` — `pnpm --dir <воркспейс> up -r <pkg>@<target>` и `pnpm --dir <воркспейс> dedupe`. Сверь число изменённых файлов с охватом из Фазы 0. Лишние манифесты приходят от `$`-ссылок в `overrides` (`'@types/node': $@types/node`): install подтягивает к корню объявления, отставшие от него. Их не откатывай, но назови отдельной фразой в сообщении коммита. Сверь и хунки: `git diff -U0 -- '*package.json' | grep '^[+-] ' | sort | uniq -c` — только строки бампаемого пакета (`pnpm up` пересериализует манифест целиком).
2. **`pnpm dedupe` двигает чужие транзитивы** — и pre-commit делает его сам. `pnpm dedupe --check` печатает сдвиги тремя блоками: `Importers` (сменился peer-суффикс), `Packages` и снапшоты `+`/`-` в конце. Сборщик, который переезжает вслед за удалённой версией движка, бывает только в первом и последнем блоке. Если среди них сборщики публикуемых `dist` (`tsdown` с `rolldown` и `rolldown-plugin-dts`, четыре сборщика из `CLAUDE.md` § «Grouped Dependabot PRs») или их общий движок, dedupe — решение: валидируй пересборкой `dist` с различающим сравнением.
3. Примени согласованное из Фаз 2–3: сними обходы, внедри фичи, выполни шаги миграции.
4. **Валидация.** Точечно `pnpm -F <pkg> bundle`/`test` двух-трёх затронутых пакетов; полный `pnpm build` предложи пользователю. Строгость, которая включается только под `CI` (`failOnWarn: "ci-only"`), проверяй с `CI=1`. Дальше — по классу тула:

- **Сканеры-гейты** (knip, jscpd, publint, attw, syncpack) влияют составом находок. Прогони до бампа и после и сравни состав. Новые находки — истинные (чинить причину) или ложные (ignore-конфиг тула); ненулевую дельту веди бисекцией до версии-виновника. Истинные находки с причиной в `src`/`shared` подавлять нельзя: откати бамп и заведи задачу (Фаза 3). Построй карту покрытия: какой пакет получает тул и каким каналом (`packages/*/package.json`).
- **Форматтеры** (prettier) влияют множеством файлов с другим выводом. Прогони обе версии через API по всем отслеживаемым файлам и сравни старый вывод с новым, а не с содержимым. Гейт — правило `prettier/prettier` в ESLint, только `*.ts`/`*.tsx`. Контроль — из реального расхождения, а не из примера в changelog.
- **Тест-фреймворки и property-либы** — прогон после бампа на 2–3 пакетах с разными генераторами.
- **Mutation-раннеры** (Stryker) — самый мелкий пакет, полный прогон с `--force`. Свежесть отчёта — по времени и коду в логе, а не по json.
- **Сборщики и генераторы** (tsdown, rollup-plugin-dts, changesets) влияют артефактом. Старая и новая версия на одном входе; сравнение по семантике — экспортируемые имена `.d.ts`, внешние спецификаторы, `size-limit`. Остаток байтового диффа классифицируй: `@license`/`@preserve`/`/*!` доезжают до бандла потребителя. Тул ходит в сеть — песочница и стаб эндпоинта (`GITHUB_GRAPHQL_URL`, verdaccio).
- **Side-effect** (sonar, публикаторы) — без боевого запуска: `bin`, `--version`, `--help`, dry-run.
- **Загрузчики** (tsx, `--import`-хуки) влияют резолюцией. Тот же набор задач плюс проба `import.meta.resolve` в форме запуска из CI и без ключевого флага: пути обязаны разойтись.
- **Вне гейтов** (`examples/`, `cross-router-bench/`, `benchmarks/`). Из гейтов сюда доходят `lint:bench` и `lint:cross-router` в pre-push, примеры линтует еженедельный `examples.yml`. Собери артефакт до и после, сравни хеш и размер.

Два шага, которых не назовёт ни PR, ни CI:

- **playwright** — пере-сидинг пиннутого Chromium на self-hosted раннере (`cross-router-bench/CLAUDE.md`).
- **CodSpeed.** Двигает ли бамп его числа, отвечает `scripts/codspeed-gate.mjs`. Прогони его на коммите-пробе без ветки: `GIT_INDEX_FILE=<tmp> git read-tree HEAD`, тем же индексом `git add -u`, `git commit-tree $(GIT_INDEX_FILE=<tmp> git write-tree) -p HEAD`, затем `--base HEAD --head <sha>`. Контроль — диапазон с противоположным вердиктом: проба дала `skip` — коммит, двигавший измеряемые зависимости, обязан дать `RUN`; проба дала `RUN` — коммит только в документации обязан дать `skip`.

## Фаза 5 — Доставка

1. Changeset команда не пишет: `src` она не правит (Фаза 3).
2. Коммит — прямо в `master`, сообщение — через `/commit-msg`, тип `chore(deps)`. **Не коммить и не пушь без явной просьбы** — предложи сообщение.

## Итоговый отчёт

- `current → target`, сколько релизов в диапазоне.
- Вердикт: **безопасно ли** и **что даст**; рекомендация — бампать сейчас, поэтапно или отложить, и почему.
- Таблица: версия → ключевые изменения → тип → влияние на проект.
- Обходы, которые можно снять (файл и что удалить); фичи, достойные внедрения, и явно — что внедрять не стоит.
- План миграции или задача на миграцию, если она нужна.
- Результат валидации; полный `pnpm build` — за пользователем.
- Предложенное сообщение коммита.

Примеры:

```
/bump-dep knip
/bump-dep tsdown@0.23.0
/bump-dep size-limit @size-limit/preset-small-lib
```

## Самокоррекция скила (журнал кандидатов)

Скил правится по накопленному, а не после каждого прогона: правка по одному инциденту описывает случай, а не класс, а платит за неё каждый следующий прогон.

1. **Запись в журнал, а не правка** — после отчёта (анализ релизов + решение о внедрении/миграции). Где текст скила промолчал, был двусмыслен или неверен и это стоило вызовов, реплики владельца или риска ошибки, допиши строку в `.claude/skill-candidates/bump-dep.md` основного чекаута (gitignored; из worktree — `dirname "$(git rev-parse --path-format=absolute --git-common-dir)"`): дата, задача, раздел, класс (молчит / двусмыслен / неверен), инцидент, цена. Строка того же класса уже есть — допиши инцидент к ней. В отчёте — одна строка: что записано.
2. **Правка созревает, когда класс повторился** — в другой задаче или сессии. Неверный факт текста (команда, флаг, путь, число) — исправление, а не правило: его предлагай сразу. Планка: правка предотвратила бы ошибку или сняла бы лишние шаги.
3. **Разовое ≠ паттерн.** Специфику конкретной зависимости (разовую) → в задачу/память, НЕ в скил. В скил идёт только повторяющийся класс, полезный СЛЕДУЮЩЕМУ бампу ДРУГОЙ зависимости.
4. **Правка не растит файл:** сначала заточи существующий абзац; новое правило называет, что в том же разделе сжато или удалено. Рост — только с согласия владельца.
5. **Предлагай, не применяй молча.** Созревшие правки — таблицей (раздел | инциденты из журнала | текст | что сжато), спроси разрешения; итог помечай в журнале. В скил — правило в настоящем времени, без номеров прогонов и дат; инциденты — в сообщение коммита. Применил по согласию → `.claude/commands/` это infra, в master напрямую, без changeset.
6. **Ничего не записано и не созрело** — так и скажи одной строкой.
