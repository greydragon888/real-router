Сгенерируй changeset файл на основе текущих изменений в git.

Changeset пишет только этот скил: его вызывают через Skill все команды и задачи, которым нужен changeset, а Write, heredoc и скрипт, размножающий один текст по пакетам, его не заменяют. Аргументы — номер задачи и, если он есть, прецедент симметричного фикса.

## Шаги

1. **Получи контекст задачи из GitHub issue.** Номер бери в таком порядке: **(1)** номер, переданный аргументом; **(2)** `#NNNN` из свежего диффа — нового теста, комментария фикса, сообщения последнего коммита; **(3)** имя ветки (`git branch --show-current | grep -oE '^[0-9]+'`) — последним, сверив `gh issue view <N>` с тем, что реально в диффе. Ветка PR-группы названа по первой задаче группы (`/bugfix-batch`), и ошибка тут молчаливая: changeset соберётся, гейт пропустит, а в release notes уйдёт ссылка на чужую задачу. Описание задачи — `gh issue view <N>`. **Issue не найден — прекрати** и сообщи об этом.

2. **Проанализируй изменения.** Changeset часто генерится ДО коммита фикса (например из `/bugfix` Фазы 4, или когда ветка задачи ещё указывает на тот же HEAD, что и `master`) — тогда `git diff master...HEAD` покажет **пусто** и слепое следование ему даст ложное «changeset не нужен». Сначала проверь рабочее дерево, и анализируй именно его, если оно грязное:

   ```bash
   git status --short          # есть ли uncommitted-изменения?
   git diff HEAD --stat        # working tree vs HEAD (включая ещё не закоммиченный фикс)
   git diff HEAD
   ```

   Если рабочее дерево чистое (фикс уже в ветке) — используй сравнение с базой:

   ```bash
   git diff master...HEAD --stat
   git diff master...HEAD
   ```

3. **Определи затронутые публичные пакеты по полю `private` в их `package.json`, а не по статическому списку** — список пакетов дрейфует (адаптеры `vue`/`solid`/`svelte`/`preact`/`angular`, новые плагины), и хардкод устаревает:
   - Для каждого затронутого пакета: `node -p "require('./packages/<pkg>/package.json').private || 'PUBLIC'"`. `PUBLIC` → changeset нужен. Приватных пакетов в `packages/` нет.
   - Код движка, FSM, эмиттера и логгера живёт в `@real-router/core` (`src/engine`, `src/utils/*`): правка там — changeset на `@real-router/core`.
   - Правка `shared/<dir>/*.ts` попадает в пакеты, которые линкуют каталог как `src/<alias>` (`CLAUDE.md` § Symlink Consumers): changeset — каждому из них, чьё поведение изменилось; `changeset-check.yml` требует его и на такую правку.

4. **Определи уровень по таблице `.changeset/README.md` § Version Bump Guidelines** — прочитай её до выбора, а не после; правило уровня записано только там. Прежде чем поставить `patch`, сверь дифф с каждым пунктом списка несовместимых изменений под таблицей и назови в отчёте, что ни один не совпал: совпал хоть один — это не `patch`. Прецедент — аргумент вызывающего или симметричный фикс в другом пакете — довод, а не ответ: совпал с таблицей — бери, разошёлся — уровень по таблице, расхождение назови в отчёте.

5. **Задавай вопросы ТОЛЬКО если** из issue и кода неоднозначно понятно, что реализовано (например, исправление стороннего бага).

## Формат changeset файла

```markdown
---
"@real-router/core": minor
---

Краткое описание изменений на английском языке (#NN).

- Детали изменения 1
- Детали изменения 2
```

## Правила

- Описание на **английском**, безличный тон ("Add feature", не "I added")
- Путь: `.changeset/<имя>.md` — описательное kebab-case имя по README (`middleware-unsubscribe-fix.md`, `novalidate-feature.md`)
- Один пакет на файл и ссылка `#NN` на PR/issue — `.changeset/check-changeset.mjs` отвергает changeset без них
- Changeset нужен только правке кода в `packages/*/src/` и `shared/<dir>/`. Сборка, упаковка (`files`, `exports`, зависимости в `package.json`), CI, тесты, комментарии, JSDoc и доки идут в master без него — правило инфраструктуры корневого `CLAUDE.md`
- Текст — краткий и ёмкий: что меняется для консьюмера и что ему сделать
- Ломающее изменение — напиши, что консьюмеру поменять
- Changeset в `master` до релиза — ещё черновик CHANGELOG: дефект, найденный в нём, исправь в `master` до мержа релизного PR. После мержа текст уже в опубликованном CHANGELOG
- Каждое утверждение текста проверено, а не написано по памяти о замысле: что делает код, «было» (по выпущенной версии, а не по промежуточному коммиту ветки), числа и перечни. Утверждение о ДРУГОМ пакете или issue («как в #N», «включая `<Link download>`») проверь по коду или по закрывающему комментарию issue, а не по заголовку: скоуп issue меняется уже после того, как заголовок написан. Текст, размноженный на несколько пакетов, сверь с кодом каждого: у потребителя может не быть канала, директивы или копии файла, о которых говорит общий текст.

## Пример

```markdown
---
"@real-router/core": minor
---

Add support for async route guards (#NN)

- New `beforeEnter` and `beforeLeave` async guards
- Guards can return `false` to cancel navigation
```

## Самокоррекция скила (журнал кандидатов)

Где ТЕКСТ ЭТОГО скила промолчал, соврал или был двусмыслен и это стоило времени или риска ошибки, — строка в журнал `.claude/skill-candidates/changeset.md` основного чекаута (gitignored; из worktree — `dirname "$(git rev-parse --path-format=absolute --git-common-dir)"`): дата, задача, раздел, класс, инцидент, цена; есть строка того же класса — дополни её, в отчёте — одна строка. Правка созревает, когда класс повторился в другой задаче или сессии (неверный факт текста — сразу), и не растит файл. Созревшие правки — таблицей «раздел | инциденты | текст | что сжато», правилом в настоящем времени (инциденты — в сообщение коммита); применяй по согласию (`.claude/commands/` — infra, в master напрямую, без changeset). Ничего не созрело — одна строка.
