Исправь баг по методологии TDD (Red → Green → Refactor), затем синхронизируй локальную документацию и вики.

Входные данные:
$ARGUMENTS

Формат аргументов:

- Номер issue (`#812`) или ссылка на него (`https://github.com/greydragon888/real-router/issues/812`).

> **Несколько багов одной PR-группы в один PR?** Это отдельный скилл — `/bugfix-batch` (оркеструет группу в одну ветку/PR, **переиспользуя per-bug методологию этого скилла**). Здесь — один баг, линейно Фазы 0→7.
>
> **Один КОРЕНЬ в N call sites / пакетах ≠ батч.** Кросс-адаптерный / кросс-пакетный фикс одного дефекта (напр. одна и та же ошибка в `<Link>` всех 6 адаптеров) — это ЭТОТ скил, линейно: один RED→GREEN per call site, один changeset per затронутый публичный пакет, один PR. `/bugfix-batch` — для N **различных** багов (разных корней) одной PR-группы. Симметричное размножение одной правки по адаптерам — НЕ батч. Попутно всплывший «7-й call site» или директива-близнец с тем же дефектом (тот же общий хелпер) — дотягивается в этом же прогоне ради симметрии (feedback_layer_consistency), отдельным RED-тестом.

## Бюджет токенов

Каждый вызов инструмента заново читает весь контекст сессии, поэтому расход прогона — это размер контекста, умноженный на число вызовов, а не длина фикса. Контекст растёт от вывода инструментов и от работы, сделанной в сессии до вызова скила. Правила ниже экономят токены, не убирая ни одной проверки.

1. **Один баг — одна сессия.** Если до вызова скила в этой сессии шла другая работа, до Фазы 0 одной строкой предложи пользователю новую сессию (или `/clear`) с повторным `/bugfix <аргументы>` и закончи ход: весь прежний контекст перечитывается на каждом шаге прогона. Продолжай в этой сессии, только если пользователь так ответил. Когда фазы этого скила выполняются внутри другой команды (`/bugfix-batch`, `/enhance`), это правило не действует: сессию решает та команда.
2. **Независимые чтения и поиски — одним сообщением** (несколько вызовов параллельно) или одной командой. Повторяемые прогоны — батарею мутантов, матрицу проб, проверки пакета в Фазе 4 — запускай одним скриптом, который печатает таблицу или код возврата каждого шага, а не по вызову на шаг.
3. **В контекст — сводка, полный вывод — в файл.** Прогон: `… > <scratchpad>/run.log 2>&1; echo "rc=$?"; tail -n 40 <scratchpad>/run.log` — код возврата печатается до любой обработки вывода, остальное достаётся грепом по логу. Дифф — сначала `--stat`, полный — по файлам, которые читаешь. Код — по символу (`rg -n -C3 <символ>`) или узким диапазоном, а не целым файлом.
4. **Перечень кандидатов собирает субагент**, когда ответ — список мест: кто ещё регистрируется на тот же метод, вызывающие общего примитива (Фаза 2.5), страницы доков и вики с изменённым клеймом (Фаза 5). Требуй таблицу `file:line · что там · команда`; пробу и вердикт по каждому месту делаешь сам.

## Как формулировать вопрос пользователю

Если по ходу багфикса нужно спросить пользователя (нет данных для RED — 0.5; премиса issue устарела — 0.6; design-call с несколькими валидными разрешениями), формулируй вопрос **просто и понятно — для человека без накопленного тобой контекста**. Не вываливай плотную сводку из внутренних имён, аббревиатур и ссылок на спецификации.

Структура:

1. **Что это за фича/область** — одна-две фразы простым языком: что она делает для пользователя, на бытовом примере.
2. **При чём тут затронутый механизм/опция** — простыми словами, зачем он и когда применяется.
3. **Сам баг и его видимое последствие** — что идёт не так и чем это бьёт по пользователю.
4. **Сам выбор** — один чёткий вопрос с конкретными вариантами (напр. «чинить поведение по-настоящему или оставить как есть и честно описать ограничение в доках»).

Плохо: «scroll-spy: IntersectionObserver root + MutationObserver target резолвятся ОДИН РАЗ при создании, а опция обещает resolved on every event…» — плотно, на жаргоне, нечитаемо без контекста. Хорошо: то же по структуре выше — сначала «что такое scroll-spy и зачем `scrollContainer`», затем «в чём баг и последствие», затем один вопрос с двумя вариантами.

⚠ **Рекомендацию в вопросе атакуй ДО отправки:** перепроверь каждый её довод исполнением или чтением исходника (`/enhance` Фаза 5, ход 3). Неверный довод владелец опровергает одной фразой, и выбор переворачивается.

**Design-call** — у бага несколько валидных разрешений с разной архитектурной ценой (слой core/plugin/doc, breaking surface): развилка уходит владельцу с рекомендацией ДО RED, прозой, а не карточками `AskUserQuestion`; выбор, реализованный по доверию, рискует полной переделкой фикса. Прежде чем рекомендовать, прогони репродукцию из тела задачи против каждого варианта: вариант, который её не закрывает, рекомендуется только с контрактом на остаток, и задача закрывается с явным «эта половина — код, эта — контракт» — иначе ложная полнота (Фаза 0.8).

## Фаза 0 — Контекст из issue

1. Извлеки номер issue из аргумента. Чаще всего передаётся номер (`#812` или `812`) — возьми его как есть. Если передана ссылка — номер это последний числовой сегмент URL.
2. Получи описание бага **вместе с комментариями**: `gh issue view <number>` (тело) и `gh issue view <number> --comments` — вне TTY второй вызов печатает ТОЛЬКО комментарии, без тела. Комментарии читай и учитывай: в обсуждении почти всегда есть уточнения, корректировки скоупа или контр-примеры, без которых фикс будет неполным.
   - **Если issue не найден или закрыт как duplicate/invalid — остановись** и сообщи об этом.
3. **Не заводи инфраструктуру — работай в той ветке, в которой запущен.** Этот скил НЕ создаёт ветку/worktree и не решает, где работать: для одиночного запуска отдельную ветку под задачу готовишь заранее ты сам, для группового — её готовит `/bugfix-batch` на всю группу. Единственная проверка — `git branch --show-current`:
   - **Текущая ветка `master`** → на самом `master` не работай — **кроме инфраструктурного фикса**. ⚠ Инфраструктура — дифф, который не меняет кода ни одного пакета: сборка, CI, тулинг, бенчи, конфиги, доки (и доки внутри `src`, вроде `packages/core/src/**/CLAUDE.md`), только тесты, только комментарии в `packages/*/src/` и `shared/<dir>/*.ts`. Любая другая правка там — уже не инфраструктура. Для инфраструктуры CLAUDE.md предписывает «Infrastructure tasks go straight to `master` — no PR, no changeset»: ветку НЕ заводи, работай прямо в `master`, changeset не создавай. Решает СОСТАВ диффа, а не тема issue — баг в бенче или в CI выглядит как обычный баг, а доставляется как инфраструктура. Определить это можно до RED: скоуп правки известен из Фазы 0.6. Ветки под задачу нет вовсе → **заведи её сам и продолжай — в своём worktree, не `git checkout -b`**: основной чекаут остаётся на `master` (правило CLAUDE.md). Рецепт — `/bugfix-batch` Шаг 1 с номером задачи вместо `<lead>`, целиком: его оговорки про сессию, которая уже стоит в worktree прошлой задачи (`/clear` её оттуда не выводит), живут только там. Это локальные, полностью обратимые команды, и блокировать ради них вопрос — трата хода. ⚠ **В сессии, изолированной `EnterWorktree`, харнесс отклоняет составную команду, которую не может проверить, и git или prettier рядом для этого не нужны:** heredoc (`python3 - <<'EOF'`), переменная цикла на месте аргумента (`rg … $f`), слово `source` в любом месте строки, даже внутри шаблона в кавычках. Скрипты клади файлом в scratchpad и запускай по одной команде на вызов, с буквальными путями; в шаблоне пиши `sour[c]e`. ⚠ **НЕ `gh issue develop` — он СОЗДАЁТ ВЕТКУ В ORIGIN,** то есть является push-действием и нарушает «не пушить без явной просьбы». База — **`origin/master`, а не локальный `master`**: локальный может держать ещё не запушенные коммиты по другим задачам, и они уедут в твой PR. Ветка есть, но принадлежит ДРУГОЙ задаче (её имя/коммиты про другой issue, на неё открыт PR) — **заведи новую от `origin/master` тем же рецептом и продолжай**, не спрашивая: новая ветка чужой PR не трогает. Остановись и спроси, только если непонятно, к какой задаче относится сама правка.
   - **Любая другая ветка → продолжай в ней**, если это worktree. Основной чекаут (первая строка `git worktree list`) на ветке — нарушение правила CLAUDE.md: сам его не переключай, спроси пользователя. `#<number>` дублируй в коммите и changeset.
4. Из issue выдели: симптом, шаги воспроизведения, ожидаемое поведение, затронутый пакет/файл (если указан). Затем **коротко расскажи владельцу простым языком, в чём баг**, по пунктам 1–3 раздела «Как формулировать вопрос пользователю», и кто так делает и зачем: реальный это сценарий или экзотика (правило CLAUDE.md). Ответа не жди: это сводка, а не вопрос.
5. Если в issue нет данных для написания падающего теста (нет воспроизведения или ожидаемого результата) — остановись и спроси, не угадывай.
6. **Сначала воспроизведи баг эмпирически** — временной пробой через публичный API или собранный пакет, ПРЕЖДЕ чем писать формальный тест. Это триаж-гейт, который может закоротить работу в «только отчёт».
   - ⚑ **Решение в баге принимается из НЕСКОЛЬКИХ входов (два гварда, два канала, флаг × режим, sync × async)? Воспроизводи МАТРИЦУ входов, а не сообщённую клетку.** Клетка отвечает «сломано» — этого хватает для RED, но не хватает, чтобы выбрать между вариантами фикса, а именно этот выбор и стоит дорого. Матрица показывает ПРАВИЛО и почти всегда вскрывает клетку, о которой в issue нет ни слова.
   - ⚑ **Баг про ПЕРЕЧИТЫВАНИЕ (второе чтение геттера, повторный вызов коллаборатора, кэш против источника)? Ось матрицы — ПОРЯДКОВЫЙ НОМЕР обращения, а не набор входов.** Скриптуй источник «отдавать правильное до N-го обращения, испорченное — с N-го» и свипни N. Это даёт две вещи, которых обычная матрица «арка × режим» не даёт. Во-первых, ТОЧНОЕ число обращений — issue почти всегда занижает («второе чтение» на деле оказывается третьим из шести). Во-вторых, свип вскрывает, что ОДИН логический вопрос задаётся НЕСКОЛЬКО раз: у пар `canSend`+`send`, `has()`+`get()`, «проверить»+«применить» предикат один, а оценок две, и разойтись они могут ровно посередине — а между ними успевает пройти деструктивная работа.
   - ⚑ **Баг записи истории или URL: у матрицы есть ось «ОТКУДА» — с другого маршрута и с того, который роутер уже показывает.** Второй путь кончается `SAME_STATES`, идёт мимо `onTransitionSuccess` и живёт в другом файле, чем сообщённая клетка, а симптом у него тот же.
   - Проверь статус связанных/блокирующих issue (`blocked by #N`, эпики, ссылки в теле): если блокер закрыт — перепроверь, не починил ли его фикс уже этот баг.
   - Если репродукция из issue **не воспроизводится** на текущем HEAD — премиса устарела (баг уже исправлен или описание неверно). НЕ чини «по тексту»: останови RED, сообщи находку, при необходимости предложи пересмотр скоупа и спроси, продолжать ли. ⚑ **Но сбой, зафиксированный в логе и не воспроизводящийся по СОБСТВЕННОМУ сиду, — не устаревшая премиса.** Сид фиксирует входы fast-check, а не состояние движка под тестом: формы объектов V8, JIT, GC. Различитель — два прогона: реплей сида в N свежих изолятах (`worker_threads` + `node --import tsx`), где разброс между одинаковыми изолятами значит, что вердикт решает не сид; и тот же реплей с `--no-concurrent-marking` — если разброс схлопывается в N из N, это состояние движка, которое зависит от GC.
   - ⚠ **Отказ пробы по ЧУЖОЙ причине читается как вердикт.** `SAME_STATES`, `ROUTE_NOT_FOUND`, ранний выход, «уже на этом маршруте» — проба отработала, что-то вернула, и это принимается за «дверь отвергает» или «сиблинг чист», хотя вход до ветки не дошёл. Оговорка Фазы 2.5 про падение на контрольном входе этот случай НЕ ловит: там контроль есть и он красный, здесь контроля нет вовсе. Клади рядом ЗДОРОВЫЙ вход через ту же дверь: не дошёл и он — вердикта нет, есть промах пробы.
   - ⚠ **Фильтр с ранним выходом даёт ложное «чисто».** Функция, которая возвращает вход нетронутым, когда отбрасывать нечего (`if (!dirty) return input`, `??=`-аккумулятор, флаг `dropped`/`changed`), на чистом входе копирующую ветку не запускает, и проба зеленеет на живом дефекте. Прежде чем записать «не воспроизводится», добавь во вход элемент, который она обязана отбросить.
   - ⚠ **У инфраструктурного скрипта (хук, workflow, `scripts/*`) публичное API — путь реального вызывающего:** строка хука, шаг workflow, `pnpm <script>`; pre-push — `git push --dry-run <remote> HEAD:refs/heads/<scratch>`: хук получает настоящий stdin, а на удалённой стороне ничего не меняется. Дефект, достижимый только прямым `node`/`bash <script>`, которого нет ни у одного вызывающего, — латентный: `enhancement`, не баг.
   - ⚠ **jsdom хранит `history.state` по ссылке** (`History-impl.js`: «TODO structured clone data»): записи, созданные с одним объектом, делят состояние. Собирай записи пробы отдельными объектами.
   - ⚑ **Третий исход, который этот гейт не ловит: ВОСПРОИЗВОДИТСЯ, но это ПОЛИТИКА.** Гейт выше сформулирован под «баг уже починен», поэтому на зелёной репродукции он молчит — а дефекта при этом может не быть вовсе. Признаки: поведение выглядит как молчаливая деградация или как сужение того, что раньше работало; в CHANGELOG затронутого релиза есть блок `BREAKING`/`⚠` про ту же область; в `.claude/**` или в теле соседнего issue встречается «decided» / «deliberately» / «owner decision». Проверяется грепом за минуту (см. 0.7), а стоит непроверенным — целого прогона: матрица, RED и фикс строятся против решения, а не против дефекта. Исход тогда — «задокументировано, без правок src»: закрыть issue как not-planned с замерами, и сделать ту работу, которой решению не хватало (запись правила туда, где его будут искать).
   - ⚑ **Четвёртый исход, и он тише третьего: СИМПТОМ воспроизводится, а МЕХАНИЗМ в теле назван неверно.** Зелёная репродукция подтверждает наблюдаемое — числа, дрейф, отгруженное значение — и НЕ подтверждает объяснение, откуда оно берётся. А из механизма выведены три вещи, которые ты собираешься использовать как данные: форма фикса, РАДИУС («32 двери», «во всех адаптерах») и приёмка. Ошибся механизм — все три под подозрением, и ни одна не перепроверяется тем, что симптом воспроизвёлся. Различитель дешёвый: не считай обращения, а **назови читателей** — геттер, снимающий `new Error().stack`, печатает вызывающих по порядку за один прогон. Совпало с телом — иди дальше; разошлось — **остановись и перепиши тело**, потому что варианты фикса, выложенные под неверный механизм, взвешивают работу, которой нет.
   - ⚑ **Отдельный случай — `/bugfix <N>` запущен на ветке, которая `<N>` уже чинит** (типично: приёмка после ревью, или второй заход по той же задаче). Невоспроизведение тут не сюрприз, а ожидание, и «премиса устарела → стоп» срабатывает формально верно, но рано. Смени режим с ТРИАЖА на ПРИЁМКУ: прогоняй не сообщённую клетку, а **всю таблицу радиуса из тела issue** — все точки входа × все арки × альтернативные точки ВЫЗОВА (плагинные примитивы, а не только фасад) + контроли, — и предъяви её как есть. Отчёт тогда отвечает не «баг жив?», а «что из ЗАЯВЛЕННОГО скоупа уехало без регресс-защиты»: снимай по одному месту фикса и смотри, краснеет ли сьют; место, снятие которого оставляет тир зелёным, и есть незапиненное. Точки входа, исчезнувшие структурно из-за СОСЕДНИХ фиксов, называй отдельно со ссылкой на их пин, а не выкидывай из таблицы молча.
   - Если баг воспроизводится, но корень — иной класс входов, чем в issue, — фиксируй фактический корень, а не формулировку issue.
   - **Issue-на-УДАЛЕНИЕ (dead code / unused / «недостижимо из X»): «0 покрытия / достижимости из публичного API X» ≠ «удаляемо».** Метрика достижимости аудита (0 проб через core, 0 внешних импортов) говорит лишь «этот потребитель не зовёт» — а НЕ «мёртвый код». Пакет держит СВОИ тесты + property + **INVARIANTS** на этот код → это живая, тестированная возможность, не мусор. Перепроверь КАЖДЫЙ пункт на HEAD: существование + потребители + **выделенные тесты/property/INVARIANTS + `git grep` на использование внутри самого пакета/тест-хелперов**. Есть выделенное покрытие → удаление это **product-решение** (сознательный API-shrink с потерей тестированной возможности), НЕ cleanup: вынеси как design-call (прозой, «Как формулировать вопрос пользователю»), не сноси на доверии к слову «dead» ([[feedback_legacy_skepticism]]). И даже под «да, сокращаем» — верифицируй границу КАЖДОГО пункта отдельно: аудит систематически врёт про «impl vs отдельный», «мёртвая ветка vs test-only», «фантом vs используется тест-хелпером».
   - ⚠ **Считаешь ПОТРЕБИТЕЛЕЙ API — не грепай `api(...).method` одной строкой.** Идиоматичное написание двухстрочное (`const api = getXApi(router);` … `api.method()`), и однострочный паттерн его структурно не видит: результат непустой, поэтому на «пустой grep ≠ отсутствие» ([[feedback_tool_error_not_absence]]) он не ловится — ты просто получаешь МЕНЬШЕ, чем есть, и веришь числу. Ищи по имени МЕТОДА (`\.method()`) с фильтром по каталогам, а потом отсеивай одноимённые чужие вызовы (`Map.clear`, `Set.clear`) глазами.
   - **Воспроизводишь через консьюмер/пример?** Внешнее приложение без `customConditions` в своём `tsconfig` резолвит `@real-router/*` из `dist` (через `exports`), а не из `src` — **пересобери пакет** (`pnpm -F <pkg> bundle`) перед его type-check/прогоном. Примеры — отдельный воркспейс: они ставят npm-релиз из своего lockfile, а код этого чекаута получают только после `pnpm run use-checkout` в `examples/` (собирает и пакует пакеты чекаута и ставит тарболы поверх релиза; назад — `pnpm install --frozen-lockfile` там же, `examples/CLAUDE.md` § Workspace). Без этого шага и RED, и GREEN считаются против устаревшего кода (ложный результат).
   - Временные пробы удаляй до конца фазы — никаких `__probe*.test.ts` или отладочных файлов в коммите.
   - ⚠ **Пробу-скрипт запускай ИЗ каталога воркспейса, а не файлом в scratchpad.** Скрипт вне дерева репозитория не резолвит воркспейсные пакеты (`ERR_MODULE_NOT_FOUND` на `vite`, `tinybench`, любом другом), и отказ читается как «пакета нет» или как поломка пробы, а не как ошибка размещения. Дёшево и всегда работает: `cd <workspace> && node --input-type=module -e '…'`; файл в scratchpad годится, только если он ничего не импортирует по имени. Несовпадение форматов не падает, а пустеет: CJS-preload против ESM-only пакета печатает «0 предупреждений» при нуле измеренных задач — сверяй число измеренного.
   - ⚠ **Проба, живущая ВНУТРИ vitest-теста (нужен jsdom / тест-хелперы пакета), не печатает `console.log`** — конфиг пакета его глушит, и флаги репортера этого не снимают (`--reporter=verbose`, `--disable-console-intercept` — оба мимо). Не перебирай флаги: пиши результат в файл (`appendFileSync("/tmp/probe.txt", …)`) и читай его отдельной командой. **Для СТРУКТУРНЫХ данных (матрица клеток, массив объектов) дешевле другой приём — печатать через заведомо ПАДАЮЩИЙ ассерт:** `expect(matrix).toEqual("SHOW-ME")` — diff Vitest выводит всё дерево объектов целиком, без файловой возни, без второй команды на чтение и без флагов репортера. ⚠ **Клейм о КАНАЛЕ отказа — синхронный бросок против отклонённого промиса — такой хелпер не проверяет, если ждёт вызов через `await` внутри `try`:** оба канала попадают в один `catch` и печатаются одинаково. Вызывай без `await`, лови синхронный бросок отдельно, и только потом жди промис — печатая, какой из двух сработал.
7. **Если в issue предложен способ решения бага — относись к нему максимально критически.** Это гипотеза автора, а не истина. НЕ применяй его на доверии. Сначала самостоятельно найди корень бага, затем проверь предложенное решение: действительно ли оно устраняет причину (а не симптом), не ломает ли инварианты/другие сценарии, не противоречит ли границам слоёв и архитектуре проекта. Применяй его, только если есть **реальные доказательства** (тест, анализ кода), что фикс корректен **и** оптимален. Если твоё независимое решение лучше — используй его и объясни, почему предложенное в issue не подошло.
   - **Своё собственное предложение — ТОЖЕ гипотеза, не повышай к нему доверие из-за авторства.** Если fix-direction в теле issue написал ТЫ САМ (в прошлой сессии, при заведении задачи), на старте фикса его тянет принять как данность — не надо: пере-выведи минимум из кода на момент фикса. Особенно перед **добавлением API-поверхности** (новый метод/поле/экспорт на публичном типе) — сначала проверь, не достаётся ли нужное через СУЩЕСТВУЮЩИЙ surface (getter'ы, уже-прокинутые коллабораторы, реэкспорт). «Добавить метод» рефлекторно раздувает API и дифф; часто хватает 0 новых точек. ⚠ **И прежде чем звать поведение дефектом, грепни его на ПРИНЯТОЕ РЕШЕНИЕ — по `.claude/**`, `CLAUDE.md`, `INVARIANTS.md`, changeset'ам затронутого релиза.** Ищешь не фикс, а формулировку правила: «supported input», «decided», «owner decision», «deliberately», «stays refused». Отсутствие правила в `CLAUDE.md` НЕ значит, что решения нет — его могли принять и не записать, и тогда твоя находка это **невыполненная запись**, а не баг, и работа документационная. Это дороже обычного пере-вывода, потому что решение живёт не в коде: код выглядит одинаково, принято решение или нет. ⚠ **И пере-резолви КАЖДЫЙ `file:line`-анкер тела: у своего же issue они читаются как уже проверенные, а гниют первыми** — файл переехал, функция оказалась в plugin-only ветке, «второй сайт» вообще не сайт. Проверка — не открыть строку, а **протрассировать вызывающих**: сайт, до которого не доходит ни одна публичная дверь, в инвентаре не сиблинг. Так же перепроверяется и ЧИСЛО дверей: считай их обходом call-graph от точек входа, а не по списку в теле.
   - ⚑ **Номер СТРОКИ ТАБЛИЦЫ, раздела или инварианта — такой же якорь, как `file:line`, и гниёт он ТИШЕ.** У `file:line` отказ заметен: строка не та, файл переехал. Здесь файл тот же, номер существует, текст по нему читается осмысленно — просто строка принадлежит СОСЕДНЕЙ таблице. Проверяй не ТЕКСТ цитаты, а её ВЛАДЕЛЬЦА: разреши номер в заголовок, под которым строка лежит (`awk`/`grep` по `^## ` до этой строки), и сверь с дверью, которую называет тело. ⚑ И расхождение тут почти никогда не опечатка: цитата обычно ВЕРНА, а дверь названа не та — значит настоящий сиблинг стоит ровно там, куда указывал номер, и Фаза 2.5 его не найдёт, потому что ищет от двери из тела.

   - **«Обратно совместимо» — не синоним «консервативно».** Чинишь дефект ФОРМЫ (типа, сигнатуры, мешка аргументов) — сохранение старой формы сохраняет и дефект, а к нему приделывается сторож: тот, кто пишет по-старому, продолжает получать молчаливо неверный результат, зато теперь ещё и с рантайм-различителем двух форм и его edge-case'ами. В pre-1.0 сначала оцени ОДНУ форму + миграцию, и только потом совместимость: цена миграции обычно разовая и механическая, цена двух форм — постоянная.
   - **Фикс хочет БУЛЕВ ФЛАГ в сигнатуре? Это гипотеза, и она требует отдельного исследования — `.claude/prompts/boolean-flag-audit.md`.** Позиционный `boolean`, параметр с дефолтом `= true/false`, `boolean`-поле мешка опций — одна и та же форма. Проверяется НЕ чтением сигнатуры, а таблицей ВЫЗОВОВ, по признакам §3 промпта; четыре из них: множества вызывающих непересекающиеся (никто не передаёт обе полярности); какому-то ДРУГОМУ параметру большинство вызывающих даёт одну константу; флаг называет РОЛЬ, которую тот же сайт уже объявил выше по цепочке; достижимых комбинаций k+1 вместо 2^k. Сработал любой — функция это две функции, и расщепление убирает БОЛЬШЕ, чем сам флаг. ⚠ Перенос позиционного булева в объектный мешок фиксом НЕ является: именованное поле лечит читаемость вызова и ни один из признаков §3. ⚠ И инвентаризуй ВСЮ сигнатуру, а не свой флаг: добавленный последним редко бывает первым неправильным.
   - ⚠ **ИЗМЕРЕННОЕ число в теле issue, на котором стоит решение, — пере-мерь САМ.** Радиус, счётчик сайтов, «N из M тестов», «используется дважды» — если цифра гейтит выбор (чинить/не чинить, throw/drop/варн, узко/широко), она такой же клейм, как и всё остальное, и стареет ровно так же. Опаснее не устаревание, а **замер соседнего вопроса:** число получено честным прогоном, но предикат, который прогоняли, отвечал не на тот вопрос, что стоит в решении, — и разойтись они могут на порядок. Особенно когда issue завёл ТЫ САМ: авторство цифры не делает её проверенной, а «я это уже мерил» — самая дешёвая причина не перемерить. Способ: воспроизведи замер тем же методом (временный детектор + позитивный контроль) и сверь СОСТАВ попаданий, а не только итог — состав и покажет, тот ли предикат мерили.
     ⚠ **Закрытый СПИСОК вариантов в теле — такой же клейм, как число, и читается он как исчерпывающий.** «Механизмов три: A, B или C — реализующий пусть скажет, какой» ставит вопрос «который из трёх», а не «есть ли четвёртый», и на этом поиск останавливается. Опаснее всего список, обоснованный фразой вида «через опубликованную поверхность до этого не дотянуться»: автор проверял поверхность на момент письма, а ты выбираешь механизм, который переживёт релизы. Потрать ОДНУ пробу на вариант вне списка, прежде чем выбирать внутри него.

     ⚠ **Приёмочный критерий из плана/RFC — тоже клейм, и проверяется он ПЕРВЫМ.** Если пункт задан как «тест такой-то формулировки должен быть красным», напиши его и **убедись, что он красный по причине бага**, до всякого фикса. Формулировка, истинная как утверждение, запросто оказывается нечувствительной к дефекту. Не переформулируй молча: оставь обе как ОТДЕЛЬНЫЕ ассерты и скажи в отчёте, какая дискриминирует, — иначе следующий прогон повторит ошибку плана.
     ⚠ **Число, которое ты измерил СЛОМАННЫМ инструментом, — хуже, чем неизмеренное: ты назовёшь его «замеренным».** Прежде чем цитировать радиус, полученный временным guard'ом/детектором, проверь ПОЗИТИВНЫМ контролем, что инструмент срабатывает только там, где должен: включи его и убедись, что заведомо-легальный случай проходит. Иначе получишь завышенный радиус и понесёшь его в решение и в отчёт.

   - **Правка на потоке данных имеет ДВА плеча — что ЗАХОДИТ в продюсер и что берётся из его ВЫХОДА. Issue почти всегда называет одно.** Прежде чем принять предложенную формулировку, разложи её по обоим и спроси, какое плечо даёт измеренный симптом: чинить вход, когда теряется выход, — это зелёный фикс мимо бага. Провалидируй КАЖДОЕ плечо мутационно ОТДЕЛЬНО (откат одного роняет свой набор тестов) — иначе полу-фикс выглядит полным.
   - **Особый случай — REJECT малформед-конфига (throw там, где раньше молча проходило): он легко ПЕРЕ-ОХВАТЫВАЕТ.** Issue задаёт заявленный скоуп находки, но истинная граница дефекта — то, что принимают СУЩЕСТВУЮЩИЕ тесты. Перед коммитом reject'а прогони полный сьют пакета И downstream-потребителя (Фаза 2/4): падающий существующий тест, ассертящий отвергаемую форму как VALID, — сигнал **сузить** reject (у формы есть рабочий под-кейс) или **вынести как design-call** (форма толерируется by-design), а НЕ форсить reject + переписывать тест под него. Это не «подгонка фикса под тест» (её мы избегаем на баг-пиннящих тестах) — это признание, что заявленный скоуп reject'а шире реального дефекта. Тест, который форму не ассертит, а лишь построен на прежней толерантности (дубль пути или малформед в фикстуре), — другой случай: его сетап чини на корректный, сперва доказав, что старый невалиден. ⚠ **И ПЕРЕД reject'ом грепни отвергаемую форму по `INVARIANTS.md`, `tests/**/stress`, `tests/**/property` и бенчам.** Инвариант / stress-тест / бенч НА ЭТУ ФОРМУ означает, что она — шипнутая ФИЧА, а reject — ретирование инварианта (product-решение, не багфикс): выноси как design-call, не как фикс. Функциональные тесты этого не покажут — они часто покрывают лишь ОДНУ сторону контракта, и непокрытая сторона и есть баг. ⚠ **Попадание при УЖЕ принятом продуктовом решении — не повод чинить молча.** Решение владельца покрывает вопрос «ломать ли», но почти никогда — «чем именно платим». Предъяви ЦЕНУ отдельно: сломанный бенч (особенно при `throws:true` — падает весь процесс перф-харнесса), инвариант, который станет самопротиворечивым, property-блок, который исчезнет, и **ИЗМЕРЕННОЕ** число красных — включить guard временно и прогнать сьюты дешевле и честнее, чем оценивать сканом. Развилку формулируй как «чем закрывать в ЭТОМ прогоне» (весь слом / только бесспорная половина / объявить контракт варном, сломать отдельным коммитом), а не «ломать ли».
   - **Зеркальный случай — фикс-ОСЛАБЛЕНИЕ** (предикат / матчер / валидатор, раньше дававший `false`-или-throw, теперь пропускает): существующий тест, пинящий СТАРЫЙ контракт, здесь не помеха, а **измеритель радиуса** — полный сьют показывает, сколько поведения ты реально меняешь. Один-два таких теста = здоровый, локализованный радиус: переписывай их **с переименованием** (имя/коммент называют НОВЫЙ контракт и issue) и **с сохранением дискриминации** — добавь рядом кейс, который остаётся `false`, иначе тест выродится в тавтологию. Десяток упавших пинов = фикс шире дефекта → сузи правило или вынеси как design-call.
   - **Фикс добавляет initializer/setup-вызов рядом с бросающим кодом (фабрика, клон, парс) ИЛИ переносит существующий вызов в другую фазу жизненного цикла?** Он не только ДОБАВЛЯЕТ поведение — может изменить ФОРМУ существующего отказа (sync-throw vs async-reject, порядок событий), даже если твой новый RED зелёный. Реши ПО КОДУ, в какой фазе исполняется вызов (напр. Angular `provideEnvironmentInitializer` бежит раньше и СИНХРОННО, чем async `provideAppInitializer`), ДО прогона. Если полный сьют (Фаза 2.2) покраснел на СУЩЕСТВУЮЩем контракте отказа — сместить фикс в фазу, СОХРАНЯЮЩУЮ контракт, НЕ переписать тест под новую форму.
   - **Родственный случай — ДИАГНОСТИКА, читающая пользовательский объект РАНЬШЕ настоящего потребителя.** Guard / варн / лог, который трогает `params[key]`, свойство или итератор до того, как до него доберётся код, которому значение действительно нужно, меняет не форму отказа, а его **ПРОИСХОЖДЕНИЕ**: аксессор-геттер, `Proxy` или реактивный объект бросят из ДИАГНОСТИКИ. Тесты, пиннящие «ошибка приходит из X», покраснеют — и переписывать надо не их. Читай защищённо (`try` вокруг чтения значения → при броске «нечего сообщать», пусть настоящий потребитель наткнётся на тот же аксессор) и пинни это отдельным тестом.
8. **Гейт корня-цепочки: не заплатка ли фикс поверх более глубокого владельца концерна.** Пункт 7 сомневается в _предложенном решении_; этот пункт сомневается в _самой рамке issue_ — а вправе ли этот баг вообще чиниться локально, или он лишь **симптом-член цепочки долга**, где локальный RED→GREEN станет очередным band-aid'ом поверх ненайденного владельца, а класс багов продолжит рецидивировать. Триггеры (хоть один → сначала мини-проверка ниже, НЕ патч):
   - **Issue ссылается на другие / связан:** «follow-up of #N», «parallel to #N», «residual of #N», «same class as #N», «same seam», «sibling of #N», часть эпика, `blocked by #N`; или тело/комментарии называют баги-собратья. (Такие само-кросс-ссылки в телах — сильнейший сигнал сквозной **оси**; ровно из них `/debt-map` восстанавливает оси.) **Цепочка:** задача — follow-up follow-up'а, то есть фиксы уже рождали задачи, или её область — открытая папка класса (`ls -d .claude/*/ | rg /class-`). Тогда до мини-проверки одной строкой предложи пользователю `/class-hunt <номера цепочки>` или строку в §1 папки и продолжай по его ответу.
   - **Whack-a-mole:** тот же класс симптома уже чинили в другом пакете/сайте (фикс там — всплыл здесь) → сигнал отсутствующего общего примитива.
   - **Band-aid-запах:** очевидный фикс ДОБАВЛЯЕТ спец-кейс / предохранитель / флаг вокруг концерна, а не удаляет координацию (Variant-A-запах из `/chain-resolve`).
   - **Уже в карте:** issue значится членом цепочки в `project_architectural_debt_map` (память).

   **Мини-проверка — convergence по КОДУ, не рассуждением** (дешёвая версия `/debt-map`-теста): вытяни тела+фиксы названных собратьев (тело — `gh issue view <N>`, комментарии — `gh issue view <N> --comments`; фиксы — `git log --all --grep "#<N>"` / `git show <sha>`) и протрассируй: сходятся ли фиксы РАЗНЫХ issue в ОДИН helper/владельца? Есть ли у концерна авторитетный **существующий** владелец (`FSM` / `RoutesStore` / emitter / `onListenerError` / codec), на который класс должен схлопнуться? Три исхода:
   - **Сходятся к более глубокому корню + владелец существует + вокруг налипли костыли** → это **цепочка долга, не одиночный баг**; локальный фикс — следующая заплатка. **Не эскалируй в `/chain-resolve` / `/debt-map`** — на практике они почти не срабатывают; проведи раскопку **здесь, инлайн**, по коду:
     - **`git blame` багованных строк → residual-vs-original:** строки предшествуют родителю → это НЕ residual (родитель ортогонален — пиши «related to #N», не «follow-up»); введены/оставлены родителем → настоящий residual.
     - ⚠ **`git blame` называет ПОСЛЕДНЮЮ правку строки, а не ту, что её ввела:** перенос, переименование и переформатирование переписывают атрибуцию. Происхождение — `git log -S '<фрагмент>' --reverse -- <весь src пакета>`, первая строка вывода; путь в один файл повторяет ошибку, потому что код переезжает между файлами.
     - **Follow-up? Проверь «ложную полноту» родительского ФИКСА:** прочитай его коммент/диф и сверь ЗАЯВЛЕННОЕ покрытие с кодом — родительские фиксы часто заявляют, что покрыли ныне-падающий кейс («also falls under the catch», «wraps all four»), а шов/порядок-вычисления это отрицают (напр. в `wrap(produce())` аргумент вычисляется ДО `try` внутри `wrap`, и бросок `produce` идёт мимо него). Это сильнейший тэг residual'а. ⚠ **И ложным бывает не только заявленное ПОКРЫТИЕ фикса, но и СРАВНИТЕЛЬНАЯ ПОСЫЛКА в теле родителя** — «у соседнего пакета это уже работает», «X ведёт себя иначе, чем Y». Именно такая посылка обычно и объясняет, почему родитель не пошёл на сиблинга, поэтому она гейтит весь скоуп — а проверяется тем же пробником, что и сам баг, за одну минуту.
     - ⚠ **Ложно полным бывает и ОТЛОЖЕНИЕ.** Закрытый сосед назвал свой будущий фикс («a real fix needs X», «закрывается рефактором X») — проверь два факта: X отгружен? X закрыл ЭТО? Расхождение между названным фиксом и нужным — главная строка находки. Обоснование соседа, построенное на его же переписи с оговоркой о неполноте («the number is a floor», «invisible to it»), прогони по тем спеллингам, которые оговорка назвала невидимыми: `Set`, ключи объекта, `switch`, `Record<Union, …>`.
     - **Sweep сиблингов** (см. Фазу 2.5): смапь ВСЕ call-site/каналы/координаты концерна и пробь КАЖДЫЙ — фикс покроет их все или назовёт полный радиус.
     - Вынеси находку (корень · собратья · владелец · какие band-aid'ы удалятся · **рекомендованный глубокий фикс + class-guard**) и **вынеси развилку пользователю как design-call**: глубокий структурный фикс сейчас (контракт/умбрелла для single-surface корня; конвенция+sweep+инвариант для кросс-поверхностного рекуррентного класса) **или** осознанная **временная** заплатка (interim, TODO-ссылка на корневой issue). Не блокируй; не форсируй umbrella молча.
   - **Realized-владелец (gap в существующем шве)** — общий владелец/helper УЖЕ существует и потребляется, а остаток = дыра в шве (фильтр «realized?» из `/debt-map`: реализованная convergence = закрытая цепочка, RFC-payload пуст): тогда локальный фикс — ПРАВИЛЬНЫЙ ход (bugfix, не RFC). Продолжай линейно.
   - **Нет convergence, корень самодостаточен** — обычный одиночный баг. Продолжай, отметив в отчёте, что член цепочки исключён.

   **Не спутай с симметричным размножением одной правки** (шапка скила): один и тот же корень в N call sites / адаптерах — ЭТО ЭТОТ скил (чини все сайты линейно, один RED per site), НЕ цепочка. Цепочка — когда корень глубже РАЗНЫХ багов и его владелец не тронут.
   **Калибровка:** «более глубокий корень» — ГИПОТЕЗА, и её легко переоценить: раскопка по коду часто понижает корень, который выглядел сильным. Твоя роль в этом гейте — **триаж + ОГРАНИЧЕННАЯ инлайн-раскопка** (blame · ложная-полнота · sweep — дёшево и по коду), НЕ полная RFC-раскопка: ссылка на другой issue сама по себе ≠ глубокий корень, она лишь повод прогнать мини-convergence + инлайн-дig и решить «одиночный / член цепочки / class-guard». Не превращай каждую ссылку в RFC-крестовый-поход и не блокируй фикс, если корень не доказан кодом.

## Фаза 1 — RED (тест, доказывающий баг)

1. Локализуй причину: найди модуль и функцию, ответственные за поведение. Сначала пойми корень, не патч симптома. (Это корень _внутри_ бага; вопрос «не симптом ли сам баг более глубокого корня-цепочки» уже прошёл гейтом Фазы 0.8 — если тот выявил цепочку, ты уже провёл инлайн-раскопку и согласовал с пользователем скоуп: глубокий структурный фикс или осознанная interim-заплатка — с ним сюда и заходишь.)
2. Напиши **падающий** тест, воспроизводящий баг, в `tests/functional/` соответствующего пакета (или ближайший подходящий уровень — property/stress, если баг про инвариант/память/конкурентность).
   - Тест проверяет **поведение**, а не реализацию.
   - **Правильный ИСХОД спорный (design-call ещё не решён)? Пиши RED как СРАВНЕНИЕ, а не как ожидаемое значение.** Форма «с фичей не хуже, чем без неё» (тот же сценарий с гвардом и без гварда, с опцией и без) дискриминирует ДО того, как выбран вариант, и переживает выбор; «ожидаю X» приходится переписывать под каждый вариант, из-за чего RED откладывают до конца развилки и теряют его как инструмент её разрешения. Заодно такой RED — часто и сам аргумент в развилке.
   - **Дописываешь тест в СУЩЕСТВУЮЩИЙ файл — проверь, в КАКОЙ `describe` он сядет и чей `beforeEach`/фикстуры отработают.** Файл может нести НЕСКОЛЬКО top-level `describe` с разным setup; append в конец кладёт тест в ПОСЛЕДНИЙ, чей общий-но-не-сбрасываемый `api`/router даёт ложный провал НЕ по причине бага — маскируя дискриминирующую силу RED.
   - **Если фикс по замыслу НЕ меняет видимый output** (дедуп / экономия ресурса / перф — результат до и после идентичен): чистый output-тест невозможен, и RED легитимно проверяет **ресурсное следствие** — один источник/подписка/кэш-вход вместо N, отсутствие лишнего пересчёта. Это и есть тестируемое поведение, не реализация. Дискриминатор — наблюдаемый побочный эффект кэш-промаха vs шеринга (напр. повторный вызов коллаборатора при miss), а не чтение приватного поля. Не трать время на поиск output-разницы, которой по построению нет.
     - **Третья форма — дефект на ПРОМЕЖУТОЧНОМ шве, который нижележащий слой исправляет строкой ниже.** Конечный результат идентичен by design (это часть приёмки — «no-op today»), а дефект наблюдаем только в точке ДО починки, где его читают downstream-потребители. Ищи публичный способ прочитать промежуток: чаще всего это **интерцептор** (`addInterceptor("<method>")`, чей `next(...)` возвращает выход исходного примитива ДО пост-обработки шва) — и он же обычно и есть пострадавшая популяция, т.е. RED выходит тестом поведения, а не реализации. Не трать заход на поиск разницы в конечном состоянии: её отсутствие — приёмочный критерий, а не признак, что бага нет.
   - **Инвариант, который ядро (или соседний слой) и так вытягивало, зелёный и НА БАГЕ.** Когда фикс переносит работу между слоями/каналами, свежий property легко выходит тавтологией: нижележащий слой чинил симптом за тебя, и тест проходит на обеих версиях. Прогони мутацию — сломай ровно ту ветку, которую добавил, — и убедись, что в наборе есть хотя бы ОДИН кейс, падающий на до-фиксовом коде. **И формулируй ассерт как ИНВАРИАНТ, а не как снимок:** `toStrictEqual` по целому мешку затягивает в тест сторонние правила (куда ядро кладёт undeclared-ключ, какой singleton вернул пустой бэг) и падает на них, а не на баге — counterexample тогда указывает на твою формулировку, а не на дефект. Проверяй охраняемое свойство поключно (каждый слот равен переданному; искомый ключ отсутствует). ⚠ **Родственная тавтология — у фикса вида «брать из РЕЗОЛВНУТОГО выхода, а не из сырого аргумента»: кейс, где вызывающий задаёт ВСЕ ключи, зелёный по построению** (сырой и резолвнутый мешки тождественны, когда резолюция ничего не добавила). Дискриминатор обязан содержать ключ, который добавляет **резолюция** и который вызывающий НЕ передаёт.
   - **Issue-на-УДАЛЕНИЕ (dead code / unused / phantom-export): RED-теста НЕТ — не изобретай его.** Удаляемого поведения нет, воспроизводить нечего. «GREEN» здесь = после удаления кода **вместе с его выделенными тестами** полный сьют + `test:properties`/`test:stress` остаются зелёными И **coverage держится 100%** И мутационный score не проседает на РЕТЕЙНЕД-коде. Дискриминатор — **дельта coverage/mutation на неизменённом коде, а не новый failing-тест**: если после удаления теста строка/ветка теряет покрытие или в удержанном коде появляется новый выживший мутант — удалённый тест был единственным killer'ом чего-то живого → **сузь удаление** (ты снёс не только мёртвое). Обратно: выжившие мутанты, которые ЖИЛИ и на master (стойкие/эквивалентные в нетронутых файлах), регрессией НЕ являются — проверяй по расположению (нетронутый файл + был на master), не по проценту (набор мутантов меняется, когда удаляешь код с его мутантами, так что сырой % не apples-to-apples).
   - Один логический assert на причину провала; имя теста описывает ожидаемое поведение.
3. Запусти тест и **убедись, что он падает именно по причине бага** (а не по опечатке/компиляции). Падающий тест — доказательство дискриминирующей силы. Репортер **не указывай** — дефолтный печатает и падение, и причину, и строку; `--reporter=basic` в Vitest 4 не существует и падает `ERR_LOAD_URL` со стеком на 30 строк, который читается как поломка теста, а не опечатка флага.
   - **Недетерминированный баг** (конкурентность / тайминг / память — RED обычно на property/stress-уровне): одно падение силу НЕ доказывает — тест мог упасть случайно, а на исходном коде иногда проходить. Прогони RED **несколько раз** (или зафиксируй `seed` у `fast-check`) и убедись, что он падает **стабильно** до фикса. Иначе после фикса «зелёный» не отличить от случайной удачи — фикс не доказан. Если стабильного падения добиться не удаётся, воспроизведение неполное: вернись к Фазе 0.6, не закрепляй флапающий тест. ⚑ **И гоняй его в двух конфигурациях: отдельно (`-t`) и в составе полного файла.** Расхождение значит, что более ранние тесты файла двигают общее состояние, и RED надо поставить на ту его часть, которую они не трогают.
   - **Код пакета корректен, а дефект — в опубликованных артефактах или консьюмере.** Если src пакета ведёт себя правильно, но баг живёт в том, что доезжает до потребителя (`dist/*.d.ts`/бандл — например, не доходящая до консьюмера module augmentation, отсутствующий ре-эмит `.d.ts`) или в самом примере/приложении-консьюмере — package-level unit-теста для RED может **не существовать**. Ставь RED на **интеграционной границе**: собери пакет (`pnpm -F <pkg> bundle`), затем type-check/прогон консьюмера (например `tsc` примера). RED = консьюмер падает на собранном `dist`; GREEN = после фикса доставки. Дополни постоянным контракт-пином (type-level `@ts-expect-error` или conditional-type assert) против регресса, проверив его дискриминирующую силу (временно сломай тип — пин должен упасть). **Код в доке (README / вики) — тоже консьюмер, и RED для него — стенд в scratchpad, а не тест в пакете** (прототип стенда — в #2706). Извлеки фенсы и прогони type-check под `strict` ПОСТРАНИЧНО: страница — отдельная программа под JSX своего фреймворка, а имя, которое блок использует без объявления, резолвь из самой страницы — импорт или объявление другого блока, затем экспорт пакета страницы и прочих `@real-router/*` — дописыванием импорта в конец блока (строки не сдвигаются); общий `.d.ts` — только для значений читателя. Исполняемые блоки запусти против **релизных** пакетов: `node_modules` пробы — симлинки из `examples/node_modules/.pnpm`, недостающее там — `npm pack` в отдельный каталог. GREEN — тот же стенд на исправленном доке; контроль — оригинал через тот же стенд. ⚠ Массив маршрутов типизируй как `Route[]`: без контекстного типа параметр хука — неявный `any`, и type-check видит только его, а не форму «хук вместо фабрики»; TS7006 у колбэка самого дока — находка, а не шум. ⚠ Отказы рантайма (точечное имя маршрута, `clear()` на запущенном роутере) type-check не видит вовсе — такие блоки запускай. ⚠ **У стенда позитивный контроль на КАЖДОЙ стадии:** `>` снимай только с фенса, открытого внутри цитаты (иначе `>()` дженерика и JSX-`>` становятся синтаксисом); блок откладывай по `getSyntacticDiagnostics`, а не по диапазону кодов — CLI `tsc` не печатает ни одной семантической ошибки программы, пока в ней жива хоть одна синтаксическая, а TS2657 (JSX) синтаксическая с кодом 2xxx; плейсхолдер `router` — класс из корня (`import("@real-router/core").Router`): плагины аугментируют его, а не интерфейс из `/types`.

## Фаза 2 — GREEN (минимальный фикс)

1. Напиши **минимальный** код, чтобы тест прошёл. Никакой спекулятивной функциональности (YAGNI) — только то, что требует тест.
   - **Фикс должен КЛАССИФИЦИРОВАТЬ то, что ядро уже классифицирует (канал ключа, владелец, достижимость, объявлен-ли)? Не пере-выводи реестр — спроси у того, кто ПЕЧАТАЕТ/решает.** Пере-вывод в соседнем пакете или слое молча воссоздаёт дрейф, который ядро уже устранило, и расходится ровно на carve-out'ах и наследовании (коллизия имён, объявление у ПРЕДКА, объявление на КОРНЕ) — то есть на тех клетках, которых в issue нет и по которым тест никто не напишет. Если публичного доступа к реестру нет, ищи предикат по ИСХОДУ, а не по декларации: построй артефакт и прочитай его обратно (`buildPath` → `matchPath`), потому что исход по построению согласован с реестром и бесплатно наследует его режимы и исключения.
   - **Issue называет соседний фикс того же класса («the same class elsewhere: #N», «как в #N»)? До выбора предиката прочитай его раздел в `IMPLEMENTATION_NOTES.md`.** Его «Why» говорит, что держит инвариант на всём пути, и фикс берёт ту же опору, а не выводит свою.
   - **Тип из корневого `types/*.ts` — не обязательно тот, что видит потребитель.** Публичные сабпути (`/api`, `/types`, `/validation`) могут ПЕРЕОБЪЯВЛЯТЬ интерфейс точнее (`extends Omit<Base, K>` + узкий `K`). Прежде чем добавлять каст к «слишком широкому» типу (`unknown`, `Record<string, unknown>`), прочитай объявление в ТОМ сабпуте, из которого импортирует пакет: `eslint --fix` снимет лишний каст молча, tsc промолчит, а расследование «почему тип вдруг совпал/не совпал» стоит нескольких заходов.
   - **Переносишь/сплитишь существующий код с \u-escape (\\uXXXX), HTML-entity (&amp;), regex-литералами через Write/Edit?** Тул ИНТЕРПРЕТИРУЕТ escape-последовательности при записи (unicode-escape → символ, `&amp;` → `&`) и молча искажает исходник — **критично для security-escape / сериализации** (напр. split-модуля, где escape-таблица переезжает в новый файл; property-тест поймает, но лучше не ломать). НЕ ретайпи такой блок руками: вырежи byte-identical node-сплайсом из оригинала (`readFileSync` → `slice` по маркерам → `writeFileSync`), верифицируй байты (`node -e 'JSON.stringify(...)'`), затем прогони его property/security-тест. ⚠ **Но для ПЕРЕМЕЩЕНИЯ блока внутри одного файла сплайс по `index()` — плохой инструмент:** конец блока ищется по `}`, а во вложенном коде их несколько, и срез уезжает, оставляя файл невалидным. Двигай двумя `Edit` — удалить по точному тексту, вставить по якорю: обе половины падают на несовпадении, а не молча режут. ⚠ **Та же подмена бьёт и по НОВОМУ тексту, не только по переносу:** `\uXXXX` в комментарии, докблоке, heredoc'е или в `old_string` у `Edit` приходит в файл готовым символом, и правка либо искажает текст, либо не находит якорь. Пиши такие последовательности скриптом через `chr(92)` и сверяй счётчиком (`grep -c 'u0041'`) после записи.
   - **Фикс добавляет isolation try/catch в fan-out цикл (частый шаг throw-isolation класса)?** Оборачивание тела итерации **inline** во внешний try часто пробивает `sonarjs/cognitive-complexity` (лимит 15) — лишний уровень вложенности поверх уже-ветвистого цикла. Сразу вынеси тело итерации в именованный хелпер (`continue`→`return`), тогда isolation-try оборачивает ОДИН вызов, а сложность callback'а падает. Не жди lint-провала и второго рефактора.
   - **Async-вариант той же изоляции (возврат/проброс Promise листенера в центральную изоляцию — `subscribe`/`emit`) бьёт ДРУГУЮ пару правил, чем sync-isolation-try выше.** (1) Тест, моделирующий async-misuse (`() => Promise.reject(…)`, `async onStart(){throw}` там, где тип листенера `=> void`), пробивает `@typescript-eslint/no-misused-promises` («Promise returned where a void return was expected») → `eslint-disable-next-line` смежно. (2) Обёртка, которая ВОЗВРАЩАЕТ рантайм-значение `=> void`-типизированного листенера в изоляцию, пробивает `no-confusing-void-expression` — и на shorthand-стрелке (`=> listener(…)`), и на `return voidExpr`; лечится чтением в `const r: unknown = listener(…)` (disable СМЕЖНО, ср. Фаза 4.1) + `return r`. Ставь оба disable проактивно и прогони lint ДО коммита — сама вставка disable-комментария может ещё дёрнуть `@stylistic/padding-line-between-statements` (нужна пустая строка перед следующим statement).
   - **Портируешь defensive-паттерн из ПРЕЦЕДЕНТА (rx-unwind, isolation-try соседнего пакета)?** Его `eslint-disable` / `v8 ignore` / `Stryker disable` вокруг паттерна стоят НЕ случайно — та же форма нарушит те же lint-правила/метрики и у тебя. Проверь суппрессии прецедента ВМЕСТЕ с логикой, не жди, пока lint их переоткроет. НО верифицируй КАЖДУЮ суппрессию отдельно, не копируй слепо: `v8 ignore` / `Stryker disable` прецедент часто ставил из-за НЕДОСТИЖИМОСТИ шва тестом — если твой RED его ДОСТАЁТ (напр. спаем/моком), эти суппрессии тебе НЕ нужны и покрытие выйдет лучше прецедента.
2. Запусти новый тест + весь набор тестов затронутого пакета: `pnpm -F <пакет> test -- --run`. Все зелёные.
   - **Прогон (особенно кросс-адаптерный / на общей тест-инфре) показал warning/error, похоже от твоей правки — СНАЧАЛА подтверди источник, не перестраивай код вслепую.** Warning называет свой `file:line`; shared-хелперы и соседние компоненты плодят ПРЕД-существующий шум, не твой. Не трогай код, пока не увидел СВОЙ файл в источнике варнинга. Для сравнения с оригиналом — `git show HEAD:<file>` / diff / отдельный worktree, **НИКОГДА `git stash`** (stack общий между worktree, снесёшь чужое — [[feedback_no_git_stash_for_comparison]]).
   - **«Весь сьют зелёный» НЕ доказывает фикс, если тесты пакета импортят его ПО ИМЕНИ (`@real-router/<pkg>`), а фикс в `src`.** Стухший `packages/<pkg>/dist` **шэдоуит vitest src-alias** для name-импортов → эти тесты (обычно router/adapter-level, `createRouter(...)`) молча гонятся против СТАРОГО `dist`, а relative-импортные (`../src/...`) — против фикса; «N passed» тогда невалиден. Диагностика расхождения: одинаковый вход через relative-import (`../src`) и name-import даёт РАЗНЫЙ результат. ⚠ **Условие срабатывания — не «`dist` стухший СЕЙЧАС», а «`dist` есть И ты правишь `src`»:** свежесобранный `dist` становится стухшим на ПЕРВОЙ же твоей правке, а name-импортные тесты продолжают идти против него. Проверка «новее ли `dist` всех файлов `src`» на входе поэтому ничего не гарантирует — она верна ровно до первого `Edit`. Remedy ПЕРЕД первой правкой, а не когда заподозришь расхождение: `rm -rf packages/*/dist && pnpm install`, затем прогон уже против `src`; вернуть — `pnpm bundle`, и сказать об этом в отчёте, потому что ты изменил окружение пользователя. Отличается от Фазы 0.6 (там dist для примеров/консьюмеров **пересобирают** — здесь **удаляют**). Вдобавок: фоновая нотификация задачи рапортует exit-код ОБЁРТКИ (0), не сьюта/линтера — верифицируй RC чтением лога. [[feedback_stale_dist_shadows_package_name_imports]]
3. Проверь регрессии в зависимых пакетах (особенно при правке `shared/dom-utils`, `shared/browser-env`, `shared/ssr` — изменение пропагируется во всех консьюмеров через симлинки).

## Фаза 2.5 — Sweep сиблингов + class-guard (перед тем как считать фикс завершённым)

Точечный GREEN — ещё не финал: узкий фикс с непробованным сиблингом порождает следующий follow-up. Дёшево, по коду, в скоупе бага.

1. **Cross-check с `/create-issue`.** Тело записывает видимое при создании: пробу, а кандидатов радиуса и гипотезы — отдельными строками от проверенного (`/create-issue` Шаг 2.5). Кандидаты и гипотезы — не радиус и не корень: проверь каждого сам. Проверенное тоже **не принимай слепо**: пере-выведи корень из кода на HEAD, пере-проверь происхождение строк и sweep — две независимые проверки и есть ценность (одна могла ошибиться уверенно). Твоё собственное авторство текста доверия НЕ повышает.
2. **Sweep сиблингов — пробь КАЖДЫЙ канал, не аналогизируй иммунитет** ([[feedback_probe_each_sibling_no_analogy]]). ⚠ **Сначала убедись, что сам ПОИСК сиблингов не соврал:** в git-pathspec `*` НЕ переходит через `/`, поэтому `git grep … -- 'packages/*/src'` не матчит `packages/core/src` и возвращает ПУСТО — что читается как «сиблингов нет», хотя это отказ инструмента. Перед любым выводом «больше нигде» предъяви позитивный контроль (`git grep -c <term> -- <файл, где точно есть>`), а фильтруй по каталогу шире (`-- packages shared`) с последующим отсевом. Смапь ВСЕ сиблинги концерна (все call-site / каналы / координаты / писатели / поколения / счётчики) и пробь или протрассируй **КАЖДЫЙ** — не считай соседа иммунным «потому что похож» или «один уже проверил». **Проба сиблинга, падающая и на тестовом, и на КОНТРОЛЬНОМ входе, — не вердикт «не этот класс»:** у сайта может быть второй, доминирующий дефект, маскирующий твой. Варьируй оси входа по одной (канал, форма аргумента, тип значения), пока контроль не станет зелёным — только тогда вердикт по сиблингу валиден. ⚠ **Нашёл копию предиката в соседнем пакете — не останавливайся на факте копии: протрассируй, КАКАЯ из копий лежит на пути пользователя.** У пакета с fast/slow-развилкой дефолтный вызов систематически идёт мимо той копии, что ты починил, и зелёный сьют этого не покажет — оба пути зелены, потому что тестируются порознь. Способ: возьми самую типовую форму вызова из адаптера/консьюмера и пройди её до предиката руками, а потом воспроизведи пробой ЧЕРЕЗ ту точку входа, а не через ядро.

**Сиблинг может быть не твоим call-site, а чужим ПОТРЕБИТЕЛЕМ того же шва.** Меняешь канал / формат / порядок в интерцепторе, хуке или событии — грепни, кто ещё регистрируется на тот же метод (`addInterceptor("<method>"`, подписка на то же событие) и прочитай, из какого канала он ЧИТАЕТ: твой фикс мог переставить мешок у него под ногами. Документированная кросс-плагинная связка часто НЕ покрыта тестом ни в одном из пакетов, так что зелёный сьют тут ничего не доказывает — нужна проба на обе стороны связки.

⚠ **Дефект привязан к ФАЗЕ (окно до коммита / до анонса / после эмита)? Мапь сиблингов не по call-site'ам, а вопросом «что ещё исполняется в ту же фазу».** В частности — где ещё в этой фазе вызывается ПОЛЬЗОВАТЕЛЬСКИЙ код: колбэки опций, кодеки, фабрики, резолверы. Обход call-site'ов правленой функции такие входы структурно не видит.

⚠ **Сиблинг того же корня редко берёт предикат соседа ДОСЛОВНО.** Прежде чем копировать условие живости/владения, перечисли, из каких ФАКТОВ его собирает исходный сайт, и проверь, доступен ли каждый на сиблинге (свой контроллер? свой токен? своя фаза FSM?). Недостающий факт — не «упростим», а дыра: полу-предикат зелен на типовой пробе и падает там, где недостающий факт единственный различитель. Формулируй предикат от ВОПРОСА («держит ли FSM мою транзакцию?»), а не от формы соседа.

⚠ **Сиблинг идёт по пути, который RFC/план уже отложил, — прочитай, ПО КАКОЙ ПРИЧИНЕ.** План откладывает МЕХАНИЗМЫ (кто владеет коммитом, кто эмитит), а найденный тобой дефект может быть про другое свойство того же пути — живость, атомарность, порядок. Совпадение имени пути ≠ совпадение вопроса; иначе живой баг тихо списывается на «уже в плане».

⚠ **Ставишь диагностику / guard / варн в ОБЩИЙ примитив — перечисли его вызывающих и реши по КАЖДОМУ, должен ли он это получить.** Правка в разделяемой функции достаётся всем её потребителям, а «кому она полезна» и «кто её технически получит» — разные множества, и по умолчанию совпадать они не обязаны. Типовой ложный получатель — **предикат на render-пути** (`canNavigateTo`, `isActive*`, `matches*`), разделяющий с продюсером композиционную форму, но бегущий на КАЖДЫЙ `<Link>` каждый рендер: варн там не диагностика, а поток. Отсюда правило: опт-ин привязывай к РОЛИ точки (коммитит / только отвечает), а не к форме вызова — форма их не разделяет. И пинни МОЛЧАНИЕ каждого не-получателя тестом, иначе следующая правка формы тихо их переподключит.

⚠ **Скан по ШЕЙПУ тонет: сужай его ИСТОЧНИКОМ КЛЮЧА и ПРИРОДОЙ ЦЕЛИ, а не только формой записи.** «Присваивание с вычисляемым ключом» — это десятки попаданий на средний пакет, и читать их все дороже, чем найти дефект. Дискриминирует тройка: (а) ключ приходит из ПОЛЬЗОВАТЕЛЬСКОГО объекта, (б) цель НЕ защищена по построению, (в) результат сохраняется или уезжает наружу. Пункт (б) проверяй ПЕРВЫМ и по коду создания цели: `Object.create(null)` делает целый класс невозможным СТРУКТУРНО, и это сильнее любого гварда — сайт с такой целью не сиблинг, сколько бы он ни выглядел похожим.

⚠ **Свип скриптом: исключённый файл-объявление и комментарии врут о числе употреблений.** Исключив файл, где предмет объявлен (иначе объявление считается употреблением), теряешь и его ЧТЕНИЯ в том же файле — перепрогони без исключения и сверь два числа. Докблок, цитирующий член, совпадает с тем же regex, что и живой вызов, — вырезай комментарии до подсчёта. Обе ошибки ловит только контроль «заведомо известный предмет обязан найтись», а не «инструмент что-то вернул».

Три исхода на сиблинг:

- **Gap того же корня, непокрыт** → **покрой в ЭТОМ прогоне** (симметрия — отдельный RED per site, [[feedback_layer_consistency]]).
- **Gap, но вне скоупа задачи** → через `/create-issue` (комментарий к дому или новая задача; пробу сиблинга — в тело как проверенное) и назови в отчёте.
- **УЖЕ покрыт другим guard'ом/backstop'ом** (проба-контроль зелёная 🟢, не gap) → отметь в отчёте и **НЕ добавляй избыточный guard** — это over-reach (ср. Фаза 0.7), особенно если issue предлагает «add all N» скопом. Проба-контроль отличает уже-покрытый сиблинг от реального gap'а. **Но различай ДВА зелёных:** проба зелёная из-за _guard'а_ = реально покрыт; проба зелёная потому что вход/produce **не достаёт до дефекта ПО ПОСТРОЕНИЮ, а не guard'ом** (`getState` не бросает, имя-строка не бывает malformed) = **ЛАТЕНТНЫЙ шов** (шейп есть, дремлет) → помечай `latent`, действие по нему — как в Фазе 2.6 (проактивный guard ИЛИ low-pri hardening-issue + «чем дремлет / что разбудит»), НЕ хорони под «уже покрыто».

НЕ оставляй сиблинг непробованным «на потом».

3. **Class-guard, а не только точечный фикс** («рекомендовал более глубокий фикс»). Сформулируй **инвариант/property**, ловящий ЭТОТ дефект И его сиблингов, а не один сайт (#1224/#1225: property «plugin ⊇ core: если bare core принимает — плагин не бросает»; #1165: pin release-в-`finally` против move-мутанта; on()-atomicity: validate-then-mutate property). Добавь его тестом, если дёшево и в скоупе пакета; иначе — рекомендуй в отчёте + в комменте issue (Фаза 7). Это то, что превращает «залатал симптом» в «закрыл класс».
⚠ **Прежде чем разносить сиблингов по отдельным фиксам/issue, проверь, нет ли ОДНОГО более сильного предиката, закрывающего их разом.** Class-guard бывает не только тестом, но и выбором проверки: спроси, какой факт отличает здоровый случай от ВСЕХ найденных сиблингов, а не только от того, что в issue. Смену предиката обязательно пинни мутацией «ослабить до прежнего» — иначе выбор не запинен и откатится следующей правкой.
⚠ **СНАЧАЛА грепни `tests/property/` на уже существующую property того же концерна — не пиши вторую.** Если она есть и зелена НА БАГЕ, дефект не в её отсутствии, а в её **ДОМЕНЕ**: генератор мог быть сужен той же волной, что внесла баг (типовой сценарий — миграция фикстур под новый throw/reject: форма стала нелегальной, хелпер аргументов перестал её порождать, и property потеряла ровно то плечо, где дефект живёт). Тогда правка — **расширить домен** (доп. арбитрарий на «старое написание»), а не добавить property рядом; вторая была бы дублем при живой первой. Расширение обязательно мутационно валидировать: отключи фикс — property должна упасть с контрпримером ИМЕННО на новом плече. ⚠ **Но если существующая property ЯВНО документирует исключённую ось** (в шапке/комментарии: «этот источник сюда не подходит, он не укладывается в модель»), это не сужение домена, а граница модели — тогда правильно добавить СЕСТРИНСКУЮ property рядом и сослаться в её шапке на исключение. Дубль — это вторая property на ту же ось, а не на соседнюю.

4. **Re-верифицируй ПОСЛЕ фикса, не только до.** Фикс мог сдвинуть шов — прогони sweep-пробы ещё раз на GREEN-коде. Пробы удали до коммита.

## Фаза 2.6 — Кросс-кодовый sweep потомков КЛАССА (мультиагентный; ТОЛЬКО для членов рекуррентного класса)

Фаза 2.5 прочёсывает сиблингов ЭТОГО бага — его call-sites/каналы внутри пакета. Этого мало, когда баг — **член рекуррентного класса**: тот же дефект-ШЕЙП живёт в ДРУГИХ пакетах, куда обход call-site'ов не дотягивается, и точечный фикс + локальный sweep их не видят. После того как фикс **закончен и доказан** (GREEN + 2.5 + Фаза 4-валидация), проведи кодо-широкий hunt на непойманных потомков класса.

**Гейт — фаза дорогая (3+ агента, сотни k токенов), запускай ТОЛЬКО если ВСЕ:**

1. Фаза 0.8 отметила **класс** (residual / звено цепочки / «same class as #N» / в `project_architectural_debt_map`), И
2. class-guard из 2.5 — это **детектируемый ШЕЙП**, который в принципе может повториться в другом коде (напр. `isolate(produce())`, false-reject «plugin строже core», sync-seam, missing-isolation на новом callback-сайте), И
3. у класса есть >1 известного члена в РАЗНЫХ пакетах/сайтах (один-пакетный дефект sweep'а не требует).
   Иначе — **пропусти**, в отчёте: «класс single-site/не выявлен → кросс-кодовый sweep не нужен».

**Как:**

1. **Сформулируй дефект-ШЕЙП** в 2-3 фразы + канонический пример (только что исправленный баг) — это ТЗ агентам, дословно в каждый промпт.
2. **Раздели кодовую базу на регионы** и запусти по одному **`Agent` (`subagent_type: Explore`) на регион ПАРАЛЛЕЛЬНО** (в ОДНОМ сообщении — иначе не параллельно). Типичное деление: `core` · пакет-первоисточник класса (там ищи НЕПОКРЫТЫЙ соседний шов — как compile рядом с invoke) · остальные плагины+адаптеры+`shared`. Каждому агенту: «найди КАЖДЫЙ сайт этого шейпа; на каждый — file:line, что на нём происходит, и вердикт из ТРЁХ: **VULNERABLE** (дефект срабатывает на сегодняшнем коде → живой баг) / **LATENT** (шейп есть, но не срабатывает лишь по СЛУЧАЙНОСТИ сегодняшнего кода, а не по структурной гарантии) / **SAFE** (шейпа нет, ИЛИ срабатывание структурно невозможно). Для класса изоляции это: produce МОЖЕТ бросить сейчас / produce стоит СНАРУЖИ изоляции, но не бросает (`getState()`=чтение поля, чистые строки, НЕТ user-кода в пути) / produce ВНУТРИ try. **Дисциплина: вердикт „SAFE“ ОБЯЗАН отличать „шейпа НЕТ“ от „шейп ЕСТЬ, но дремлет“ — агент, пишущий просто „SAFE“ на дремлющем шве, ПРЯЧЕТ латентный баг.** Для каждого LATENT назови: чем дремлет (какой инцидентал держит шейп несработавшим) + какая правка его РАЗБУДИТ (для изоляции — провести user-код / бросающий router-вызов через produce). Читай РЕАЛЬНЫЙ код сайта и выражения-аргументы, трасируй КАЖДОЕ значение, от которого зависит срабатывание, до источника (гарантия типа или инцидентал реализации?), НЕ аналогизируй от имён; заключение — живые сайты И латентные швы».
3. **Параллельно реконструируй СЕМЬЮ класса:** вытяни статусы всех родственных issue (`gh issue view <N>` по цепочке из тел/#1039-подобного research-issue), подтверди что известные закрыты, и что решил research (напр. #1039: примитив ОТКЛОНЁН → lint; но lint слеп к «шов уже» — это и есть дыра).
4. **Верифицируй КАЖДУЮ находку агента САМ** (прочитай сайт) прежде чем объявлять багом — вывод агента это гипотеза ([[feedback_probe_each_sibling_no_analogy]]).

**Синтез (в отчёт + пользователю):** семья класса (все ли закрыты) · **новые живые потомки** (file:line + шейп + severity) · **латентные швы** — шейп ПРИСУТСТВУЕТ, но дремлет (безопасен по построению, не по замыслу): это **НЕ баг → НЕ заводи как `bug`**. Действие: либо **дешёвый проактивный guard сейчас** (убрать шейп — для изоляции перенести produce ВНУТРЬ неё: шейп исчезает, будущая правка его не разбудит), либо **low-pri hardening-issue** (`enhancement`, не `bug`) + назови в отчёте с «чем дремлет / что разбудит»; развилку вынеси пользователю. Латентный шов дешевле закрыть проактивно, чем дать ему стать живым багом позже — и, в отличие от живого бага, **RED на него нестандартный** (срабатывать сегодня нечему → надо СИМУЛИРОВАТЬ срабатывание — для изоляции throw produce, напр. замокать `getState`, и проверить ресурсное следствие: соседи-слушатели всё равно уведомлены). · **структурная иммунность** (где шейп невозможен и ПОЧЕМУ — напр. core компилирует guard/plugin-фабрики жадно при регистрации, а не лениво-в-точке-вызова → форма `wrap(produce())` там не собирается).

**Действия (по явной просьбе пользователя — внешние):** живые потомки — экземпляры класса, а не N задач: предложи `/class-hunt` с номерами семьи, а при открытой папке класса (`ls -d .claude/*/ | rg /class-`) — строки потомков в её §1. Пользователь отказался — `/create-issue` на каждого потомка (в тело — корень, родословная и class-guard, уже доказанные в этом прогоне) и на **class-level предохранитель** (shape-lint / конвенция), если его нет. Потомков в других пакетах **НЕ чини в этом прогоне** (другой скоуп).

## Фаза 3 — REFACTOR

1. Улучши структуру фикса и теста, не меняя поведения. Тесты остаются зелёными.
2. Проверь, что не осталось дубля логики и фикс лежит на правильном слое (core / plugin / dom-utility — границы симметричны, не размывать ради одной правки).
3. **Пост-фикс анализ (когда фикс подтверждён тестами и проверками).** Вернись к фиксу свежим взглядом и подумай: можно ли его упростить, оптимизировать, улучшить?
   - Нет ли более короткого/прямого решения, которое устраняет ту же причину.
   - Нет ли лишних аллокаций, обходов, копий, повторных вычислений на горячем пути.
   - Не дублирует ли фикс существующий хелпер/утилиту, которые можно переиспользовать.
   - Читается ли он в стиле окружающего кода (именование, идиомы, плотность комментариев).
   - Любое упрощение применяй, только если все тесты затронутого пакета остаются зелёными (`pnpm -F <pkg> test -- --run`). Если упрощение ухудшает читаемость или ломает границы слоёв — оставь как есть и зафиксируй, почему.

## Фаза 4 — Валидация

1. **Точечная валидация затронутых пакетов** — НЕ полный `pnpm build`: он тяжёлый (turbo гонит весь граф вместе с property-тестами), а весь граф — и `test:stress` вдобавок — прогоняет pre-push hook. На каждый изменённый пакет: `pnpm -F <pkg> type-check`, `pnpm -F <pkg> lint`, `pnpm -F <pkg> test -- --run` (+ `test:properties` / `test:stress`, если фикс касался инварианта / конкурентности / памяти). Дифф в `packages/*/src`, `packages/*/tests` или `shared/` — плюс один `pnpm lint:repo-scans` на весь дифф: сканы ядра из `scripts/repo-wide-scans.json` читают все пакеты, а прогон пакета их не запускает. ⚠ **Фильтр `-F`, под который не попал ни один пакет, молчит и выходит с кодом 0** (замер: `pnpm -F @real-router/no-such-package test -- --run` — rc=0, ноль байт вывода), поэтому зелёным считается вывод, где видны имя пакета и число тестов, а не код возврата. 100% coverage обязательно. **Для адаптеров с пониженным порогом (`grep -A6 thresholds packages/*/vitest.config.mts` — порог <100% из-за compiler-кода) aggregate suite-pass НЕ доказывает покрытие ТВОЕГО файла: phantom-allowance поглощает новые непокрытые ветки/функции в изменённом `src`. Проверяй per-file (строка файла в coverage-таблице = 100% Stmts/Branch/Funcs), не только `Tests N passed` — иначе мёртвый код (напр. никогда не вызываемый `destroy`/`noop`) или новая ветка уедет в коммит под порогом.** **Если строки твоего файла в таблице НЕТ вовсе (печатается только заголовок `File | % Stmts…`) — это `skipFull: true`: репортер выводит ТОЛЬКО <100%-файлы. Отсутствие строки + exit-0 на НЕ-phantom пакете = 100% (не трать вызовы на попытку «увидеть строку» — её нет by design). На phantom-адаптере файл с непокрытой веткой, наоборот, ПОКАЖЕТСЯ — тогда читай строку.** **Финальный lint-гейт большого пакета (`core` и т.п.) гони СВЕЖИМ (`rm <pkg>/.eslintcache`) и в фоне (`run_in_background`), не с тесным таймаутом:** его скрипт — `eslint --cache` (~2 мин на `core`), и прогон, оборванный SIGTERM по короткому Bash-таймауту, либо `--cache`-прогон со старым вердиктом — ложно рапортует «чисто». **Не цепляй `; echo`/иную команду ПОСЛЕ lint — она затирает `$?`; **симметрично, `| tail`/`| grep`/`| head` ПЕРЕД снятием `$?` отдаёт код ПОСЛЕДНЕЙ стадии пайпа**, поэтому `eslint … | tail -5; echo "RC=$?"` бодро печатает `RC=0` от `tail` даже на красном линтере (тот же капкан у `vitest`/`tsc`); а background-нотификация `exit 0` — это код ОБЁРТКИ, не линтера. Верифицируй собственный код возврата инструмента: снимай его с САМОЙ команды (`pnpm lint; RC=$?` без хвоста, `--max-warnings 0` роняет и на warning'ах), а вывод фильтруй ОТДЕЛЬНЫМ вызовом либо читай лог (строка `✖ N problems` от eslint). ⚠ **И не спасайся `${PIPESTATUS[0]}` — это bash-изм, а шелл здесь zsh, где массив зовётся `$pipestatus` и индексируется с ЕДИНИЦЫ.** Bash-идиома в zsh раскрывается в ПУСТУЮ строку, так что печатается `RC=` — не ошибка, не ноль, просто ничто, и читается как «претензий нет».** ⚠ **Список изменённых файлов, собранный из `git status --porcelain`, НЕ фильтруй по `^??`:** новый тест/файл фикса ещё untracked, вылетает из списка, и линтер честно рапортует RC=0 по оставшимся — а в невключённом файле лежат ошибки. Проверяй ЧИСЛО переданных файлов против ожидаемого, а не только код возврата. Вдобавок `--fix` молча СНИМАЕТ неправильно расположенный `eslint-disable` как unused, оставляя реальную ошибку непокрытой — держи `disable`-директиву и её цель (`!`, и т.п.) на СМЕЖНЫХ строках; иначе твой «зелёный» lint скроет ровно то, что поймают хуки: pre-commit гоняет `turbo run test lint`, pre-push — весь граф. Каждый НОВЫЙ тест-блок прогоняй через `lint:fix` **сразу после написания**, до гейта: prettier-переносы в многострочных `expect(...)` / `test.prop(...)` — гарантированный источник 2–3 холостых раундов «гейт → fix → гейт», а `--fix` снимает их молча. ⚠ **Жалоба линтера на приведение или сравнение типов (`no-base-to-string`, `no-unnecessary-condition`, `no-confusing-void-expression`) бывает СЕМАНТИЧЕСКИМ сигналом, а не стилевым.** Прежде чем глушить её `disable`-ом или писать компаратор под неё, спроси, нужно ли сравнение вообще: часто достаточно факта присутствия/отсутствия, и это ещё и устойчивее. Тот же класс — правила про ФОРМУ API (`sonarjs/no-selector-parameter` и родня): boolean-флаг, выбирающий поведение, обычно значит, что решение принадлежит вызывающему — вынеси ветвление на call-site, и общий хелпер станет однозначным. ⚠ И если добавляешь **новый ПУБЛИЧНЫЙ метод в существующий класс** — сразу ставь его в блок публичных методов, до `#private`, иначе `@typescript-eslint/member-ordering` даст warning, а при `--max-warnings 0` это красный гейт; перенос метода с уже написанным докблоком стоит отдельного раунда «подвинул → prettier → гейт». **Симметрично и коварнее — новый `#private`-хелпер, положенный РЯДОМ с правленым публичным методом:** нарушителем становится не он, а КАЖДЫЙ публичный член ниже по файлу, поэтому вывод линтера выглядит как внезапная поломка половины класса и уводит расследование от твоей вставки. Новый приватный клади в приватную секцию сразу, а не рядом с местом правки.
2. **Changeset** — если дифф меняет код публичного пакета (`packages/*/src/` или `shared/<dir>/*.ts`), вызови Skill `changeset` с номером задачи аргументом — не пиши файл сам, heredoc-ом или скриптом: пакеты, уровень и сверку текста с кодом каждого пакета делает скил. **Симметричный фикс с прямым прецедентом** (тот же дефект-класс УЖЕ починен в другом пакете/адаптере — напр. зеркалишь vue #1352 в остальные `<Link>`): найди changeset прецедента (`git log --grep`/CHANGELOG затронутого пакета) и передай его скилу аргументом. Инфраструктурный дифф (0.3) — сюда входят и доки внутри `src`, и только тесты, и только комментарии — идёт в master без changeset, и `/changeset` не нужен.

## Фаза 4.5 — Атака на СВОЁ решение (обязательно; фикс без неё не считается готовым)

Фазы 2.5/2.6 прочёсывают радиус ДЕФЕКТА. Эта фаза — про дефекты самого ФИКСА: зелёный тир доказывает, что фикс не сломал того, что уже пинилось, и ничего не говорит о том, что фикс внёс. Заходи сюда, только когда фикс закончен и Фаза 4 зелёная — иначе атакуешь черновик. Всё найденное чини ЗДЕСЬ, до Фазы 5: доки и changeset должны описывать атакованное решение, а не первую версию (иначе в CHANGELOG уедет клейм, который атака опровергла — а он там навсегда).

Прогоняй ВСЕ векторы. Отсутствие находки по вектору — тоже результат, его называют в отчёте.

⚑ **Вектор 0 — ПЕРЕД коммитом, не после: батарея враждебных входов.** `packages/core/tests/helpers/hostileBags.ts` — шесть форм контейнера (свой перечислимый, унаследованный, свой неперечислимый, сквозной Proxy, null-прототип, собственный `__proto__` из `JSON.parse`), шесть не-объектных контейнеров и три аксессорных мешка (`countingBag` считает чтения, `driftingBag` меняет ответ со второго, `throwingBag` бросает из чтения), а для определения маршрута, где ядро аксессоры отвергает, — `countingProxy`. Если фикс трогает ЧТЕНИЕ или КОПИРОВАНИЕ объекта, который дал вызывающий, прогони её и **закоммить прогон вместе с фиксом**: прогон после коммита находит те же дефекты уже закоммиченными, а до коммита стоит столько же.

⚑ **Фикс поведения платформенного API (Navigation API, History API, DOM-события) — GREEN ещё и в реальном браузере, не только на моке.** Мок кодирует модель автора о платформе, и фикс стоит ровно на этой модели: зелёный тир на моке подтверждает модель, а не браузер. Рецепт: собери `src` пакета esbuild'ом (`node_modules/.pnpm/esbuild@*/node_modules/esbuild`, `conditions: ["@real-router/internal-source"]`, `nodePaths: [<pkg>/node_modules]`), отдай страницу через `context.route()` Playwright из `cross-router-bench/node_modules`, у каждого сценария — контроль.

⚠ **Мерь в КАЖДОМ движке и в версии без нужной возможности, и у каждой клетки две контрольные руки: тот же сценарий на каноническом URL в том же движке и сырой API без плагина.** Первая отделяет дефект фикса от свойства движка, вторая — предел платформы от тайминга самого плагина.

⚠ **Фикс впервые читает поле платформенного объекта (`id`, `key`, `sameDocument` записи)? Сначала посмотри, как его выдаёт мок, и измерь поле в браузере:** мок моделирует только то, что читали до тебя.

⚑ **Вектор 9 — назови УРОВЕНЬ, который закрыл, и проверь следующий.** Самый частый рецидив — не «фикс неверен», а «фикс верен на один уровень ниже дыры»: заморожен снапшот, а контейнер открыт; заморожен контейнер, а открыт слот, который его держит; захвачен интринсик в файле, а правило было про интринсик; захвачена одна половина примитива, а вторая читает глобал. Каждый раз тир зелёный, и каждый раз следующий круг находит то же самое уровнем выше.

Дешёвая проверка, одна фраза: **«что ДЕРЖИТ то, что я только что закрыл, и кто ещё делает то же самое?»** Заморозил объект — кто владеет слотом. Захватил интринсик — где ещё он читается. Починил писателя — есть ли второй писатель. Выпиши ответ ДО коммита, и если он не «никто», вектор не закрыт.

⚑ **И грепни, не написал ли ты заново доктрину соседнего файла** (для соседнего фикса, названного в issue, её читает Фаза 2): признак копии — в проверку добавлен очередной частный случай, а не термин, и правильная правка тогда — ПРОВОДКА.

⚑ **Фикс добавляет ЕЩЁ ОДНУ запись в канал, у которого писатели уже есть (история, URL, состояние)? Та же проверка, только над их защитами.** Перечисли, что делают существующие писатели канала и соседние плагины: откуда берут значение, как отсекают устаревшую навигацию, что делают с фрагментом и с тем же URL. Возьми то же или запиши, почему иначе. То же с предикатом, который добавляешь в ОБЩУЮ функцию ради одного вызывающего: прежде чем писать условие, выпиши всех её вызывающих и что каждому от неё нужно.

⚠ Формулировка «фикс на один уровень ниже» имеет зеркало: **проверка, привязанная к НАПИСАНИЮ там, где нужна привязка.** Спелинг вызываемого вместо символа, вид оператора вместо потока данных, позиция оператора вместо ветвления — всё это стенд-ины, и каждый ломается на первом же легальном переписывании. Если предикат сравнивает строку с именем, спроси, есть ли у этого имени символ, и резолви символ.

⚑ **Вектор 8 — не выводи заново то, чем уже владеет модуль.** Перед тем как написать копир, перечисление полей, производную или таблицу — грепни имена: если они уже встречаются вместе где-то в `src`, ты пишешь копию N+1, и правильное место фикса — тот модуль. Проверяется за один `grep`.

⚑ **Характеризующий пин ЗАМЕНЯЕМОГО места — до подстановки, не после.** Меняешь выражение на другое «эквивалентное» — сперва зафиксируй, что старое делает, по фиксированному списку осей: **происхождение ключа** (свой / унаследованный / неперечислимый), **терпимость к nullish**, **число чтений**, **заморозка**, **идентичность**. Ловит класс «substitution меняет ось, о которой никто не думал»: спред вместо чтения по именам молча теряет цепочку прототипов; `Object.hasOwn` вместо `?.[]` начинает бросать на `null`; литерал вместо ссылки теряет заморозку, которую давал сосед.

⚑ **Мутация нового СТОРОЖА направлена на него, а не назад на баг.** «Мутационно провалидировано» без направления — галочка: мутанты, которые все указывают на исходный дефект, ничего не говорят о самом стороже. Каждый новый тестовый артефакт получает мутанта того дефекта, который он заявляет, что ловит, плюс собственное опустошение/удаление (пустой `it.each` регистрирует НОЛЬ ячеек молча; ряд, добавленный в таблицу с порогом `toBeGreaterThan(N)`, делает удаляемой одну старую строку).

⚑ **Считаемое утверждение в прозе — только со считающим тестом.** «Читается один раз», «только свои ключи», «бросает на любой другой форме» — если число не производится командой в следе коммита, оно не проверено. Правило шире: **любое предложение, утверждающее что-то о коде ВНЕ правимого куска, обязано нести либо запускаемую команду с выводом, либо адрес по ИМЕНИ СИМВОЛА (никогда `:NNN` — номера строк гниют), либо метку `UNMEASURED`.** Короткое утверждение — не исключение: «две соседние enum-опции» — четыре слова, и это тоже утверждение о коде вне куска. Измерительные и ловушечные комментарии правилу уже удовлетворяют, так что ценного оно не отнимает.

⚑ **`git checkout <ref> -- <path>` и `git checkout -- <path>` — обе формы разрушительны, и на ветке БЕЗ коммитов вторая стирает всё.** `git checkout -- <файл>` восстанавливает из индекса/HEAD; если правка ещё не закоммичена, она исчезает без следа и без предупреждения. Первая форма вдобавок **стейджит** то, что пишет, и следующий `git commit` без путей унесёт это в коммит, даже если `git add` ты делал только своим файлам. Для сравнения ревизий бери `git show <ref>:<path> > /tmp/...` или `git archive`; для отката своей же пробы — `cp` из копии, снятой ДО правки. Копию снимай ПЕРВОЙ командой, а не когда понадобится.

⚑ **Одна правда — один дом.** Прежде чем писать клейм, грепни его: если он уже где-то живёт, ссылайся, а не пересказывай. Исправляя измеренную ошибку, грепни ТЕКСТ ошибки и почини все копии одним коммитом.

⚑ **Правка, СДЕЛАННАЯ по итогам атаки, атакуется тоже — и она опаснее исходной.** Пишется в убеждении, что думать уже закончили; добавляет обычно не строку, а МЕХАНИЗМ (бросок, ассерт, производную), то есть больше поверхности на строку; и её не атакует никто, потому что «фаза атаки уже была». Прогоняй по ней только ИЗМЕНЁННОЕ: по мутанту на каждый новый механизм (`P` вектора 2), по пробе на каждый новый клейм в постоянном артефакте (`M` вектора 3), `Q` — если менялась форма возврата или ассерта. Векторы, чей предмет не менялся, не перепрогоняй, и рой не перезапускай — его гейт по наличию предмета. **Останавливайся, когда раунд не добавил ни механизма, ни клейма:** рекурсия конечна, потому что коррекция всегда меньше исправляемого (`1 терм` → `2 механизма + 3 клейма` → `0 + 0`). Замер клейма читай по коду возврата, а не по выводу: `head -N` обрезает список ошибок `tsc`, а `grep "error TS"` даёт ноль, когда между `error` и `TS` стоят ANSI-коды.

1. **Мутируй КАЖДЫЙ терм, который ты ДОБАВИЛ ИЛИ ПЕРЕНЁС — включая «очевидно несущие».** ⚠ **И читай ЧИСЛО упавших клеток, а не цвет: красный мутант с ОДНОЙ упавшей клеткой — сигнал, а не зачёт.** Если терм обслуживает таблицу из N ячеек, а его снятие роняет одну, охраняет его не таблица, а один соседний ассерт — и следующая правка формы снимет его молча. Сравнивай число упавших клеток с числом ячеек, которые терм обязан покрывать; расхождение означает, что охрана лежит не там, где ты думал. Не «фикс в целом», а каждое условие, каждый `&&`/`||`, каждый ранний выход и каждый добавленный оператор или объявление — вызов, присваивание, функцию, поле, флаг, слушатель, `try`, обёртку — по отдельности: сними, прогони тир. То, без чего тир зелёный, — это **эквивалентный мутант, посаженный твоей рукой**: гарантированный выживший в Stryker, лишняя ветка под 100 %-гейтом и ложное впечатление, что условие что-то охраняет. Убери его или перепиши так, чтобы избыточность была ЕСТЕСТВЕННЫМ short-circuit'ом, названным в комментарии, — но не оставляй молча. ⚠ **Прежде чем назвать выжившего эквивалентным, проверь, что мутант делает то, что ты задумал.** Мутант, который бросает внутри существующего `try`, — уже другой мутант: `catch` запускает запасной путь, и тир зеленеет не потому, что терм лишний.

   ⚑ **Третий исход, которого в правиле выше нет: терм принадлежит ЧУЖОМУ авторитету.** «Убери или перепиши» предполагает, что терм твой. Новый член СЕМЕЙСТВА наследует контракт семейства, и пинить его надо в доме этого контракта, а не рядом с термом; удаление тогда не убирает избыточность, а молча выводит нового члена из-под общего правила. Признак — терм повторяет то, что соседние члены делают безусловно.

   ⚠ **Строка результата батареи обязана содержать ЧИСЛО: ПУСТО — это отказ харнесса, а не зелёный прогон.** Пустая строка читается как «нечего показать», то есть в сторону «запинено», и контроль восстановления её не ловит — он пустеет тем же способом. Сверь с сырым выводом одной команды, прежде чем читать результат. (В zsh неквотированное раскрытие параметра на слова не расщепляется: список тест-файлов уходит в vitest одним аргументом, тот не находит ничего, и строки батареи выходят пустыми.) ⚠ **Второй отказ того же рода — КРАСНАЯ база: на ней каждый мутант читается как убитый.** Батарея сначала прогоняет тир без мутации и останавливается, если он не зелёный.

   ⚠ **Зелёный мутант — это ещё и вопрос «сколько ДВЕРЕЙ у этого терма, и сколько из них достаёт мой тир».** Терм, прикрытый соседним на единственной двери, которую ты проверяешь, печатается как эквивалентный — и удаление «лишнего» открывает двери, до которых ячейки не доходили. Прежде чем звать терм лишним, перечисли его вызывающих (греп по имени ПРЕДИКАТА, а не по имени функции) и убедись, что у каждой двери есть ячейка; дверь без ячейки — это не эквивалентность, а непроверенная половина. Признак: мутанты нескольких термов роняют ОДИН и тот же тест.

   ⚑ **УСЛОВИЕ ЗАКРЫТИЯ, а не ощущение полноты.** Перед вектором выпиши `N` — число термов, которые дифф ДОБАВИЛ или ПЕРЕНЁС (условия, `&&`/`||`, ранние выходы, перемещённые проверки), и мутируй все `N`. В отчёте печатай `N/N` с перечислением, а не «мутировал ключевые»: закрытие вектора — это сошедшийся счёт, и решать его должен счёт, а не тот, кто от вектора устал. Незакрытый остаток называй числом («мутировал 3 из 4, четвёртый — X, потому что …»), тогда он виден и тебе, и ревьюеру.

   ⚠ **Единица этого вектора — терм УПРАВЛЯЮЩЕГО ПОТОКА, поэтому фикс-ДАННЫЕ закрывает его, не коснувшись риска.** Добавил член в перечисление (ключ в `Set`, имя в union, поле в таблицу режимов) — условий не добавилось ни одного, честный `N` равен единице или нулю, и вектор сходится за один прогон. Для данных мутанты другой формы, и их надо прогонять ОБА: снять члена (это откат) **и посадить ФАНТОМНОГО** члена, которого не объявляет ничто. Второй мутант проверяет обратное направление и обычно оказывается единственным сторожем целого класса.

   ⚠ **Терм — не всегда условие, и не всякий мёртвый терм можно УДАЛИТЬ.** Флаги дескриптора (`writable`/`enumerable`/`configurable`), поля литерала опций, элементы `init`-объекта мутируются тем же приёмом, но пропуск меняет семантику на дефолт — то есть «убери избыточное» тут неприменимо. Такой мёртвый терм закрывается **усилением ассерта**: пинь дескриптор или объект ЦЕЛИКОМ, а не значение: запись copy-on-write через spread сбрасывает дескрипторы, поэтому такие флаги часто не охраняет ни один тест.

   ⚠ **Перенесённый терм — тоже твой.** Он мог быть незапиненным и ДО тебя, а после переноса гарантия за него на тебе, и зелёный тир этого не покажет — он был зелёным и на старом месте. Тот же приём и та же цена.
   ⚠ **И проверь ОБРАТНОЕ: не сделал ли твой фикс эквивалентным или МЁРТВЫМ чужой, уже отгруженный код.** Признак — тесты чужого фикса краснеют не потому, что ты его сломал, а потому что их форму больше не построить; и второй, более тихий — просадка COVERAGE в соседнем пакете, которую видно только под полным гейтом (пакет проходит без coverage и падает с ним). Не глуши `v8 ignore`: недостижимый код удаляй, а его историю пиши в коммит и changeset, не в комментарий на его месте (CLAUDE.md «No historiography»). Назови это в отчёте отдельно, потому что цена крупная — исчезают чужие тесты и целый класс дефектов.
   ⚠ **Мутант, который ты СОБРАЛ, а не откатил, обязан иметь позитивный контроль ДО прогона.** `?.`, опциональное поле, несуществующий метод, каст `as any` мимо реального объекта — всё это компилируется в no-op, мутант НЕ ИСПОЛНЯЕТСЯ, и тир выходит ЗЕЛЁНЫМ — неотличимо от «тест не дискриминирует». Честное чтение такого прогона — «замера не было», а не «guard слабый». Дешёвый и всегда верный вариант — откатить фикс ЦЕЛИКОМ (`git show HEAD:<path> > <path>`), а не изобретать эквивалент; если откат слишком широк, докажи, что мутант ИСПОЛНЯЕТСЯ (счётчик, лог, заведомо падающий ассерт внутри него), прежде чем читать результат: вызов через `?.` на отсутствующем свойстве молча не исполняется. ⚠ **Второй способ не исполниться: мутант исполняется, а его ТРИГГЕРА нет во входах.** Мутант продакшена, срабатывающий на значении, которого генератор не порождает, зелёный при любом тесте. Прежде чем читать зелёный, измерь частоту триггера сэмплом генератора (`fc.sample`): редкое значение, например `NaN` в `fc.anything()`, может не встретиться ни разу.

   ⚠ **И первое вхождение мутируемого терма нередко лежит в ТВОЁМ ЖЕ комментарии.** Докблок фикса цитирует код, который фикс и вводит, поэтому `perl`/`sed` без `/g` — и любая замена «первого совпадения» — правит ПРОЗУ, а код остаётся целым: мутант не исполняется, прогон зелёный, и читается это как «не запинено». Якори замену на строку КОДА (отступ, завершающая запятая, `^…$` с `/m`), а исполнение подтверждай счётчиком в ОБЕ стороны: `grep -c` по мутируемому тексту обязан дать ожидаемое число и после мутации, и после восстановления — «не ноль» тут не проверка.

   ⚠ **Ассерт сравнивает РАЗНОСТЬ или дельту? Вакуум у неё — равенство операндов, а не ноль в одном из них.** Мутант, обнуляющий одну половину, ломает равенство и краснеет — то есть отчитывается «охраняется» ровно там, где сторож пуст. Мутируй так, чтобы обе стороны выродились ОДИНАКОВО (убери источник значения целиком, а не одно слагаемое), и ставь рядом отдельный ассерт, что уменьшаемое непусто, — иначе проба, не дошедшая до замера, проходит навсегда. (Пример: в `(reads ?? 0) - afterRegistration` мутант `afterRegistration = 0` даёт `1 - 0 = 1` и честную красноту, а убранное из мешка поле — `0 - 0 = 0` и зелёный тир на живом вакууме.)

   ⚠ **Восстанавливай мутанта из КОПИИ ФАЙЛА, а не из git, пока фикс не закоммичен.** `git checkout -- <file>` и `git reset --hard` возвращают к HEAD, а HEAD твоего фикса ещё не содержит — так батарея мутантов стирает сам предмет замера, и следующие мутанты меряют пустоту. Перед КАЖДОЙ батареей и откатом 1b — новая копия всех файлов, которые они меняют: `cp <file> <backup>`, после каждого мутанта `cp <backup> <file>`, и контроль после восстановления: отпечаток `git diff HEAD` и созданных файлов совпадает со снятым до батареи.
   ⚠ **И после восстановления верь `git diff` + `tsc`, а не панели диагностик редактора.** Диагностики, посчитанные ПОКА мутант был жив, переживают восстановление файла и выглядят как настоящие ошибки — причём в файлах, которых ты не трогал, что читается как «фикс сломал соседей».

   ⚠ **Скриптовая правка БЕЗ `assert old in s` не падает — она молча ничего не делает, и последствие ты прочитаешь как находку о КОДЕ.** Это касается не только мутантов: любой `python`-скрипт, правящий файл через `.replace()`, обязан утверждать наличие якоря перед заменой. Отдельно опасен якорь, захваченный ДО `lint:fix` — форматтер переносит строки и рвёт его, так что заготовленная замена перестаёт совпадать. Симптом всегда один: тест ведёт себя не так, как объясняет твоя модель, и ты начинаешь чинить модель вместо скрипта.

   ⚠ **Скрипт мутации пиши на АБСОЛЮТНЫХ путях и без `cd`.** cwd у Bash-тула персистентен между вызовами, поэтому повторный `cd <dir>` падает — а `cd <dir> && <правка>` тихо съедает правку целиком, и следующая команда того же блока при этом отрабатывает. Получается ЧАСТИЧНО применённый мутант: один сайт мутирован, второй нет либо мутанты легли друг на друга, и замер по нему невалиден, хотя выглядит нормально. После каждого restore предъявляй позитивный контроль (`grep -c <маркер-фикса> <файл>`) — код возврата `cp` о содержимом файла не говорит.

   ⚠ **Счётчик «мутант применился» — ассерт на РАВЕНСТВО ожидаемому числу, а не проверка «не ноль».** `landed=2` там, где мутант один, означает не более сильного мутанта, а то, что предыдущий не снялся, — и замер по такому прогону невалиден, хотя и печатает правдоподобное «1 failed». Самая тихая причина этого — **мутация собственного бэкапа**: команда правки, которой достался путь внутрь каталога копий, запекает мутанта в эталон, после чего restore честно отрабатывает и возвращает его же. Отсюда два следствия: проверяй восстановление по ОРИГИНАЛЬНОМУ маркеру (`grep -c <исходный-текст>`), а не по маркеру мутанта — второй ноль одинаково даёт и чистый файл, и файл, где мутант просто написан иначе; и никогда не давай команде мутации путь в каталог бэкапов.

1b. **Откати свой фикс ЦЕЛИКОМ и посмотри, покраснеет ли хоть что-то.** Вектор 1 мутирует термы, которые ты ДОБАВИЛ; этот спрашивает другое — охраняется ли то, что ты закрыл. Возьми точный обратный дифф (`freeze(` → `Object.freeze(`, снятая заморозка, снятый гвард) и прогони ВСЁ. Зелёный прогон под откатом означает, что дефект найден, измерен, закрыт — и оставлен без охраны: следующий рефактор вернёт его молча, а мутационный отчёт назовёт твой фикс эквивалентным мутантом. **Пин, которого не существует, неотличим от фикса, которого не было.**

⚠ Не засчитывай красноту от СОСЕДНЕЙ клетки. Мутация, которая краснит что-то, но не то, — самый частый способ прочитать вакуум как покрытие: у фикса и у соседа общий файл, и глаз читает «покрыто». Спроси, какая именно клетка упала и про твой ли она сайт.

⚑ **Гейт вектора: перед ним выпиши, ЧТО именно ты закрыл — по одному наблюдаемому исходу на фикс, — и для каждого предъяви откат, который его краснит.** Не «фикс покрыт», а `R/R` исходов с названной клеткой на каждый.

2. **Атакуй CLASS-GUARD отдельно от кода, по одному сайту класса.** Property/инвариант из Фазы 2.5 обязан краснеть на мутации **КАЖДОГО** сайта, а не одного: мутируй сайт-1 → property красная, восстанови, мутируй сайт-2 → красная, и так далее. Guard, зелёный хотя бы на одном сайте своего класса, — не class-guard, а тест одного сайта под широким именем, и именно он даёт ложную уверенность «класс закрыт».

   ⚑ **УСЛОВИЕ ЗАКРЫТИЯ — ДВА счёта, и второй про сам guard.** Сайты класса — это `S`. Ассерты, без которых guard не может даже ЗАДАТЬ свой вопрос, — это `P`: каждая ПРОИЗВОДНАЯ, из которой строится ожидание (AST-обход, `it.each(<список>)`, скан по `src`, таблица фикстур), каждый порог непустоты и каждый КОНТРОЛЬ. ⚠ **Производная от уже проверенной производной считается ОТДЕЛЬНО — непустота родителя НЕ наследуется.** `SUB = ALL.filter(...)` / `.slice(...)` при пустом результате снимает свои `each`-ячейки молча, а порог, стоящий на `ALL`, остаётся зелёным: он про другой список. Порог нужен на КАЖДЫЙ список, которым индексируется `each`. Мутируй `S + P`, печатай `S/S` и `P/P`. **И читай не ЦВЕТ, а ЧИСЛО ТЕСТОВ** — на каждый мутант печатай `N_до → N_после` из строки `Tests N passed`: сломанная производная не краснеет, она отдаёт `it.each([])`, и файл молча ХУДЕЕТ (в `@vitest/runner` `each` делает `cases.forEach` без проверки на пустоту). Мутант, после которого тестов стало МЕНЬШЕ, — это не «guard устоял», а «guard не запускался». Симметрично для КОНТРОЛЯ: мутант, делающий дверь API безусловно `undefined`, оставляет каждый ассерт «мешок пуст» вакуумно-зелёным. ⚠ И контроль обязан быть проверяемо **ВНЕ охраняемого множества**, а не только непуст: после фикса охраняемое значение и контрольное ведут себя ОДИНАКОВО, поэтому подмена контроля на члена множества не краснит ничего и тихо лишает таблицу единственной колонки, доказывающей, что она не выродилась в «у всех пусто». Ассерть принадлежность (`expect(GUARDED).not.toContain(CONTROL)`). ⚠ **Тот же вакуум прячется в сравнении ДВУХ вычисленных значений** — `expect(f(name)).toEqual(f(CONTROL))` истинно, когда обе стороны вырождаются ОДИНАКОВО, поэтому сломанная дверь проходит его, а не роняет. Рядом с каждым таким сравнением нужен ассерт, что КОНТРОЛЬНАЯ сторона непуста. **И мутируй КАЖДУЮ дверь отдельно:** один regex-мутант по всем сайтам обычно достаёт лишь один из них (двери пишутся по-разному — `return f(...)`, `x = f(...)`, `.filter(...)`), а зелёный результат на недостигнутой двери читается как «этот контроль избыточен» и приводит к его удалению.

   ⚑ **Утверждение теста, что фикстура упражняет производственный терм («X is tagged», «Y is private»), — тоже `P`: мутируй этот терм, даже если фикс его не трогал.** Такое утверждение живёт в комментарии или имени теста, и ни один ассерт его не держит. Если другая часть фикстуры даёт тот же исход, терм не решает ни одной клетки, а текст продолжает обещать обратное.

   ⚠ **Guard, чьё ожидание ВЫВЕДЕНО (AST-обход, скан по `src`, чтение файла по пути), держится на ИМЕНАХ-КРЮЧКАХ — мутируй и их.** Переименуй интерфейс/константу, на которую смотрит производная, и передвинь файл: это ЛЕГАЛЬНЫЙ рефакторинг с зелёным тиром, после которого guard либо краснеет, либо находит НОЛЬ и молчит — тогда он мёртв, а узнаешь ты через релиз. «Ноль найденного» у СВОЕГО теста читается так же неверно, как пустой grep. И отдельно проверь, что производная **падает** на форме, которой не понимает, а не ПРОПУСКАЕТ её: пропуск даёт ЧАСТИЧНЫЙ список, а его не поймает никакой порог непустоты. Форма такой производной: явно пропускать известные не-члены (индексную подпись), собирать любое именованное объявление, бросать на неопознанной форме и проверять, что крючок найден (`found`), — тогда переименование называет себя в падении.

3. ⚑ **Клейм, выведенный из ФОРМЫ твоего же кода, — не замер, и он самый опасный из всех.** «Ровно N значений делают X», «только эти три случая», «всё остальное — Y» звучит как факт о предметной области, а на деле пересказывает `if`, который ты только что написал. Предикат отвечает на вопрос «как это НАПИСАНО», спецификация — «куда это РЕЗОЛВИТСЯ», и расходятся они ровно там, где фикс что-то ЗАБИРАЕТ: значение, которое твоё сравнение относит к «чужим», по спецификации может резолвиться в «своё». Перед тем как записать такое предложение, перечитай первоисточник ПО КАЖДОМУ члену перечисления отдельно — и учти, что процитировать спецификацию в той же сессии недостаточно: клейм пишется из головы, а не из вкладки.

3b. **Перепроверь ПРОБОЙ каждый клейм, который ты написал в changeset/коммит/комментарий** — особенно формы «ничего больше не меняется», «только X», «для здорового дерева поведение прежнее». Это самые дешёвые в написании и самые дорогие в CHANGELOG утверждения, и пишутся они по памяти о замысле, а не по замеру.

⚑ **«Было» клейма — это ВЫПУЩЕННАЯ версия, а не состояние до твоего первого коммита.** Ветка живёт днями и успевает внести и починить собственные дефекты; описанный в changeset как «раньше падало» такой дефект уезжает в CHANGELOG пакета и читается консьюмером как баг предыдущего релиза — которого у него не было. Способ: возьми SHA последнего релиза (`git log --format=%h -1 origin/master` на релизном коммите), сделай worktree и прогони пробу ТАМ; если «до» воспроизводится только на промежуточном коммите ветки — это не фикс, а внутренняя история, и в changeset ей место лишь как явной оговорке.

⚠ **Перф-числа — тот же клейм, и мерить их надо против той же базы.** Заголовочная цифра, посчитанная против «до моей ветки», нетто-вычитает из своего выигрыша регресс, который у консьюмера уже стоит, и печатает МЕНЬШЕЕ число. Если два прогона одного протокола расходятся, печатай ОБА конца, а не удобный.

⚑ **АРТЕФАКТЫ — всё, что уедет НАРУЖУ, а не только черновик.** ОПУБЛИКОВАННЫЙ текст комментария, докблок фикса, комментарий теста, строка `INVARIANTS.md`, абзац вики, тело коммита — каждый несёт клеймы, и каждый живёт дольше прогона.

⚑ **И раздели `M` на ДВА класса, потому что метод у них разный.** **Клейм о ПОВЕДЕНИИ** закрывается пробой. **Клейм об ИНВЕНТАРЕ** («N мест», «единственный потребитель», «ноль консьюмеров», «все шесть адаптеров») пробой не закрывается в принципе: проба подтверждает ЧЛЕНА множества, а клейм говорит о его ЗАМКНУТОСТИ. Инвентарь закрывается ПЕРЕПИСЬЮ, и перепись обязана напечатать четыре вещи: КОМАНДУ, ПОРОГ («что я считаю кандидатом»), число кандидатов ДО отсева и позитивный контроль инструмента. Число, полученное двумя грепами, — это два грепа, а не перепись. Дешёвейшее закрытие инвентарного клейма — не считать, а НЕ УТВЕРЖДАТЬ: вычеркни цифру, если она ничего не гейтит. Печатай `M = M_поведение + M_инвентарь`. ⚠ **Перепись, на которую ссылается текст, снимается ПОСЛЕ последней правки дерева:** число, снятое раньше собственной правки, описывает дерево, которого уже нет, и при этом выглядит замеренным.

⚑ **СКОУП клейма обязан совпадать со скоупом ЗАМЕРА.** «Единственный тест, который краснеет», «ни один потребитель», «нигде больше» — это утверждения о РЕПОЗИТОРИИ; прогон одного пакета их не закрывает, а `pnpm -F <pkg> test` — это ровно один пакет. Либо сузь формулировку до того, что мерил («единственный **в ядре**»), либо прогони всё, что могло бы покраснеть.

⚑ **УСЛОВИЕ ЗАКРЫТИЯ.** Перечитай СВОЙ changeset и черновик комментария и выпиши `M` — число ФАКТИЧЕСКИХ утверждений (то, что можно опровергнуть прогоном: числа, «не меняется», «покрыто», «запинено», «единственный», «ноль потребителей»). Проверь все `M` и напечатай `M/M`. Клейм про ЧУЖОЙ код проверяется так же, как про свой: «эти два поведения запинены как контроли» — утверждение о тире, а не о твоём диффе, и мерится оно мутацией тира.
⚠ **Число, придуманное по ходу написания фикса, проверяй при ПЕРВОМ употреблении, а не на этом векторе.** Клеймы из тела issue перепроверяет Фаза 0.7, а это — цифра, которой в issue не было: «для трёх релизов», «в двух местах», «единственный потребитель». К моменту вектора 3 она уже стоит в докблоке фикса, комментарии теста, changeset'е и черновике комментария, и правка стоит N патчей вместо одного.

4. **Ищи, что фикс ЗАБРАЛ.** Старый код что-то делал, и на это кто-то мог опираться: сузил предикат — кто попадал в отброшенную часть? Перестал чистить — что теперь копится (слоты лимитов, подписки, записи кэша)? Начал отказывать — чей рабочий сценарий стал отказом? Каждое «забрал» — либо улучшение, которое надо НАЗВАТЬ и запинить тестом, либо регрессия.

   ⚑ **Превращаешь проглоченный сбой в отказ внутри цикла по независимым элементам — не бросай на первом.** Проглоченный сбой пропускал один элемент, и остальные доходили до отчёта. Бросок прячет находки ВСЕХ остальных: до ещё не сравненных цикл не доходит, а уже сравненные теряются, если отчёт печатается после цикла. Копи сбои, доведи сравнение остальных до конца, напечатай оба списка, потом решай exit code.

   ⚑ **Переписал механизм целиком — перечисли ОТКАЗЫ старой версии.** Замена, а не правка, теряет отказные дорожки молча: они живут в побочных свойствах старого кода, а не в его назначении, и новый код их не наследует. По `git show HEAD:<file>` выпиши каждое место, где старая версия бросала, давала находку или владела тем, что в новой стало «ничьим», и для каждого предъяви ячейку, где новая отказывает там же.

5. **Замерь то, что объявил перф-решением.** «Не чиню там, потому что горячий путь» — это КЛЕЙМ, и он гейтит скоуп. Померь стоимость примитива, который пришлось бы туда поставить, и сопоставь с уже задокументированной стоимостью той операции. Число либо оправдывает отказ, либо его опровергает — и в первом случае оно ещё и даёт follow-up'у ДИЗАЙН вместо «сделать правильно».

   ⚠ **Домен вектора — не «перф», а ЛЮБОЕ обоснование, которое ГЕЙТИТ скоуп.** «Слишком рискованно», «вне скоупа», «этот сайт такой же, как тот, что я прочитал» несут тот же долг предъявления, что и «горячий путь», — и самое частое из них не число, а АНАЛОГИЯ. Сайт, объявленный чистым по сходству с прочитанным, обязан быть прочитан: это одна минута против клейма, который иначе уходит в отчёт как проверенный.

   ⚑ **Позитивный контроль достижимости — ВНУТРИ арки, а не в голове.** Инструмент бывает рабочим, арки настоящими, а изменённой ветки не достигает ни одна — и тогда он честно печатает «в шуме» при нуле измерений. Арка обязана сама предъявить, что дошла: флаг рядом с числом, а не уверенность до прогона.

   ⚠ **A/B поверх ПОВЕДЕНЧЕСКОГО фикса: арка годится, только если выход обеих рук идентичен.** Там, где поведение и должно было измениться, сравнения нет — есть две разные работы, а разница читается как цена фикса и способна откатить решение. Печатай выход обеих рук ПРЕЖДЕ, чем называть дельту.

6. **Прогони граничные формы ВХОДА, а не только ту, что в issue**: та же фигура на уровень глубже; фигура, у которой есть ещё и дети; имена-ловушки (`__proto__`, `constructor`); глубина рекурсии против УЖЕ существующего обрыва стека (новый ли он у тебя, или падает раньше и не твой); и десинхронизация того коллаборатора, на который твой новый предикат опёрся (может ли он ответить `undefined`/устаревшим — и что тогда).

   ⚠ **`K` считается и по перечислениям, которые называет КОД, а не только тело issue.** Определение «сколько названо в теле» даёт вектору условие закрытия ровно там, где перечисление кто-то уже выписал за тебя, — а несущие перечисления фикса обычно в теле не названы вовсе: члены типа, писатели поля, точки входа, адреса в доках. Перечисление, которое ты обнаружил сам или которое выдал скан, — тоже чек-лист с числом.

   ⚠ **И наоборот: перечисление В ТЕЛЕ issue — это чек-лист, а не проза.** Если тело называет N форм / клеток / сайтов, покрыть надо ВСЕ N, и «сколько я проверил» сверять с «сколько названо», а не с ощущением полноты. Пропущенный член перечисления опаснее непридуманной формы: ты строишь по остальным таблицу, объявляешь её матрицей и делаешь из неё вывод, а недостающая строка ровно его и меняет.

   ⚑ **Заглушка внешнего процесса обязана падать ВСЕМИ способами, которыми падает настоящий: код выхода, сигнал, «не найден».** `execFileSync` даёт `status: null` и при сигнале, и при ENOENT, поэтому заглушка с одним `exit 1` пропускает мутант, который считает только статус. **И заглушка обязана ДЕРЖАТЬ то, что получила: журнал вызовов плюс ячейка, которая сверяет точные аргументы.** Заглушка, отвечающая на любой argv, пропускает мутанты, теряющие аргументы.

   ⚠ **Копия скрипта в фикстуре запускается из ПОДКАТАЛОГА фикстуры:** иначе скрипт, берущий корень из cwd, неотличим от берущего корень из своего расположения.

7. **Проверь ФОРМУ возврата и связанность флагов**, если ты её менял: не стало ли значение трёхзначным, не читается ли один и тот же флаг дважды, не появилось ли у `undefined` двух смыслов. Здесь ошибку ловит не тест, а чтение.

   ⚑ **УСЛОВИЕ ЗАКРЫТИЯ — таблица `Q/Q`,** по строке на каждое значение, которое функция может вернуть (и на каждую комбинацию флагов): значение → что оно означает. Значение с ДВУМЯ смыслами и есть находка; без напечатанной таблицы вектор невозможно предъявить прогнанным.
   ⚠ **И наведи его на АССЕРТ, а не только на продуктовый код.** Ровно этот дефект живёт в `expect(x).toBeUndefined()`, где `undefined` означает и «пусто по контракту» (то, что пинится), и «дверь сломана» (вакуум) — то есть «у `undefined` два смысла» дословно, только в тесте. Если твой ассерт сравнивает с `undefined`/`false`/`[]`, рядом обязан стоять КОНТРОЛЬ, который отличает контракт от поломки.

**Рой агентов.** ⚑ **Гейт — по НАЛИЧИЮ ПРЕДМЕТА, а не по размеру диффа** (форма гейта — как в Фазе 2.6, фаза дорогая: агент на линзу, и каждый перечитывает свой контекст на каждом шаге). Запускай, если ВЕРНО ХОТЯ БЫ ОДНО: (а) фикс принёс **выведенный / authority-guard** (ожидание строится обходом AST, сканом `src`, чтением файла по пути); (б) в твоём тексте есть хоть одно **инвентарное** число («N мест», «единственный», «ноль»); (в) дифф трогает **больше одного пакета** или ты правил доки/вики. Ни одного — **пропусти**, в отчёте: «рой не нужен, предмета нет». ⚑ **И знай, где он окупается: на ТЕКСТЕ, а не на коде.** Формулировка гейта целит в артефакты кода, но добыча систематически другая — дефекты в changeset'ах, докблоках и пинах, включая неназванную цену фикса, которая иначе уезжает в публичные CHANGELOG'и. Отсюда практическое правило: если дифф порождает changeset публичного пакета, гейт сработал, независимо от размера правки. ⚠ Размер диффа гейтом не служит: правка в одну константу тоже может нести guard, инвентарное число или правку доков — то есть предмет. ⚑ **Порядок: правишь доки или вики в Фазе 5 — рой запускай ПОСЛЕ неё, а не в конце 4.5.** Гейт (в) называет доки предметом, но по порядку фаз рой стартует раньше, чем они написаны, и текст Фазы 5 не атакует никто. То же с кодом, дописанным ПОСЛЕ роя, — расширением скоупа или правкой по его находкам: новая дельта получает свой проход, минимум регрессионную и граничную линзы, пока проход не вернётся без находок о поведении.

**Досье роя — до запуска.** Запиши один файл в scratchpad: дифф (или sha), затронутые символы с их вызывающими, клетки RED-таблицы, новые утверждения в доках и changeset, для фикса платформенного поведения — файл браузерных замеров (см. ниже). Каждой линзе отдай её мандат и путь к досье, а не пересказ; линза начинает с досье и читает код по символам, целый файл — только когда без него нельзя. Отчёт линзы ложится в твой контекст и перечитывается на каждом следующем шаге, поэтому требуй от неё только находки и список прогнанных атак — по строке на атаку, без пересказа кода.

Разошли `Agent` (`subagent_type: Explore`) ПАРАЛЛЕЛЬНО (в ОДНОМ сообщении, иначе последовательно), по одной ЛИНЗЕ на агента, а не по одному файлу:

- **мутационная** — ⚠ только КАНДИДАТЫ: термы **и АССЕРТЫ** без наблюдаемого эффекта, с точной правкой-мутантом и предсказанием; мутация и прогон за тобой, потому что агент read-only. Требуй ЗНАМЕНАТЕЛЬ — что проверено и найдено НЕСУЩИМ, иначе получишь список хитов без охвата;
- **вакуумная** — предмет не дифф продукта, а НОВЫЕ ТЕСТЫ: каждый ассерт, чей субъект — выведенный список, порог непустоты, КОНТРОЛЬ или сравнение с `undefined`/`[]`; для каждого списка ответ на «может ли он стать пустым и что тогда напечатает прогон». Без неё вектор 2 закрывается ложно;
- **инвентарная (перепись)** — самая agent-shaped: каждое число и каждое «единственный/ноль/все» в твоём тексте, с командой, порогом, кандидатами до отсева и позитивным контролем инструмента;
- **регрессионная** — что старый код делал и для кого, а новый не делает (включая каналы ОТКАЗА: вход, который раньше отвергался, а теперь проходит, и обратное — вход, который раньше принимался, а теперь отвергается); каждое найденное сверь с уровнем changeset по списку несовместимых изменений под таблицей `.changeset/README.md`;
- **граничная** — входы, которых нет в тестах;
- **потребительская** — кто ещё читает изменённый выход/событие/сигнатуру, и КАК читает (по ключу против перебора/спреда/сериализации);
- **ротовая** — крючки выведенных guard'ов: какое ЛЕГАЛЬНОЕ переименование или переезд заставит guard найти НОЛЬ.

Каждому — досье и требование `file:line` + ВОСПРОИЗВЕДЕНИЕ, а не мнение; требуй позитивный контроль поискового инструмента и список прогнанных команд. После компакции отчёт линзы бери из транскрипта её агента (`<output-file>` уведомления, он же `subagents/agent-<id>.jsonl`) до проверки её находок: сводка хранит ярлыки, а не содержание. ⚠ Вывод агента — гипотеза: **верифицируй каждую находку сам**, прогоном или пробой, прежде чем чинить — и проверяй не только ВЕРДИКТ, но и МЕХАНИЗМ: агент называет ближайшую видимую причину, и правка под неверный механизм выходит зелёной и бесполезной. И наоборот, «агент ничего не нашёл» не закрывает вектор — закрывает его твой прогон. ⚠ Векторы 1, 2 и половина 3 роем СТРУКТУРНО не закрываются: мутация требует правки дерева и прогона, а агенты read-only. Отдачу линз сведи в таблицу итогового отчёта: по ней решается состав роя.

⚑ **Фикс поведения платформы: дай рою файл всех браузерных замеров прогона и проб, которыми они сняты,** иначе линзы выводят поведение браузера из мока. **Находку о ТАЙМИНГЕ проверяй в браузере до правки:** мок зовёт обработчики не тогда, когда браузер.

⚑ **Скажи рою, что ПУСТОЙ отчёт — результат, иначе прогон перестаёт быть измерением.** Инструкция «исходи из того, что дефект есть» правильна для охоты и разрушительна для проверки: агент найдёт что-нибудь при любом состоянии кода, и результат больше ничего не различает. Когда заход отвечает на вопрос «устоялось ли», пиши дословно: «это измерение, а не охота; если ничего нет — так и скажи, приложив список того, что пробовал; чистый отчёт с полным перечнем атак ценен ровно настолько же, насколько находка, и заметно ценнее, чем маргинальная находка, растянутая до заголовка; если худшее найденное — опечатка в комментарии, так и напиши». Без этой фразы «рой опять что-то нашёл» не является данными ни за, ни против.

⚠ **И заранее назови, что будет считаться подтверждением, а что опровержением.** Иначе результат перечитывается постфактум в удобную сторону: находка читается как «атака работает», пустота — как «код чист», и обе трактовки доступны всегда. Заход по коду, который правил предыдущий круг, меряет плотность дефектов в новом коде, а не сходимость.

⚠ Агенты read-only и НЕ совместимы с правками дерева: пока рой работает, ничего не меняй — иначе они анализируют одно, а ты чинишь другое.

Повторный заход по фиксу, который эта фаза уже атаковала и который закоммичен (просьба «ещё раунд», «узкий аудит»), — это `/audit-bugfix`, а не новый круг этой фазы.

## Фаза 5 — Синхронизация документации и вики (обязательно после фикса)

Баг-фикс часто означает, что задокументированное поведение расходилось с реальным. Пройди по документации и проверь, не описывает ли она старое (баговое) поведение, нет ли устаревших примеров или сигнатур.

**Проверяй не только «описывает ли док баговое поведение», но и не отстала ли страница правленого метода от ПРЕДЫДУЩЕЙ волны** — сигнатура, форма возврата, число каналов/аргументов. Такая страница по ключевым словам ТВОЕГО бага не находится вовсе, поэтому её пропускают прогон за прогоном. Улика парадоксальная: **пустой** `rg` по ключевому термину текущей модели данных на странице, которая обязана его упоминать (`rg 'search' <page>` → 0 строк на странице метода, у которого есть query-канал), означает не «нечего править», а «страница до-волновая».

**Строку, которую ты ПЕРЕНОСИШЬ в новый текст, проверь пробой, а не глазами.** Стухшее утверждение переживает рефактор именно потому, что его копируют не читая. Особенно «митигации» / «обходные пути» — они пишутся один раз и годами не перепроверяются. **Числа и факты, которые ты измерил на Фазе 0.6** (сколько раз позвана фабрика, сколько аллокаций, в какой фазе бежит код), — готовый детектор доковой лжи: прежде чем читать страницу глазами, грепни её на утверждения о ТОЙ ЖЕ величине («runs once», «only at», «never»); пробник уже сказал, верны ли они.

**Грепни номер чинимого issue по докам и вики ПЕРЕД синком** (`rg "#<N>" packages */*.md <abs-wiki>`): предыдущий багфикс мог оставить там «известное ограничение, отслеживается в #N» — после фикса это самая заметная ложь в документации, и по имени метода/опции такие абзацы не находятся.

⚠ **Фикс добавляет член в ПЕРЕЧИСЛЕНИЕ (список ключей, union имён, набор полей, таблица режимов)? Ни новое имя, ни номер issue не найдут ни одного адреса — по построению.** Нового члена в доках нет нигде (его же и добавляют), а номер issue появится только после твоей правки, поэтому оба грепа возвращают пусто и читаются как «синхронизировать нечего». Ищи по имени **СОСЕДНЕГО** члена перечисления — он и находит каждое место, где список воспроизведён дословно, включая страницы, отставшие ещё от ПРЕДЫДУЩЕЙ волны. ⚠ **И правь не СТРОКУ, а БЛОК: прочитай абзац под ней и над ней.** «Известное ограничение» про чинимый баг живёт ровно там, вплотную к списку, — и номера issue в нём обычно НЕТ (его писали, когда issue ещё не было), поэтому греп по `#<N>` его не находит, а обновлённый список начинает противоречить сохранённому предупреждению на той же странице.

⚠ **Грепни по ТЕКСТУ СИМПТОМА, который ты только что перестал воспроизводить** — дословное сообщение об ошибке, имя падающего метода, обороты «cryptic» / «instead of» / «known limitation». Доки любят процитировать сбой целиком как известное ограничение, и такая страница не находится ни по номеру issue, ни по имени API, ни по соседу-члену перечисления — только по самой цитате. После фикса это самая заметная ложь в документации, потому что она подробная и звучит проверенной.

1. **Локальная документация** — проверь и при расхождении обнови:
   - Корневые: `README.md`, `ARCHITECTURE.md`, `IMPLEMENTATION_NOTES.md`, `CLAUDE.md` (формат записи решений — Problem → Solution → Why, исторические решения не удалять).
   - Затронутого пакета: `packages/<pkg>/README.md`, `ARCHITECTURE.md`, `CLAUDE.md`, при наличии — `INVARIANTS.md` (если фикс касался инварианта).
   - **Контракт INVARIANTS ↔ property-тесты:** если фикс ввёл или изменил инвариант — добавь/обнови соответствующий кейс в `tests/property/*` И синхронизируй таблицу маппинга «инвариант → тест-файл» в `INVARIANTS.md` (в этом репозитории строки инвариантов маппятся 1:1 на property-тесты; прозаическая строка без теста ломает контракт).
   - Точечно ищи устаревшие упоминания: `grep -rn "<имя метода/опции>" packages/<pkg>/*.md README.md ARCHITECTURE.md`.
   - ⚠ **Форматтер на Фазе 5 гоняй ПОИМЁННО, никогда по глобу.** Формат Markdown (prettier) в этом репозитории не гейтится, поэтому доки массово не отформатированы — и `prettier --write 'packages/*/ARCHITECTURE.md'` переписывает КАЖДЫЙ файл, до которого дотянулся, включая пакеты, которых задача не касается. Дифф вырастает на сотни строк чужих правок, а заметишь ты это в лучшем случае на `git add -A`. Правило: форматируй только те файлы, которые сам правил, и только если `--check` на их HEAD-версии был зелёным (`git show HEAD:<file> | pnpm exec prettier --check --stdin-filepath <file>` из корня: парсер и конфиг prettier берёт по пути файла; код 1 — был грязным); файл, неотформатированный ДО тебя, оставляй как есть.
   - ⚠ **После ПОСЛЕДНЕЙ правки дока перезапусти `node scripts/claim-census.mjs --diff`.** Реестр `packages/core/tests/functional/claim-census-ledger.json` хранит клеймы не только `src`, но и доков вроде `INVARIANTS.md`, так что чистый `--diff` из Фазы 4 на Фазу 5 не переносится — а дрейф краснит `claim-census-authority-2092.test.ts`, который прогон только твоих тестов не запускает. ⚠ **И прогони сам тест (из `packages/core`: `pnpm exec vitest run --coverage.enabled=false tests/functional/claim-census-authority-2092.test.ts`): `--diff` сверяет только файлы реестра.** Новый `⚠`/`⚑` в файле ВНЕ реестра — `src` или доке — он не видит, а тест краснеет на «remainder». `--update` такому файлу не годится: он молча расширяет перепись, а это решение владельца — сними глиф.
2. **Вики** (отдельный репозиторий `real-router.wiki/`):
   - Найди страницы, описывающие затронутый API/метод/компонент (например `Route.md`, `RouterOptions.md`, `<Plugin>.md`, `*-Integration.md`).
   - Обнови сигнатуры, примеры и описания поведения, если они расходятся с фиксом.
   - Поиск: `rg "<имя метода/опции>" <wiki-path>`. Путь вики — **абсолютный**, из environment (секция `Additional working directories`): относительный `../real-router.wiki` зависит от текущего каталога, и из worktree в `.claude/worktrees/<name>/` он ведёт мимо вики, а `grep` отвечает «no matches». И НЕ делай `cd` в вики-репо (или `cd` обратно сразу): персистентный cwd Bash уводит последующие `git`-команды (Phase 6 `git diff`/commit) в чужой репозиторий — можно собрать commit message из чужого диффа. ⚠ **`cd <wiki> && <команда>` в ОДНОЙ строке спасает не больше, чем отдельный `cd`** — cwd у Bash-тула персистентен между вызовами, а не в пределах команды, так что после такой цепочки следующий `git status` смотрит уже в вики. Работай через `rg <pattern> <abs-wiki-path>` и `git -C <worktree>`; коммить в вики только СВОИ файлы (`git add <files>`) — там бывают чужие незакоммиченные правки.
3. Сообщи список проверенных файлов и что именно обновил (или явно укажи, что расхождений в документации не найдено).

## Фаза 6 — Commit message

1. Когда фикс, валидация, changeset и документация готовы, вызови скилл `/commit-msg` — он сгенерирует сообщение в формате Conventional Commits по текущему diff. Для баг-фикса ожидаемый тип — `fix(<scope>): ...`.

   ⚠ **Фикс лежит в worktree — сообщение собирай по `git -C <worktree>`, а не по основному чекауту, и проверяй до коммита, как в `/commit-msg` («Проверка»).** Основной чекаут делят сессии: его дифф может нести чужие незакоммиченные правки, и сообщение описало бы их. Хук `commit-msg` git запускает и в свежем worktree, но `commitlint` ему даёт только `pnpm install` в нём.

2. Выведи готовое сообщение пользователю. **НЕ коммить и НЕ пуш без явной просьбы** — только предложи сообщение.
3. **Когда пользователь явно попросит запушить** — пуш текущей ветки: `git push -u origin HEAD`. Pre-push hook гоняет полную валидацию; его падения — настоящие, не обходи. PR — через `/create-pr`.

## Фаза 7 — Комментарий в issue (как решён баг)

Подготовь комментарий, кратко и по делу объясняющий **как решён баг** — это остаётся в публичной истории issue и закрывает контур обратной связи с автором.

1. Содержание (на **английском** — issues ведутся на английском):
   - **Корень бага** — подтверждённый, в одну-две фразы.
   - **Фикс** — суть подхода + ключевой фрагмент кода/диффа; плюс почему поведение в остальном сохранено (какие инварианты/проверки остались на месте).
   - **Тест(ы)**, доказывающие фикс — имена.
   - **Скоуп-решения** — если в issue предлагалось решение или несколько пунктов: что принято, что задокументировано вместо рефакторинга, что осознанно отложено как follow-up — каждое с краткой причиной. Это самая ценная часть для автора issue.
   - **Sweep сиблингов + class-guard** (из Фазы 2.5) — какие сиблинги концерна проверены и покрыты/заведены отдельно (полный радиус, не один сайт), и рекомендованный class-guard (инвариант/property, закрывающий класс), если он не добавлен тестом в этом прогоне. Если инлайн-раскопка (Фаза 0.8) выявила ложную полноту родительского фикса или структурный тэг (isolate-produce, false-reject, sync-seam и т.п.) — назови его: это спасает следующий follow-up.
   - Не переобещай статус: описывай реализованный подход, **не** заявляй «merged/released», если фикс ещё на ветке.
2. Публикация: `gh issue comment <number> --body-file <file>` — используй `--body-file` (не `--body`), чтобы сохранить markdown и код-блоки. **Публикуй только по явной просьбе пользователя** — тот же гейт, что коммит/пуш: комментарий в публичный issue — внешнее действие (обычно идёт в паре с просьбой закоммитить/запушить). Без просьбы — только покажи черновик в итоговом отчёте.

## Итоговый отчёт

- Ветка: `git branch --show-current` и каталог её worktree (заведены по 0.3 или были готовы); infra-фикс — `master` основного чекаута.
- Корень бага и где исправлен.
- Если в issue было предложено решение — принято оно или нет и почему.
- Тест, доказывающий фикс (путь + имя).
- Пост-фикс анализ: что упрощено/оптимизировано (или почему оставлено как есть).
- **Атака на своё решение (Фаза 4.5): по каждому вектору — что найдено и починено, либо явное «чисто».** **Векторы 1, 1b, 2, 3b, 6 и 7 отчитываются ЧИСЛОМ** — `N/N` мутированных термов (1), `R/R` исходов, чей откат краснеет (1b), `S/S` сайтов класса и `P/P` механизмов самого guard'а (2), `M/M` проверенных клеймов (3b), `K/K` покрытых форм из перечислений — тела issue и тех, что называет код (6), `Q/Q` строк таблицы возвратов (7); несошедшийся счёт называй остатком, а не опускай.

  ⚠ **Знаменатель вектора 1 — ПЕРЕПИСЬ, а не число сделанных мутаций.** `N/N`, где оба N это «сколько я мутировал», сходится всегда и не значит ничего: он сообщает про выборку, которую ты сам и выбрал. Выпиши список термов ДО мутирования — грепом по своей дельте на `if (`, `&&`, `||`, `??`, `=== `, `!== `, ранние `return` — посчитай его, и отчитывайся `мутировано / всего`. ⚠ **И собери перепись так, чтобы она видела СОЗДАННЫЕ файлы.** `git diff` показывает только трекаемое, поэтому новый тест-файл выпадает из знаменателя ЦЕЛИКОМ — и `N/N` сходится на выборке, которую ты не выбирал, а просто не увидел. Бери список из `git status --porcelain`, строки `??` считай грепом по самому файлу, а не по диффу, и печатай обе половины. Отдельно назови: эквивалентные термы и операторы, которые ты сам внёс и убрал; сайты класса, на которых class-guard оказался зелёным и был усилен; клеймы changeset'а, опровергнутые пробой; что фикс ЗАБРАЛ; и замер, которым обоснован отказ чинить соседний сайт.

- **Рой (Фаза 4.5):** `линза | находок | подтверждено | не проверено | нашла только она` — строка на линзу, второй проход отдельно; «нашла только она» считается среди подтверждённых.
- Sweep сиблингов (Фаза 2.5): какие каналы/сайты концерна проверены, покрыты в прогоне vs заведены отдельным issue; рекомендованный class-guard; структурный тэг/ложная-полнота, если найдены (Фаза 0.8). Follow-up у задачи, которая сама follow-up, — цепочка: вместо новых задач предложи `/class-hunt <номера цепочки>`.
- Результат точечной валидации затронутых пакетов — **СПИСКОМ ПРОГНАННЫХ КОМАНД, по строке на команду**, с кодом возврата; у `test:properties` и `test:stress` либо RC, либо явное «не гонял, потому что …». Условная формулировка Фазы 4.1 («если фикс касался инварианта / конкурентности / памяти») сама себя не проверяет: молчаливый пропуск неотличим от неприменимости, пока не назван, а «валидация зелёная» удовлетворяется одним прилагательным. Полный `pnpm build` не запускался: весь граф прогоняет pre-push hook.
- Changeset: создан через `/changeset` (какие пакеты/бамп) или не нужен — почему.
- Документация и вики: что проверено и что обновлено.
- Предложенный commit message из `/commit-msg`.
- Черновик комментария в issue (или подтверждение, что опубликован, если была явная просьба).

Важно:

## Самокоррекция скила (журнал кандидатов)

Скил правится по накопленному, а не после каждого прогона: правка по одному инциденту описывает случай, а не класс, а платит за неё каждый следующий прогон.

1. **Запись в журнал, а не правка** — после отчёта (Red→Green→Refactor + синхронизация локальных доков/вики). Где текст скила промолчал, был двусмыслен или неверен и это стоило вызовов, реплики владельца или риска ошибки, допиши строку в `.claude/skill-candidates/bugfix.md` основного чекаута (gitignored; из worktree — `dirname "$(git rev-parse --path-format=absolute --git-common-dir)"`): дата, задача, раздел, класс (молчит / двусмыслен / неверен), инцидент, цена. Под `EnterWorktree` запись в основной чекаут отклоняется, а «копия в worktree», которую предлагает отказ, пропадёт вместе с worktree (`.claude/*` в `.gitignore`) — держи строку в scratchpad и перенеси её сам: `ExitWorktree` (`keep`), запись, `EnterWorktree` с `path` обратно. Этот выход владелец просит заранее, и это та просьба пользователя, которой ждёт описание `ExitWorktree`: не переспрашивай. Строка того же класса уже есть — допиши инцидент к ней. В отчёте — одна строка: что записано.
2. **Правка созревает, когда класс повторился** — в другой задаче или сессии. Неверный факт текста (команда, флаг, путь, число) — исправление, а не правило: его предлагай сразу. Планка: правка предотвратила бы ошибку или сняла бы лишние шаги.
3. **Разовое ≠ паттерн.** Специфику конкретного бага/пакета (разовую) → в черновик issue-комментария/память, НЕ в скил. В скил идёт только повторяющийся класс, полезный СЛЕДУЮЩЕМУ фиксу ДРУГОГО бага.
4. **Правка не растит файл:** сначала заточи существующий абзац; новое правило называет, что в том же разделе сжато или удалено. Рост — только с согласия владельца.
5. **Предлагай, не применяй молча.** Созревшие правки — таблицей (раздел | инциденты из журнала | текст | что сжато), спроси разрешения; итог помечай в журнале. В скил — правило в настоящем времени, без номеров прогонов и дат; инциденты — в сообщение коммита. Применил по согласию → `.claude/commands/` это infra, в master напрямую, без changeset.
6. **Ничего не записано и не созрело** — так и скажи одной строкой.
