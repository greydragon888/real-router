Исправь баг по методологии TDD (Red → Green → Refactor), затем синхронизируй локальную документацию и вики.

Входные данные:
$ARGUMENTS

Формат аргументов:
- Номер issue (`#812`) или ссылка на него (`https://github.com/greydragon888/real-router/issues/812`).

> **Несколько багов одной PR-группы в один PR?** Это отдельный скилл — `/bugfix-batch` (оркеструет группу в одну ветку/PR, **переиспользуя per-bug методологию этого скилла**). Здесь — один баг, линейно Фазы 0→7.
>
> **Один КОРЕНЬ в N call sites / пакетах ≠ батч.** Кросс-адаптерный / кросс-пакетный фикс одного дефекта (напр. одна и та же ошибка в `<Link>` всех 6 адаптеров) — это ЭТОТ скил, линейно: один RED→GREEN per call site, один changeset per затронутый публичный пакет, один PR. `/bugfix-batch` — для N **различных** багов (разных корней) одной PR-группы. Симметричное размножение одной правки по адаптерам — НЕ батч. Попутно всплывший «7-й call site» или директива-близнец с тем же дефектом (тот же общий хелпер) — дотягивается в этом же прогоне ради симметрии (feedback_layer_consistency), отдельным RED-тестом.

## Как формулировать вопрос пользователю

Если по ходу багфикса нужно спросить пользователя (нет данных для RED — 0.5; премиса issue устарела — 0.6; design-call с несколькими валидными разрешениями), формулируй вопрос **просто и понятно — для человека без накопленного тобой контекста**. Не вываливай плотную сводку из внутренних имён, аббревиатур и ссылок на спецификации.

Структура:
1. **Что это за фича/область** — одна-две фразы простым языком: что она делает для пользователя, на бытовом примере.
2. **При чём тут затронутый механизм/опция** — простыми словами, зачем он и когда применяется.
3. **Сам баг и его видимое последствие** — что идёт не так и чем это бьёт по пользователю.
4. **Сам выбор** — один чёткий вопрос с конкретными вариантами (напр. «чинить поведение по-настоящему или оставить как есть и честно описать ограничение в доках»).

Плохо: «scroll-spy: IntersectionObserver root + MutationObserver target резолвятся ОДИН РАЗ при создании, а опция обещает resolved on every event…» — плотно, на жаргоне, нечитаемо без контекста. Хорошо: то же по структуре выше — сначала «что такое scroll-spy и зачем `scrollContainer`», затем «в чём баг и последствие», затем один вопрос с двумя вариантами.

## Фаза 0 — Контекст из issue

1. Извлеки номер issue из аргумента. Чаще всего передаётся номер (`#812` или `812`) — возьми его как есть. Если передана ссылка — номер это последний числовой сегмент URL.
2. Получи описание бага **вместе с комментариями**: `gh issue view <number> --comments`. Комментарии читай и учитывай ВСЕГДА — в обсуждении почти всегда есть уточнения, корректировки скоупа или контр-примеры, без которых фикс будет неполным.
   - **Если issue не найден или закрыт как duplicate/invalid — ПРЕКРАТИ** и сообщи об этом.
3. **Не заводи инфраструктуру — работай в той ветке, в которой запущен.** Этот скил НЕ создаёт ветку/worktree и не решает, где работать: для одиночного запуска отдельную ветку под задачу готовишь заранее ты сам, для группового — её готовит `/bugfix-batch` на всю группу. Единственная проверка — `git branch --show-current`:
   - **Текущая ветка `master`** → на самом `master` не работай. Ветки под задачу нет вовсе → **заведи её сам и продолжай** (`gh issue develop <number> --name <number>-<slug>` + checkout): это одна команда, полностью обратимая, и блокировать ради неё вопрос — трата хода. ПРЕКРАТИ и спроси только если ветка есть, но принадлежит ДРУГОЙ задаче (её имя/коммиты про другой issue, на неё открыт PR) — тогда коммит уедет в чужой PR, и выбор за пользователем.
   - **Любая другая ветка → продолжай в ней.** `#<number>` дублируй в коммите и changeset.
4. Из issue выдели: симптом, шаги воспроизведения, ожидаемое поведение, затронутый пакет/файл (если указан).
5. Если в issue нет данных для написания падающего теста (нет воспроизведения или ожидаемого результата) — остановись и спроси, не угадывай.
6. **Сначала воспроизведи баг эмпирически** — временной пробой через публичный API или собранный пакет, ПРЕЖДЕ чем писать формальный тест. Это триаж-гейт, который может закоротить работу в «только отчёт».
   - ⚑ **Решение в баге принимается из НЕСКОЛЬКИХ входов (два гварда, два канала, флаг × режим, sync × async)? Воспроизводи МАТРИЦУ входов, а не сообщённую клетку.** Клетка отвечает «сломано» — этого хватает для RED, но не хватает, чтобы выбрать между вариантами фикса, а именно этот выбор и стоит дорого. Матрица показывает ПРАВИЛО и почти всегда вскрывает клетку, о которой в issue нет ни слова. (Прогон #1652: матрица `canDeactivate` × `canActivate` дала решающий довод — **с гвардом исход ХУЖЕ, чем без него** (404 против рабочего маршрута), то есть фикс не «меньшее зло», а восстановление нормы; и вторую находку — отказ деактивации ЗАКОРАЧИВАЛ проверку активации, так что «можно ли вообще быть на новом маршруте» не спрашивалось вовсе. Ни того, ни другого в теле issue не было, а обосновать выбор из трёх вариантов без них не получалось.)
   - ⚑ **Баг про ПЕРЕЧИТЫВАНИЕ (второе чтение геттера, повторный вызов коллаборатора, кэш против источника)? Ось матрицы — ПОРЯДКОВЫЙ НОМЕР обращения, а не набор входов.** Скриптуй источник «отдавать правильное до N-го обращения, испорченное — с N-го» и свипни N. Это даёт две вещи, которых обычная матрица «арка × режим» не даёт. Во-первых, ТОЧНОЕ число обращений — issue почти всегда занижает («второе чтение» на деле оказывается третьим из шести). Во-вторых, свип вскрывает, что ОДИН логический вопрос задаётся НЕСКОЛЬКО раз: у пар `canSend`+`send`, `has()`+`get()`, «проверить»+«применить» предикат один, а оценок две, и разойтись они могут ровно посередине — а между ними успевает пройти деструктивная работа. (Прогон #1717: issue называл клетку «флип на 3-м чтении» — отказ здорового коммита; свип по N показал шесть чтений и ВТОРУЮ клетку на 4-м — фантомный resolve, где пермит уже выдан и `completeTransition` возвращает состояние, которого таблица не коммитила. Матрица по аркам дала бы три одинаковых клетки и остановилась на симптоме из issue.)
   - Проверь статус связанных/блокирующих issue (`blocked by #N`, эпики, ссылки в теле): если блокер закрыт — перепроверь, не починил ли его фикс уже этот баг.
   - Если репродукция из issue **не воспроизводится** на текущем HEAD — премиса устарела (баг уже исправлен или описание неверно). НЕ чини «по тексту»: останови RED, сообщи находку, при необходимости предложи пересмотр скоупа и спроси, продолжать ли.
   - ⚑ **Отдельный случай — `/bugfix <N>` запущен на ветке, которая `<N>` уже чинит** (типично: приёмка после ревью, или второй заход по той же задаче). Невоспроизведение тут не сюрприз, а ожидание, и «премиса устарела → стоп» срабатывает формально верно, но рано. Смени режим с ТРИАЖА на ПРИЁМКУ: прогоняй не сообщённую клетку, а **всю таблицу радиуса из тела issue** — все точки входа × все арки × альтернативные точки ВЫЗОВА (плагинные примитивы, а не только фасад) + контроли, — и предъяви её как есть. Отчёт тогда отвечает не «баг жив?», а «что из ЗАЯВЛЕННОГО скоупа уехало без регресс-защиты»: снимай по одному месту фикса и смотри, краснеет ли сьют; место, снятие которого оставляет тир зелёным, и есть незапиненное. Точки входа, исчезнувшие структурно из-за СОСЕДНИХ фиксов, называй отдельно со ссылкой на их пин, а не выкидывай из таблицы молча. (Прогон #1684: матрица 16 клеток на HEAD дала ноль воспроизведений и один незапиненный контракт — три из четырёх сайтов отцепления слушателя; ни того, ни другого «проверить сообщённую клетку» не показывает.)
   - Если баг воспроизводится, но корень — иной класс входов, чем в issue, — фиксируй фактический корень, а не формулировку issue.
   - **Issue-на-УДАЛЕНИЕ (dead code / unused / «недостижимо из X»): «0 покрытия / достижимости из публичного API X» ≠ «удаляемо».** Метрика достижимости аудита (0 проб через core, 0 внешних импортов) говорит лишь «этот потребитель не зовёт» — а НЕ «мёртвый код». Пакет держит СВОИ тесты + property + **INVARIANTS** на этот код → это живая, тестированная возможность, не мусор. Перепроверь КАЖДЫЙ пункт на HEAD: существование + потребители + **выделенные тесты/property/INVARIANTS + `git grep` на использование внутри самого пакета/тест-хелперов**. Есть выделенное покрытие → удаление это **product-решение** (сознательный API-shrink с потерей тестированной возможности), НЕ cleanup: вынеси как design-call (`AskUserQuestion`), не сноси на доверии к слову «dead» ([[feedback_legacy_skepticism]]). И даже под «да, сокращаем» — верифицируй границу КАЖДОГО пункта отдельно: аудит систематически врёт про «impl vs отдельный», «мёртвая ветка vs test-only», «фантом vs используется тест-хелпером» (прогон #1302: 7 «мёртвых» пунктов = тестированный API с INVARIANTS; `createRouteTree` оказался ПОСТРОЕН на «мёртвом» билдере — удаление стало рефактором-инлайном, не сносом).
   - ⚠ **Считаешь ПОТРЕБИТЕЛЕЙ API — не грепай `api(...).method` одной строкой.** Идиоматичное написание двухстрочное (`const api = getXApi(router);` … `api.method()`), и однострочный паттерн его структурно не видит: результат непустой, поэтому на «пустой grep ≠ отсутствие» ([[feedback_tool_error_not_absence]]) он не ловится — ты просто получаешь МЕНЬШЕ, чем есть, и веришь числу. Ищи по имени МЕТОДА (`\.method()`) с фильтром по каталогам, а потом отсеивай одноимённые чужие вызовы (`Map.clear`, `Set.clear`) глазами. (Прогон #1612: «ровно один потребитель `clear()` вне тестов ядра» — реально их было ШЕСТЬ примеров плюс их тесты; найден лишь тот, у которого вызов случайно оказался в README одной строкой. Число ушло в рекомендацию владельцу и в комментарий issue.)
   - **Воспроизводишь через консьюмер/пример?** Примеры и внешние приложения без `customConditions` в своём `tsconfig` резолвят `@real-router/*` из `dist` (через `exports`), а не из `src`. Значит баг, завязанный на опубликованные типы/бандл, проявляется только против собранного `dist` — **пересобери пакет** (`pnpm -F <pkg> bundle`) перед type-check/прогоном консьюмера, иначе и RED, и GREEN считаются против устаревшего `dist` (ложный результат).
   - Временные пробы удаляй до конца фазы — никаких `__probe*.test.ts` или отладочных файлов в коммите.
   - ⚠ **Проба, живущая ВНУТРИ vitest-теста (нужен jsdom / тест-хелперы пакета), не печатает `console.log`** — конфиг пакета его глушит, и флаги репортера этого не снимают (`--reporter=verbose`, `--disable-console-intercept` — оба мимо). Не перебирай флаги: пиши результат в файл (`appendFileSync("/tmp/probe.txt", …)`) и читай его отдельной командой. (Прогон #1645: три холостых прогона, прежде чем это стало очевидно.) **Для СТРУКТУРНЫХ данных (матрица клеток, массив объектов) дешевле другой приём — печатать через заведомо ПАДАЮЩИЙ ассерт:** `expect(matrix).toEqual("SHOW-ME")` — diff Vitest выводит всё дерево объектов целиком, без файловой возни, без второй команды на чтение и без флагов репортера (прогон #1684).
7. **Если в issue предложен способ решения бага — относись к нему максимально критически.** Это гипотеза автора, а не истина. НЕ применяй его на доверии. Сначала самостоятельно найди корень бага, затем проверь предложенное решение: действительно ли оно устраняет причину (а не симптом), не ломает ли инварианты/другие сценарии, не противоречит ли границам слоёв и архитектуре проекта. Применяй его, только если есть **реальные доказательства** (тест, анализ кода), что фикс корректен **и** оптимален. Если твоё независимое решение лучше — используй его и объясни, почему предложенное в issue не подошло.
   - **Своё собственное предложение — ТОЖЕ гипотеза, не повышай к нему доверие из-за авторства.** Если fix-direction в теле issue написал ТЫ САМ (в прошлой сессии, при заведении задачи), на старте фикса его тянет принять как данность — не надо: пере-выведи минимум из кода на момент фикса. Особенно перед **добавлением API-поверхности** (новый метод/поле/экспорт на публичном типе) — сначала проверь, не достаётся ли нужное через СУЩЕСТВУЮЩИЙ surface (getter'ы, уже-прокинутые коллабораторы, реэкспорт). «Добавить метод» рефлекторно раздувает API и дифф; часто хватает 0 новых точек. (Прогон #1301: я сам авторил «add 2 getters to RouterInternals»; пользователь дважды поправил — реальность 0 новых методов: дерево уже даёт `getTree()`, сегменты/существование — матчер, а реэкспорт понадобился ровно для ОДНОЙ функции без эквивалента на матчере.)
   - **«Обратно совместимо» — не синоним «консервативно».** Чинишь дефект ФОРМЫ (типа, сигнатуры, мешка аргументов) — сохранение старой формы сохраняет и дефект, а к нему приделывается сторож: тот, кто пишет по-старому, продолжает получать молчаливо неверный результат, зато теперь ещё и с рантайм-различителем двух форм и его edge-case'ами. В pre-1.0 сначала оцени ОДНУ форму + миграцию, и только потом совместимость: цена миграции обычно разовая и механическая, цена двух форм — постоянная. (Прогон #1580: я сам в теле issue предложил «принимать обе», понёс это в план не пере-выведя, и слабость вскрыл пользователь вопросом «зачем?» — плоский мешок и БЫЛ формой бага, а различитель тянул живой edge-case на path-слоте по имени `params`.)
   - ⚠ **ИЗМЕРЕННОЕ число в теле issue, на котором стоит решение, — пере-мерь САМ.** Радиус, счётчик сайтов, «N из M тестов», «используется дважды» — если цифра гейтит выбор (чинить/не чинить, throw/drop/варн, узко/широко), она такой же клейм, как и всё остальное, и стареет ровно так же. Опаснее не устаревание, а **замер соседнего вопроса:** число получено честным прогоном, но предикат, который прогоняли, отвечал не на тот вопрос, что стоит в решении, — и разойтись они могут на порядок. Особенно когда issue завёл ТЫ САМ: авторство цифры не делает её проверенной, а «я это уже мерил» — самая дешёвая причина не перемерить. Способ: воспроизведи замер тем же методом (временный детектор + позитивный контроль) и сверь СОСТАВ попаданий, а не только итог — состав и покажет, тот ли предикат мерили. (Прогон #1579: issue — мой, в нём «core 0 из 3766, три сайта в двух плагинах»; пере-замер дал **52 теста в 6 пакетах**, потому что прежний детектор ловил необъявленный ключ в СОСЕДНЕМ канале, уже закрытом другим фиксом. Решение «дропать ключ» на верной цифре не выжило: дроп ретировал бы документированную в вики возможность.)
     ⚠ **Приёмочный критерий из плана/RFC — тоже клейм, и проверяется он ПЕРВЫМ.** Если пункт задан как «тест такой-то формулировки должен быть красным», напиши его и **убедись, что он красный по причине бага**, до всякого фикса. Формулировка, истинная как утверждение, запросто оказывается нечувствительной к дефекту. Не переформулируй молча: оставь обе как ОТДЕЛЬНЫЕ ассерты и скажи в отчёте, какая дискриминирует, — иначе следующий прогон повторит ошибку плана. (Прогон #1610: план требовал property «пока FSM в TRANSITION_STARTED/LEAVE_APPROVED, committed state неизменен»; она ИСТИННА, но зелена НА БАГЕ — вложенная навигация вытесняет, поэтому её коммит всегда внутри её собственного перехода. Дискриминировала только обращённая к вызывающему половина.)
     ⚠ **Число, которое ты измерил СЛОМАННЫМ инструментом, — хуже, чем неизмеренное: ты назовёшь его «замеренным».** Прежде чем цитировать радиус, полученный временным guard'ом/детектором, проверь ПОЗИТИВНЫМ контролем, что инструмент срабатывает только там, где должен: включи его и убедись, что заведомо-легальный случай проходит. Иначе получишь завышенный радиус и понесёшь его в решение и в отчёт. (Прогон #1612: guard читал `ctx.getState()`, которого на `RouterInternals` нет, и бросал `TypeError` на КАЖДОМ вызове, включая незапущенные роутеры → «39 тестов в 6 файлах» вместо реальных 32 в 3; обе цифры были озвучены владельцу как измеренные.)
   - **Правка на потоке данных имеет ДВА плеча — что ЗАХОДИТ в продюсер и что берётся из его ВЫХОДА. Issue почти всегда называет одно.** Прежде чем принять предложенную формулировку, разложи её по обоим и спроси, какое плечо даёт измеренный симптом: чинить вход, когда теряется выход, — это зелёный фикс мимо бага. Провалидируй КАЖДОЕ плечо мутационно ОТДЕЛЬНО (откат одного роняет свой набор тестов) — иначе полу-фикс выглядит полным. (Прогон #1574: тело предлагало «передавать query явным `search`-аргументом» — это вход; измеренная потеря была на выходе, где хелпер брал `params` из резолвнутого состояния, а `search` — из сырого аргумента, и в наблюдаемом кейсе вызывающий `search` вообще не передавал.)
   - **Особый случай — REJECT малформед-конфига (throw там, где раньше молча проходило): он легко ПЕРЕ-ОХВАТЫВАЕТ.** Issue задаёт заявленный скоуп находки, но истинная граница дефекта — то, что принимают СУЩЕСТВУЮЩИЕ тесты. Перед коммитом reject'а прогони полный сьют пакета И downstream-потребителя (Фаза 2/4): падающий существующий тест, ассертящий отвергаемую форму как VALID, — сигнал **сузить** reject (у формы есть рабочий под-кейс — прогон #1242 §5.4: детект ловил ВСЕ param-родители slash-child, а работал только required, дефект лишь у optional+splat) или **вынести как design-call** (форма толерируется by-design — §5.2 `?name=value`: buildParamMeta даёт мусорное имя, но существующие «valid query» тесты его принимают), а НЕ форсить reject + переписывать тест под него. Это не «подгонка фикса под тест» (её мы избегаем на баг-пиннящих тестах) — это признание, что заявленный скоуп reject'а шире реального дефекта. ⚠ **И ПЕРЕД reject'ом грепни отвергаемую форму по `INVARIANTS.md`, `tests/**/stress`, `tests/**/property` и бенчам.** Инвариант / stress-тест / бенч НА ЭТУ ФОРМУ означает, что она — шипнутая ФИЧА, а reject — ретирование инварианта (product-решение, не багфикс): выноси как design-call, не как фикс. Функциональные тесты этого не покажут — они часто покрывают лишь ОДНУ сторону контракта, и непокрытая сторона и есть баг. (Прогон #1568: «нетерминальный splat» выглядел малформедом, а оказался инвариантом Matching #24 со stress-тестом, property и бенчем — покрыта была только сторона match, а дефект жил в build; reject удалил бы рабочий catch-all-паттерн. Корень нашёлся ровно там, где контракт задокументирован, а не в call-site'ах.) ⚠ **Попадание при УЖЕ принятом продуктовом решении — не повод чинить молча.** Решение владельца покрывает вопрос «ломать ли», но почти никогда — «чем именно платим». Предъяви ЦЕНУ отдельно: сломанный бенч (особенно при `throws:true` — падает весь процесс перф-харнесса), инвариант, который станет самопротиворечивым, property-блок, который исчезнет, и **ИЗМЕРЕННОЕ** число красных — включить guard временно и прогнать сьюты дешевле и честнее, чем оценивать сканом. Развилку формулируй как «чем закрывать в ЭТОМ прогоне» (весь слом / только бесспорная половина / объявить контракт варном, сломать отдельным коммитом), а не «ломать ли». (Прогон #1572: скан дал попадание во все четыре категории, включая именованную бенч-задачу; измеренный радиус throw — 95 тестов в 6 пакетах; развилка дала вариант «warn сейчас, throw отдельно», которого в issue не было.)
   - **Зеркальный случай — фикс-ОСЛАБЛЕНИЕ** (предикат / матчер / валидатор, раньше дававший `false`-или-throw, теперь пропускает): существующий тест, пинящий СТАРЫЙ контракт, здесь не помеха, а **измеритель радиуса** — полный сьют показывает, сколько поведения ты реально меняешь. Один-два таких теста = здоровый, локализованный радиус: переписывай их **с переименованием** (имя/коммент называют НОВЫЙ контракт и issue) и **с сохранением дискриминации** — добавь рядом кейс, который остаётся `false`, иначе тест выродится в тавтологию. Десяток упавших пинов = фикс шире дефекта → сузи правило или вынеси как design-call. (Прогон #1554: толерантное сравнение значений уронило РОВНО один тест `should use strict equality for param comparison (number !== string)` — переписан в `should match a number against the same value as a string` + негативный `{ id: 124 }`; удаление вместо перезаписи потеряло бы единственный пин класса.)
   - **Фикс добавляет initializer/setup-вызов рядом с бросающим кодом (фабрика, клон, парс) ИЛИ переносит существующий вызов в другую фазу жизненного цикла?** Он не только ДОБАВЛЯЕТ поведение — может изменить ФОРМУ существующего отказа (sync-throw vs async-reject, порядок событий), даже если твой новый RED зелёный. Реши ПО КОДУ, в какой фазе исполняется вызов (напр. Angular `provideEnvironmentInitializer` бежит раньше и СИНХРОННО, чем async `provideAppInitializer`), ДО прогона. Если полный сьют (Фаза 2.2) покраснел на СУЩЕСТВУЮЩем контракте отказа — сместить фикс в фазу, СОХРАНЯЮЩУЮ контракт, НЕ переписать тест под новую форму (прогон #1232: env-init прайм error-source → `inject(ROUTER)` бросил `cloneRouter` синхронно, сломав Option-A async-reject; перенёс прайм в app-init — контракт цел, #1232 всё равно чинится).
   - **Родственный случай — ДИАГНОСТИКА, читающая пользовательский объект РАНЬШЕ настоящего потребителя.** Guard / варн / лог, который трогает `params[key]`, свойство или итератор до того, как до него доберётся код, которому значение действительно нужно, меняет не форму отказа, а его **ПРОИСХОЖДЕНИЕ**: аксессор-геттер, `Proxy` или реактивный объект бросят из ДИАГНОСТИКИ. Тесты, пиннящие «ошибка приходит из X», покраснеют — и переписывать надо не их. Читай защищённо (`try` вокруг чтения значения → при броске «нечего сообщать», пусть настоящий потребитель наткнётся на тот же аксессор) и пинни это отдельным тестом. (Прогон #1572: channel-guard читал `params[key]` на фасаде и перехватил происхождение ошибки у `persistent-params`, чей сьют пиннит именно источник; тот же класс — дельта #1569, где стадия ③ читала мешок до проверки существования маршрута.)
8. **Гейт корня-цепочки: не заплатка ли фикс поверх более глубокого владельца концерна.** Пункт 7 сомневается в *предложенном решении*; этот пункт сомневается в *самой рамке issue* — а вправе ли этот баг вообще чиниться локально, или он лишь **симптом-член цепочки долга**, где локальный RED→GREEN станет очередным band-aid'ом поверх ненайденного владельца, а класс багов продолжит рецидивировать. Триггеры (хоть один → сначала мини-проверка ниже, НЕ патч):
   - **Issue ссылается на другие / связан:** «follow-up of #N», «parallel to #N», «residual of #N», «same class as #N», «same seam», «sibling of #N», часть эпика, `blocked by #N`; или тело/комментарии называют баги-собратья. (Такие само-кросс-ссылки в телах — сильнейший сигнал сквозной **оси**; ровно из них `/debt-map` восстанавливает оси.)
   - **Whack-a-mole:** тот же класс симптома уже чинили в другом пакете/сайте (фикс там — всплыл здесь) → сигнал отсутствующего общего примитива.
   - **Band-aid-запах:** очевидный фикс ДОБАВЛЯЕТ спец-кейс / предохранитель / флаг вокруг концерна, а не удаляет координацию (Variant-A-запах из `/chain-resolve`).
   - **Уже в карте:** issue значится членом цепочки в `project_architectural_debt_map` (память).

   **Мини-проверка — convergence по КОДУ, не рассуждением** (дешёвая версия `/debt-map`-теста): вытяни тела+фиксы названных собратьев (`gh issue view <N> --comments`; фиксы — `git log --all --grep "#<N>"` / `git show <sha>`) и протрассируй: сходятся ли фиксы РАЗНЫХ issue в ОДИН helper/владельца? Есть ли у концерна авторитетный **существующий** владелец (`FSM` / `RoutesStore` / emitter / `onListenerError` / codec), на который класс должен схлопнуться? Три исхода:
   - **Сходятся к более глубокому корню + владелец существует + вокруг налипли костыли** → это **цепочка долга, не одиночный баг**; локальный фикс — следующая заплатка. **Не эскалируй в отдельный скил** — `/chain-resolve` / `/debt-map` на практике почти не срабатывают; проведи раскопку **здесь, инлайн** (дёшево, по коду, БЕЗ RFC-крестового-похода):
     - **`git blame` багованных строк → residual-vs-original:** строки предшествуют родителю → это НЕ residual (родитель ортогонален — пиши «related to #N», не «follow-up»); введены/оставлены родителем → настоящий residual (#1206: blame дал оригинал #474, фикс #767 тронул другой шов → изолированный).
     - **Follow-up? Проверь «ложную полноту» родительского ФИКСА:** прочитай его коммент/диф и сверь ЗАЯВЛЕННОЕ покрытие с кодом — родительские фиксы часто заявляют, что покрыли ныне-падающий кейс («also falls under the catch», «wraps all four»), а шов/порядок-вычисления это отрицают (#1222: #798 заявил «compile-throw falls under the catch», но `runHook(compileHook())` вычисляет compile аргументом ДО try — покрытия не было). Это сильнейший тэг residual'а. ⚠ **И ложным бывает не только заявленное ПОКРЫТИЕ фикса, но и СРАВНИТЕЛЬНАЯ ПОСЫЛКА в теле родителя** — «у соседнего пакета это уже работает», «X ведёт себя иначе, чем Y». Именно такая посылка обычно и объясняет, почему родитель не пошёл на сиблинга, поэтому она гейтит весь скоуп — а проверяется тем же пробником, что и сам баг, за одну минуту. (Прогон #1645: #524 перевернул дефолт `forceDeactivate` у одного плагина из трёх, аргументируя «под browser-plugin confirm-on-back работает»; замер через реальный popstate дал НОЛЬ вызовов гварда, и дефолт стоял неизменным с v0.1.0 — то есть посылка была ложной с самого начала, а два пакета остались непочиненными на четыре релиза.)
     - **Sweep сиблингов** (см. Фазу 2.5): смапь ВСЕ call-site/каналы/координаты концерна и пробь КАЖДЫЙ — фикс покроет их все или назовёт полный радиус.
     - Вынеси находку (корень · собратья · владелец · какие band-aid'ы удалятся · **рекомендованный глубокий фикс + class-guard**) и **вынеси развилку пользователю как design-call**: глубокий структурный фикс сейчас (контракт/умбрелла для single-surface корня; конвенция+sweep+инвариант для кросс-поверхностного рекуррентного класса) **или** осознанная **временная** заплатка (interim, TODO-ссылка на корневой issue). Не блокируй; не форсируй umbrella молча.
   - **Realized-владелец (gap в существующем шве)** — общий владелец/helper УЖЕ существует и потребляется, а остаток = дыра в шве (фильтр «realized?» из `/debt-map`: реализованная convergence = закрытая цепочка, RFC-payload пуст): тогда локальный фикс — ПРАВИЛЬНЫЙ ход (bugfix, не RFC). Продолжай линейно.
   - **Нет convergence, корень самодостаточен** — обычный одиночный баг. Продолжай, отметив в отчёте, что член цепочки исключён.

   **Не спутай с симметричным размножением одной правки** (шапка скила): один и тот же корень в N call sites / адаптерах — ЭТО ЭТОТ скил (чини все сайты линейно, один RED per site), НЕ цепочка. Цепочка — когда корень глубже РАЗНЫХ багов и его владелец не тронут.
   **Калибровка (жёсткий урок `/debt-map`):** «более глубокий корень» — ГИПОТЕЗА, и её легко переоценить (на реальном прогоне 5/5 STRONG-корней флипнули в WEAK при раскопке). Твоя роль в этом гейте — **триаж + ОГРАНИЧЕННАЯ инлайн-раскопка** (blame · ложная-полнота · sweep — дёшево и по коду), НЕ полная RFC-раскопка: ссылка на другой issue сама по себе ≠ глубокий корень, она лишь повод прогнать мини-convergence + инлайн-дig и решить «одиночный / член цепочки / class-guard». Не превращай каждую ссылку в RFC-крестовый-поход и не блокируй фикс, если корень не доказан кодом.

## Фаза 1 — RED (тест, доказывающий баг)

1. Локализуй причину: найди модуль и функцию, ответственные за поведение. Сначала пойми корень, не патч симптома. (Это корень *внутри* бага; вопрос «не симптом ли сам баг более глубокого корня-цепочки» уже прошёл гейтом Фазы 0.8 — если тот выявил цепочку, ты уже провёл инлайн-раскопку и согласовал с пользователем скоуп: глубокий структурный фикс или осознанная interim-заплатка — с ним сюда и заходишь.)
2. Напиши **падающий** тест, воспроизводящий баг, в `tests/functional/` соответствующего пакета (или ближайший подходящий уровень — property/stress, если баг про инвариант/память/конкурентность).
   - Тест проверяет **поведение**, а не реализацию.
   - ⚑ **Правильный ИСХОД спорный (design-call ещё не решён)? Пиши RED как СРАВНЕНИЕ, а не как ожидаемое значение.** Форма «с фичей не хуже, чем без неё» (тот же сценарий с гвардом и без гварда, с опцией и без) дискриминирует ДО того, как выбран вариант, и переживает выбор; «ожидаю X» приходится переписывать под каждый вариант, из-за чего RED откладывают до конца развилки и теряют его как инструмент её разрешения. Заодно такой RED — часто и сам аргумент в развилке. (Прогон #1652: `expect(getState() с гвардом).toBe(getState() без гварда)` был красным до фикса, зелёным после, и не зависел от того, какой из трёх вариантов выберет владелец.)
   - **Дописываешь тест в СУЩЕСТВУЮЩИЙ файл — проверь, в КАКОЙ `describe` он сядет и чей `beforeEach`/фикстуры отработают.** Файл может нести НЕСКОЛЬКО top-level `describe` с разным setup; append в конец кладёт тест в ПОСЛЕДНИЙ, чей общий-но-не-сбрасываемый `api`/router даёт ложный провал НЕ по причине бага — маскируя дискриминирующую силу RED. Прогон #1191: RED упал `already claimed`, т.к. сел в чужой `describe("State.context")` без fresh-router `beforeEach` (общий `api` протёк из предыдущего теста) → перенёс в целевой `describe` с нужным setup, и RED упал уже по реальной причине (proto-swap).
   - **Если фикс по замыслу НЕ меняет видимый output** (дедуп / экономия ресурса / перф — результат до и после идентичен): чистый output-тест невозможен, и RED легитимно проверяет **ресурсное следствие** — один источник/подписка/кэш-вход вместо N, отсутствие лишнего пересчёта. Это и есть тестируемое поведение, не реализация. Дискриминатор — наблюдаемый побочный эффект кэш-промаха vs шеринга (напр. повторный вызов коллаборатора при miss), а не чтение приватного поля. Не трать время на поиск output-разницы, которой по построению нет.
     - **Третья форма — дефект на ПРОМЕЖУТОЧНОМ шве, который нижележащий слой исправляет строкой ниже.** Конечный результат идентичен by design (это часть приёмки — «no-op today»), а дефект наблюдаем только в точке ДО починки, где его читают downstream-потребители. Ищи публичный способ прочитать промежуток: чаще всего это **интерцептор** (`addInterceptor("<method>")`, чей `next(...)` возвращает выход исходного примитива ДО пост-обработки шва) — и он же обычно и есть пострадавшая популяция, т.е. RED выходит тестом поведения, а не реализации. Не трать заход на поиск разницы в конечном состоянии: её отсутствие — приёмочный критерий, а не признак, что бага нет. (Прогон #1570: `forwardState` клал chain-дефолт в не тот канал, а `separateChannels` на шве переносил ключ строкой ниже — коммит побайтно тот же; RED встал на выход `forwardState`-интерцептора.)
   - **Инвариант, который ядро (или соседний слой) и так вытягивало, зелёный и НА БАГЕ.** Когда фикс переносит работу между слоями/каналами, свежий property легко выходит тавтологией: нижележащий слой чинил симптом за тебя, и тест проходит на обеих версиях. Прогони мутацию — сломай ровно ту ветку, которую добавил, — и убедись, что в наборе есть хотя бы ОДИН кейс, падающий на до-фиксовом коде. (Прогон #1563: «значение из любого канала лежит в `state.search`» проходило и до фикса, потому что `separateChannels` переносил ключ сам; уликой стал только второй property — removal-маркер, проверяемый ещё и по `state.path`.) **И формулируй ассерт как ИНВАРИАНТ, а не как снимок:** `toStrictEqual` по целому мешку затягивает в тест сторонние правила (куда ядро кладёт undeclared-ключ, какой singleton вернул пустой бэг) и падает на них, а не на баге — counterexample тогда указывает на твою формулировку, а не на дефект. Проверяй охраняемое свойство поключно (каждый слот равен переданному; искомый ключ отсутствует). ⚠ **Родственная тавтология — у фикса вида «брать из РЕЗОЛВНУТОГО выхода, а не из сырого аргумента»: кейс, где вызывающий задаёт ВСЕ ключи, зелёный по построению** (сырой и резолвнутый мешки тождественны, когда резолюция ничего не добавила). Дискриминатор обязан содержать ключ, который добавляет **резолюция** и который вызывающий НЕ передаёт. (Прогон #1574: `replaceHistoryState` строил `history.state` из сырого `search`, и «вызывающий перекрывает дефолт цепочки» проходило и до фикса; красным стал только кейс, где цепочка даёт `tab`, вызывающий — `sort`.)
   - **Issue-на-УДАЛЕНИЕ (dead code / unused / phantom-export): RED-теста НЕТ — не изобретай его.** Удаляемого поведения нет, воспроизводить нечего. «GREEN» здесь = после удаления кода **вместе с его выделенными тестами** полный сьют + `test:properties`/`test:stress` остаются зелёными И **coverage держится 100%** И мутационный score не проседает на РЕТЕЙНЕД-коде. Дискриминатор — **дельта coverage/mutation на неизменённом коде, а не новый failing-тест**: если после удаления теста строка/ветка теряет покрытие или в удержанном коде появляется новый выживший мутант — удалённый тест был единственным killer'ом чего-то живого → **сузь удаление** (ты снёс не только мёртвое). Обратно: выжившие мутанты, которые ЖИЛИ и на master (стойкие/эквивалентные в нетронутых файлах), регрессией НЕ являются — проверяй по расположению (нетронутый файл + был на master), не по проценту (набор мутантов меняется, когда удаляешь код с его мутантами, так что сырой % не apples-to-apples). Прогон #1505: удаление `parse`/`getSearch` + миграция тестов на `parseQuery` — 0 новых выживших в движке, 100% coverage сохранён; вердикт «no drop» по расположению выживших, не по числу.
   - Один логический assert на причину провала; имя теста описывает ожидаемое поведение.
3. Запусти тест и **убедись, что он падает именно по причине бага** (а не по опечатке/компиляции). Падающий тест — доказательство дискриминирующей силы. Репортер **не указывай** — дефолтный печатает и падение, и причину, и строку; `--reporter=basic` в Vitest 4 не существует и падает `ERR_LOAD_URL` со стеком на 30 строк, который читается как поломка теста, а не опечатка флага.
   - **Недетерминированный баг** (конкурентность / тайминг / память — RED обычно на property/stress-уровне): одно падение силу НЕ доказывает — тест мог упасть случайно, а на исходном коде иногда проходить. Прогони RED **несколько раз** (или зафиксируй `seed` у `fast-check`) и убедись, что он падает **стабильно** до фикса. Иначе после фикса «зелёный» не отличить от случайной удачи — фикс не доказан. Если стабильного падения добиться не удаётся, воспроизведение неполное: вернись к Фазе 0.6, не закрепляй флапающий тест.
   - **Код пакета корректен, а дефект — в опубликованных артефактах или консьюмере.** Если src пакета ведёт себя правильно, но баг живёт в том, что доезжает до потребителя (`dist/*.d.ts`/бандл — например, не доходящая до консьюмера module augmentation, отсутствующий ре-эмит `.d.ts`) или в самом примере/приложении-консьюмере — package-level unit-теста для RED может **не существовать**. Ставь RED на **интеграционной границе**: собери пакет (`pnpm -F <pkg> bundle`), затем type-check/прогон консьюмера (например `tsc` примера). RED = консьюмер падает на собранном `dist`; GREEN = после фикса доставки. Дополни постоянным контракт-пином (type-level `@ts-expect-error` или conditional-type assert) против регресса, проверив его дискриминирующую силу (временно сломай тип — пин должен упасть).

## Фаза 2 — GREEN (минимальный фикс)

1. Напиши **минимальный** код, чтобы тест прошёл. Никакой спекулятивной функциональности (YAGNI) — только то, что требует тест.
   - **Фикс должен КЛАССИФИЦИРОВАТЬ то, что ядро уже классифицирует (канал ключа, владелец, достижимость, объявлен-ли)? Не пере-выводи реестр — спроси у того, кто ПЕЧАТАЕТ/решает.** Пере-вывод в соседнем пакете или слое молча воссоздаёт дрейф, который ядро уже устранило, и расходится ровно на carve-out'ах и наследовании (коллизия имён, объявление у ПРЕДКА, объявление на КОРНЕ) — то есть на тех клетках, которых в issue нет и по которым тест никто не напишет. Если публичного доступа к реестру нет, ищи предикат по ИСХОДУ, а не по декларации: построй артефакт и прочитай его обратно (`buildPath` → `matchPath`), потому что исход по построению согласован с реестром и бесплатно наследует его режимы и исключения. (Прогон #1580: `getTree().paramMeta.queryParams` на листе неверен на ТРЁХ клетках из четырёх — рапортует carve-out `/items/:id?id` как query-имя, не видит `?q` предка и `setRootPath("?lang")`; это дословно дрейф, который #1556 убрал из ядра, сделав один реестр и классификатором, и принтером.)
   - **Тип из корневого `types/*.ts` — не обязательно тот, что видит потребитель.** Публичные сабпути (`/api`, `/types`, `/validation`) могут ПЕРЕОБЪЯВЛЯТЬ интерфейс точнее (`extends Omit<Base, K>` + узкий `K`). Прежде чем добавлять каст к «слишком широкому» типу (`unknown`, `Record<string, unknown>`), прочитай объявление в ТОМ сабпуте, из которого импортирует пакет: `eslint --fix` снимет лишний каст молча, tsc промолчит, а расследование «почему тип вдруг совпал/не совпал» стоит нескольких заходов. (Прогон #1564: `PluginApi.getTree` в `types/api.ts` — `() => unknown`, но `@real-router/core/api` переобъявляет его как `() => RouteTree`.)
   - **Переносишь/сплитишь существующий код с \u-escape (\\uXXXX), HTML-entity (&amp;), regex-литералами через Write/Edit?** Тул ИНТЕРПРЕТИРУЕТ escape-последовательности при записи (unicode-escape → символ, `&amp;` → `&`) и молча искажает исходник — **критично для security-escape / сериализации** (напр. split-модуля, где escape-таблица переезжает в новый файл; property-тест поймает, но лучше не ломать). НЕ ретайпи такой блок руками: вырежи byte-identical node-сплайсом из оригинала (`readFileSync` → `slice` по маркерам → `writeFileSync`), верифицируй байты (`node -e 'JSON.stringify(...)'`), затем прогони его property/security-тест. ⚠ **Но для ПЕРЕМЕЩЕНИЯ блока внутри одного файла сплайс по `index()` — плохой инструмент:** конец блока ищется по `}`, а во вложенном коде их несколько, и срез уезжает, оставляя файл невалидным (прогон #1644: перенос `#private`-метода сломал парсинг, `tsc` дал `Unexpected token`, восстанавливать пришлось из бэкапа). Двигай двумя `Edit` — удалить по точному тексту, вставить по якорю: обе половины падают на несовпадении, а не молча режут.
   - **Фикс добавляет isolation try/catch в fan-out цикл (частый шаг throw-isolation класса)?** Оборачивание тела итерации **inline** во внешний try часто пробивает `sonarjs/cognitive-complexity` (лимит 15) — лишний уровень вложенности поверх уже-ветвистого цикла. Сразу вынеси тело итерации в именованный хелпер (`continue`→`return`), тогда isolation-try оборачивает ОДИН вызов, а сложность callback'а падает. Не жди lint-провала и второго рефактора (прогон #1478: inline-обёртка дала 17/15 → извлёк `notifyName` вторым заходом; попутно вынес инвариантные-per-transition чтения из цикла).
   - **Async-вариант той же изоляции (возврат/проброс Promise листенера в центральную изоляцию — `subscribe`/`emit`) бьёт ДРУГУЮ пару правил, чем sync-isolation-try выше.** (1) Тест, моделирующий async-misuse (`() => Promise.reject(…)`, `async onStart(){throw}` там, где тип листенера `=> void`), пробивает `@typescript-eslint/no-misused-promises` («Promise returned where a void return was expected») → `eslint-disable-next-line` смежно. (2) Обёртка, которая ВОЗВРАЩАЕТ рантайм-значение `=> void`-типизированного листенера в изоляцию, пробивает `no-confusing-void-expression` — и на shorthand-стрелке (`=> listener(…)`), и на `return voidExpr`; лечится чтением в `const r: unknown = listener(…)` (disable СМЕЖНО, ср. Фаза 4.1) + `return r`. Ставь оба disable проактивно и прогони lint ДО коммита — сама вставка disable-комментария может ещё дёрнуть `@stylistic/padding-line-between-statements` (нужна пустая строка перед следующим statement). Прогон #1412: 3 lint-раунда впустую.
   - **Портируешь defensive-паттерн из ПРЕЦЕДЕНТА (rx-unwind, isolation-try соседнего пакета)?** Его `eslint-disable` / `v8 ignore` / `Stryker disable` вокруг паттерна стоят НЕ случайно — та же форма нарушит те же lint-правила/метрики и у тебя. Проверь суппрессии прецедента ВМЕСТЕ с логикой, не жди, пока lint их переоткроет (прогон #1440: `unsubs.push()` по одному для unwind = `unicorn/prefer-single-call`, rx его `disable`'ит — я скопировал логику без disable → lint-цикл впустую). НО верифицируй КАЖДУЮ суппрессию отдельно, не копируй слепо: `v8 ignore` / `Stryker disable` прецедент часто ставил из-за НЕДОСТИЖИМОСТИ шва тестом — если твой RED его ДОСТАЁТ (напр. спаем/моком), эти суппрессии тебе НЕ нужны и покрытие выйдет лучше прецедента (#1440: rx v8-ignore'ил свой unwind без теста, мой покрыт RED'ом → без ignore).
2. Запусти новый тест + весь набор тестов затронутого пакета: `pnpm -F <пакет> test -- --run`. Все зелёные.
   - **Прогон (особенно кросс-адаптерный / на общей тест-инфре) показал warning/error, похоже от твоей правки — СНАЧАЛА подтверди источник, не перестраивай код вслепую.** Warning называет свой `file:line`; shared-хелперы и соседние компоненты плодят ПРЕД-существующий шум, не твой. Не трогай код, пока не увидел СВОЙ файл в источнике варнинга (прогон #1441: 23 svelte-`state_referenced_locally` шли из ЧУЖИХ тест-хелперов, а я дважды переписал свой компонент впустую + полез сравнивать через `git stash`). Для сравнения с оригиналом — `git show HEAD:<file>` / diff / отдельный worktree, **НИКОГДА `git stash`** (stack общий между worktree, снесёшь чужое — [[feedback_no_git_stash_for_comparison]]).
   - **«Весь сьют зелёный» НЕ доказывает фикс, если тесты пакета импортят его ПО ИМЕНИ (`@real-router/<pkg>`), а фикс в `src`.** Стухший `packages/<pkg>/dist` **шэдоуит vitest src-alias** для name-импортов → эти тесты (обычно router/adapter-level, `createRouter(...)`) молча гонятся против СТАРОГО `dist`, а relative-импортные (`../src/...`) — против фикса; «N passed» тогда невалиден. Диагностика расхождения: одинаковый вход через relative-import (`../src`) и name-import даёт РАЗНЫЙ результат (прогон #1407: `createRouteTree` давал `/foo`, `createRouter([{path:"foo"}])` — стухший `foo`). Remedy ПЕРЕД доверием прогону: `rm -rf packages/*/dist && pnpm install`, затем прогон уже против `src`. Отличается от Фазы 0.6 (там dist для примеров/консьюмеров **пересобирают** — здесь **удаляют**). Вдобавок: фоновая нотификация задачи рапортует exit-код ОБЁРТКИ (0), не сьюта/линтера — верифицируй RC чтением лога. [[feedback_stale_dist_shadows_package_name_imports]]
3. Проверь регрессии в зависимых пакетах (особенно при правке `shared/dom-utils`, `shared/browser-env`, `shared/ssr` — изменение пропагируется во всех консьюмеров через симлинки; для `shared/dom-utils` синхронизируй git-tracked копию в `packages/angular/src/dom-utils`).

## Фаза 2.5 — Sweep сиблингов + class-guard (перед тем как считать фикс завершённым)

Точечный GREEN — ещё не финал: без этой фазы фикс порождает следующий follow-up (весь класс #647→#1211 / #757→#1210 / #798→#1222 — это узкие фиксы с непробованным сиблингом). Дёшево, по коду, в скоупе бага.

1. **Cross-check с `/create-issue`.** Если тело несёт готовый глубокий анализ (корень · родословную · радиус сиблингов · class-guard из `/create-issue` Шаг 2.5) — это ПЕРВАЯ из двух прошивок, а ты ВТОРАЯ: **не доверяй ей слепо.** Пере-выведи корень из кода на HEAD, пере-`blame`, пере-проверь sweep — две независимые проверки и есть ценность (одна перепроверка могла ошибиться уверенно). Твоё собственное авторство анализа доверия НЕ повышает.
2. **Sweep сиблингов — пробь КАЖДЫЙ канал, не аналогизируй иммунитет** ([[feedback_probe_each_sibling_no_analogy]]). ⚠ **Сначала убедись, что сам ПОИСК сиблингов не соврал:** в git-pathspec `*` НЕ переходит через `/`, поэтому `git grep … -- 'packages/*/src'` не матчит `packages/core/src` и возвращает ПУСТО — что читается как «сиблингов нет», хотя это отказ инструмента. Перед любым выводом «больше нигде» предъяви позитивный контроль (`git grep -c <term> -- <файл, где точно есть>`), а фильтруй по каталогу шире (`-- packages shared`) с последующим отсевом (прогон #1645). Смапь ВСЕ сиблинги концерна (все call-site / каналы / координаты / писатели / поколения / счётчики) и пробь или протрассируй **КАЖДЫЙ** — не считай соседа иммунным «потому что похож» или «один уже проверил» (#1210: 3 координаты записи, живая лишь hash; #1212: 4 писателя кэша; #1222: 4 hook-call-site). **Проба сиблинга, падающая и на тестовом, и на КОНТРОЛЬНОМ входе, — не вердикт «не этот класс»:** у сайта может быть второй, доминирующий дефект, маскирующий твой. Варьируй оси входа по одной (канал, форма аргумента, тип значения), пока контроль не станет зелёным — только тогда вердикт по сиблингу валиден. (Прогон #1554: проба `navigateWithHash` падала на ОБОИХ значениях, что читалось как «provenance тут не живёт»; разделение осей `routeParams` vs `routeSearch` вскрыло ДВА дефекта — искомый provenance И доминирующий M2-канальный, сравнивающий неразведённый мешок с разведёнными каналами состояния.) ⚠ **Нашёл копию предиката в соседнем пакете — не останавливайся на факте копии: протрассируй, КАКАЯ из копий лежит на пути пользователя.** У пакета с fast/slow-развилкой дефолтный вызов систематически идёт мимо той копии, что ты починил, и зелёный сьют этого не покажет — оба пути зелены, потому что тестируются порознь. Способ: возьми самую типовую форму вызова из адаптера/консьюмера и пройди её до предиката руками, а потом воспроизведи пробой ЧЕРЕЗ ту точку входа, а не через ядро. (Прогон #1763: ядро починено и `router.isActiveRoute('users')` уже `false`, а `<Link to="users">` продолжала рисоваться активной — обычная ссылка во всех шести адаптерах идёт быстрым путём `@real-router/sources`, где живёт своя копия. Клейм issue «все адаптеры ключуются на этот предикат» был ложным, и без этой трассировки фикс уехал бы «полным».)

**Сиблинг может быть не твоим call-site, а чужим ПОТРЕБИТЕЛЕМ того же шва.** Меняешь канал / формат / порядок в интерцепторе, хуке или событии — грепни, кто ещё регистрируется на тот же метод (`addInterceptor("<method>"`, подписка на то же событие) и прочитай, из какого канала он ЧИТАЕТ: твой фикс мог переставить мешок у него под ногами. Документированная кросс-плагинная связка часто НЕ покрыта тестом ни в одном из пакетов, так что зелёный сьют тут ничего не доказывает — нужна проба на обе стороны связки. (Прогон #1563: `persistent-params` переехал в `search`, а `search-schema` на navigate-направлении читает мешок `params` — покрытие не пропало, а СМЕНИЛО направление; поймал только грепом чужих `addInterceptor`.)

   ⚠ **Дефект привязан к ФАЗЕ (окно до коммита / до анонса / после эмита)? Мапь сиблингов не по call-site'ам, а вопросом «что ещё исполняется в ту же фазу».** В частности — где ещё в этой фазе вызывается ПОЛЬЗОВАТЕЛЬСКИЙ код: колбэки опций, кодеки, фабрики, резолверы. Обход call-site'ов правленой функции такие входы структурно не видит. (Прогон #1610: окон оказалось три, а не одно; `resolveDefault` (колбэки `defaultRoute`/`defaultParams`/`defaultSearch`) найден только этим вопросом.)

   ⚠ **Сиблинг того же корня редко берёт предикат соседа ДОСЛОВНО.** Прежде чем копировать условие живости/владения, перечисли, из каких ФАКТОВ его собирает исходный сайт, и проверь, доступен ли каждый на сиблинге (свой контроллер? свой токен? своя фаза FSM?). Недостающий факт — не «упростим», а дыра: полу-предикат зелен на типовой пробе и падает там, где недостающий факт единственный различитель. Формулируй предикат от ВОПРОСА («держит ли FSM мою транзакцию?»), а не от формы соседа. (Прогон #1610: синхронная дуга не имеет своего контроллера — копирование предиката давало полу-фикс в три захода.)

   ⚠ **Сиблинг идёт по пути, который RFC/план уже отложил, — прочитай, ПО КАКОЙ ПРИЧИНЕ.** План откладывает МЕХАНИЗМЫ (кто владеет коммитом, кто эмитит), а найденный тобой дефект может быть про другое свойство того же пути — живость, атомарность, порядок. Совпадение имени пути ≠ совпадение вопроса; иначе живой баг тихо списывается на «уже в плане». (Прогон #1611: `replace()`-ревалидация отложена в 10b за прямой emit мимо FSM — про живость там не было ни слова, а коммит на disposed-роутере через неё воспроизводится.)

   ⚠ **Ставишь диагностику / guard / варн в ОБЩИЙ примитив — перечисли его вызывающих и реши по КАЖДОМУ, должен ли он это получить.** Правка в разделяемой функции достаётся всем её потребителям, а «кому она полезна» и «кто её технически получит» — разные множества, и по умолчанию совпадать они не обязаны. Типовой ложный получатель — **предикат на render-пути** (`canNavigateTo`, `isActive*`, `matches*`), разделяющий с продюсером композиционную форму, но бегущий на КАЖДЫЙ `<Link>` каждый рендер: варн там не диагностика, а поток. Отсюда правило: опт-ин привязывай к РОЛИ точки (коммитит / только отвечает), а не к форме вызова — форма их не разделяет. И пинни МОЛЧАНИЕ каждого не-получателя тестом, иначе следующая правка формы тихо их переподключит. (Прогон #1579: диагностику заключил на `resolveForward !== false`; sweep поймал `canNavigateTo` — она резолвит `forwardTo`, значит формально тот же класс, что `navigate`, — и предупреждала на предикате. Перевёл на явный опт-ин коммитящих продюсеров, молчание всех шести предикатов запинено.)

   Три исхода на сиблинг:
   - **Gap того же корня, непокрыт** → **покрой в ЭТОМ прогоне** (симметрия — отдельный RED per site, [[feedback_layer_consistency]]).
   - **Gap, но вне скоупа задачи** → заведи через `/create-issue` (с полным Шагом 2.5) и назови в отчёте.
   - **УЖЕ покрыт другим guard'ом/backstop'ом** (проба-контроль зелёная 🟢, не gap) → отметь в отчёте и **НЕ добавляй избыточный guard** — это over-reach (ср. Фаза 0.7), особенно если issue предлагает «add all N» скопом. Проба-контроль отличает уже-покрытый сиблинг от реального gap'а (#1351: конструктор молчал на dup-name **и** @@ → покрыл оба, но dup-path уже ловил path-matcher-backstop #1153 → добавил 2 ассерта из 3, а не слепо все три из тела issue). **Но различай ДВА зелёных:** проба зелёная из-за *guard'а* = реально покрыт; проба зелёная потому что вход/produce **не достаёт до дефекта ПО ПОСТРОЕНИЮ, а не guard'ом** (`getState` не бросает, имя-строка не бывает malformed) = **ЛАТЕНТНЫЙ шов** (шейп есть, дремлет) → помечай `latent`, действие по нему — как в Фазе 2.6 (проактивный guard ИЛИ low-pri hardening-issue + «чем дремлет / что разбудит»), НЕ хорони под «уже покрыто».

   НЕ оставляй сиблинг непробованным «на потом».
3. **Class-guard, а не только точечный фикс** («рекомендовал более глубокий фикс»). Сформулируй **инвариант/property**, ловящий ЭТОТ дефект И его сиблингов, а не один сайт (#1224/#1225: property «plugin ⊇ core: если bare core принимает — плагин не бросает»; #1165: pin release-в-`finally` против move-мутанта; on()-atomicity: validate-then-mutate property). Добавь его тестом, если дёшево и в скоупе пакета; иначе — рекомендуй в отчёте + в комменте issue (Фаза 7). Это то, что превращает «залатал симптом» в «закрыл класс».
   ⚠ **Прежде чем разносить сиблингов по отдельным фиксам/issue, проверь, нет ли ОДНОГО более сильного предиката, закрывающего их разом.** Class-guard бывает не только тестом, но и выбором проверки: спроси, какой факт отличает здоровый случай от ВСЕХ найденных сиблингов, а не только от того, что в issue. Смену предиката обязательно пинни мутацией «ослабить до прежнего» — иначе выбор не запинен и откатится следующей правкой. (Прогон #1611: `isActive()` → `isTransitioning()` закрыл вторым бесплатно фабрику, стартующую вложенную навигацию; ослабление роняет ровно её тест.)
   ⚠ **СНАЧАЛА грепни `tests/property/` на уже существующую property того же концерна — не пиши вторую.** Если она есть и зелена НА БАГЕ, дефект не в её отсутствии, а в её **ДОМЕНЕ**: генератор мог быть сужен той же волной, что внесла баг (типовой сценарий — миграция фикстур под новый throw/reject: форма стала нелегальной, хелпер аргументов перестал её порождать, и property потеряла ровно то плечо, где дефект живёт). Тогда правка — **расширить домен** (доп. арбитрарий на «старое написание»), а не добавить property рядом; вторая была бы дублем при живой первой. Расширение обязательно мутационно валидировать: отключи фикс — property должна упасть с контрпримером ИМЕННО на новом плече. (Прогон #1576: SOUNDNESS «canNavigateTo=true ⟹ navigate resolves» существовала и не ловила баг, потому что `navArgsForRoute` отдаёт предразведённые каналы — «passing them in `params` is what the channel guard rejects» прямо в её докстринге.) ⚠ **Но если существующая property ЯВНО документирует исключённую ось** (в шапке/комментарии: «этот источник сюда не подходит, он не укладывается в модель»), это не сужение домена, а граница модели — тогда правильно добавить СЕСТРИНСКУЮ property рядом и сослаться в её шапке на исключение. Дубль — это вторая property на ту же ось, а не на соседнюю. (Прогон #1609: `cancellation.properties.ts` прямо пишет, что supersede не укладывается в её «settle after each step» модель, — а дефект жил именно там.)
4. **Re-верифицируй ПОСЛЕ фикса, не только до.** Фикс мог сдвинуть шов — прогони sweep-пробы ещё раз на GREEN-коде (тот же урок: re-верификация после фикса выявила, что фикс #798 сместил изоляцию на body, оставив compile-шов → #1222). Пробы удали до коммита.

## Фаза 2.6 — Кросс-кодовый sweep потомков КЛАССА (мультиагентный; ТОЛЬКО для членов рекуррентного класса)

Фаза 2.5 прочёсывает сиблингов ЭТОГО бага — его call-sites/каналы внутри пакета. Этого мало, когда баг — **член рекуррентного класса**: тот же дефект-ШЕЙП живёт в ДРУГИХ пакетах, куда обход call-site'ов не дотягивается, и точечный фикс + локальный sweep их не видят. После того как фикс **закончен и доказан** (GREEN + 2.5 + Фаза 4-валидация), проведи кодо-широкий hunt на непойманных потомков класса. (Прогон #1222: локальный sweep закрыл все 4 lifecycle-сайта, но кодо-широкий выявил ЖИВОГО потомка того же класса в другом пакете — `svelte/Lazy.svelte`, sync-throw loader'а мимо `.catch`, — которого call-site-обход не достал бы никогда.)

**Гейт — фаза дорогая (3+ агента, сотни k токенов), запускай ТОЛЬКО если ВСЕ:**
1. Фаза 0.8 отметила **класс** (residual / звено цепочки / «same class as #N» / в `project_architectural_debt_map`), И
2. class-guard из 2.5 — это **детектируемый ШЕЙП**, который в принципе может повториться в другом коде (напр. `isolate(produce())`, false-reject «plugin строже core», sync-seam, missing-isolation на новом callback-сайте), И
3. у класса есть >1 известного члена в РАЗНЫХ пакетах/сайтах (один-пакетный дефект sweep'а не требует).
Иначе — **ПРОПУСТИ**, в отчёте: «класс single-site/не выявлен → кросс-кодовый sweep не нужен».

**Как:**
1. **Сформулируй дефект-ШЕЙП** в 2-3 фразы + канонический пример (только что исправленный баг) — это ТЗ агентам, дословно в каждый промпт.
2. **Раздели кодовую базу на регионы** и запусти по одному **`Agent` (`subagent_type: Explore`) на регион ПАРАЛЛЕЛЬНО** (в ОДНОМ сообщении — иначе не параллельно). Типичное деление: `core` · пакет-первоисточник класса (там ищи НЕПОКРЫТЫЙ соседний шов — как compile рядом с invoke) · остальные плагины+адаптеры+`shared`. Каждому агенту: «найди КАЖДЫЙ сайт изоляции/шва этого шейпа; на каждый — file:line, что изолируется, и вердикт из ТРЁХ: **VULNERABLE** (produce МОЖЕТ бросить сейчас → живой баг) / **LATENT** (produce стоит СНАРУЖИ изоляции, но не бросает лишь по СЛУЧАЙНОСТИ сегодняшнего кода — `getState()`=чтение поля, чистые строки, НЕТ user-кода в пути — а не по структурной гарантии) / **SAFE** (produce ВНУТРИ try, ИЛИ бросить структурно невозможно). **Дисциплина: вердикт „SAFE“ ОБЯЗАН отличать „шейпа НЕТ“ от „шейп ЕСТЬ, но дремлет“ — агент, пишущий просто „SAFE“ на дремлющем шве, ПРЯЧЕТ латентный баг.** Для каждого LATENT назови: чем дремлет (какой инцидентал держит produce не-бросающим) + какая правка его РАЗБУДИТ (провести user-код / бросающий router-вызов через produce). Читай РЕАЛЬНЫЙ код try/catch и выражения-аргументы, трасируй КАЖДЫЙ produce до источника (бросает? — гарантия типа или инцидентал реализации?), НЕ аналогизируй от имён; заключение — живые сайты И латентные швы».
3. **Параллельно реконструируй СЕМЬЮ класса:** вытяни статусы всех родственных issue (`gh issue view <N>` по цепочке из тел/#1039-подобного research-issue), подтверди что известные закрыты, и что решил research (напр. #1039: примитив ОТКЛОНЁН → lint; но lint слеп к «шов уже» — это и есть дыра).
4. **Верифицируй КАЖДУЮ находку агента САМ** (прочитай сайт) прежде чем объявлять багом — вывод агента это гипотеза ([[feedback_probe_each_sibling_no_analogy]]).

**Синтез (в отчёт + пользователю):** семья класса (все ли закрыты) · **новые живые потомки** (file:line + шейп + severity) · **латентные швы** — шейп ПРИСУТСТВУЕТ, но дремлет (безопасен по построению, не по замыслу): это **НЕ баг → НЕ заводи как `bug`**. Действие: либо **дешёвый проактивный guard сейчас** (перенести produce ВНУТРЬ изоляции — шейп исчезает, будущая правка его не разбудит), либо **low-pri hardening-issue** (`enhancement`, не `bug`) + назови в отчёте с «чем дремлет / что разбудит»; развилку вынеси пользователю. Латентный шов дешевле закрыть проактивно, чем дать ему стать живым багом позже — и, в отличие от живого бага, **RED на него нестандартный** (бросать сегодня нечему → надо СИМУЛИРОВАТЬ throw produce, напр. замокать `getState`, и проверить ресурсное следствие: соседи-слушатели всё равно уведомлены). Прогон #1478: `createActiveNameSelector` per-name пересчёт вне #767-try дремлет, т.к. `getState()` не бросает; ни один существующий тест это не поймал бы. · **структурная иммунность** (где шейп невозможен и ПОЧЕМУ — напр. core компилирует guard/plugin-фабрики жадно при регистрации, а не лениво-в-точке-вызова → форма `wrap(produce())` там не собирается).

**Действия (по явной просьбе пользователя — внешние):** на каждого нового живого потомка — `/create-issue` (Шаг 2.5: корень · родословная · class-guard); отдельный issue на **class-level предохранитель** (shape-lint / конвенция), если его нет — точечные фиксы класс структурно НЕ закрывают, следующий потомок появится. Потомков в других пакетах **НЕ чини в этом прогоне** (другой скоуп) — вынеси развилку пользователю.

## Фаза 3 — REFACTOR

1. Улучши структуру фикса и теста, не меняя поведения. Тесты остаются зелёными.
2. Проверь, что не осталось дубля логики и фикс лежит на правильном слое (core / plugin / dom-utility — границы симметричны, не размывать ради одной правки).
3. **Пост-фикс анализ (когда фикс подтверждён тестами и проверками).** Вернись к фиксу свежим взглядом и подумай: можно ли его упростить, оптимизировать, улучшить?
   - Нет ли более короткого/прямого решения, которое устраняет ту же причину.
   - Нет ли лишних аллокаций, обходов, копий, повторных вычислений на горячем пути.
   - Не дублирует ли фикс существующий хелпер/утилиту, которые можно переиспользовать.
   - Читается ли он в стиле окружающего кода (именование, идиомы, плотность комментариев).
   - Любое упрощение применяй, только если все тесты затронутого пакета остаются зелёными (`pnpm -F <pkg> test -- --run`). Если упрощение ухудшает читаемость или ломает границы слоёв — оставь как есть и зафиксируй, почему.

## Фаза 4 — Валидация

1. **Точечная валидация затронутых пакетов** — НЕ полный `pnpm build` (он тяжёлый: turbo гонит весь граф с property/stress; его финальный прогон делегируется пользователю). На каждый изменённый пакет: `pnpm -F <pkg> type-check`, `pnpm -F <pkg> lint`, `pnpm -F <pkg> test -- --run` (+ `test:properties` / `test:stress`, если фикс касался инварианта / конкурентности / памяти). 100% coverage обязательно. **Для адаптеров с phantom-порогом (vue/solid/svelte/angular — branch/func <100% из-за compiler-кода) aggregate suite-pass НЕ доказывает покрытие ТВОЕГО файла: phantom-allowance поглощает новые непокрытые ветки/функции в изменённом `src`. Проверяй per-file (строка файла в coverage-таблице = 100% Stmts/Branch/Funcs), не только `Tests N passed` — иначе мёртвый код (напр. никогда не вызываемый `destroy`/`noop`) или новая ветка уедет в коммит под порогом.** **Если строки твоего файла в таблице НЕТ вовсе (печатается только заголовок `File | % Stmts…`) — это `skipFull: true`: репортер выводит ТОЛЬКО <100%-файлы. Отсутствие строки + exit-0 на НЕ-phantom пакете = 100% (не трать вызовы на попытку «увидеть строку» — её нет by design; прогон #1478). На phantom-адаптере файл с непокрытой веткой, наоборот, ПОКАЖЕТСЯ — тогда читай строку.** **Финальный lint-гейт большого пакета (`core` и т.п.) гони СВЕЖИМ (`rm <pkg>/.eslintcache`) и в фоне (`run_in_background`), не с тесным таймаутом:** его скрипт — `eslint --cache --fix` (~2 мин на `core`), и прогон, оборванный SIGTERM по короткому Bash-таймауту, либо `--cache`-прогон со старым вердиктом — ложно рапортует «чисто». **Не цепляй `; echo`/иную команду ПОСЛЕ lint — она затирает `$?`; **симметрично, `| tail`/`| grep`/`| head` ПЕРЕД снятием `$?` отдаёт код ПОСЛЕДНЕЙ стадии пайпа**, поэтому `eslint … | tail -5; echo "RC=$?"` бодро печатает `RC=0` от `tail` даже на красном линтере (тот же капкан у `vitest`/`tsc`); а background-нотификация `exit 0` — это код ОБЁРТКИ, не линтера. Верифицируй собственный код возврата инструмента: снимай его с САМОЙ команды (`pnpm lint; RC=$?` без хвоста, `--max-warnings 0` роняет и на warning'ах), а вывод фильтруй ОТДЕЛЬНЫМ вызовом либо читай лог (строка `✖ N problems` от eslint). ⚠ **И не спасайся `${PIPESTATUS[0]}` — это bash-изм, а шелл здесь zsh, где массив зовётся `$pipestatus` и индексируется с ЕДИНИЦЫ.** Bash-идиома в zsh раскрывается в ПУСТУЮ строку, так что печатается `RC=` — не ошибка, не ноль, просто ничто, и читается как «претензий нет» (прогон #1644).** ⚠ **Список изменённых файлов, собранный из `git status --porcelain`, НЕ фильтруй по `^??`:** новый тест/файл фикса ещё untracked, вылетает из списка, и линтер честно рапортует RC=0 по оставшимся — а в невключённом файле лежат ошибки (прогон #1644: 3 файла вместо 4, RC=0, в четвёртом 3 error'а). Проверяй ЧИСЛО переданных файлов против ожидаемого, а не только код возврата. Вдобавок `--fix` молча СНИМАЕТ неправильно расположенный `eslint-disable` как unused, оставляя реальную ошибку непокрытой — держи `disable`-директиву и её цель (`!`, и т.п.) на СМЕЖНЫХ строках; иначе твой «зелёный» lint скроет ровно то, что поймает полный build пользователя (и уедет в коммит). Каждый НОВЫЙ тест-блок прогоняй через `lint:fix` **сразу после написания**, до гейта: prettier-переносы в многострочных `expect(...)` / `test.prop(...)` — гарантированный источник 2–3 холостых раундов «гейт → fix → гейт», а `--fix` снимает их молча (прогон #1554: два раунда впустую — второй после добавления property-теста уже ПОСЛЕ зелёного гейта). ⚠ **Жалоба линтера на приведение или сравнение типов (`no-base-to-string`, `no-unnecessary-condition`, `no-confusing-void-expression`) бывает СЕМАНТИЧЕСКИМ сигналом, а не стилевым.** Прежде чем глушить её `disable`-ом или писать компаратор под неё, спроси, нужно ли сравнение вообще: часто достаточно факта присутствия/отсутствия, и это ещё и устойчивее. (Прогон #1580: `no-base-to-string` на `String(unknown)` заставил пересмотреть сравнение значений — оказалось, что оно активно ВРЕДНО: маршрут с `encodeParams`, законно переписывающим значение по дороге в URL, получал ложный отказ. Обход линтера закрепил бы дефект; проверка присутствия и короче, и корректнее.) Тот же класс — правила про ФОРМУ API (`sonarjs/no-selector-parameter` и родня): boolean-флаг, выбирающий поведение, обычно значит, что решение принадлежит вызывающему — вынеси ветвление на call-site, и общий хелпер станет однозначным (прогон #1609: `resolveFailureOutcome(error, isLive)` → `asCancellation(error)` + тернарник у каждой дуги — короче и честнее). ⚠ И если добавляешь **новый ПУБЛИЧНЫЙ метод в существующий класс** — сразу ставь его в блок публичных методов, до `#private`, иначе `@typescript-eslint/member-ordering` даст warning, а при `--max-warnings 0` это красный гейт; перенос метода с уже написанным докблоком стоит отдельного раунда «подвинул → prettier → гейт» (прогон #1610). **Симметрично и коварнее — новый `#private`-хелпер, положенный РЯДОМ с правленым публичным методом:** нарушителем становится не он, а КАЖДЫЙ публичный член ниже по файлу, поэтому вывод линтера выглядит как внезапная поломка половины класса и уводит расследование от твоей вставки (прогон #1644: 20 warning'ов на нетронутых методах из-за одного `#refuseSystemCommit`). Новый приватный клади в приватную секцию сразу, а не рядом с местом правки. Полный `pnpm build` **не запускай** — в итоговом отчёте сообщи, что финальная сборка за пользователем.
2. **Changeset** — если правились `packages/*/src/` публичного пакета, вызови скилл `/changeset` (он сам определит затронутые публичные пакеты и тип бампа по issue + diff). Для баг-фикса тип обычно `patch`; в pre-1.0 фазе breaking changes идут как `minor`. **Симметричный фикс с прямым прецедентом** (тот же дефект-класс УЖЕ починен в другом пакете/адаптере — напр. зеркалишь vue #1352 в остальные `<Link>`): сверь bump changeset'а прецедента (`git log --grep`/CHANGELOG затронутого пакета) и **matchни его**, не переопределяй из эвристики «runtime-смена наблюдаемого поведения → minor» в изоляции — minor-vs-patch там уже адъюдицирован. Прогон #1436: эвристика тянула к `minor`, но vue #1352 (идентичный фикс) отгружен как `patch` (0.16.16) → взял `patch` ради консистентности серии. Инфраструктурные правки (не трогают `packages/*/src/`) идут в master без changeset — `/changeset` сам это распознает.

## Фаза 4.5 — Атака на СВОЁ решение (обязательно; фикс без неё не считается готовым)

Фазы 2.5/2.6 прочёсывают радиус ДЕФЕКТА. Эта фаза — про дефекты самого ФИКСА: зелёный тир доказывает, что фикс не сломал того, что уже пинилось, и ничего не говорит о том, что фикс внёс. Заходи сюда, только когда фикс закончен и Фаза 4 зелёная — иначе атакуешь черновик. Всё найденное чини ЗДЕСЬ, до Фазы 5: доки и changeset должны описывать атакованное решение, а не первую версию (иначе в CHANGELOG уедет клейм, который атака опровергла — а он там навсегда).

Прогоняй ВСЕ векторы. Отсутствие находки по вектору — тоже результат, его называют в отчёте.

1. **Мутируй КАЖДЫЙ терм, который ты ДОБАВИЛ ИЛИ ПЕРЕНЁС — включая «очевидно несущие».** Не «фикс в целом», а каждое условие, каждый `&&`/`||`, каждый ранний выход по отдельности: сними терм, прогони тир. Терм, без которого тир зелёный, — это **эквивалентный мутант, посаженный твоей рукой**: гарантированный выживший в Stryker, лишняя ветка под 100 %-гейтом и ложное впечатление, что условие что-то охраняет. Убери его или перепиши так, чтобы избыточность была ЕСТЕСТВЕННЫМ short-circuit'ом, названным в комментарии, — но не оставляй молча. (Прогон #1757: предикат был написан `!isExactMatch && chain.some(…)`; цепочка сегментов маршрута заканчивается им самим, поэтому lookup отвечает `true` и для точного совпадения — 4156/4156 зелёные без ведущего терма.)

   ⚠ **Перенесённый терм — тоже твой, и по букве «что ты добавил» его мутировать не обязательно.** Обязательно: он мог быть незапиненным и ДО тебя, а после переноса гарантия за него на тебе, и зелёный тир этого не покажет — он был зелёным и на старом месте. Тот же приём и та же цена. (Прогон #1756: условие `isTransitioning()` я не добавил, а сдвинул на два оператора ниже; снятие его на сайте `remove` оставило все 4173 теста зелёными — половина условия не охранялась ничем, и нашлось это только потому, что мутация была прогнана по инерции, а не по правилу.)
   ⚠ **И проверь ОБРАТНОЕ: не сделал ли твой фикс эквивалентным или МЁРТВЫМ чужой, уже отгруженный код.** Признак — тесты чужого фикса краснеют не потому, что ты его сломал, а потому что их форму больше не построить; и второй, более тихий — просадка COVERAGE в соседнем пакете, которую видно только под полным гейтом (пакет проходит без coverage и падает с ним). Не глуши `v8 ignore`: недостижимый код — это код, который надо удалить, а историю оставить комментарием на его месте. Назови это в отчёте отдельно, потому что цена крупная — исчезают чужие тесты и целый класс дефектов. (Прогон #1763: reject на регистрации сделал непостроимыми шесть клеток #1757 и превратил дот-проверку в `validation-plugin` в единственную непокрытую строку пакета.)
   ⚠ **Скрипт мутации пиши на АБСОЛЮТНЫХ путях и без `cd`.** cwd у Bash-тула персистентен между вызовами, поэтому повторный `cd <dir>` падает — а `cd <dir> && <правка>` тихо съедает правку целиком, и следующая команда того же блока при этом отрабатывает. Получается ЧАСТИЧНО применённый мутант: один сайт мутирован, второй нет либо мутанты легли друг на друга, и замер по нему невалиден, хотя выглядит нормально. После каждого restore предъявляй позитивный контроль (`grep -c <маркер-фикса> <файл>`) — код возврата `cp` о содержимом файла не говорит. (Прогон #1756: два мутанта слились в один, «2 failed» было прочитано как «каждый сайт запинен», и раунд пришлось переделывать.)

2. **Атакуй CLASS-GUARD отдельно от кода, по одному сайту класса.** Property/инвариант из Фазы 2.5 обязан краснеть на мутации **КАЖДОГО** сайта, а не одного: мутируй сайт-1 → property красная, восстанови, мутируй сайт-2 → красная, и так далее. Guard, зелёный хотя бы на одном сайте своего класса, — не class-guard, а тест одного сайта под широким именем, и именно он даёт ложную уверенность «класс закрыт». (Тот же прогон: property покрывала чистку конфига и payload, а на мутанте гвардового предиката оставалась ЗЕЛЁНОЙ — половина класса была не охраняема, при том что её же имя обещало обратное.)
3. **Перепроверь ПРОБОЙ каждый клейм, который ты написал в changeset/коммит/комментарий** — особенно формы «ничего больше не меняется», «только X», «для здорового дерева поведение прежнее». Это самые дешёвые в написании и самые дорогие в CHANGELOG утверждения, и пишутся они по памяти о замысле, а не по замеру. (Тот же прогон: «Nothing changes for a well-formed tree» опровергнуто — внешний гвард на НЕ-маршрут с точечным префиксом раньше сметался удалением, а теперь выживает.)
4. **Ищи, что фикс ЗАБРАЛ.** Старый код что-то делал, и на это кто-то мог опираться: сузил предикат — кто попадал в отброшенную часть? Перестал чистить — что теперь копится (слоты лимитов, подписки, записи кэша)? Начал отказывать — чей рабочий сценарий стал отказом? Каждое «забрал» — либо улучшение, которое надо НАЗВАТЬ и запинить тестом, либо регрессия.
5. **Замерь то, что объявил перф-решением.** «Не чиню там, потому что горячий путь» — это КЛЕЙМ, и он гейтит скоуп. Померь стоимость примитива, который пришлось бы туда поставить, и сопоставь с уже задокументированной стоимостью той операции. Число либо оправдывает отказ, либо его опровергает — и в первом случае оно ещё и даёт follow-up'у ДИЗАЙН вместо «сделать правильно». (Тот же прогон: структурная проверка 60,2 нс против 7,6 нс лексической, при полной стоимости предиката 32,9 нс — отказ оправдан, а нужной формой оказался булев гейт на уровне стора, а не lookup.)
6. **Прогони граничные формы ВХОДА, а не только ту, что в issue**: та же фигура на уровень глубже; фигура, у которой есть ещё и дети; имена-ловушки (`__proto__`, `constructor`); глубина рекурсии против УЖЕ существующего обрыва стека (новый ли он у тебя, или падает раньше и не твой); и десинхронизация того коллаборатора, на который твой новый предикат опёрся (может ли он ответить `undefined`/устаревшим — и что тогда).
7. **Проверь ФОРМУ возврата и связанность флагов**, если ты её менял: не стало ли значение трёхзначным, не читается ли один и тот же флаг дважды, не появилось ли у `undefined` двух смыслов. Здесь ошибку ловит не тест, а чтение.

**Рой агентов — когда поверхность шире одного файла.** Разошли `Agent` (`subagent_type: Explore`) ПАРАЛЛЕЛЬНО (в ОДНОМ сообщении, иначе последовательно), по одной ЛИНЗЕ на агента, а не по одному файлу: «мутационная» (найди в диффе термы без наблюдаемого эффекта), «регрессионная» (что старый код делал и для кого, а новый — нет), «клеймовая» (сверь каждое утверждение changeset'а/коммента с кодом), «граничная» (входы, которых нет в тестах), «потребительская» (кто ещё читает изменённый выход/событие/сигнатуру). Каждому — дословный дифф и требование `file:line` + ВОСПРОИЗВЕДЕНИЕ, а не мнение. ⚠ Вывод агента — гипотеза: **верифицируй каждую находку сам**, прогоном или пробой, прежде чем чинить; и наоборот, «агент ничего не нашёл» не закрывает вектор — закрывает его твой прогон.

⚠ Агенты read-only и НЕ совместимы с правками дерева: пока рой работает, ничего не меняй — иначе они анализируют одно, а ты чинишь другое.

## Фаза 5 — Синхронизация документации и вики (обязательно после фикса)

Баг-фикс часто означает, что задокументированное поведение расходилось с реальным. Пройди по документации и проверь, не описывает ли она старое (баговое) поведение, нет ли устаревших примеров или сигнатур.

**Проверяй не только «описывает ли док баговое поведение», но и не отстала ли страница правленого метода от ПРЕДЫДУЩЕЙ волны** — сигнатура, форма возврата, число каналов/аргументов. Такая страница по ключевым словам ТВОЕГО бага не находится вовсе, поэтому её пропускают прогон за прогоном. Улика парадоксальная: **пустой** `rg` по ключевому термину текущей модели данных на странице, которая обязана его упоминать (`rg 'search' <page>` → 0 строк на странице метода, у которого есть query-канал), означает не «нечего править», а «страница до-волновая». (Прогон #1570: вики `forwardState.md` документировала 2-арг сигнатуру и `{name, params}` без query-канала — отставание от M2/#1548, не от чинимого бага.)

**Строку, которую ты ПЕРЕНОСИШЬ в новый текст, проверь пробой, а не глазами.** Стухшее утверждение переживает рефактор именно потому, что его копируют не читая. Особенно «митигации» / «обходные пути» — они пишутся один раз и годами не перепроверяются. (Прогон #1563: обе связанные страницы обещали «дай ключу route-дефолт — ядро перебьёт инжект»; проба показала обратное — любой route-дефолт мёржится ПОД значением, и я чуть не перенёс ложь в новый абзац.) **Числа и факты, которые ты измерил на Фазе 0.6** (сколько раз позвана фабрика, сколько аллокаций, в какой фазе бежит код), — готовый детектор доковой лжи: прежде чем читать страницу глазами, грепни её на утверждения о ТОЙ ЖЕ величине («runs once», «only at», «never»); пробник уже сказал, верны ли они. (Прогон #1611: `guards.md` обещала «the factory runs once at registration time», а замер часом раньше показал вызов фабрики ВНУТРИ навигации.)

**Грепни номер чинимого issue по докам и вики ПЕРЕД синком** (`rg "#<N>" packages */*.md <abs-wiki>`): предыдущий багфикс мог оставить там «известное ограничение, отслеживается в #N» — после фикса это самая заметная ложь в документации, и по имени метода/опции такие абзацы не находятся. (Прогон #1564: шесть мест, засеянных прогоном #1563 днём раньше.)

1. **Локальная документация** — проверь и при расхождении обнови:
   - Корневые: `README.md`, `ARCHITECTURE.md`, `IMPLEMENTATION_NOTES.md`, `CLAUDE.md` (формат записи решений — Problem → Solution → Why, исторические решения не удалять).
   - Затронутого пакета: `packages/<pkg>/README.md`, `ARCHITECTURE.md`, `CLAUDE.md`, при наличии — `INVARIANTS.md` (если фикс касался инварианта).
   - **Контракт INVARIANTS ↔ property-тесты:** если фикс ввёл или изменил инвариант — добавь/обнови соответствующий кейс в `tests/property/*` И синхронизируй таблицу маппинга «инвариант → тест-файл» в `INVARIANTS.md` (в этом репозитории строки инвариантов маппятся 1:1 на property-тесты; прозаическая строка без теста ломает контракт).
   - Точечно ищи устаревшие упоминания: `grep -rn "<имя метода/опции>" packages/<pkg>/*.md README.md ARCHITECTURE.md`.
2. **Вики** (отдельный репозиторий `real-router.wiki/`):
   - Найди страницы, описывающие затронутый API/метод/компонент (например `Route.md`, `RouterOptions.md`, `<Plugin>.md`, `*-Integration.md`).
   - Обнови сигнатуры, примеры и описания поведения, если они расходятся с фиксом.
   - Поиск: `rg "<имя метода/опции>" <wiki-path>`. **Из worktree** относительный `../real-router.wiki` НЕ достаёт до sibling-репо (worktree лежит в `.claude/worktrees/<name>/`, `../` не выходит к корню-соседу — `grep` вернёт «no matches») — бери **абсолютный** путь вики из environment (секция `Additional working directories`). И НЕ делай `cd` в вики-репо (или `cd` обратно сразу): персистентный cwd Bash уводит последующие `git`-команды (Phase 6 `git diff`/commit) в чужой репозиторий — можно собрать commit message из чужого диффа. ⚠ **`cd <wiki> && <команда>` в ОДНОЙ строке спасает не больше, чем отдельный `cd`** — cwd у Bash-тула персистентен между вызовами, а не в пределах команды, так что после такой цепочки следующий `git status` смотрит уже в вики (прогон #1574). Работай через `rg <pattern> <abs-wiki-path>` и `git -C <worktree>`; коммить в вики только СВОИ файлы (`git add <files>`) — там бывают чужие незакоммиченные правки.
3. Сообщи список проверенных файлов и что именно обновил (или явно укажи, что расхождений в документации не найдено).

## Фаза 6 — Commit message

1. Когда фикс, валидация, changeset и документация готовы, вызови скилл `/commit-msg` — он сгенерирует сообщение в формате Conventional Commits по текущему diff. Для баг-фикса ожидаемый тип — `fix(<scope>): ...`.
2. Выведи готовое сообщение пользователю. **НЕ коммить и НЕ пуш без явной просьбы** — только предложи сообщение.
3. **Когда пользователь явно попросит запушить** — пуш текущей ветки: `git push -u origin HEAD`. Pre-push hook гоняет полную валидацию; в git-worktree шаг `lint:audit` (osv-scanner) известно даёт спурьозные падения (обход дерева от `/`). Если pre-push спотыкается **только** на нём — верифицируй чисто в основном чекауте (`pnpm lint:audit` из корня основного репозитория), затем повтори пуш с `--no-verify`. Все прочие падения pre-push — настоящие, не обходи.

## Фаза 7 — Комментарий в issue (как решён баг)

Подготовь комментарий, кратко и по делу объясняющий **как решён баг** — это остаётся в публичной истории issue и закрывает контур обратной связи с автором.

1. Содержание (на **английском** — issues ведутся на английском):
   - **Корень бага** — подтверждённый, в одну-две фразы.
   - **Фикс** — суть подхода + ключевой фрагмент кода/диффа; плюс почему поведение в остальном сохранено (какие инварианты/проверки остались на месте).
   - **Тест(ы)**, доказывающие фикс — имена.
   - **Скоуп-решения** — если в issue предлагалось решение или несколько пунктов: что принято, что задокументировано вместо рефакторинга, что осознанно отложено как follow-up — каждое с краткой причиной. Это самая ценная часть для автора issue.
   - **Sweep сиблингов + class-guard** (из Фазы 2.5) — какие сиблинги концерна проверены и покрыты/заведены отдельно (полный радиус, не один сайт), и рекомендованный class-guard (инвариант/property, закрывающий класс), если он не добавлен тестом в этом прогоне. Если инлайн-раскопка (Фаза 0.8) выявила ложную полноту родительского фикса или структурный тэг (isolate-produce, false-reject, sync-seam и т.п.) — назови его: это спасает следующий follow-up.
   - Не переобещай статус: описывай реализованный подход, **не** заявляй «merged/released», если фикс ещё на ветке.
2. Публикация: `gh issue comment <number> --body-file <file>` — используй `--body-file` (не `--body`), чтобы сохранить markdown и код-блоки. **Публикуй только по явной просьбе пользователя** — тот же гейт, что коммит/пуш: комментарий в публичный issue — внешнее действие (обычно идёт в паре с просьбой закоммитить/запушить). Без просьбы — только покажи черновик в итоговом отчёте.

## Итоговый отчёт

- Ветка: текущая ветка задачи (`git branch --show-current`) — скил не заводил ветку/worktree, работал в предоставленной.
- Корень бага и где исправлен.
- Если в issue было предложено решение — принято оно или нет и почему.
- Тест, доказывающий фикс (путь + имя).
- Пост-фикс анализ: что упрощено/оптимизировано (или почему оставлено как есть).
- **Атака на своё решение (Фаза 4.5): по каждому вектору — что найдено и починено, либо явное «чисто».** Отдельно назови: эквивалентные термы, которые ты сам внёс и убрал; сайты класса, на которых class-guard оказался зелёным и был усилен; клеймы changeset'а, опровергнутые пробой; что фикс ЗАБРАЛ; и замер, которым обоснован отказ чинить соседний сайт.
- Sweep сиблингов (Фаза 2.5): какие каналы/сайты концерна проверены, покрыты в прогоне vs заведены отдельным issue; рекомендованный class-guard; структурный тэг/ложная-полнота, если найдены (Фаза 0.8).
- Результат точечной валидации затронутых пакетов (`pnpm -F <pkg> test/lint/type-check`); полный `pnpm build` делегирован пользователю.
- Changeset: создан через `/changeset` (какие пакеты/бамп) или не нужен — почему.
- Документация и вики: что проверено и что обновлено.
- Предложенный commit message из `/commit-msg`.
- Черновик комментария в issue (или подтверждение, что опубликован, если была явная просьба).

Важно:
- НЕ коммить и НЕ пуш без явной просьбы пользователя.
- НЕ публикуй комментарий в issue без явной просьбы пользователя — только подготовь черновик.
- Не помечай задачу выполненной при падающих тестах, частичном фиксе — или непройденной Фазе 4.5: зелёный тир доказывает, что фикс не сломал старое, и НЕ доказывает, что он не внёс своего.

Примеры:
```
/bugfix 812
/bugfix https://github.com/greydragon888/real-router/issues/812
```

## Самокоррекция скила (ОБЯЗАТЕЛЬНО, в конце КАЖДОГО прогона)

Этот файл — живой; каждый прогон обязан его затачивать. После отчёта (Red→Green→Refactor + синхронизация локальных доков/вики) вынеси короткую секцию **«Самокоррекция»** — критику не своей работы, а САМОГО ЭТОГО СКИЛА: где его текст промолчал, соврал, был двусмыслен или избыточен — и это стоило времени, лишнего шага или риска ошибки.

1. **Привязка к ИНЦИДЕНТУ, не общие советы.** Каждая правка — из конкретного момента ЭТОГО прогона: «скил сказал X / промолчал про X → реальность Y → я потерял/чуть не ошибся на Z». Нет инцидента — нет правки (не выдумывай улучшения впрок).
2. **Высокая планка: изменило бы исход?** Предлагай, только если правка реально предотвратила бы ошибку, сократила перебор или сняла двусмысленность, на которой ты споткнулся. Косметику и «было бы неплохо» — отбрасывай.
3. **Разовое ≠ паттерн.** Специфику конкретного бага/пакета (разовую) → в черновик issue-комментария/память, НЕ в скил. В скил идёт только повторяющийся класс, полезный СЛЕДУЮЩЕМУ фиксу ДРУГОГО бага.
4. **Сначала заточи, потом дописывай (анти-раздувание).** Предпочитай усиление существующего абзаца новой секции; если правка делает прежний текст избыточным — консолидируй, не дублируй.
5. **Предлагай, не применяй молча.** Выведи кандидатов таблицей (раздел | инцидент | предлагаемый текст), спроси разрешения. Применил по согласию → `.claude/commands/` это infra, в master напрямую, без changeset.
6. **Честность про «нечего править».** Прогон прошёл чисто и скил нигде не подвёл → так и скажи: «правок нет». Пустая самокоррекция честнее придуманной — пункты 1–2 это допускают.
