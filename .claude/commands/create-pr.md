Создай и опубликуй pull request для текущей ветки на основе решённых задач, истории коммитов и changeset-файлов.

Входные данные (опционально):
$ARGUMENTS

Аргументы — голый список номеров (`#807 #808`, авторитетный), `--draft` (черновик PR) или бриф вызывающего, обычно модели: ветка и worktree, решённые задачи, запушена ли ветка и чем кончился pre-push, что уже измерено — какой командой и на каком коммите. В брифе авторитетен номер, который он прямо называет решённым (`closes #N`, «задача #N»); прочие его `#N` — контекст.

## Фаза 0 — Проверка состояния

Базовая ветка PR — **всегда `master`**. Команды шагов 1–5 и источников A–C Фазы 1 гони одним вызовом, `git fetch origin` — первым.

1. Текущая ветка: `git branch --show-current`.
2. **Проверь базовую ветку репозитория**: `gh repo view --json defaultBranchRef -q .defaultBranchRef.name`.
   - **Если это не `master` — ПРЕКРАТИ** и сообщи пользователю: скилл рассчитан на базу `master`, продолжать нельзя.
3. Убедись, что в ветке есть что оформлять: `git log master..HEAD --oneline`.
   - **Пусто, и `git status --porcelain` тоже пуст — ПРЕКРАТИ**: ветка не опережает `master`, PR оформлять не из чего. Сообщи пользователю.
   - **Диапазон пуст, но в рабочем дереве есть незакоммиченная работа** — ветка не пустая. Если просьба включает коммит («коммить, пушь и открывай PR»), закоммить через хуки и начни Фазу 0 заново. Если не включает, спроси, коммитить ли.
4. Проверь, нет ли уже PR для этой ветки: `gh pr view --json number,url,state 2>/dev/null` — команда находит и слитый PR.
   - `OPEN` — **не создавай дубль**: сообщи URL и предложи обновить тело через `gh pr edit --body-file` (один PR на ветку — конвенция проекта).
   - `MERGED` — прошлый PR ветки слит, новый можно. Squash не переносит её коммиты в `master` по SHA: в `git log origin/master..HEAD` должны остаться только новые, лишние снимает `git rebase --onto origin/master <последний слитый коммит>`. `CLOSED` — спроси, открыть новый или переоткрыть прежний.
5. **Проверь, не ушёл ли `origin/master` с базы ветки**: `git fetch origin && git merge-tree --write-tree --name-only origin/master HEAD`; ушёл ли — `git merge-base --is-ancestor origin/master HEAD` (код 1 — ушёл). Ушёл — в теле PR перемерь всё, что цитирует `master` как базу.
   - Ветки ещё нет на remote — `git rebase origin/master`, и без конфликта: force-push не понадобится, а PR родится на свежей базе. Хеш, уже процитированный в комментарии к задаче, после push поправь. `master` принёс новый `pnpm-lock.yaml` — `pnpm install` до тестов и хуков.
   - Ветка уже на remote и конфликтует — влей `master` (или сообщи пользователю).
   - ⚠ **`IMPLEMENTATION_NOTES.md` и `claim-census-ledger.json` конфликтуют у параллельных PR по устройству:** обе стороны дописывают запись в конец заметок и хеши в одну и ту же запись ledger'а. Заметки — склей обе записи, запись `master` первой. Ledger — возьми сторону `master` целиком (при rebase это `--ours`, при merge — `--theirs`), руками удали записи файлов, которые ветка переименовала, и перезапиши только СВОИ файлы: `node scripts/claim-census.mjs --update <файлы> --yes`. Затем сверь с `master`: добавились ровно хеши твоих claim'ов, остальные записи не изменились. Тот же `--update` по чужим файлам молча внёс бы в ledger claim'ы, которых никто не читал.

## Фаза 1 — Сбор номеров решённых задач (из трёх источников)

В ветке может быть решено **несколько** задач. Собери кандидатов из всех источников, объедини и верифицируй.

1. **Источник A — имя ветки** (ведущий числовой сегмент, формат `<number>-<slug>`):
   `git branch --show-current | grep -oE '^[0-9]+'`
2. **Источник B — ЗАГОЛОВКИ коммитов ветки** (`--format='%s'`), а не полные тела: тела штатно ссылаются на родословную (`related to #N`, `the shape #N fixed`, `keeps #N's reason`) и на номера инвариантов/секций (`INVARIANTS #2`), и всё это НЕ решённые задачи. Кандидат, встречающийся только в теле и отсутствующий в заголовке/changeset/имени ветки, — ссылка: исключай молча, не гоняй через `gh issue view` и не спрашивай про `Closes`. ⚠ **Заголовок ИНФРА-коммита (`docs(config)`, `chore`, `docs`) цитирует чужие номера так же** («two rules from the #N run», «follow-up of #N»), а правило «только из тела ⇒ ссылка» его не отсеивает: номер стоит в заголовке. Отсеивай такого кандидата по ТИПУ коммита: коммит, не трогающий `packages/*/src` и не несущий changeset, задач не решает — его `#N` это происхождение урока, а не `Closes`; сам коммит — по п. 1 Фазы 2. ⚠ **`master` и `origin/master` расходятся в ОБЕ стороны — сравни оба диапазона (`master..HEAD` и `origin/master..HEAD`) и не бери молча ни один.** Локальный ref ОТСТАЁТ после чужих мержей, и тогда в `master..HEAD` попадают уже смерженные коммиты — там права база `origin/master`. Но он же бывает ВПЕРЕДИ: у владельца лежат незапушенные инфра-коммиты в `master` (правило репо — инфра идёт в `master` напрямую), ветка их несёт, и `origin/master..HEAD` подмешивает к задачам чужие номера. Разводится так: **номера задач бери из более УЗКОГО диапазона**, а разницу двух диапазонов объясни — если она непуста, PR покажет на GitHub больше коммитов и файлов, чем сделала ветка. Публикацию это не блокирует — дифф пересчитается, когда `master` запушат, — но **скажи об этом в отчёте**: иначе владелец увидит в PR чужие файлы и будет искать причину.
   `git log master..HEAD --format='%s' | grep -oE '#[0-9]+' | sort -u`
3. **Источник C — changeset-файлы, добавленные/изменённые в ветке**:
   `git diff master...HEAD --name-only -- .changeset | grep -v README` → прочитай каждый → извлеки `#N`.
   ⚠ **Но не «все `#N` из файла» — только из ПЕРВОЙ строки описания** (`Short title … (#N)`, в т.ч. `([#N](…/issues/N))`). Тело changeset'а по конвенции репозитория объясняет корень и родословную, поэтому несёт ссылки (`the shape #N fixed`, `unreachable since #N`) ровно так же, как тело коммита, — и правило «только из тела ⇒ ссылка» из источника B обязано действовать здесь тоже. Иначе через `gh issue view` пойдут номера, к ветке не относящиеся, а на закрытых из них скил велит спрашивать пользователя.
   ⚠ И тот же отсев нужен для `#N`, который вообще не issue: **номер СЕКЦИИ** (`INVARIANTS #4`, `RFC-4 M2`) по форме неотличим от задачи и встречается и в коммитах, и в changeset'ах. Отсеивай его по КОНТЕКСТУ строки, а не по существованию номера: он может совпасть с чужим открытым issue.
4. Авторитетные номера аргументов — список задач; источники A–C их перепроверяют.
5. **Объедини кандидатов и верифицируй каждый** — это должен быть открытый issue, а не PR и не несуществующий номер:
   `gh issue view <N> --json number,title,state,url,updatedAt`
   - Команда падает (номер — это PR или его нет) → исключи кандидата, сообщи об этом.
   - `state == CLOSED` → предупреди (возможно, задача уже закрыта другим PR) и **спроси**, включать ли `Closes` для неё.
6. **Если источники расходятся — НЕ угадывай.** Источник правды — что реально изменено в коде (коммиты + changeset); имя ветки вторично (ветку могли переиспользовать). Пример расхождения: имя ветки `757-…`, а коммиты/changeset ссылаются на `#807`. Перечисли расхождение и **спроси**, какие задачи реально решены в этой ветке, прежде чем продолжать.
7. Для каждой подтверждённой задачи прочитай тело и комментарии одним вызовом: `gh issue view <N> --json body,comments` (`--comments` вне TTY печатает одни комментарии, а с `--json` не сочетается). Не перечитывай, если сессия уже читала их после последнего сжатия, а `updatedAt` из п. 5 старше первого коммита ветки (`TZ=UTC git log --reverse --date=iso-strict-local --format=%cd origin/master..HEAD | head -1` — тот же формат, что у `updatedAt`): с начала работы задача не менялась. Список приёмки, по которому решается `Closes` против `Part of`, живёт в теле; в комментариях — уточнения скоупа и контр-примеры.

## Фаза 2 — Изучение изменений ветки

1. **Коммиты**: `git log master..HEAD --format='%H %s%n%b'`. В этом проекте действует «один PR — несколько независимых коммитов»: каждый коммит обычно решает свою задачу. Сопоставь коммиты с задачами из Фазы 1. Коммит **без `#N`**, который обслуживает задачи ветки (тест, док, конфиг), — норма батча: он идёт в **Maintainability**, не требует `Closes` и не считается расхождением источников. Коммит, которому в этом PR не место (чинит `master`, правит скил), — в `master` отдельно, по просьбе владельца: squash спрячет его под заголовком задачи.
2. **Diff-обзор**: `git diff master...HEAD --stat`; точечно `git diff master...HEAD -- <ключевые файлы>`.
3. **Добавленные тесты** (доказательство фикса) — найди их в diff (`tests/functional`, `tests/property`, `tests/stress`). Они идут в раздел **Test plan**.
4. **Changeset-файлы**: тип бампа (`patch`/`minor`) и тексты — основа для Summary и для типа PR (`fix` vs `feat`). Пакет из frontmatter changeset (`@real-router/<pkg>`) даёт `<scope>` заголовка.

## Фаза 3 — Сборка PR по шаблону проекта

### Заголовок (Conventional Commits, как squash-commit)

- **Не длиннее 92 символов целиком**: squash-коммит получит заголовок PR и суффикс ` (#<номер PR>)` от GitHub, а `header-max-length` ставит 100 на всю строку. Проверка — как в `/commit-msg`, с суффиксом: `printf '%s\n' "<заголовок> (#9999)" | pnpm exec commitlint`.
- **Одна задача**: `<type>(<scope>): <description> (#N)`
- **Батч** (несколько задач одного класса — `/bugfix-batch`): описание класса и номер ведущей задачи, по которой названа ветка, — `fix(memory-plugin): <класс> (#807)`. Остальные номера — в строках `Closes` тела.
- `<type>`: `fix` для баг-фиксов, `feat` для фич (определи по changeset-бампу и характеру задач). `<scope>` — из changeset-пакета / скоупов коммитов, и только из `SCOPES` в `commitlint.config.mjs`.
- **Смешанные типы в батче** (`refactor` + `fix` + `perf` и т.п.): НЕ выводи несколько `type:`-префиксов в одном заголовке. Возьми один наиболее значимый тип как префикс (`fix` > `feat` > `perf` > `refactor` > `chore`).
- **Разные скоупы** (например, `core` и `sources`): один префикс со скоупами через запятую, как в `/commit-msg`, — `perf(core,sources): <класс> (#N)`.

### Тело (на английском, по `.github/PULL_REQUEST_TEMPLATE.md`)

```markdown
## Summary

<!-- одна задача: 2–4 bullet'а про то, что получает пользователь, не детали реализации -->

### #807 — <короткий заголовок задачи> <!-- по подсекции на задачу, если задач несколько -->

- Что починено/добавлено (поведение, а не реализация).
- **Root cause:** корень проблемы и как фикс его устраняет.

### #808 — <короткий заголовок задачи>

- …

### Maintainability <!-- опционально: побочные чистки (lint/refactor) -->

- …

## Test plan

- [x] <добавленные тесты: путь + что проверяют — fail before / pass after>
- [x] <чек-пункты из ФАКТИЧЕСКОГО .github/PULL_REQUEST_TEMPLATE.md: источник правды — он, а не этот пример>
- [x] 100% coverage maintained

Closes #807
Closes #808
```

Правила тела:

- **Английский**, безличный тон (как в существующих PR и changeset'ах).
- **Summary** — польза для пользователя, не детали реализации (буквально как просит шаблон).
- Для каждого бага укажи **Root cause** (так оформлены реальные PR проекта).
- Раскомментируй секции шаблона **`## New API`** (короткий пример нового публичного API) или **`## Breaking changes`** (before/after), если применимо.
- **Test plan**: ставь `[x]` только для реально проверенного. Если не уверен, что валидационный пункт (type-check/lint/tests) зелёный, — либо прогони его, либо оставь `[ ]` и явно предупреди пользователя (успешный pre-push-хук покрывает полную валидацию). ⚠ **Каждое измеримое число в теле PR — тесты, файлы, сайты, строки, проценты, мутанты; в Summary так же, как в Test plan, цифрой или словом, — предъявляй выводом команды, которая шла на коде публикуемого коммита**: после неё не правился ни один файл ветки. Годится вывод этой сессии, видимый в контексте; число, которое только пересказано (память, бриф, сообщение коммита, issue, RFC, changeset), — нет: в теле PR оно читается как измеренное тобой. Лог батареи мутантов годится, если `diff` её копий с файлами коммита пуст или показывает одни комментарии, а тесты после неё только дополнялись; иначе перезапусти её ДО push: она переписывает рабочее дерево, а pre-push требует его чистым. Команда меряет ту единицу, что названа во фразе (файлы ≠ копии ≠ строки диффа), и показывает, что посчитала (границы диапазона, список); утверждение о полноте («везде», «ни одного») проверяй поиском по дереву ветки, а не по диффу. Обе стороны сравнения меряются на одном дереве, и различается только сравниваемое: «до фикса» — подменой файла на базовую версию (`git show <base>:<path> > <path>` → прогон → восстановить из копии АБСОЛЮТНЫМ путём: `cd` в той же команде переживает её, и `cp` промахнётся).
- **`Closes #N` — отдельной строкой для КАЖДОЙ решённой задачи**, в самом низу тела: GitHub закрывает при merge только задачу, перед номером которой стоит закрывающее слово, — `Closes #1, #2` закроет одну. Число строк `Closes` равно числу задач, которые PR решает целиком.
- ⚠ **Задача ШИРЕ этого PR** (issue на класс / umbrella / батч, а PR закрывает один инстанс) → пиши `Part of #N`, а НЕ `Closes #N`, и добавь в Summary секцию `### Scope`, называющую, что осталось: `Closes` на umbrella-issue закроет её при merge и потеряет остаток. Признак: тело issue перечисляет радиус (N сайтов / пакетов / адаптеров), а diff трогает меньше — сверь их перед выбором глагола. Сверяй и **acceptance-список**: каждый пункт либо сделан в диффе, либо назван в `### Scope`. Остаток остаётся в этой задаче — `Part of`; вынесен в новую задачу, снят решением владельца или закрыт доводом, который приводит PR, — `Closes`, а `### Scope` называет новую задачу, решение или довод. Пункт, который делается после мержа (вики, пример после релиза), не прячь в `[x]`: строка `After merge:` в теле с тем, кто его делает, и тот же пункт в отчёте.

## Фаза 4 — Публикация

1. Покажи пользователю финальные заголовок и тело. **Явная просьба создать PR — сама по себе согласование**: публикуй и показывай результат (заголовок + `Closes`/`Part of` + URL), не жди отдельного «да». Превью с ожиданием ответа нужно там, где скоуп или номера задач ты вывел САМ и пользователь их ещё не видел — прежде всего при расхождении источников из Фазы 1 или при выборе `Part of` вместо `Closes`.
2. **Проверь синхронизацию ПЕРВЫМ действием этой фазы — до любого `git push`**, даже если прошлый вызов скила показал, что пушить было нужно: ветку часто уже запушили (в `/bugfix`, эта сессия или владелец между коммитом и просьбой о PR), а повторный push стоит полного pre-push-гейта, минуты. Происхождение пуша для отчёта — `git reflog show origin/<branch>`: `update by push` = пушили с этой машины (владелец или эта сессия до вызова скила), `fetch … storing head` = ветку создали на стороне GitHub. Вызов `/create-pr` = явная авторизация на push **именно этой** ветки и создание PR — но пушить нужно, только если есть что отправлять.
   - Проверь синхронизацию с remote:
     ```bash
     git fetch origin >/dev/null 2>&1
     git status -sb | head -1   # первая строка: upstream + ahead/behind
     ```
   - **Уже запушена и синхронна** (строка вида `## <branch>...origin/<branch>` без `[ahead …]`) — **НЕ пушь повторно**, сразу переходи к шагу 3.
   - **Есть неотправленные коммиты** (`[ahead N]`) или **нет upstream** (в строке нет `...origin/<branch>`) — пушь: `git push -u origin HEAD`.
     - **Из linked worktree** pre-push проходит целиком, `--no-verify` не нужен — и под `.claude/`: `lint:audit` перечисляет lock-файлы через `git ls-files`, а не обходом дерева. ⚠ Pre-push собирает `dist` в worktree — перед следующими тестами или коммитом там `rm -rf packages/*/dist && pnpm install`, иначе vitest разрешит workspace-пакеты в `dist` мимо `src`.
     - ⚠ **Пуш в фоне — читай код выхода САМОГО `git push`, а не статус фоновой задачи.** Обёртка вида `git push … > log; echo "exit=$?" >> log` завершается кодом 0 при любом исходе пуша, и уведомление «completed (exit code 0)» читается как успех. Вердикт — строка `exit=` в логе и `git ls-remote --heads origin <branch>`.
     - ⚠ **Pre-push упал на тесте, к ветке НЕ относящемся, — не повторяй пуш вслепую.** Сначала докажи несвязанность: дифф ветки по упавшему пакету и его shared-источникам пуст, а сбой воспроизводится детерминированно на `master` (для property — контрпример из лога прямым вызовом, без seed). Затем заведи задачу (`/create-issue`) и только потом повторяй: повтор на случайном seed — бросок костей, и зелёная вторая попытка молча прячет живой контрпример. В тело PR — строка про эту задачу: CI гоняет то же свойство со своим seed. Тест падает на `master` при каждом прогоне, без случайного seed, — повтор не поможет: фикс — отдельный коммит в `master` по просьбе владельца, не в этот PR.
   - **Remote ушёл вперёд** (`[behind N]` / `[ahead N, behind M]`) — **НЕ форс-пушь**: подтяни линейно (`git pull --rebase`), затем `git push`.
   - ⚠ **Upstream ветки — `origin/master`**, если её создали от него (`git switch -c <branch> origin/master`, `git worktree add -b <branch> <path> origin/master`): тогда `[ahead N, behind M]` описывает `master`, а не remote ветки, и строка подходит сразу под «нет upstream» и под «remote ушёл вперёд». Есть ли ветка на remote — `git ls-remote --heads origin <branch>`; `behind` здесь — вопрос Фазы 0 п. 5 (merge-tree), а не `git pull --rebase`. Пример: `...origin/master [ahead 1, behind 1]`, ветки на remote нет, merge-tree чистый → `git push -u origin HEAD`.
3. Создай PR в базовую ветку. Тело — в ФАЙЛ, и передавай его `--body-file`, а не `--body`: тело PR — многострочный markdown с фенсами и inline-кодом, а zsh разбирает подстановку `$(…)` раньше heredoc, и backticks внутри ломают вызов. Файл понадобится и для `gh pr edit --body-file`, когда тело правят после публикации:
   ```bash
   gh pr create --base master --head "$(git branch --show-current)" --title "<title>" --body-file "$BODY"
   ```
   Добавь `--draft`, если он был передан в аргументах.
4. Выведи URL созданного PR.

## Итоговый отчёт

- Подтверждённые задачи и их источники (имя ветки / коммиты / changeset).
- Заголовок PR.
- Строки `Closes #N` / `Part of #N` — по одной на задачу, все решённые задачи покрыты — и `After merge:`, если есть.
- URL опубликованного PR.
- Журнал самокоррекции: что записано, или «ничего».

Примеры:

```
/create-pr
/create-pr --draft
/create-pr #807 #808
```

## Самокоррекция скила (журнал кандидатов)

Скил правится по накопленному, а не после каждого прогона: правка по одному инциденту описывает случай, а не класс, а платит за неё каждый следующий прогон.

1. **Запись в журнал, а не правка** — после публикации PR (вывод URL). Где текст скила промолчал, был двусмыслен или неверен и это стоило вызовов, реплики владельца или риска ошибки, допиши строку в `.claude/skill-candidates/create-pr.md` основного чекаута (gitignored; из worktree — `dirname "$(git rev-parse --path-format=absolute --git-common-dir)"`): дата, задача, раздел, класс (молчит / двусмыслен / неверен), инцидент, цена. Строка того же класса уже есть — допиши инцидент к ней. В отчёте — одна строка: что записано.
2. **Правка созревает, когда класс повторился** — в другой задаче или сессии. Неверный факт текста (команда, флаг, путь, число) — исправление, а не правило: его предлагай сразу. Планка: правка предотвратила бы ошибку или сняла бы лишние шаги.
3. **Разовое ≠ паттерн.** Специфику конкретного PR/ветки (разовую) → в описание PR/память, НЕ в скил. В скил идёт только повторяющийся класс, полезный СЛЕДУЮЩЕМУ ДРУГОМУ PR.
4. **Правка не растит файл:** сначала заточи существующий абзац; новое правило называет, что в том же разделе сжато или удалено. Рост — только с согласия владельца.
5. **Предлагай, не применяй молча.** Созревшие правки — таблицей (раздел | инциденты из журнала | текст | что сжато), спроси разрешения; итог помечай в журнале. В скил — правило в настоящем времени, без номеров прогонов и дат; инциденты — в сообщение коммита. Применил по согласию → `.claude/commands/` это infra, в master напрямую, без changeset. ⚠ В сообщении такого коммита не ставь закрывающее слово (close/fix/resolve) вплотную к `#N`, даже в бэктиках: push в `master` закроет задачу.
6. **Ничего не записано и не созрело** — так и скажи одной строкой.
