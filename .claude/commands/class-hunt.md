Найди и исправь КЛАСС ошибок, а не очередной экземпляр: когда фикс одного issue находит следующий, установи, какой факт записан во многих местах, перепиши ВСЕ места, найди признак, который отделяет верные места от слепых, и закрой класс структурно — устранением варианта, к которому слепы копии, и fail-closed сторожем, — исправив все текущие экземпляры в той же доставке.

Входные данные:
$ARGUMENTS

Формат аргументов:

- Номера issue цепочки (`#2626 #2627 #2628`) или один экземпляр с описанием повторяющегося дефекта.
- `--report-only` — только исследование и выводы (Фазы 0–2), без правок.

Пример:

```
/class-hunt #2626 #2627 #2628
/class-hunt #2627 --report-only
```

> **Протокол папки, README, роя и эксперимента — `/research`.** Здесь — только то, что в нём специфично для класса: триггер, стандартные линзы, дизайн сторожа, доказательство сторожа и доставка. Кластеризация всей баг-истории рантайма по корням — `/debt-map`; одна цепочка архитектурного долга — `/chain-resolve`; один баг — `/bugfix`.

## Когда запускать

- **Фикс issue нашёл ещё одно место с тем же дефектом, и это уже второй раз по одному корню.** Третий issue не заводи — запускай этот скил. (Прогон #2627: #2626 → #2627 → #2628 за один день по одному каталогу `packages/angular/ssr/`; каждое issue находило следующее, остановил владелец.)
- Свип перед фиксом нашёл «ещё N мест с тем же литералом».
- Тот же вид дефекта уже чинили в другом месте: `rg` по `IMPLEMENTATION_NOTES.md` и `gh issue list --search` по предмету.

## Принцип

- **Класс — один факт о системе, записанный в N независимых местах**, вместо того чтобы выводиться из одного источника. Экземпляр — место, где копия разошлась с фактом или не видит одно из его значений.
- **Экземпляры находят друг друга бесконечно**, потому что каждый фикс смотрит в один список. Исправить класс — значит сделать новое неверное место невозможным или видимым в день его появления.
- **Два способа, в порядке предпочтения:** (1) **убрать вариант**, к которому слепы копии, — тогда все копии становятся верными, не будучи тронутыми; (2) **сторож**, который сам выводит множество мест из дерева и валит место, расходящееся с фактом. Обычно нужны оба: (1) для одного варианта, (2) для того, что убрать нельзя.
- **Сторож, у которого не доказана различающая сила, — декорация.** Каждое его правило проверяется мутантом.

## Фаза 0 — Экземпляры и гипотезы

1. Каждое issue цепочки — с комментариями (`gh issue view <N> --comments`). Таблица для README: issue | что не видело или было не так | как найдено.
2. Гипотезы (формат и папка — `/research` Фазы 0–1):
   - **H1 — определение класса:** какой факт, в каких местах записан, как (литерал, копия, ручной список).
   - **H2 — варианты:** значения факта, к которым слепы копии (в прогоне #2627: код в `shared/<dir>`, доступный пакету только через симлинк, и код в `angular/ssr/` рядом с `src/`).
   - **H3 — вариант устраним структурно,** не меняя опубликованного контракта.
   - **H4 — одна декларация:** если H3 неверна, какой один источник может кормить все места (вывод при загрузке, генерация, проверка).
   - У каждой — «опровергнет: …».

## Фаза 1 — Стандартные линзы

Рой по `/research` Фаза 2. Линзы этого скила:

| линза                                                                                              | вопрос                                                  | метод                                                                                                                                                                |
| -------------------------------------------------------------------------------------------------- | ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Перепись** (1–3 агента по областям: CI, хуки и скрипты; конфиги инструментов; сканирующие тесты) | где записан факт и видит ли каждое место каждый вариант | множество мест — ВЫВЕДЕННОЕ (`git ls-files`, AST), не угаданное; «видит ли» — замером на варианте, а не чтением конфига                                              |
| **Механизм**                                                                                       | чем зрячие места отличаются от слепых                   | для каждого места — откуда оно берёт множество: литерал или вывод (индекс git, манифесты, команда пакета); признак должен делить все места без исключений            |

| **Структура**                                                                                      | можно ли убрать вариант                                 | исходники инструментов → предсказания для эксперимента; что сломается и что изменится в опубликованном                                                               |

Сигналы из истории, которые решают, нужен ли сторож: **«ни одно обнаружение не пришло от сторожа»** — класс не охраняется; **«фиксов уровня класса — 0»** — каждый фикс чинил одно место. (Прогон #2627: 14 обнаружений за 112 дней, 11 фиксов по одному списку, 3 по нескольким, 0 уровня класса, ни одного от сторожа.)

## Фаза 2 — Эксперимент по H3

По `/research` Фаза 4. Для переноса или переименования кода:

- сборка до и после, побайтное сравнение артефактов — каждое отличие объяснено;
- линтеры публикации, тесты, покрытие;
- ⚑ **список проверок, которые ВПЕРВЫЕ увидят перенесённое** — покрытие, храповики, сканы: их находки появятся в доставке, и лучше знать о них до коммита.

`--report-only` заканчивается здесь: выводы (§5 README) и суть в чат.

## Фаза 3 — Дизайн исправления

- **Устранение варианта** (если H3 подтверждена) — плюс проверка раскладки или инварианта, которая **fail-closed**: новый вариант — ошибка, а не новый ключ в списке. Сторож, который выводит «разрешённые исключения» и подстраивается под них, закрепляет класс, а не закрывает.
- **Перепись-тест для оставшегося варианта:**
  - множество файлов — `git ls-files`, а не обход диска (трекаемое — это то, что видят CI и хуки);
  - читает КОД, а не комментарии: JS/TS — через печать `typescript` без комментариев (`ts.createPrinter({ removeComments: true })`), потому что построчный стриппер режет регекс-литерал, оканчивающийся на `\//`, и теряет остаток строки; YAML и shell — без `#`-комментариев;
  - **именованные исключения с причиной** и отдельный тест, что каждое исключение ещё применимо (иначе они копятся);
  - **CONTROL:** известные места находятся — без него тест зеленеет, когда шаблон ослеп;
  - фикстура на каждое написание места (строка, шаблон, `join`, shell, регекс).
- **Где сторож будет исполняться:** найди раннер, а не предполагай. `scripts/tests/*.test.mjs` гоняет `scripts/scripts-tests.mjs` в pre-push и в CI: новый сторож идёт на месте и без кеша; в `TOOLING` (задача turbo `//#test:tooling`: копия с одними её входами, вердикт из кеша, пока не менялись входы и версии инструментов) вписывай только тест, который читает одни её входы: тест, ищущий проверяемое списком (git, glob), получает в копии одни входы и может пройти, ничего не проверив; пакетные сканы по всему дереву регистрируются в `scripts/repo-wide-scans.json`, иначе turbo воспроизводит их из кеша.
- **Утверждение о поведении инструмента — только замеренное:** «глобы не ходят по симлинкам» верно для Node `globSync`, экстрактора CodeQL и jscpd 5.3.2 под корнем скана (замер 2026-10-05; корень-ссылку, которую раскрыла оболочка, jscpd обходит), а `tsconfig.sonar.json` по ним ходит и исключает алиасы. В доке называй инструменты, для которых замерено.

## Фаза 4 — Доказательство сторожей

- **Мутации:** на каждое правило сторожа — мутант, который его выключает (снять условие, ослабить сравнение, пропустить вложенный случай, не сообщать). Каждый обязан краснеть на фикстуре. После батареи — файлы восстановлены, `git diff` пуст.
- ⚠ **Контрольная рука для самой переписи.** Список форм переписи — тоже литерал, написанный её автором, и он слеп к форме, о которой автор не подумал: это тот же класс внутри сторожа. Прогони грубую выборку — каждый файл, в КОДЕ которого встречаются токены факта (для корней: `packages` и `src`), без второго корня и НЕ найденный переписью, — и разбери её глазами: форма, которой нет в шаблонах, — это новый шаблон, фикстура и, скорее всего, новый нарушитель. (Прогон #2627: перепись читала только корень `src`; контрольная выборка из 28 файлов нашла форму «префикс корня `packages/`» — `startsWith("packages/")`, `grep "^packages/"` — и пятый живой список, `raiser-text-equality.mjs`, уже после открытия PR.)
- **Прогон на БАЗОВОМ дереве:** `git worktree add --detach <scratchpad>/base <база>`, `node_modules` симлинком из рабочего worktree, тест скопирован — и его вывод даёт точный список нарушителей «до». Этот список — измеренный, он идёт в NOTES и в PR. После — `git worktree remove`. Сменились шаблоны переписи — прогон на базе повторяется.
- **Зонды для стражей сборки:** испорти артефакт в копии (переименуй подпуть, удали файл) — страж обязан бросить; контроль на настоящей сборке — пройти.

## Фаза 5 — Все экземпляры в той же доставке

- **Каждый нарушитель переписи чинится здесь.** Отдельный issue на экземпляр класса — ровно то, от чего скил уводит.
- ⚑ **Устранение варианта открывает ранее слепые проверки, и они находят старое.** Это часть класса: обработать в этой доставке — тест на впервые видимую непокрытую ветку, стоящие пары храповика — в его базовую линию, — а не заводить issue. (Прогон #2627: покрытие показало непротестированную dev-проверку `<http-status-code>`, которую пять других адаптеров тестируют; `lint:doc-dup` — четыре пары в перенесённых докблоках.)
- **Базовую линию храповика дополняй только своими записями:** его `--update` переписывает и чужие записи (номера строк в описаниях), такие ханки откатывай.
- **Числа в тронутых доках — перемерить,** и на базе тоже, чтобы знать, чья правка их сдвинула. (Прогон #2627: «426 ошибок `tsc`» оказалось 419 — и на базе 419, число устарело раньше.) Вторую копию числа замени указателем на первую.

## Фаза 6 — Доставка и запись

- **Состав диффа решает путь:** `packages/*/src/` → ветка в worktree, PR, changeset; иначе — прямо в `master`.
- **Коммиты по частям класса,** каждый — проверенный хуком на СВОЁМ дереве: A — устранение варианта и проверка раскладки; B — перепись и исправленные нарушители. Хуки читают рабочее дерево, поэтому на время коммита A файлы B переносятся в scratchpad (не `git stash`) и возвращаются после. Ledger переписи утверждений пересчитывается для каждого коммита отдельно — только по файлам, уже записанным в ledger.
- **`IMPLEMENTATION_NOTES.md`:** запись Problem → Solution → Why — класс, варианты, история (обнаружения, скоупы фиксов), механизм, замеры; `> ⚠ Superseded/Refuted on <дата>` в записях, которые правка отменяет.
- **`CLAUDE.md`:** правило класса одним абзацем и где стоит сторож.
- **Память:** project-запись класса со ссылкой на папку исследования; статус в README исследования.

## Жёсткие правила

- Не заводи issue на экземпляры класса по ходу — сначала перепись.
- Не расширяй сторожа исключением без причины, записанной рядом.
- Не называй сторож готовым без мутаций и без прогона на базе.
- Не обобщай поведение инструмента дальше замеренного.
- Push и PR — только по явной просьбе.

## Самокоррекция скила (ОБЯЗАТЕЛЬНО, в конце КАЖДОГО прогона)

Этот файл — живой; каждый прогон обязан его затачивать. После доставки вынеси короткую секцию **«Самокоррекция»** — критику не своей работы, а САМОГО ЭТОГО СКИЛА: где его текст промолчал, соврал, был двусмыслен или избыточен — и это стоило времени, лишнего шага или риска ошибки.

1. **Привязка к ИНЦИДЕНТУ, не общие советы.** Каждая правка — из конкретного момента ЭТОГО прогона: «скил сказал X / промолчал про X → реальность Y → я потерял/чуть не ошибся на Z». Нет инцидента — нет правки.
2. **Высокая планка: изменило бы исход?** Предлагай, только если правка реально предотвратила бы ошибку, сократила перебор или сняла двусмысленность. Косметику отбрасывай.
3. **Разовое ≠ паттерн.** Специфику конкретного класса — в NOTES или память, НЕ в скил.
4. **Сначала заточи, потом дописывай.** Предпочитай усиление существующего абзаца новой секции; общее для всех исследований — в `/research`, не сюда.
5. **Предлагай, не применяй молча.** Выведи кандидатов таблицей (раздел | инцидент | предлагаемый текст), спроси разрешения. Применил по согласию → `.claude/commands/` это infra, в master напрямую, без changeset. ⚠ В сообщении такого коммита не ставь закрывающее слово (close/fix/resolve) вплотную к `#N`: push в `master` закроет задачу.
6. **Честность про «нечего править».** Прогон прошёл чисто — так и скажи: «правок нет».
